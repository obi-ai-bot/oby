### Job pipeline and pull request following

Every job response (list, detail, dispatch, stop, message, wait, plan and `job` SSE event) includes `pipeline`, derived in Engine from the job's execution facts and last observed PR state. Clients render it instead of reconstructing stages from `step` text.

- `pipeline.stages`: ordered `prepare`, `work`, optional `check`, `publish`, `review`, `merged`. Each has `id`, `title`, `state`, optional `detail` and optional `reason`. States are `done`, `current`, `upcoming`, `failed`, `skipped`; every failed stage includes a reason. Check is absent when no check command is configured. Work includes the round and live agent step. Publish includes secret scan, push and PR creation progress.
- **Stage times (obid only, #733).** A stage the job reached also has `started` (RFC 3339) and `waited` (seconds paused on the owner: a permission, a question or a plan to approve, as of the job's last change), and, once it's no longer current, `finished` (RFC 3339) and `seconds` (the time it ran, every round's added up, `waited` left out). A current stage has no `seconds`, since it would change every second: the apps count it from `started`. A stage a later round enters again keeps its first `started`, and `finished` goes until it ends again. Time a queued job waits for a free slot counts in no stage's `seconds`. An upcoming or current stage may have `estimate`, `{"low": 120, "high": 780}` in seconds, from the job's `estimate` (below); the Check stage's is the last full run (every step passed) of the same check command in the repository. Stages a job never reached have none of these.
- `peakRss` (obid only): the most resident memory the job's processes (its agent, its check and everything they started) held at once while it ran, in bytes, as `status.memory` read it every 5 seconds; a job that ran again keeps the larger. `agentPeakRss` and `checkPeakRss` (obid only) are its agent's tree and its check's, each at its most, what the builds' width learns budgets from (Jobs run side by side, above). All three are kept as they grow (by 128 MiB, or a quarter, past what's kept), not only at the end, so a job obid didn't see end is learned from too. Absent before obid read them once (a job that ran less than a reading, or on an older runner).
- `peakRss` (obid only): the most resident memory the job's processes (its agent, its check and everything they started) held at once while it ran, in bytes, as `status.memory` read it every 5 seconds; a job that ran again keeps the larger. Absent before obid read it once (a job that ran less than a reading, or on an older runner).
- `buildFreed` (obid only): what deleting its worktree's build outputs and its HOME's caches freed once it ended (or the disk was low), `{"bytes": 6436484096, "at": "2026-10-24T23:40:00Z"}` (`cleanup`, below; [CLEANUP-1](contracts/cleanup.md)); absent before that, and on older runners.
- `estimate` (obid only, #733): what the whole job should take from Prepare to Publish (waiting on people left out), `{"low": 720, "high": 1200, "basis": "From the last 14 jobs like this in obi on Claude Code (13m in the middle).", "samples": 14, "firstGiven": {"low": 660, "high": 1200}}`, in seconds. It's the middle 80% (10th to 90th percentile) of the last 50 jobs done in the same repository with the same agent and kind; with fewer than 5 of those, the range of the repository's last 50 jobs done, and `basis` says so: `"Too early to say: 2 jobs like this so far. Jobs in obi take 4m–19m."`. `samples` is how many jobs like this it read. The time Plan mode spent reading before its plan isn't counted. obid computes it again whenever a stage starts or ends while the job runs; `firstGiven` is the first range it gave, kept so a finished job can show it next to what it took. The history is the finished jobs obid keeps (their stage times, in `home/jobs/`): obid has no SQLite of its own. Absent when the repository has no finished job with stage times yet.
- `pipeline.number` and `pipeline.total`: one-based position and count of displayed stages, including skipped ones. Display “Stage n of m”. The position is the first current/failed stage, otherwise the last completed/skipped stage. A completed investigation with no commits skips Publish, Review and Merged and reports 5 of 5. A failure/cancellation marks its execution stage failed with its reason and skips downstream stages.
- A done, published job progresses through Review: waiting (`current`), changes requested (`failed`, with reason), approved (`done`, with merge current). A merged PR completes Review (`Approved`, or `Merged without review` when GitHub has no review decision) and the final stage; a closed, unmerged PR fails Review and skips Merged. The merge title uses GitHub's actual base, normally “Merged into dev”. Running again shows Work before the earlier round's PR progress.
- `phase` (optional): persisted execution phase `prepare`, `work`, `check` or `publish`. `publishStep` (optional): `scan`, `push` or `pullRequest`. These are execution facts, not separate client derivation rules. Older saved jobs have neither; Engine derives their best available progress.
- On `obid`, the same read asks for what a merge needs too (obid only: merging): `gh pr view --json state,reviewDecision,mergedAt,baseRefName,headRefOid,statusCheckRollup,mergeable,mergeStateStatus,author`, and its reviews from the REST API, every page (`gh api --paginate --slurp repos/{repo}/pulls/{n}/reviews?per_page=100`): `latestReviews` gives no commit for an approval (cli/cli#14805). Of the reviews obid keeps, for each reviewer's latest that counts (an approval, a change request or a dismissal; a comment or a pending review never replaces it), only its `id`, the login, the state, the commit (`commit_id`), `author_association`, whether `user.type` is `User`, and its body, which reaches an agent only quoted as data in a change request's round (MERGING-40, below) and is never in the API; of the checks, only how they went. None of it is in `pullRequest` yet.
- `pullRequest`: null until a successful read, otherwise `{"state":"OPEN","reviewDecision":"REVIEW_REQUIRED","base":"dev","mergedAt":null,"checkedAt":"2026-10-09T21:43:30Z"}`. State is `OPEN`, `CLOSED` or `MERGED`; review decision is `REVIEW_REQUIRED`, `CHANGES_REQUESTED`, `APPROVED`, or absent/null (no decision yet). `mergedAt` is present only after a merge. `head` is the pull request's head commit as GitHub has it (absent on older observations): one Oby didn't push is an intervention (Failure record, below). All dates are ISO 8601.
- The runner polls published PRs on startup and every three minutes while open/unknown, using its own `gh pr view` outside the agents' sandbox. It follows `published`, not the input `pr`, including saved jobs older than the latest 50. Closed and merged PRs stop polling. On `obid`, red checks or a review asking for changes on a pull request a job published wait on the owner: a card says why (`Not merged yet: its checks failed on GitHub.`), once obid's own round for them is spent or can't be had (MERGING-39, 40: one per job for red checks, one per head for change requests by the owner or members of their organization); an older obid's open `Address it` and `Fix CI` offers are done when obid starts. Fresh saved observations wait for the next interval after restart.
- `pullRequestError`: null after a successful refresh; otherwise a short retry message. Network/authentication/JSON failures preserve the last successful observation and retry at the next interval. `checkedAt` remains the date of that last success. Updates are saved and sent as `job` events without overwriting a concurrent agent step or resumed round.
- Following is read-only: it never posts a review, pushes, or merges (merging is the Mac check's, below). [`gh pr view` JSON fields](https://cli.github.com/manual/gh_pr_view) supply only typed status data; GitHub prose never enters an agent prompt.
- Older clients ignore these additive fields. New clients accept an absent pipeline from an older runner and show its ordinary status/step instead.

### Oby's review

When a job publishes (or pushes new commits to its pull request), the runner has the pull request reviewed by one of its own jobs, on a different account than the author's: it prefers the other tool (Claude Code reviews Codex's work, Codex reviews Claude Code's; a Cursor job's pull request goes to Claude Code, else Codex, and Cursor never reviews), takes only an account that's signed in with room on its limits (under 95% of its 5-hour window and under 80% of its weekly one, which keeps the rest for jobs the user sends to it by name), preferring one running ahead of its weekly pace, since a review is short (Routing, under Account), and runs it on that account's model from Settings › Models. With no such account, the runner falls back, last, to the author's own account when it's signed in and under 95% of both windows (#408): the review is still a new job in a new session of its own, with its own worktree and the pull request quoted as data, and never resumes or reads the author's session. It says so: the review's `account` carries `sameAccount: true`, its check run is titled `Oby review · Codex · Deskree (same account as the author): Approved`, and the job's review line in the Lead's and the brain's briefings names it the same way. Reviews still prefer another account and the other tool: the fallback is taken only when none of them has room. A security review never uses it; it needs a different account and waits for one. With no account at all, nothing reviews and `reviewError` says so.

When the PR diff changes a security surface (`Runner/API.swift`, `Runner/Gateway.swift`, `Runner/Devices.swift`, `Runner/Routes.swift`, `Runner/Auth*`, `apps/shared/E2E*` (and `Shared/E2E*`, from branches cut before it moved), `Engine/Vault*`, `Engine/Jobs.swift`, `Engine/Publish*`, anything under `cloud/`, or a path naming auth, tokens, keys, secrets, crypto, listeners or routes), Oby starts a separate security review after the general review approves. It writes an independent `Oby security review` check run. Its reviewer examines privilege escalation, route reachability, token/key and crypto handling, injection, agent/log exposure and unsandboxed Mac access. Every authentication or route-reachability claim must include a HummingbirdTesting or test-server curl probe with command and output. Only likely exploitable HIGH or MEDIUM findings block; denial of service, rate limits and theoretical issues do not. If Git cannot read the changed paths from an existing author worktree, Oby conservatively requires the security pass. Both verdicts must approve before a Mac check can gate the merge.

In chat, asking to review an Oby-authored pull request again goes through its author job: the conversation tells that job (`oby_tell_job`) or answers its review item (Try again, or One more round), so the verdict and any Mac check stay with that job. obid refuses a standalone `review` dispatch for a pull request that already has an Oby author job. A manually requested follow-up grants one additional review when the normal review cap has been reached. A review job that makes commits ends failed with `A review made commits; nothing was published`; `Publish` also refuses every `kind: review` job.

Oby runs up to three regular reviews (`Review.maxRounds`). If the third still requests changes, it gives the fourth review to the strongest configured model with account capacity. That escalation reads the whole pull request and all three earlier reviews, then approves or sends its final blockers to the user. It does not start another author round. A changes-requested result at the escalation creates one inbox card per PR head, with Open the PR, One more round and Dismiss. The card says `Oby's reviews are done: review #N yourself`; another published head gets a new card. Reviews triggered by a Mac check, conflict, Xcode Cloud or the user count toward these four. When the runner starts, commits refused under an earlier cap (`reviewError` "Oby reviewed it N times already…") still get reviewed. `obid` stops sooner: three reviews and two author rounds, with no fourth review, no escalation and no inbox card ("obid only: what obid leaves out").

- **The review job** is an ordinary `Job` in the list and the event stream: `kind` `review`, `pr` the published pull request's number, `branch` like `oby/review-80`, `task` the author's task, and `reviewOf` the author job's `id` (null on every other job). It reads the diff and the author's task, makes no commits and never publishes. Its `summary` is the review; its last line is the verdict (`VERDICT: APPROVED` or `VERDICT: CHANGES REQUESTED`).
- A first review checks the issue's acceptance criteria and completion tests, bugs in the change and called code, repository rules, and end-to-end behavior on each affected platform in one pass. A blocker must include `Evidence:`: a failing test or probe with its command and relevant output, or exact lines proving the bug for an input. A `Blocking:` item without evidence is treated as worth doing later. Blockers are limited to 10 and ordered by severity; style, pre-existing issues, general requests for more tests, wording and lint findings do not block.
- Follow-up findings that cite a file and line are checked against the added-line ranges in `git diff <last reviewed> HEAD`; if the location is outside the new commits, Swift demotes the finding to worth doing later.
- When the PR merges with review follow-ups, Oby creates one issue containing the accumulated list. Its stable marker lets a retry after a runner restart find the issue it already created; `review.followUpIssue` contains its URL once filed.
- **On the author job:** `reviewing` is the review job's `id` while it runs, else null. `review` is Oby's latest verdict, or null:

  ```json
  {"verdict": "approved", "job": "3c9d1e20", "agent": "codex", "account": "Work", "round": 1,
   "date": "2026-10-09T22:04:11Z", "checkRun": "https://github.com/deskree-inc/oby/runs/41800000001"}
  ```

  `verdict` is `approved` or `changesRequested`; `job` the review job; `agent` and `account` the reviewer's tool and account name (`sameAccount` is true when it ran on the author's own account because no other had room, else absent); `round` which of Oby's reviews of this pull request it is (from 1: rounds that fix the last blocker are reviewed however many it takes); `checkRun` the check run it was written as, or absent with `postError` saying why it wasn't (a possible secret in the review, `gh` failing, or the GitHub app missing or without Checks: write: `Not posted: the Oby app needs Checks: Read and write on its installation.`). Reviews from runners before check runs carry `comment`, the pull request comment they were posted as, instead. `applying` is true from the moment the verdict is recorded until its check run is posted and the author's round started (or the approval's Mac check queued), and absent after: it's cleared in the same save as the round (after the round's message is in `restarts.json`) or the Mac check, so a restart anywhere before leaves it set, and the runner does them when it starts again ("After any restart"). `reviewError` says why no review ran or none gave a verdict (no account with room, the reviewer failed, was stopped or interrupted, or gave no verdict), else null.
- **The check run** (#198). GitHub doesn't let the user approve or request changes on their own pull request, and a comment from the app emails the owner, so the runner writes the review as a check run named `Oby review` on the commit the reviewer read, as the GitHub app (`POST repos/{owner}/{repo}/check-runs`, `status` `completed`): `conclusion` `success` when approved and `failure` when changes are requested, titled `Oby review · Claude Code · Personal: Approved` (or `Changes requested`; `Oby review · Codex · Deskree (same account as the author): Approved` when it ran on the author's own account), its summary the review itself in a code block (so no mention, link or image in it takes effect) and a `by Oby` line. A check run sends nobody an email. Another review of the same commit updates the app's own `Oby review` check run there (`PATCH …/check-runs/{id}`) rather than adding one. The secret scan gates it, with the same rules and encoded copies as publishing: a possible secret means no check run, and the verdict still counts. Only a GitHub app can write check runs, and only with **Checks: Read and write**: with no app, or until the owner grants that permission, nothing goes on the pull request, the review stays in Oby (the job, the inbox, the apps), `postError` says why, and [`GET /v1/status`](#get-v1status) says `"checks": "missing permission"` (or `"no app"`). Oby never comments on a pull request. A written check run is listed in the author job's `outgoing`.
- **The Review stage** shows GitHub's decision when it has one, else Oby's: `Oby is reviewing` (current), `Approved by Oby` (done, with Merged following the Mac check, below), or `Changes requested` (failed, reason `Oby requested changes.`). A failed review leaves it current with `Waiting for review · <reviewError>`. A merged pull request with no GitHub decision reads `Approved by Oby` or `Oby requested changes` instead of `Merged without review`.
- **Changes requested** from reviews one through three go to the author's agent as the next round, in the same session and worktree: the review is quoted in `.oby/inputs/review-<round>.md`, never pasted into the prompt. The job goes back to `running` with a new `round` and `step` `Working on Oby's review`; when it publishes, Oby reviews again. Follow-ups start a finding with `Again:` when an earlier blocker was not fixed or came back. Review four includes `.oby/inputs/review-history.md` and reviews the whole pull request, rather than only the last diff. Its changes-requested result stays `done` and needs the user (`reviewNeedsYou`); there is no automatic fifth review. `One more round` lets the author work again and grants one more review. Each review's `blocking` lists its blockers and `blockedBefore` lists the earlier ones.
- **Approved:** the commit the reviewer read is checked on the user's Mac, and the runner merges it into `dev` when that passes (below). A `Blocking:` section containing `(none)` has no blocking findings; an approved follow-up proceeds even at the review cap.
- What needs you now includes a `done`, published job whose escalation review requested changes (`reviewNeedsYou`, while the pull request is open), and one whose merge stopped (`mergeNeedsYou`, Mac check below). Its inbox item id includes the pushed PR head, so the same head has one card and a later head has a new one. Say so where the apps list what needs you ("1 job needs your review").

### obid only: merging (#853, #854)

Oby carries a task the whole way (AGENTS.md, the owner's decision of 2026-10-24): once its pull request is approved and green, it merges it the way the repository's workflow says, and asks the owner only when something goes wrong. This part is the merge itself and the rules it keeps (`crate::merge`), and the typed workflow it follows (obid only: memory, below).

**What the follower does** (every read of a job's open pull request: when `obid` starts, right after it publishes one, and every three minutes). Only for a `done`, published job that isn't dismissed, a review or research job, or another Obi's:

1. **Oby's own review is the review** (the owner's decision of 2026-10-24: "approve using my own GitHub account, just like Claude Code does"). GitHub never lets a pull request's author approve it, so for the owner's own pull requests Oby's own review of exactly the head obid pushed (`review`, while it's the pull request's head) is what an `oby` workflow (the default it proposes) waits on, and the owner's own `gh` merges it: no second GitHub account is needed, and nothing is posted on GitHub for it. obid has no GitHub app, so no `Oby review` check run is written either; the verdict is on the job (`review`). It counts only on the owner's own pull request: its author must be the owner's gh login (any case), else the owner hears it. Where GitHub's rules for the base require an approving review, the owner's own approval can't count: `reviewDecision` `REVIEW_REQUIRED` always means another person's is needed, whatever approvals obid sees (GitHub knows who may approve, code owners included); otherwise the most of its rulesets' `pull_request` rule and its classic protection's `required_approving_review_count` (`GET repos/{repo}/rules/branches/{base}` and `…/branches/{base}/protection/required_pull_request_reviews`) must be met by approvals from other people with write access, never one of Oby's reviewer accounts. Classic protection counts as 0 only for GitHub's `Branch not protected`, `Required pull request reviews not enabled` and the `Not Found` an owner without admin rights gets (then `reviewDecision` still says when it asks for a review); a rate limit, a 5xx, a timeout or an answer it can't read is unknown. Then a teammate's Oby is asked (below), on a workflow the owner taught Oby; when none can, the owner hears it once (`GitHub requires another person's approval here.`, and why). A repository Oby hasn't learned asks the owner first, once for that head (the owner's decision of 2026-10-25), unless they said yes to it before (a `review` memory: then a teammate's Oby is asked by itself, with no card): a `merge` card, `Needs a teammate: <title>`, `GitHub requires another person's approval on <repo>. Ask a teammate's Oby to review it, and remember that for this repository?`, with `Ask a teammate, and remember` and `Not now` (`id` `merge-teammate-<job>-<head>`). Out of an Obysphere it says so instead, with what to do (`GitHub requires another person's approval on <repo>, and Oby isn't in an Obysphere, so no teammate's Oby can review it. Invite a teammate who can push to <repo> to an Obysphere with you, or get their approval on GitHub yourself.`). Rules it can't read: it waits, asking nobody, unless GitHub refused in a way that won't pass by itself (a `401`, or a `403` that isn't a rate limit: an organization's SSO not authorized for the owner's login, a token without access); then the owner hears it once for that head, learned workflow or not, in GitHub's words (`Oby can't read this repository's merge rules (GitHub said: …).`), and the card settles once GitHub shows them. The reviewer account's own state matters only to a `reviewer` workflow: one signed in once and stale since never stalls any other. On a `reviewer` workflow, a reviewer login that isn't signed in any more, that gh can't read, or that is the owner's own waits on that account for good, so the owner hears it once for that head (`Oby's reviewer account needs signing in again, or signing out (…).`), settled once it's signed in again.
2. **The reviewer account, an option.** With a `reviewer` workflow and Oby's reviewer account signed in, once Oby's own review approved exactly the head obid pushed, on the owner's own pull request (its author is the owner's gh login), obid posts an approval as Oby's reviewer account (`POST …/pulls/{n}/reviews` with `event` `APPROVE` and `commit_id` that head, as the reviewer, `body` obid's fixed words, scanned first), once: none when the reviewer approved that head already, and never again on a head where someone dismissed its approval. It never posts changes requested: those stay in Oby and drive the author's rounds. Right before it's sent, the job is read again (still done, not let go, at that head), and a mark of what's being sent is saved (`sending`, never in the API: one per kind, the approval, the merge and the branch's deletion, so one never overwrites another); a restart in between reads GitHub on the next pass and settles each: an approval it finds there is listed, the pull request open or merged since (a merged or closed one is read again until its reviews read); a merge that landed is listed as who had it merged; a branch deletion is tried again (one gone counts) and listed. The post is in `outgoing` as `pullRequestApproval` (`id` the review's URL; the pull request's when it's listed after a restart). Where it can't be posted (the reviewer can't push, or someone dismissed its approval: `Someone dismissed Oby's approval of this commit on GitHub, so Oby won't approve it again: …`), the job needs the owner: `mergeError`, `mergeNeedsYou`, and one `merge` card. With no reviewer signed in, a `reviewer` workflow merges on Oby's own review, as an `oby` one does. Anywhere else (an `oby`, `teammate` or `person` workflow, or a repository Oby hasn't learned) nothing is ever posted as the reviewer: it can push, so GitHub's branch rules would count its approval where only a teammate's should.
3. **A teammate's approval.** With a `teammate` or `person` workflow, while the merge waits on an approval of the head from someone other than the owner and Oby's reviewer accounts (`merge::wanted_approval`; checks may still be running), or where GitHub's rules require one on a pull request Oby's own review approved (`merge::needs_another_person`), the follower asks a teammate's Oby over the Obysphere to review that head and approve it on GitHub as that teammate ([teammate approval](#obid-only-teammate-approval), `Link::ask_teammate`), on each read: one teammate at a time, never another after a review that asked for changes. While one has it, nothing waits on the owner; where none can (Oby isn't in an Obysphere, no teammate's Oby can approve it, or one's review asked for changes), one `merge` card with X5's words. The merge goes on once GitHub shows that approval.
4. **The merge.** With a workflow the owner taught Oby for the repository, when everything below holds, it merges (`mergedBy` `{"by": "memory", "memory": "<id>"}`, the memory's `used` + 1), with the same mark saved right before the merge is sent; a restart that finds the pull request merged lists the merge as that, and one still open tries again as anything does. Where Oby can't go on by itself, one `merge` card (`Not merged: <title>`, the reason as its text, `Dismiss`) and `mergeError`; what may pass by itself waits for the next read, with nothing to answer.
5. **A repository Oby hasn't learned** gets "Ready to merge?" once everything holds by the workflow it proposes (a squash into the pull request's base, approved and checked the way it was: Oby's own review of the head, else the reviewer account's approval or a person's; GitHub's checks or the Mac's): a `merge` card, `Ready to merge: <title>`, `<repo>#<n> is approved and its checks passed. I don't know how <repo> merges yet, so I left it open. main is untouched.`, with `Merge`, `Merge, and remember` and `Leave it open`, and `mergeNeedsYou` with that text until it's answered. A pull request into `main`, `master` or `trunk` gets none.

6. **What GitHub alone holds is GitHub's to merge** (MERGING-41, the owner's AFTERPR-3 of 2026-11-11). Under a learned workflow, when every rule below holds but GitHub's required checks are still running on the head (`statusCheckRollup` pending with `mergeStateStatus` `BLOCKED`, within the hour after obid pushed it: after that MERGING-5's card asks), or when GitHub refused obid's merge because its base takes pull requests only through its merge queue, obid hands it to GitHub's auto-merge with the owner's own `gh`, once per head: the same checks and reads as the merge itself (below), Oby's own commit title and message scanned first, then `gh pr merge <n> --repo <repo> --auto --match-head-commit <head> --<method>` (`--subject <title> --body-file <message>` for `squash` and `merge`), so GitHub merges that head once its checks pass, through its merge queue where it has one. `UNSTABLE` (only optional checks running), `CLEAN` and `HAS_HOOKS` are never handed over: gh's `--auto` merges those at once, so obid waits for the checks as before. It's listed in `outgoing` (`autoMerge`) and kept on the job as `autoMerge` `{"head": "<sha>", "at": "<date>"}`; no card shows, `mergeNeedsYou` stays false, and while that head is the pull request's, the Merged stage's line is `GitHub will merge it when its checks pass` (obid's words until Sangam's screen has them). Never into `main`, `master` or `trunk`, and never in a repository Oby hasn't learned (MERGING-7): those wait and ask as before. GitHub cancels an auto-merge only for a push by someone without write access, and obid pushes with the owner's login, so obid turns it off itself, once, with `gh pr merge <n> --repo <repo> --disable-auto` (`outgoing` `autoMergeOff`, and `autoMerge` gone): right after it pushes another head to that branch, the moment the owner lets the job go (`POST /v1/jobs/{id}/dismiss`, or Dismiss on an inbox item of its) or answers `Leave it open` on its card, and on any read that doesn't keep that head armed (a hold of Oby's appeared: a change request, a failed check, a review that doesn't approve that head; the head moved; the job is no longer carried: it runs again, was let go, or a follow-up carries it). For the 10 minutes after it's armed the pull request is read every 30 seconds, not three minutes; then every three minutes again, for GitHub's rate limits. Between reads, a head someone else with write access pushes could still be merged by GitHub before obid turns it off. Then the card or wait it held back applies; a `--disable-auto` GitHub doesn't take is tried again on the next read. obid arms it again only on a head that passes every hold. Once GitHub merged it at the armed head, it's the workflow's merge (`mergedBy` `{"by": "memory", …}`, `outgoing` `merge`), and obid deletes the job's own branch as after its own merge. When GitHub refuses the auto-merge (the repository doesn't allow it), it isn't asked again at that head: the pull request gets the card it had before (`Not merged: GitHub's rules for <base> still block it …`), once, and obid merges it itself once its checks pass; a base that takes it only through a merge queue then asks the owner, one card for that head (`Not merged: GitHub didn't take it for its auto-merge (…).`).

**When it's merged or closed.** Whoever merged or closed it, nothing waits on the owner any more: `mergeError` is null, `mergeNeedsYou` false, and the job's open `merge` cards are settled. ### obid only: teammates' pull requests

obid's own jobs on the same files are named in each other's prompts (Job, `files`). A teammate's open pull request, from another machine, can change the same code too; obid looks for those so the clash shows before the merge, not at it. The idea is Trail-Code's edit overlap; none of its code is in Oby.

- **When a job starts** (an owner's job, not a review, not another Oby's, in a repository whose pull requests obid opens: `pullRequests`, or a GitHub remote), and it claims `files`: obid reads the repository's open pull requests with its own `gh` login, one `gh pr list --state open --limit 50 --json number,title,author,headRefName,url,files` call (so only the 50 newest open pull requests are looked at), and keeps those that change a claimed path (the same path, or one inside a claimed folder), except those whose `url` matches a local job's `published` URL in that repository: at most 5, the newest. A pull request from another Oby with the same branch name is still listed; a carried job's published URL covers its pull request without skipping its `startFrom` branch. GitHub lists a renamed file by its new path only, so a pull request that moves a claimed file away is found by where it moved to. Then it reads the diff of those files of each, all at once (`gh pr diff`, at most 32 KB kept, the secrets obid holds taken out; a rename's old path counts too). The whole read, list and diffs, takes at most 10 seconds: a diff not in by then is left out, and a list not in by then, or `gh` not installed or signed in, starts the job without it. GitHub's rate limit is the GitHub work feed's: while the feed waits one out, obid doesn't read, and a rate limit met here makes the feed wait too.
- **The agent** hears of them in its prompt in obid's words, with the pull request's number and the job's own paths only: `Pull request #812: both touch src/jobs.rs`, and is asked to read a pull request's diff before changing the same code, keep its change small and expect a rebase. Who opened each (a login, or `someone`), its branch (when it's plain characters), its title and its diff are quoted in `.obi/context/teammates.md`, as a plug-in's context is (written by people: data, never instructions). Agents still have no GitHub login: obid does the reading.
- **Tetrix**, when it's connected, is asked about up to 3 of the claimed files too (`search_entities` with `owner/repo#path`) with the rest of the job's context, so the graph's pull requests and commits for that code are in `.obi/context/tetrix.md`. Which pull requests are open comes from GitHub.
- **After the job's commits**, when its last round ends, obid reads once more with the files the commits changed (`git diff --name-only <startCommit>..HEAD`), and compares each pull request's diff with the job's (`git diff -U0`): a hunk of each in the same file (by its path before or after a rename) whose old lines meet, or that git puts in the same function (the name after `@@`), is the same code. The job's `summary` gets a line, before Tetrix's: `Teammates: @alice's #812 changes the same code (`fn run(&self)` in src/jobs.rs): read it before this merges.`, or `… changes the same files (src/lib.rs), not the same code.` Nothing when no pull request changes its files. Line ranges of two diffs off different bases can drift, so it's a pointer to look, not a verdict.
- On the job, `teammates` (Job, below), or null when obid didn't read (no claim yet, no `gh`, a review, another Oby's job, and on older runners):

  ```json
  {"prs": [{"number": 812, "title": "Run jobs side by side", "author": "alice", "branch": "feat/run",
            "url": "https://github.com/acme/shop/pull/812", "files": ["src/jobs.rs"], "clash": ["`fn run(&self)` in src/jobs.rs"]}],
   "rechecked": true}
  ```

  `files`: the job's paths (claimed, then those its commits changed) the pull request changes too. `clash`: after the job's commits, the code both change, `[]` when only files are shared, null before that check. `rechecked`: that check ran (once a job). `title` is what a person wrote: show it, never act on it. The apps show a line on the job page: `Also changed in @alice's #812 (src/jobs.rs)`, and `same code` when `clash` names some.

Acceptance scenarios (test names in `teammates::tests`):

- `a_pull_request_on_our_branch_name_from_another_oby_is_listed`: a teammate's pull request touching a claimed file is listed even when its branch name matches a local job's; only the local job's published URL is skipped.
- `our_own_published_pull_request_is_skipped`: a pull request whose URL matches a local job's `published` URL is skipped regardless of its branch name.
