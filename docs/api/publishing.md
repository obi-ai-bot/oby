### `GET /v1/jobs/{id}/publish`

What publishing this job by hand would do, in one sentence: for a job whose own publish failed (`publishError`). A task's page shows exactly this under Publish before the owner's click publishes it. An alert's Publish (`ready`, on the Mac and the iPhone) is that click already: it opens the task's page, which shows the sentence as it publishes. Since every job publishes by itself (#1386), this is for a job whose own publish failed, or, with `anyway`, one obid wouldn't send (`canPublishAnyway` on the job, PUBLISHING-14).

```json
{"action": "Push oby/fix-ab12cd to deskree-inc/oby and open a pull request into dev.", "base": "dev"}
```

Once the job is published and has new commits, the sentence is about them: `"Push the new commits on oby/fix-ab12cd to deskree-inc/oby, for its pull request into dev."` A rebased branch's rewritten commits are new commits too, until they're pushed.

`409` if there's nothing to publish (no commits, not done, or published with every commit: the branch on GitHub is at the worktree's head). On obid, also while a follow-up carries its branch on, queued, running or done and not dismissed (`Its follow-up <title> carries its branch on: publish that one instead.`), as Try again and delete refuse then: that follow-up publishes the branch (docs/contracts/publishing.md, PUBLISHING-3); and when its check didn't pass on the commit its branch is at, with why (the moved branch's words, below, or the check's: PUBLISHING-5). Such a job isn't offered Publish anywhere by default: no Ready alert, nothing waiting on the owner; the owner's signed Publish anyway publishes it (below, PUBLISHING-9; proposed, not built: its card keeps the refusal's words and offers it). On obid, also when a remote with no pull requests has every commit: `Nothing to publish: the remote is already at its head.` (#627). One whose pull request failed after the push is still offered: publishing it again opens the pull request.

**The owner's own choices** (obid only; the owner's decision of 2026-10-31, docs/contracts/publishing.md PUBLISHING-9 to 11): `?anyway=true&to=<branch>&force=true`, any of them, ask for more than Oby's default, and the sentence names each, so the owner's signature covers it; the `POST` body carries the same keys. `anyway` publishes a job whose check failed or didn't run, or that a follow-up carries on, where the default answers `409`: the answer's `head` is the commit it sends (the worktree's head for a job that didn't end done, which then takes its commits into obid's clone first; else its branch's in obid's clone), and the sentence ends ` Its check didn't pass on <head>, or didn't run: it goes out anyway.`; a branch somewhere else by the `POST` is refused (`Not published: <branch> is at <commit> now, not <head>, the commit you approved.`). `to` is the branch it goes to on the remote, any branch (the default branch too): onto its base it lands there with no pull request (`Push oby/fix-ab12cd to dev on deskree-inc/oby, with no pull request.`), else it's pushed as `to` and a pull request opens from it (`Push oby/fix-ab12cd to deskree-inc/oby as release/2 and open a pull request into dev.`). `force`: the answer's `over` is the commit on that branch now (empty for none), the sentence says ` It replaces <over> on <branch> (force-push).`, and the push uses `--force-with-lease=refs/heads/<branch>:<over>`, so one that moved since sends nothing. Each lets a root commit go, its whole tree scanned. The secret scan runs on every one, and a finding sends nothing (`409`). Oby never chooses any of them by itself.

How a push goes out, by itself or by hand: the runner reads the branch's head on GitHub. No branch yet, the same commit, or one the new head builds on: a plain push (by itself, a branch the job made that it never pushed and that's on GitHub now is someone's: it stops being the job's and nothing goes out, PUBLISHING-13). Anything else is a rebase, pushed with `--force-with-lease=refs/heads/<branch>:<the commit there>`, and only when that's the commit the runner itself pushed last (`outgoing`) and the branch is one it made: an `oby/` one, or a new one the owner named (PUBLISHING-13). For a follow-up carrying the same branch, that last push is its own, else its parent's, and so on through matching `follow_up_of` and `start_from` links in the same repository; it publishes to that chain's existing pull request, never opening a second one (PUBLISHING-27). When someone else pushed to it, nothing goes out by itself (over someone else's work only on the owner's signed `force`, which names the commit it replaces, below): `publishError` is `Not published: oby/fix-75 on GitHub is at <commit>, not the commit Oby pushed, so the rebase would overwrite someone else's work.` (or `… moved on GitHub while Oby pushed the rebase …` when the lease didn't hold). The secret scan, the pinned commit and the stop checks are the same either way.

### `POST /v1/jobs/{id}/publish`

Publishes by hand, for a job whose own publish failed, after the user approved on a registered device: the owner's click in the iPhone app or the Electron app (main shows obid's own sentence in its own dialog, and signs it on Publish there, PUBLISHING-14). Each has its own key (`apps/shared/DeviceKey.swift`); either one opens the same door.

```json
{"device": "d7c1…", "action": "Push oby/fix-ab12cd to deskree-inc/oby and open a pull request into dev.",
 "signedAt": "2026-10-09T22:01:07Z", "signature": "MEUCIQ…"}
```

- `signature`: ECDSA P-256 with SHA-256 (DER, base64) over the UTF-8 bytes of `"oby-publish\n<job id>\n<action>\n<signedAt>"`, made with the device's Secure Enclave key. The owner's click is the approval: the key has no presence check (`.privateKeyUsage` only), so signing asks for no Touch ID, Face ID or password (the owner's decision of 2026-10-24). The key never leaves the device's Secure Enclave, and its wrapped blob is kept where only Oby reads it without asking: the iPhone app's own keychain, and on the Mac the login keychain, whose access list makes macOS ask the owner before another app reads it (a boxed agent can't reach the Keychain at all). So an approval comes only from the owner's own app, never from a job, another Oby or the API token alone. A program running as the owner that the owner lets read the Mac's item could sign; the data-protection keychain, which binds it to Oby alone, waits for Developer ID's provisioning profile. Until 2026-10-24 the keys asked for Touch ID, Face ID or the Mac's password; each device makes its new key once (Keychain account `approval-key`, the old ones deleted) and registers it: the iPhone as its paired phone's key on its next connection, the Mac on the owner's first click (`POST /v1/devices`).
- The runner checks:
  - the device is registered;
  - the signature;
  - `action` matches its own sentence exactly, for the body's `to`, `force` and `anyway` (obid only, as `GET` takes them; left out, Oby's default);
  - `signedAt` is within 2 minutes;
  - this signature hasn't been used before.
- A Confirm in the inbox is the same proof with its own prefix, `oby-confirm\n<item id>\n<title>\n<signedAt>` (obid only, `POST /v1/inbox/{id}/answer`, #776): a publish signature never passes for a Confirm, nor the other way.
- Then it runs Publish, as a job's own publish does: guards, the secret scan, push one pinned commit, then the pull request, ready for review (the one already open for the branch, if there is one). It returns `{"url": "https://github.com/…/pull/42"}`, or an error line (for example the scan's findings, never the secret).

### obid only: publishing the owner's work

`obid` publishes as [Job](#job) and [`GET`](#get-v1jobsidpublish) and [`POST /v1/jobs/{id}/publish`](#post-v1jobsidpublish) say, by itself when a job ends `done` with commits made in that run, and by hand with a registered device's signature. What is particular to `obid`:

- **Where it runs.** Every git command of publishing runs in `obid`'s own clone (`home/clones/<owner>/<name>`), on the commit its check passed on, never in the job's worktree, whose git files the agent could write. Before a job's check runs, obid reads its worktree's HEAD and `git status --porcelain --untracked-files=all`; the check passed on that commit only when nothing of the job's own was uncommitted and the check left HEAD there. What its earlier checks left (each path `git status` lists after a check that wasn't there before it, or that an earlier check left, with a hash of its content read in the job's sandbox) isn't the job's own while it's there unchanged: a test report or a coverage folder a check writes doesn't hold the job back. When the job ends `done`, obid takes its commits into the clone, moves its branch there and keeps that commit with the job (`checkedHead` in its file, not in the API; a job with no check keeps its head): publishing, by itself or by hand, pushes that one commit and nothing else, and only while the job's branch in the clone is still there. A check that ran with work uncommitted gets one round telling the agent to commit it (`COMMIT_HERE`'s words); uncommitted still, or a check that moved HEAD, ends the job `done` with nothing published, `reason` `Not published: its check ran with changes in the worktree that weren't committed, …` or `Not published: its commits changed while its check ran, …`. Whenever obid moves a branch in its clone, the jobs whose checked commit there is another lose it, and with it Publish. When the branch moved since (another job's commits on it, a follow-up's that failed its check), nothing goes out: `publishError` (or the `409` of a Publish by hand) is `Not published: oby/fix-75 moved since this job's check passed on it, so its commits now aren't the ones checked.`; a job from before obid kept that commit says `Not published: this job ended before Oby kept the commit its check passed on, so Oby can't tell what it checked. Tell it to carry on, and it checks again.` (docs/contracts/publishing.md, PUBLISHING-1, PUBLISHING-2). Objects are read as they are (`--no-replace-objects`), no hook runs, and every diff the scan reads is `--no-ext-diff --no-textconv --text`, root commits included (`--root`). What the scan reads, it reads with the clone's own configuration only (`GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`): a setting of the person's (`log.showRoot = false`, an attributes file) can't narrow it. The fetch and the push keep the person's git configuration (their remotes' addresses and sign-in).
- **Where it goes.** The push goes to the repository's `remote` (obid only: configuration) by its address, not to `origin`, whose push URL stays invalid; it pushes one commit, `--no-follow-tags --no-signed --recurse-submodules=no`, and `--force-with-lease` only for a rebase of a branch it made (`oby/`, or a new one the owner named: PUBLISHING-13) over the commit it pushed there last. A remote whose address carries a login (`https://user:token@…`) is refused (`publishError` says so), since the address would be in git's arguments. For an `https` remote, git signs in with the owner's `gh` as its credential helper (`gh auth git-credential`: the credential travels on a pipe, never in an argument or the environment). Clones and fetches of an `https` remote sign in the same way, git's own helpers reset first, so a private repository clones with nothing set up but gh's own sign-in (no `gh auth setup-git`), and gh's token never reaches another helper (after a clone git asks every helper to `store` it, and Apple's git turns `osxkeychain` on system-wide). Without a gh, a clone uses git's own settings.
- **GitHub.** `obid` has no GitHub app: the pull request is opened (`gh pr create`, ready for review, never a draft), found (`gh pr list --head`), brought up to date (`gh pr edit --body-file`) and followed (`gh pr view`) with the owner's own `gh` login: the `gh` Oby.app carries (`Contents/MacOS/gh`, pinned and signed with the app, apps/mac/app/Tools/bundle-gh.sh) when obid runs from inside the app, else the one on the login shell's `PATH` (`GET /v1/status` says `"github": "owner"` and `"checks": "no app"`). `gh` runs with `obid`'s environment and `GH_PROMPT_DISABLED=1`; its description goes in a 0600 file in `home/tmp/publish-<job id>/`, removed afterwards. Only a pull request URL of the job's own repository, `https://github.com/<repo>/pull/<n>`, is kept or followed. An open pull request is taken as the job's only when it comes from the repository itself (`isCrossRepository` false: a fork's branch of the same name is someone else's), into the job's base, and its head is the commit obid just pushed, or the one it pushed before; otherwise obid opens its own. Without `gh`, `publishError` says the pull request couldn't be opened; a push that went out before (one to an `ssh` or `file` remote needs no `gh`) is listed in `outgoing` and counted in `pushed`. Only a remote on GitHub (`https://github.com/…`, `ssh://git@github.com/…` or `git@github.com:…`) gets a pull request, unless the repository's `pullRequests` says otherwise: for any other, nothing is asked of `gh` (no pull request, no issue read), and the push is the whole publish (#627). `POST` then answers `{"url": null}`.
- **Git LFS and submodules** (docs/contracts/publishing.md, PUBLISHING-19 and 20). A job's worktree, Oby's review's and the rebase onto a moved base run with `-c filter.lfs.smudge= -c filter.lfs.process= -c filter.lfs.required=false` (`git::LFS_POINTERS`), so LFS files are pointers, as the check sees them; while a job gets ready its `step` is `Getting <repo> ready: its Git LFS files are pointers, so what needs them won't work`. A job's worktree then gets its submodules from obid itself, never its agent (docs/contracts/setup.md, SETUP-1): with a `.gitmodules`, its `step` is `Getting <repo>'s submodules` while obid runs `git submodule init`, `sync` and `update --init` for each gitlink of the commit, then of each submodule it filled (at most 100 tried in all, the failed ones too, `obid tries at most 100`, within 20 minutes in all, `obid gives submodules 20 minutes in all`, under the repository's preparing lock, since `init` and `sync` write the clone's shared config; a Stop ends it at once and the job ends stopped), unboxed as its fetches are, with `-c protocol.file.allow=never` (`always` with `allowFileRemotes`), `-c submodule.recurse=false -c fetch.recurseSubmodules=false` and the LFS settings above; git's own credential helpers are reset for every host, and the owner's gh login signs in only on the repository's own `https` host (`credential.https://<host>.helper`), so a submodule anywhere else gets no credentials. Each URL is checked as `sync` wrote it, the one `update` fetches, fail-closed: a path `.gitmodules` names twice isn't filled (`` `.gitmodules` names it more than once ``); nor one whose URL obid can't read strictly (`its URL isn't one obid can check`: a `%`, `[`, `]`, `\`, whitespace or control character anywhere, a user or host of anything but letters, digits, `.` and `-`, a port of anything but digits, a `.` or `..` in its path, a scheme but `https`, `http`, `git`, `ssh`, `git+ssh`, `ssh+git` or git's `host:path`); nor an ssh one on another host than the remote's (`another host's ssh submodule gets no keys`), so the person's ssh agent and keys sign in nowhere else; nor one on this Mac or its network, unless the remote is on that host (`its URL is on this Mac or its network`: `localhost`, a loopback, private, link-local, shared or unspecified IPv4 address, or a numeric name such as `127.1`; a name whose DNS answers with one isn't caught). One that fails is named on the step, `Getting <repo> ready: its submodule \`<path>\` wasn't filled (<git's first fatal line, at most 200 characters>), so what needs them won't work` (joined with ` and ` to the LFS words), and the job goes on. A submodule (nested ones too) whose URL isn't on the repository's host under its owner marks the clone as holding someone else's commits (`obid.foreign`, `a submodule from <url>`). Oby's review's worktree, the rebase and the check's checkout leave submodules empty. Why not, by itself: a change that adds or changes LFS pointer files since its merge base with the base (read by content at the head, never by `.gitattributes`) isn't published by itself, since obid never uploads LFS files: `publishError` `Not published: it adds or changes Git LFS files (<files>), and Oby doesn't upload LFS files, so the remote may not have what they point to. Read its change, then Publish it by hand.` Any Publish of the owner's (`POST /v1/jobs/{id}/publish`, the plain one too) sends it. obid never runs git-lfs.
- **The base** is fetched from the remote first and pinned to the commit it is at then: what the push sends beyond it is what the scan reads. Jobs on one repository that end together all publish (#628): obid's clone sets `fetch.hideRefs` to `worktrees/`, so a fetch doesn't check what it got against the HEAD of another job's worktree, whose commits stay in that job's own object folder until obid keeps them (git said `did not send all necessary objects` otherwise); one fetch runs at a time per clone, no job's commits land in the clone while one runs, and a fetch that still gets that answer is tried once more. When it can't be fetched, nothing goes out (`publishError` `Not published: couldn't fetch <base>: …`, git's own line, never its command line or the remote's address).
- **The scan** is `crate::scan`'s, on everything that goes out: each commit's patch (`git log -p --diff-merges=remerge`), its added lines (named by the diff's `+++` line, which names a file exactly), with gitleaks on them; every name a commit adds at a path its parent didn't have (each file's, folder's and submodule's own name, from `git log --raw -z --diff-merges=separate --ignore-submodules=none`, so never split or quoted, a merge read against each parent and a submodule never hidden, whatever the clone's settings; a name already on the base at the same path is the base's), with the built-in rules reading a name as they read a line, and gitleaks on them, one name per line (a newline in a name written as `\n`), a finding it can't place in a name counting all the same; a file whose name alone holds secrets (`.env`, a private key's file) counts only as a file, not a folder named so; every file those commits send, read whole, for the secrets `obid` holds (its API token, its Obi key, the Sphere's delegation and token, and the vault's: [obid only: the vault](#obid-only-the-vault)), in every form `crate::secrets` knows, a file over 32 MiB being a finding; each commit as git keeps it (`cat-file`), its author and committer (`commit author`) and its message's own bytes (`commit message`); and the branch's name, the pull request's title and description, and each of the agent's summaries as it wrote them (`agent's summary`: the description's quote of it has invisible characters in it, which a known secret holding `@x` or `#1` would no longer match). A commit whose headers aren't exactly what git writes for a plain commit (one `tree`, its `parent`s, one `author`, one `committer`, in UTF-8: no `encoding`, which would re-encode its message, no signature, no other header) or whose message isn't UTF-8 text is refused: nothing goes out, and `publishError` names the commit, never what it holds. A name that holds a possible secret is never repeated: wherever `obid` says where it found something (`publishError`, the summary, the log, the API), that file is `a file whose name obid won't show`, and the line adds that it is among the names of the files and folders the branch adds to its base, which is where the owner looks. A possible secret in `commit author`, or in a file obid won't name, gets no fix round. A file finding names the commit whose patch introduced it, and whether the branch's tip still has it. A gitleaks that can't run is a scan that couldn't run: nothing goes out, and the job stays `done` with `publishError` `Not published: the secret scan couldn't run (…)`. So is no gitleaks at all (#1026): the built-in rules alone miss keys only gitleaks knows (Google's `AIza…`, npm, Hugging Face, Twilio, SendGrid tokens, JWTs), so they aren't the scan, and every outgoing path that scans (publishing, merges, memories, alerts, Tetrix) sends nothing, saying `gitleaks isn't installed: Oby.app carries its own; elsewhere, put gitleaks on obid's PATH`. obid takes the gitleaks Oby.app carries (`Contents/MacOS/gitleaks`: gitleaks 8.30.1, universal, checked against its SHA-256 and signed with the app when it's built, apps/mac/app/Tools/bundle-gitleaks.sh), else the login shell's. gitleaks always reads a fixed first line of obid's (`obid`, no word a rule looks for) before the lines it's given: what starts like a PDF, a zip or a gzip (`%PDF-1.4`, `PK\x03\x04`) is something gitleaks skips whole, so a diff whose first added line looked like one would otherwise be scanned as nothing. A finding wholly on that line doesn't count; one that runs past it (its `EndLine` 2 or more) does, on the first line given. gitleaks also sniffs further in (`ustar` at byte 257 for a tar, `CD001` at byte 32769 for an ISO image) and then reads nothing at all, whatever comes first, so obid puts a canary last: a made-up GitHub token, new every run and never kept, in the shape gitleaks' `github-pat` rule always flags, after another `obid` line, so a last line that only names a secret (`API_KEY=`, `token:`) isn't read on into it. A report without the canary (gitleaks exited 0, or wrote no report it could read) is a scan that couldn't run, `gitleaks didn't read its input`, and nothing goes out; the canary's own finding, and any wholly on that `obid` line, are dropped. gitleaks runs with `--ignore-gitleaks-allow`: a `gitleaks:allow` comment in what's scanned hides nothing (without it, gitleaks drops every finding in the part of its input that holds one, and past about 300 KB the canary is in another part, so the scan would read clean). The Swift engine's own gitleaks call has none of this yet (#657).
- **The pull request's description** quotes each of the agent's summaries as Markdown, under a label saying they are the agent's words, less any line saying `Generated with Claude Code` (with or without its link, in any letter case: the owner's rule); an invisible character (U+200B) after each `<`, `&`, `@`, `[` and `]`, after a `#` before a letter or digit or one that starts a heading, and in each closing keyword and heading underline, keeps any of it from acting (no HTML or open `<!--` comment, entity such as `&commat;` or `&#x23;` that reads as `@` or `#`, link, image, alert, task box, mention or closed issue). Code gets the same characters: a fence closed by an indented line or a code span across lines is easy to misread, and one missed would leave the rest of the summary live. It ends with `by Oby: Oby opened this pull request after the check passed and the secret scan was clean. Oby merges it only when its owner says so.` in place of the Swift runner's merge sentence; a job with no check says `- Check: none, the task had no check.` and ends `by Oby: Oby opened this pull request after the secret scan was clean. Oby merges it only when its owner says so.` Where the owner taught Oby how the repository merges (obid only: merging), its last sentence is `Oby merges it by itself, the way its owner taught it: <the workflow's own sentence>` instead (MERGING-11).
- **Following** reads a published pull request when `obid` starts, right after it publishes one, and every three minutes while it is open (every 30 seconds in the 10 minutes after obid armed GitHub's auto-merge on it, MERGING-41); a read or a try in the last three minutes (30 seconds) isn't repeated. Each read carries the job on (obid only: merging). A pull request obid has recorded as merged isn't set back open by a read that started earlier, and isn't merged again (MERGING-2).
- **By hand.** The device's key is the one it registered (`POST /v1/devices`); each approval is let through once, and what was used is kept for 10 minutes in `home/approvals.json` (0600), so a restart opens no replay. An approval is used up when it is checked, even when publishing then fails. The sentence names the branch, not its commits, so an approval publishes only the run that was approved: when the job's latest run ended after the device signed (`signedAt`), or when `obid` described an earlier run of it (`GET`; a run is told from the next by its round, even when both end in the same second) in the two minutes before the device signed, the approval could be of either, and `POST` answers `409` `The job ran again since obid said what publishing it would do. Approve it again in two minutes.` What `obid` described, and when, is kept with the job, across restarts. This is a narrowing, not a seal: signing the commit itself is #553. While a publish by hand runs, the job takes no words (`POST /v1/jobs/{id}/messages`, `422`) and can't be dismissed (`409`). The refusals are `403`: `That device isn't registered with this Oby.`, `The signature doesn't match the device's key.`, `The device approved something else. Approve it again.`, `The approval is more than two minutes old. Approve it again.` and `That approval was already used. Approve it again.`. A publish that fails answers `409` with its line.
- **The journal.** `obid`'s log has one line per thing it sent (`job <id>: sent push <repo> <branch> <commit>`), ids only, and one line per publish that didn't go out, saying why (never a secret).
