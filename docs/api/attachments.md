### `POST /v1/attachments` (obid only, #1576)

A file the owner picked or pasted in the Mac app, kept for the words it goes with. `?name=` is the file's name; the body is its bytes as they are (`Content-Type: application/octet-stream`). obid keeps it as `attachments/app/<uuid>/<name>` under its home (0600 in 0700 folders), the name cleaned to letters, digits, `.`, `_` and `-`, with no leading dot and at most 100 characters (`attachment` when nothing is left), and answers `201`:

```json
{"path": "/Users/me/Library/Application Support/Oby/Runner/attachments/app/3f…/shot_1.png", "name": "shot_1.png"}
```

`path` goes in `attachments` on `POST /v1/plans` or `POST /v1/jobs/{id}/messages`. A file over 25 MB is `413` (`<name> is larger than 25 MB, so Oby can't take it.`), an empty one `422` (`<name> is empty.`). obid keeps the newest 200 uploads and removes older ones (the conversation's room and a job's inputs keep their own copies). A conversation keeps the paths of its words' files, and deleting it (`DELETE /v1/conversations/{id}`, or obid forgetting it past 500) removes them, except one a job that hasn't ended holds. A file gone before its turn or job copies it is named in that prompt as `(left out: <name>, it is no longer on this Mac)`; a job keeps such names in its `attachmentsGone`, left out when there are none.

`DELETE /v1/attachments?path=<path>` removes an upload whose words never went (another upload or the words were refused): `204`, the file and its folder gone. A path that isn't one of `POST /v1/attachments`'s is `422` (`That isn't a file the Oby app uploaded.`); one a conversation or a job that hasn't ended holds is `409` (`Words or a task still use that file.`) and stays. Only on the Mac: the gateway doesn't list it, so a phone can't upload. The file is untrusted, as every attachment (docs/contracts/attachments.md).

`runsOn` (obid only, #808) is taken and ignored: compute sharing is gone (2026-10-27), and every job runs on this Mac. A job's `runsOn` is always null.

`jobs` (obid only, #1173), when present, is the jobs the owner attached to the words (Sangam's + › Attach tasks), by id: at most 20, each one this runner has, else `422` and the words go nowhere. They're kept on the owner's turn (its `jobs`, below), where the apps show their cards, and the conversation's agent reads that the owner attached them, by id, before the words, and looks each up with `oby_job`. An id grants nothing: the agent can read every job anyway, and what a job's agent wrote reaches it quoted.

`folders` (obid only, #1572), when present, is folders on this Mac the conversation works in from now on (obid only: working folders, below): absolute paths, added to the conversation's (never removing one). With `new: true` they go on the new conversation. Words sent again with the same `id` are `repeated`, whatever their folders, and add none. A path that's refused is `422` naming it and why, and nothing of the request happens. An empty list is the same as none. Through the gateway or the phone relay, `folders` with any path is `422` (`Folders are added only on the Mac.`): only the owner's Mac app adds a folder.

To answer the brain's question, send the original words with the answer:

```json
{"said": "Review PR 12", "answer": {"question": "Which repository is PR #12 in?", "option": "deskree-inc/oby"}}
```

**The brain answers with context.** Before the user's words it reads a briefing the runner builds: the conversation so far, the jobs (running, needing the user, in review, finished or merged in the last two days, with their titles and stages), the inbox, each account's usage, and the week's failure records (below: counts by cause, the rounds the failed jobs used, and each record's trigger, cause, signature, issue and fix job; what the post-mortem wrote is in the quoted file). So it answers "why did jobs fail this week?", questions about the work ("how are the jobs going?", "what did the #12 job change?", "how long until Codex resets?") as a `reply`, and reads follow-ups ("and the vault one?", "cancel it"). The briefing holds only what the user and Oby said and what the runner knows; what agents wrote (a job's result and current step, an inbox question and its options, a failure's reason), and an inbox item's `headline`, `happened` and recommendation, which a model wrote from those words, reach the brain as a quoted file it may read, never in a prompt, as every other outside text does. The typed plan is still checked in Swift. A plan acts once it's made: the runner can't tell a client that gave up waiting from a slow one, so an app that lets the user cancel a turn only drops the answer, and a stop the turn asked for still happens.

**The chat looks things up.** When the briefing cannot answer a question about code, docs, issues or pull requests, the brain can request up to 4 read-only lookups at once: `search_code`, `list_files`, `read_file`, `git_log`, `view_issue`, `view_pr` and `fetch_url`. Code reads use Oby's clone at one resolved commit and cite GitHub links pinned to that SHA. Search returns at most 50 hits, file listings 300 entries, file reads 400 lines and 24 KB, logs 20 commits, issue/PR bodies 6 KB and 10 comments of 1 KB each, and web responses stop at 1 MB and return at most 16 KB. A turn runs at most 12 lookups and quotes at most 48 KB into the brain's `work.md`; repeated lookups reuse the quoted result. Web reads allow public HTTPS hosts only and check every redirect. The brain has no shell or edit tools: Swift runs a fixed argv for each lookup, and every result is quoted data, never an instruction. Research answers questions; it never starts work. If research shows work is warranted, the jobs wait in a `start` inbox item until the user taps Start.

Bare cancel words ("never mind", "stop", "cancel", "forget it") never reach the brain. When a conversation turn is underway they request a boundary stop; otherwise the answer is `none` and nothing stops. Stopping coding work still takes a job's name or "stop everything".

The conversation so far is the runner's own, the last 50 of the turns it keeps (`GET /v1/conversation`, below). An app that shows its own thread sends it instead, oldest first; `who` is `user` or `oby`, `text` 1 to 2,000 characters (on obid, any length but empty), at most 50 turns (`422` otherwise). Either way the new exchange joins the runner's conversation. On `obid`, which keeps many conversations, the request may name the one it joins (`conversation`, or `new`), and the answer says which it joined: obid only: conversations, below.

While a turn carries out actions, `GET /v1/events` sends a `step` event when each action starts and when it ends. Its `turn` is the user's turn id, `index` starts at 1, `action` is the plan action (including `research`), `text` is a short description, `state` is `running`, `done` or `failed`, and `at` is ISO 8601 time:

```json
{"turn":"8d…","index":1,"action":"research","text":"Searching oby for “Runner API”","state":"running","at":"2026-10-12T12:00:00Z"}
```

Oby says what it's doing before it knows what it will do (#592, obid only): a turn sends a `thinking` event as soon as it starts, well within half a second of `POST /v1/plans`, however long its brain then takes, and one for each later call to its brain as it begins. Each line is `running`, then `done` when that call's plan comes, or `failed` when the turn was cancelled, stopped or ran out of time first. `index` is the step the call plans, as the `step` events count them; `text` is what it thinks about: `Thinking` for the first call, then `Looking at <job>` after reading a job, `Going over what it found` after research, `Deciding what's next` after an action, `Checking nothing was missed` for the completion check (below):

```json
{"turn":"8d…","conversation":"c1…","index":1,"text":"Thinking","state":"running","at":"2026-10-12T12:00:00Z"}
```

Then a `reply` event carries what Oby says as soon as it knows (#592, obid only), so an app can show or speak it while the rest of the turn happens: for a plan that starts jobs, its words as soon as the plan is checked, before the jobs are made (the jobs' own `job` events come after it, and `POST /v1/plans` answers once they're made); for a reply or a question, the words once they're settled. At most one per turn, never for a turn that's cancelled or stopped before it, and never empty. When the answer of `POST /v1/plans` says the same words, they've been said already. A turn cancelled after its `reply` went out (`POST /v1/plans/cancel` while its jobs are made) still answers `none` and starts nothing:

```json
{"turn":"8d…","conversation":"c1…","text":"On it: one job for the README.","at":"2026-10-12T12:00:03Z"}
```

The brain still answers with `--output-format json`, all at once: streaming the reply's words while they're written (`stream-json`) waits until the per-call records (#533) show it doesn't slow the turn.

`POST /v1/conversation/stop` asks the turn underway to stop after its current action, and answers `{"stopped": true}`. On obid, which runs a turn per conversation, the body may name it, `{"conversation": "<id>"}`; with no body it's the conversation of the latest turn under way, and turns in other conversations go on (`400` for any other body). A bare cancel word sent with `"new": true` stops no turn. `POST /v1/plans/cancel` takes the same body. The in-flight `POST /v1/plans` then returns a reply describing what it completed. The cancel words `stop` and `never mind` have the same effect. The turn budget is 110 seconds; clients should wait 120 seconds while following its step events.

`POST /v1/plans/cancel` drops the turn underway instead, and answers `{"cancelled": true}`: the plan its brain is making does nothing when it comes, and the in-flight `POST /v1/plans` answers `none`. What the turn already did stays done. On obid it drops the words waiting for that turn too (obid only: conversations); the turn's words and the waiting ones stay in the conversation with `delivery.status` `cancelled`. An app sends it before it replaces a turn with new words: on obid, new words wait their turn instead unless it does.

**What happened while you were away (#594, obid only).** obid keeps the time of the owner's last message (`POST /v1/plans`) or tap (`POST /v1/inbox/{id}/answer`: an answer, done or later), in memory: after obid starts, the first one is a first sight. #### The Lead: vague goals

A vague goal, like "work on the roadmap", "Obi, next issue", "pick the next open issues" or anything naming the roadmap, the board or the backlog, goes to the Lead instead of the brain (when a Claude account is signed in). Words that stop work ("stop working on the roadmap") stay with the brain, which stops the jobs. The Lead is a fresh Claude Code turn on Sonnet 5.5 (the model the spike proved), with only Read, Grep and Glob, boxed like a job. It takes 6 to 20 seconds. Before each turn the runner:

- reads the GitHub project **Oby — Roadmap** with its own `gh` login: the open issues in board order, each with its status column, labels, milestone, assignees and the open pull requests that close it;
- builds the **skipped list** itself, never trusting the Lead's: done, in review, `status:needs-test`, blocked, `oby:skip`, assigned to someone else, a queued or running Oby job on it, or an open pull request (the board's, or one Oby published for it);
- writes `.oby/context/roadmap.md` (the board with the runner's verdict on every row, workable or why it's skipped) and `.oby/context/jobs.md` (the runner's running and recent jobs, with the files each expects to touch) where the Lead reads them.

The Lead answers one typed plan, checked in Swift and retried once with the reasons: `start_jobs` (one brief per job: repository, issue, kind, title, goal, the files it will touch, a one-line check and what's out of scope), `reply`, or `ask_user`. No push, merge, approve or publish action exists. A brief is refused unless its issue is one the board lists as workable: a skipped issue is refused with its reason, and a closed, made-up or off-board issue is refused too (Oby would claim it on GitHub). So the same request twice starts nothing new.

The jobs start right away, with no Dispatch tap, each routed to the signed-in account with the most room (the picks spread out, as a plan's drafts do), with 4 rounds (one attempt and three fix rounds) and the brief's check. Right before each job starts, the runner checks the live jobs again: an issue that got a queued or running job while the turn ran (the same request from the Mac and the iPhone at once, or repeated after the app gave up waiting) starts nothing new, and the reply says so. The answer is a `reply`: `"Started 2 jobs: Safe when nobody watches (#7), Watch first slice (#12). Skipped 8 on the board."`, and the jobs arrive as `job` events and in `GET /v1/jobs` with `files`, `lead` and, once each starts, `claim`. When nothing can start, the reply says why (every issue skipped or taken, the board unreadable, no account with room, or the Lead's plans refused twice). A `question` is answered as the brain's is. The runner keeps the last 20 goals' context folders.

All issue jobs use `Engine/IssueSync.swift` on the runner and in the Mac app, with Oby's own `gh` login. Issue sync never comments on an issue or assigns it: the app's comments and assignments email the owner, and the labels, the board and Oby's inbox already say it (#162). Starting adds `status:in-progress`, writes a hidden claim line (`<!-- oby-claim: job <id> -->`, one at the end of the issue's body, replacing any earlier one) and moves its existing roadmap item to **In progress**. An opened PR adds `status:in-review`; GitHub links it to the issue through its `Closes #N` (an issue with a checklist gets `Part of #N`, below). Waiting for an answer, a failed publish or the review cap adds `status:blocked`. A merged PR ticks issue checklist tasks explicitly checked in the PR description by exact text or a unique bold heading. Unfinished tasks in `## Build`, or another active slice, keep `status:in-progress`; otherwise the issue gets `status:needs-test`. Ending another slice preserves this handoff. Real-device testing remains a user handoff. PR descriptions say `Closes #N` so GitHub links the PR to its issue, or `Part of #N` for an issue with a checklist, which one slice must never close; the Lead reads `closingIssuesReferences` and the `(#N)` that ends Oby's PR titles. On obid, a PR's title is the first Conventional Commits subject on its branch that changes the code (`fix`, `feat`, `perf` or `refactor`, the one matching the job's kind first), so a test-first fix goes out as `fix(…)`, not `test(…)` (#765); else the first Conventional subject, else the job's kind and the agent's summary.

An unlinked job is linked only when a standalone `Part of #N` line, an exact brain title (or its `(#N)` suffix), or an `oby/<kind>-N` branch identifies one open issue; incidental issue references and ambiguous jobs stay unlinked. Lifecycle hooks are serialized, and a transition repeats only what isn't on GitHub yet. Every claim, label, checklist and project mutation passes the existing secret scan first and is listed in the job's report. Failure stops that transition and is reported in `claim`. A failed transition backs off per job (1 minute, doubling, at most an hour, kept in `issue-audit.json` across restarts) and stops after 4 tries until the job's state changes; agent steps in between send nothing. Only the Desk whose job the issue's claim line names (or, on an issue claimed before #162 that has no claim line, its latest `Oby is working on …` comment, read only) removes `status:in-progress` or `status:blocked`: a Desk can't see another's jobs (the runner can't see the Mac's), so it leaves those labels alone otherwise.

The runner checks hourly whether the UTC day's audit has run, using a separate persisted ledger (`issue-audit.json`). It resolves `Oby — Roadmap` by title and owner as the Lead does, reads its fields and paginated items once, and audits only open issues already on that project that it has jobs for; issues it has no job for are left alone. It posts no comments. It fixes labels and board columns, removes unsupported running/review/blocked labels, and preserves merged slices' remaining Build work or device-test handoff. Board updates never add items, set Todo, or move Done/Shipped/Closed items. A desired status with no Status option on the roadmap leaves the column alone and is a decision for the owner (#215): one `audit` item per missing column, titled `Roadmap column <column>`, naming the issues that belong there, offering `Add the column` (recommended), `Use <closest column> instead` (when the roadmap has one) and `Ignore this status`, each with what it does (`details`). The answer is remembered for that status in `issue-audit.json` and applies to issue sync and the audit from then on; while it waits, or is put off, the audit doesn't ask again, and once nothing needs that column any more (it was added, or no issue belongs there) the item is done by itself. A report appears only for drift or errors, with a one-line report, an empty `job` and optional `outgoing` records of its repairs: already `done` when nothing failed (the runner fixed the drift itself, which needs nobody), otherwise waiting with `Try again`. Repairs for existing jobs also appear in those jobs' reports; no audit jobs enter history. Limited issue/PR results refuse cleanup instead of assuming unseen work is absent. Missing project scopes from `gh project` (gh prints the scopes line before its refresh hint; any line counts) report exactly: `Runner gh login lacks read:project or project scope; run gh auth refresh -s read:project,project on the runner`. The Lead reports the same fix rather than claiming the project does not exist; repository permission failures retain their actual cause.

Every Lead turn is logged on the runner (the words, the plan or why it was refused, the skipped list, the jobs started) and kept in `oby.sqlite` with the brain's turns.
