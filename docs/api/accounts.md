### Account

```json
{"id": "default", "agent": "claude", "name": "Personal", "payer": "Alex", "label": "Max · someone@example.com",
 "signedIn": true, "fiveHour": 0.12, "sevenDay": 0.4,
 "fiveHourResets": "2026-10-10T02:14:40Z", "sevenDayResets": "2026-10-14T19:27:22Z", "running": 1, "fullUntil": null,
 "tetrix": true, "tetrixJobs": 12, "tetrixUsed": 9, "reserved": false, "reserveLiftedUntil": null}
```

- `email`, `plan`, `org` (obid only, each only when the account's tool said; docs/contracts/accounts.md): who it is, `plan` in the tool's own word (`max`, `plus`). Older runners don't send these keys.
- `login`, `loginEmail` (obid only, only on an account signed in with Continue with ChatGPT; docs/contracts/chatgpt-sign-in.md): `login` is `"chatgpt"`, `loginEmail` the email its id token said, for display. `signedIn` follows its refresh token, never its access token's expiry; `label` says why it can't run (`ChatGPT plan use is off`, `Continue with ChatGPT again`), or why its last sign-in didn't take. `agent` stays `"codex"`. Such an account has no usage read (`account/rateLimits/read` isn't asked), so it shows none and routes as unknown; at a limit it's offered as a Move though it reports no usage, and never taken by itself.
- `backgroundConsent` (obid only, only on an account signed in with Continue with ChatGPT, once the owner answered): whether work nobody's watching may use it (routines, Oby's own reviews, what they start, and `POST /v1/jobs` no app signed). Left out: not asked yet, and it's a no. With no yes such work passes the login by; with nowhere else to go, a job is `queued` with a `waiting` of kind `limit`, `reserved` empty, and its `step` says why (`POST /v1/jobs/{id}/start` answers `409` for it: the owner's yes starts it) (docs/contracts/chatgpt-sign-in.md, "Background use").
- `agent` is `claude`, `codex` or `cursor`. `label` is what the tool says about the login (null while signed out). Its first part is the plan (`Max`, `Team`, `Plus`), which Settings shows next to the account's name. A Cursor account's label comes from `cursor-agent status` (boxed, with the account's own `CURSOR_CONFIG_DIR`; `Signed in` when it says neither way but `cursor-agent models` lists models), and Oby reads Cursor's token files only for a run's copy and its usage read (its login is a file under the account's own `XDG_CONFIG_HOME`, or Cursor's own login's Keychain items). obid sends `label` null but for a Codex login whose access token ends within 5 minutes: `Run codex once` (only Codex itself refreshes it; `signedIn` is false meanwhile). A Codex login OpenAI refused (a run ended on `workspace routing discovery unauthorized (401)`, `401 Unauthorized`, `token_revoked` or `refresh_token_invalidated`, though its token's `exp` is still ahead) reads `Run codex login` with `signedIn` false until the login holds another token (the owner signed in again); obid keeps only a hash of the refused token, in memory, so a restart tries it once more. A boxed copy whose access token's JWT `exp` has already passed, ending on a bare 401 (`unauthorized (401)`, `401 Unauthorized`, not a revocation), is only expired (no refresh token): the job says `The Mac's Codex login for <account> needs refreshing: run codex once.` and the account stays signed in; a revocation on that expired copy still ends the login (`run codex login`) (docs/contracts/accounts.md, ACCOUNTS-18).
- `payer` (obid only): who pays for the account, as the owner put it in Settings › Accounts ("Paid by Deskree"), or null. The Swift runner doesn't send it.
- `fiveHour` and `sevenDay` are 0…1 or null when unknown. An account with both null hasn't reported usage yet. A Cursor account's `sevenDay` is its plan's included usage over its plan's period, a week or a month, and its `sevenDayResets` that period's end; it never has `fiveHour` (below). When an app looks (`GET /v1/status`, or its `GET /v1/events` stream opening), obid asks each signed-in account not asked in the last 10 minutes, in the background, and the answer comes in an `accounts` event; while no app looks nothing is read, and a running job reports its own. No read asks a model. **Cursor** (obid only, the owner's decision of 2026-11-03; docs/contracts/usage.md, USAGE-6 to 9; docs/contracts/keychain.md, KEYCHAIN-8 and 9): obid itself, never in a box or for an agent, `POST`s `GetCurrentPeriodUsage`, then `GetPlanInfo`, of `aiserver.v1.DashboardService` on `https://api2.cursor.sh` (Connect over JSON, body `{}`) with the account's access token. These endpoints are undocumented and can change. A read that gives no figure (signed out, a 4xx or 5xx, no `planUsage`, an answer that doesn't read) leaves `sevenDay` and `sevenDayResets` null, whatever it read before. The figure holds nothing: at any number the account has `fullUntil` null and `reserved` false, and takes work as it did with none. Claude Code's own `/usage` (`claude -p /usage --model haiku --max-turns 1 --output-format stream-json --verbose`, its `usage_report`: `session` is `fiveHour`, `weekly_all` is `sevenDay`; its whole percents never mark an account `fullUntil`) and Codex's `account/rateLimits/read` from an app-server with no thread, each boxed with its own copy of the account's login as the brain's run is. A Claude Code login is readied first as a job's is (#1626, docs/contracts/usage.md): one in the Keychain with `claudeKeychain` (the default login, or an account obid added) that has ended or ends within 5 minutes is refreshed by the Mac's own Claude Code running its own `/usage` (The job sandbox), which asks no model, so a Mac whose `claude` hasn't run in days shows its usage from the first look. The boxed read itself never refreshes: a copy within 10 minutes of its end isn't read with, and a login obid doesn't refresh (a login file, an account's own folder, #655) near its end isn't read until the person runs `claude` on it. An account whose Claude Code asked a model for `/usage` (one without its own) isn't asked again until obid restarts; one that answered with no usage (an API key's) or failed (offline, a refused login) is asked again after the 10 minutes. No read starts while obid is stopping. The Swift runner's Claude Code limits arrive with its first job.
- Cursor's figure is the highest reported share of `planUsage.includedSpend / limit` (a numeric limit above zero), `totalPercentUsed`, `autoPercentUsed` and `apiPercentUsed` (percentages divided by 100), clamped to 0…1. Missing or nonnumeric fields don't count; no share means null, including a limit without spend. One INFO line per parsed read contains only these numbers and the winning field (USAGE-7); the figure remains advisory (USAGE-9).
- `fiveHourResets` and `sevenDayResets`: when each window resets, or null when the tool didn't say. Claude Code sends them in its `rate_limit_event` (`resetsAt` per window) and its `/usage` (`resets_at`), Codex in `account/rateLimits/read` and its `account/rateLimits/updated` notifications (`resetsAt`), Cursor's read as `sevenDayResets`. A window keeps its last reset time until the tool sends a new one (Cursor's goes with its figure). Older runners don't send these keys.
- `running`: jobs queued or running on the account.
- `fullUntil` is set while a job of the account's hit its usage limit: no job goes to it before then. A Claude Code `rate_limit_event` sets it only for the whole account (docs/contracts/usage.md, USAGE-12 and 13): a `rejected` `status` whose `rateLimitType` is `five_hour`, `seven_day`, `overage` or absent, or a `unifiedWindows` window at 100%, and neither while Claude's paid overage carries the work (`isUsingOverage` true, or `overageInUse` true with `overageStatus` `allowed` or `allowed_warning`). A scoped refusal (`seven_day_opus`, `seven_day_sonnet`, `seven_day_overage_included`) leaves `fullUntil` null: it holds only the job it stopped, and the refused model's family when it names one, off the account until that refusal's reset, kept in obid's hold table in `usage.json` (docs/contracts/account-limits.md, LIMITS-21). The account's other work goes on, a job of another family or of a model obid can't place included, and its windows show as reported; the job it stopped moves to another account with room (never one that refused it that limit, until that refusal's reset) or waits as at any limit, with no card (docs/contracts/account-limits.md, LIMITS-15), its wait ending 90 seconds after that refusal's own `resetsAt`, and a conversation turn shows Claude Code's words. While the overage carries the account, a window at 100% doesn't make a passing error its limit: it is tried again; the first event that says so clears a `fullUntil` an earlier one set. Accounts are signed in on the runner itself, through each tool's own login; the app only shows them.
- `tetrix`: true while the account's agents get Tetrix: on obid, every tool's agents get it through Oby's own Tetrix connection (obid's MCP server, with the job's broker token) while that connection is usable, and not while Tetrix refuses it for its organization (`error`, reconnect with `?org=`); null otherwise. Older runners asked each tool (`claude mcp list`, Codex's `mcpServerStatus/list`). `tetrixJobs`: of the account's recent jobs (the latest 50 the runner keeps in memory) that ended and whose tool said what it had, how many there are; `tetrixUsed`: how many of them called Tetrix. Settings shows `Tetrix: connected · used in 9 of 12 recent jobs (75%)`, or `Tetrix: not connected: sign in` (signing in is the tool's own login for its `tetrix` server, on the runner; never Oby holding the token). Older runners don't send these keys.
- `reserved`: the account is at 80% of its week before `sevenDayResets` (never a Cursor account, whose figure holds nothing), so work nobody watches (routines, `unattended` jobs) passes it by unless sent to it by name (and reviews take it, last: Routing below); the owner's own jobs and conversations take it like any account up to 95% of either window (LIMITS-20). False while its reserve is lifted. `reserveLiftedUntil`: until when the user let it past its reserve (`POST /v1/accounts/{id}/reserve`), its week's reset; null when they didn't, or once that time has passed. Older runners don't send these keys.
- `model`, `effort`, `complexEffort` (obid only, #1574): the model and efforts the account's jobs run on, each only when the owner chose it (`PATCH /v1/accounts/{id}`); a key left out is the tool's own. Older runners don't send them (docs/contracts/agents.md, AGENTS-5). The message-box model menu uses this same optional `model`, per account, for conversation turns as well as jobs (CONVERSATION-AGENT-19 to 22). `PATCH /v1/accounts/{id}` with `{"model":"<id>"}` saves it across restarts; `{"model":null}` clears it. Unknown model ids are `422`; choices come from that account's own list when status sent `models` on it, else from `GET /v1/settings/models/options` under the account's tool. An account choice no longer offered falls back to that tool's `GET /v1/status` `models.<tool>.model`, as does an absent choice; a job judges a Codex or Cursor account's choice against its live list only once obid has read one since it started, and until then runs the saved model (AGENTS-6); the saved choice stays visible to clients so the row can say `Previous model unavailable · using default`. Tool defaults remain unchanged. Explicit job models still take precedence. These reuse existing add-only keys and routes, with no closed enum changes.
- `models` (obid only, CONVERSATION-AGENT-22): this account's own `[{"id","name"},…]` when it differs from that tool's `GET /v1/settings/models/options` list (Codex and Cursor from their CLIs; Claude Code only once its CLI lists them). Left out when it matches or nothing has been read yet (the fixed fallback). Add-only; older apps ignore it.
- `modelsRead` (obid only, AGENTS-6): `true` once this account's own list is known (a Claude Code account's always; a Codex or Cursor account's once a live read was kept since obid started), left out until then. A client says `Previous model unavailable · using default` only when it's true, as a job judges the saved model only then. Add-only.

Accounts are signed in on the runner itself, through each tool's own login; the app only shows them (on obid the app can add, rename and remove them, and start that login: [obid only: accounts](#obid-only-accounts)). Settings shows one card per account, grouped by tool, with a bar per window, its reset time, and the running count.

**Routing.** Oby budgets each subscription by its weekly pace, not just the 5-hour window: new work goes to accounts on pace, accounts running ahead of pace get reviews or nothing, and the account with the most weekly room per remaining day wins. Cursor comes last, whatever its figure reads, after the reserved accounts: it takes automatic work only when nothing else can, or when named (`agent: "cursor"`, or a move to it); among its accounts, the fewest running jobs, then list order. Cursor accounts keep separate logins (docs/cursor.md, proven on tetrix-lab): each runs with a `HOME`, `XDG_CONFIG_HOME` and `CURSOR_CONFIG_DIR` of its own, so any number can be signed in. Every automatic choice goes through it (the brain's dispatch, the Lead's picks, failure fixes, failover, reviews); a job named to an account skips it.

- An account gets nothing while it's signed out, marked `fullUntil`, at 95% of either window, or, for work nobody watches (a routine's run, an `unattended` job), at 80% of its week (`reserved`: kept from it until `sevenDayResets` unless sent to it by name; a review may take it, last). The owner's own jobs take a reserved account as one with room, up to 95% (LIMITS-20). Above 80% of its 5-hour window it gets work only when every account is.
- **Use anyway:** the user can lift an account's reserve until its week resets (`POST /v1/accounts/{id}/reserve`): it then takes new work, failovers, the Lead's picks and moves like any account, still never at 95% of a window or while marked full. When only reserves keep work nobody watches from starting (the owner's own jobs run past them, LIMITS-20), its job still starts, waiting for room (`startWhen` `[{"room": true}]`, on the first of those accounts until then), and the reply says so: `On it. Claude Code will fix oby on Personal once what it waits for has happened. Waiting: Personal and Codex are in their weekly reserve. Use one anyway to start it now; otherwise it starts when an account has room.` Queued, the job's `waiting.reserved` names those accounts, and the Mac's and the iPhone's job screens show `Use Personal anyway (82% of week)` for each one still under 95% of both windows, with `Oby keeps 20% of each week in reserve; this lifts it for Personal until Thu 7:00 PM.` under it: one tap lifts that reserve and the job starts there. A failover with nowhere to go, and the Lead's jobs that found no account, say `Personal and Codex are in their weekly reserve: use one anyway from Settings › Accounts.` Settings shows `Use past reserve this week` on an account in its reserve, with `Oby keeps 20% of each week in reserve; this lifts it for Personal until Thu 7:00 PM.`
- **Room per remaining day:** `(1 − sevenDay) / daysLeft`, `daysLeft` from `sevenDayResets` (at least 0.25; 7 when null). Higher is better.
- **Ahead of pace:** `sevenDay / max(weekGone, 1/7) > 1`, the share used over the share of the week gone: at this burn it runs out before its reset. The floor keeps the first hours of a week from swinging it.
- **New work** takes an account on pace first, then one whose `sevenDay` is null (unknown, not 0%: Claude Code reports usage only during a job), then one ahead of pace. **A review** takes one ahead of pace first, then on pace, then unknown; the other tool still comes first.
- Within those, the most room per day; within 0.01/day of it, the fewest `running`, then list order.
- The job's report says why, once (a review's, whose last line is its verdict, in the runner's log): `On Claude Code · Deskree: most weekly room per day left (0.12/day), though 1.4× ahead of pace: none is on pace; Codex · Deskree is 2.3× ahead of pace.` After failover, the handoff says it: `Codex · Deskree hit its limit; continued on Claude Code · Default: its usage isn't known yet.`

### obid only: accounts

The owner adds, renames and removes the agents' accounts, and signs them in, from the apps (Settings › Accounts). The configuration's `agents.<tool>.accounts` are the seed. What these endpoints change is kept in `home/accounts.json` (0600) and laid over the seed at every start; the configuration file is never rewritten.

- **When a change applies.** Every change reaches routing, the brain and the gateway's scrubbing at once, and every app following `GET /v1/events` gets `accounts` (the whole list, as `GET /v1/status` has it).
- **Checks at start.** Each entry of `home/accounts.json` is checked as the API checks it, and one that isn't right is left out and logged: an id obid didn't make (eight lowercase hex digits: macOS ignores letter case, so two ids differing only in case would share a folder), a folder other than `home/accounts/<id>`, a name or payer the API would refuse, a name (added or changed) another account of the tool has, a change for an account obid doesn't have, or past 32 accounts.
- **A file that doesn't read.** obid logs why, runs with the configuration's accounts, and answers `503` to every change until the owner fixes or removes the file.
- **No tool comes back on its own.** A tool whose accounts were all removed is gone, rather than back on its own default login (the person's), which an empty `accounts` otherwise means. Its default login is listed, as `default` (Claude Code) or `codex` (Codex), once anything about the tool's accounts changed, and can be removed like any account.
- **Logins already on the Mac.** At every start, and again at every `GET /v1/status`, obid looks for each tool's own login (with `claudeKeychain` or `cursorKeychain` left out and off, a login that is now only in the Keychain turns its copy on then, as it would have at start; a tool's CLI is also looked for in `~/.local/bin`, `~/.bun/bin`, `~/.cargo/bin` (where `cargo install` puts tools, `oby-check-blok` among them), nvm's default node and `/opt/homebrew/bin` each time, so one installed after obid started is found): its CLI is found (the configuration's `bin`, else `claude`, `codex` or `cursor-agent`) and its login is there (Claude Code's `~/.claude/.credentials.json`, or its Keychain item with `claudeKeychain`; Codex's `~/.codex/auth.json`; Cursor's `~/.cursor/auth.json` on macOS, `~/.config/cursor/auth.json` elsewhere, which cursor-agent writes only with `AGENT_CLI_CREDENTIAL_STORE=file`; its default on macOS is the Keychain, where obid finds it with `cursorKeychain`). On a fresh obid (its first start: no `home/accounts.json` and no `home/jobs` yet), each such tool with no account at all (none configured or added; an empty `accounts` is Claude Code's or Codex's own login already) gets its own login listed: `default`, `codex` or `cursor`, with no folder, within the 32 accounts. An obid that ran before keeps its accounts as they are, so routing never moves to a login the owner didn't pick: what it finds is only offered, in `GET /v1/status`'s `availableLogins`, and listed with `{"agent", "default": true}` (below). Never one the tool lists already (by its id, an empty list, or any account without a `configDir`), nor one whose name another of its accounts has. Those obid listed are kept in `home/accounts.json` (`own`); one the owner removes stays removed across restarts, offered again, until it's asked back. A Cursor job on its own login runs as an account's does: in a folder of the job's own, with a copy of the login file (only `accessToken` and `apiKey`) and of `~/.cursor/cli-config.json`, obid's settings over it.
- **Not on the gateway**, but one. None of these endpoints is on the gateway's allowlist but `PATCH /v1/accounts/{id}` (the owner's decision of 2026-11-01: the iPhone's Settings › Agents changes an agent's name, payer, model and efforts): a paired phone's token must never add, remove or sign in an account, or sign obid into someone else's login, which would send the owner's code to that account. The Mac app calls them over loopback.

**`POST /v1/accounts`** adds one:

```json
{"agent": "codex", "name": "Personal", "payer": "Wellington"}
```

- `name` is optional (docs/contracts/accounts.md, ACCOUNTS-1 and ACCOUNTS-2): `{"agent": "codex"}` takes the tool's name, unique per tool and never its own login's (`Claude Code`, `Codex 2`), until its first sign-in fills it from what the tool says: its plan with a capital (`Max`), unique per tool, never its org, which shows on the card. A name given, or set with `PATCH` before it signs in, stays.
- `agent` is `claude`, `codex` or `cursor`. A tool the configuration doesn't name gets one while it has an account, run as `claude`, `codex` or `cursor-agent` found on the login shell's `PATH`. A tool whose configured `accounts` is empty keeps its default login beside what's added.
- `name`, when given, and `payer` are each one line of 1 to 60 characters, trimmed. `payer` is optional: null or empty means none.
- No two accounts of a tool have the same name, nor a name that is another one's id, letter case aside: jobs name an account by either.
- obid makes the folder, `home/accounts/<id>` (0700), and removes it with the account. The API names no folder: a body with `configDir`, or any other key, is `422`. obid makes the `id` (eight hex digits). At most 32 accounts (the owner's `limits.accounts`), the configuration's among them.
- `201` with the Account; `422` with the reason for a wrong body.
- **The tool's own login back.** `{"agent": "claude" | "codex" | "cursor", "default": true}` and nothing else lists the tool's own login (`default`, `codex`, `cursor`) after it was removed, as it was, or when obid found it on this Mac and offers it (`availableLogins`): no folder, signed in with the tool itself. `201` with it; `409` while it's listed, or when it was neither removed here nor found. The Mac offers it as `Use Claude Code's Own Login` under Add an account once it was removed there. Any other account removed stays removed.

**`PATCH /v1/accounts/{id}`** with `{"name": "…"}`, `{"payer": "…" | null}`, `{"model": "…" | null}`, `{"effort": "…" | null}`, `{"complexEffort": "…" | null}`, or several, answers the Account. `model`, `effort` and `complexEffort` (#1574) are the account's own, kept in `home/settings.json` and removed with the account; null is the tool's own. A model is one the tool offers and an effort one it takes (`GET /v1/settings/models/options`: Claude Code `low` to `max`, Codex `low` to `xhigh`, Cursor none), else `422`; a body that's refused (a `name` too) changes nothing. A job made with no model of its own runs on its account's, at its `complexEffort` when its plan called it complex, else at its `effort` (Claude Code `--model` and `--effort`, Codex the turn's `model` and `effort`, Cursor its session's model option), and the job's `model` and `effort` say so; whenever a job changes account they're the new account's (a model the job named stays) (docs/contracts/agents.md, AGENTS-5, AGENTS-6). Errors are `422` as above, and `404` for an unknown account. The configuration's accounts can be renamed and given a payer too.

**`DELETE /v1/accounts/{id}`** answers `204`. An account signed in with Continue with ChatGPT is revoked at OpenAI first and its vault entry deleted; `200` with `{"revoked": false}` when OpenAI didn't confirm that (at most three tries within 10 seconds), and it's gone all the same: the person can disconnect it in ChatGPT's settings.

- A sign-in under way ends first; `409` (`Personal's sign-in didn't end within 5 seconds: try again in a moment.`) when it doesn't within 5 seconds.
- `409` while a job of the account is queued or running: `Personal has a job queued or running: stop it first. A stopped job can move to another account.` A job waiting for a five-hour limit's reset (`resumesAt`) counts as queued.
- Its folder is removed only when obid made it (a real folder, never through a link). A configuration account that is removed stays removed across restarts. Its id is never made again, and its folder (one obid didn't make stays) is still hidden from every box, kept in `home/accounts.json` (`retired`).
- What the tool itself keeps stays: on macOS, Claude Code's Keychain item for the folder (Keychain Access removes it), and the login on the provider's side (signed in with Anthropic, OpenAI or Cursor until the person signs it out there).

**Who an account is** (docs/contracts/accounts.md): after every sign-in that took, for every account with a login as obid starts, and when a tool's own login is listed, obid asks the tool itself, run as its sign-in is (the account's folder, or for its own login the person's home): `claude auth status --json` (`email`, `subscriptionType`, `orgName`, a personal login's `<someone>'s Organization` being no org), `account/read` with `refreshToken: false` over a `codex app-server` started for that alone (`account.email`, `account.planType`), `cursor-agent status --format json` (`userInfo.email`, `userInfo.teamName`), each within 15 seconds. It keeps those three in `home/accounts.json` (`identities`, 0600) and nothing else of the answer: it's never logged. They reach only the owner's apps, as the Account's `email`, `plan` and `org`.

**The same login twice** (ACCOUNTS-7, ACCOUNTS-8, ACCOUNTS-17): a sign-in on an account just added, never signed in before, with the `email` (letter case aside), `org` and `plan` of another signed-in account of the tool takes the new account off as `DELETE` does, and the other stays as it was. `GET` and `POST /v1/accounts/{id}/sign-in` for it then answer `409` `{"error": "That's Personal again.", "reason": "sameAccount", "sameAs": "<the other's id>"}`, until obid restarts.

**`POST /v1/accounts/{id}/background`** `{"given": true | false}`, on an account signed in with Continue with ChatGPT, answers whether work nobody's watching may use it, and answers with the Account. `given: true` is `403` unless `X-Oby-Words` signs exactly this request ("Words the owner typed"): the token alone, a job or an agent can't say yes. `given: false` needs no signature, and takes effect at once: background jobs running on the account stop, a review starts again elsewhere, and jobs queued go to another account or wait; the owner's own go on. A job waiting for the yes doesn't hold the account: signing it in or removing it isn't `409` for that. `404` for an account obid doesn't have, `422` for any other body or an account that isn't a ChatGPT login. Off the gateway's allowlist. Removing the account, or a device login replacing it, forgets the answer (docs/contracts/chatgpt-sign-in.md, CHATGPT-20 to 26).

**`GET /v1/accounts/{id}/sign-in?with=chatgpt`**, Codex accounts only, is Continue with ChatGPT (docs/contracts/chatgpt-sign-in.md), the one sign-in where obid is the OAuth client: it listens on a loopback port of its own (`http://127.0.0.1:<port>/auth/callback`) and answers this route's shape, with the page to open, no code and `pasteCode` false. The account stays off jobs until the browser comes back, `DELETE` below, or 15 minutes pass. While it's under way the Account says `signingIn: true` (a key left out otherwise, any sign-in's), since a `label` may be there already. How it ended shows on the Account: `login: "chatgpt"` and `signedIn`, or `signedIn` false with `label` saying why. A sign-in of the other kind under way answers `409` `busy`; the tool's own login (`ownLogin`) can't, so the app adds an account and signs that one in.

**`GET /v1/accounts/{id}/sign-in`** runs the tool's own login for the account, never obid's (AGENTS.md: obid never reads, stores or forwards the login), and answers what the person needs to finish it:

```json
{"account": "a1b2c3d4", "url": "https://claude.com/cai/oauth/authorize?code=true&…", "userCode": null,
 "pasteCode": true, "expiresAt": "2026-10-18T10:15:00Z"}
```

- **What the app does.** It opens `url` in the browser. `userCode` (Codex) is the one-time code the person types on that page. `pasteCode` (Claude Code) means the page ends by showing a code, which the app sends back with `POST`.
- **One at a time.** Asked again while it's under way, the answer is the same sign-in; there is one per account. It ends after 15 minutes (Codex's code lasts that long), or once it has signed in.
- **Jobs wait.** While a sign-in is under way, and while an account is being removed, no job is dispatched to the account (a job naming it is refused: `Personal is being signed in or removed: try again in a moment.`; routing passes it by) and none starts on it: a job queued on it in the meantime stays queued and starts once the change ends. That holds from the moment no job of it was queued or running, and both are looked at under the same lock. An abandoned sign-in is ended with `DELETE` (below), rather than keeping the account's jobs waiting until it runs out.
- **Where it runs.** The login runs in the account's own folder: no box ever gets that folder (#655, "The job sandbox"), so nothing a job wrote can steer the login. The tool writes the login there itself, and obid never reads or copies what it writes there except for the boxed runs' copies.
  - **Claude Code:** `claude auth login` with `CLAUDE_CONFIG_DIR` set to the account's folder. On macOS the login goes to that folder's Keychain item, the one obid copies for a boxed run with `claudeKeychain`, so on macOS it's `409` unless `claudeKeychain` is on. Without a terminal, Claude Code prints a link whose page shows the code, and reads the code on its stdin.
  - **Codex:** `codex login --device-auth -c cli_auth_credentials_store="file"` with `CODEX_HOME` and `HOME` set to the account's folder. It prints a link and a one-time code, and listens on no port (its browser login needs `localhost:1455`). It ends by itself once the person has signed in.
  - **Cursor:** `cursor-agent login` with `NO_OPEN_BROWSER=1`, the account's own `HOME`, `XDG_CONFIG_HOME` and `CURSOR_CONFIG_DIR`, and `AGENT_CLI_CREDENTIAL_STORE=file`, so its login is a file under the folder rather than the macOS Keychain (jobs run with the same setting and get a copy of that file). Its caches (`NODE_COMPILE_CACHE`, `XDG_CACHE_HOME`) go in obid's folder for the sign-in, and its `cli-config.json` is rewritten first, as before a job. It ends by itself once the person has signed in.
- **How it runs.** Every login runs unboxed, since it must reach the Keychain and the network:
  - by its absolute path (`503` when obid can't find one);
  - with its environment made from scratch: the kept variables, `PATH=/usr/bin:/bin:/usr/sbin:/sbin` plus the folder of the tool's own binary (links followed: Cursor runs the `node` beside it) and, for a script that starts `#!/usr/bin/env <program>` (a CLI installed with npm: `#!/usr/bin/env node`), the folder of that program as obid finds it on the login shell's `PATH`, no token, and no Claude Code or Anthropic variable;
  - with `BROWSER=true`, so nothing opens on the runner;
  - with `TMPDIR` and its working folder set to a new folder of obid's (`home/tmp/sign-in-…`, removed when it ends, and swept at obid's next start);
  - in a process group of its own, which obid kills when the login ends, when the sign-in runs out, is ended or the account is removed, when obid stops, and when the request that started it ends before the login gave its link (its folder removed with it).
- **What obid takes from its output.** What a login prints is read, at most 4,096 bytes of each line, only for the link and the code:
  - the link is the first `https://` link on the tool's own sites (`claude.com`, `claude.ai`, `anthropic.com`; `openai.com`, `chatgpt.com`; `cursor.com`, `cursor.sh`, or below them), with no login, port or space in it;
  - the code is Codex's, a line like `3U0G-DCVSU`.
  Nothing else it prints is kept, answered or logged. obid's log says only that a sign-in started and whether it signed the account in.
- **Errors.** `404` for an unknown account. `409` in four cases:
  - the tool's own default login (an account without a folder: it is the person's, signed in with the tool itself), and a folder whose login file or its lock (Claude Code's `.credentials.json…`, Codex's `auth.json…`, Cursor's `.cursor/auth.json` or `.config/cursor/auth.json` and the folders on the way) is a link or not the person's, since the login would write the new sign-in wherever it leads;
  - a job of the account is queued or running;
  - the account is being removed;
  - Claude Code on macOS without `claudeKeychain`.
  `502` when the login gave no link within 30 seconds.

**`POST /v1/accounts/{id}/sign-in`** with `{"code": "…"}` sends the code the page showed to Claude Code's login, on its stdin, once. The code is never kept or logged.

- It answers the Account once it's signed in.
- `422` when the code isn't one line of at most 4,096 characters, or when Claude Code didn't sign in with it (`Claude Code didn't sign in with that code. Start again for a new link.`: the sign-in has ended).
- `409` when no sign-in is under way, a code went to it already, or the tool takes no code (Codex, Cursor).
- `504` when it didn't end within 60 seconds.

**`DELETE /v1/accounts/{id}/sign-in`** ends the account's sign-in under way, with everything its login started: `204`, also when none was under way. `404` for an unknown account; `409` when it didn't end within 5 seconds.

These refusals carry a `reason` ([Sign-in reasons](#obid-only-sign-in-reasons)); the others (`404`, `POST`'s other `409`s, `504` and its `422` for a code that isn't one line) carry none. `GET …/sign-in`: `ownLogin` for the tool's own login, `folderUnsafe` for a login file, lock or folder that is a link or not the person's (`409`), and for the account's folder that isn't a folder or can't be made (`502`), `busy` for a job queued or running or the account being removed (also on `DELETE /v1/accounts/{id}`'s job `409`), `keychainOff` for Claude Code without `claudeKeychain`, `notInstalled` for the `503`, and `didNotStart` for a login that couldn't start or gave no link (`502`). `POST …/sign-in`: `codeRefused` for the `422` of a code Claude Code didn't sign in with.

When a sign-in ends, every app gets `accounts`, with `signedIn` as obid finds it (the login file, or the Keychain item with `claudeKeychain`, or Cursor's own login's with `cursorKeychain`).
