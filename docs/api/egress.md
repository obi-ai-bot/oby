### obid only: the egress proxy (#616)

On macOS a job's agent has one way off the Mac: an HTTP `CONNECT` proxy obid runs on `127.0.0.1`, on a port it picks at start (only where the job sandbox is Seatbelt's). Its Seatbelt profile denies `network-outbound` to every address but loopback, and the DNS resolver's socket (the proxy names hosts itself), so a socket the agent or anything it runs opens to anywhere else fails at the OS (`a_proxied_agent_reaches_loopback_and_nothing_beyond`: IPv4, IPv6, UDP and a host name lookup all fail inside, while the same probe reaches 1.1.1.1, resolves and sends UDP outside; it fails on the profile without the proxy). The agent gets `HTTPS_PROXY`, `https_proxy`, `HTTP_PROXY` and `http_proxy` set to `http://oby:<token>@127.0.0.1:<port>`, `NO_PROXY` and `no_proxy` set to `localhost,127.0.0.1,::1` (obid's MCP servers and the job broker, a test's own servers), and `NODE_USE_ENV_PROXY=1`, so Node's own `fetch` and `https` use it too; these win over a proxy in obid's own environment. The token is the job worker's own, made when its agent first starts and learned as a secret (masked wherever it's repeated); it, and everything decided for it, goes when the worker ends, and it's never in an argument or a log line. A request without it, or with a token no worker holds, gets `407 Proxy Authentication Required` and nobody is asked. A plain `http://` request (absolute-form, its `Host`, if any, the address's host) is decided the same way, for its host on its port (80 by default), and forwarded alone: the proxy's headers (the job's token) taken out and `Connection: close`, so a second request never rides on one site's answer; anything else gets `405`.

git in a proxied job has no credential helper (an empty `credential.helper` in `GIT_CONFIG_PARAMETERS`, #1814, with LANES-2's push URL: "Agents can't publish"): git offers the proxy's login to every helper it has, and Xcode's git has the Keychain's in its own settings, which from a box with no Keychain makes macOS show the owner a dialog.

**A tunnel carries TLS for the host it was opened for, and nothing else** (#1471's review). A CDN's edge serves whichever of its sites the TLS hello names, whatever `CONNECT` named: `chatgpt.com`'s and `registry.npmjs.org`'s addresses serve `developers.cloudflare.com`, `pypi.org`'s `www.python.org`. So after `200` the proxy reads the client's whole ClientHello (its records reassembled, at most 64 KiB, within 15 seconds) and sends it on only when its `server_name` is the `CONNECT` host (case and a final dot aside), or, for an IP address, when it names none; a hello with `encrypted_client_hello`, one naming another host, two names or any extension twice, no name for a host, or anything that isn't TLS closes the tunnel before a byte reaches the site.

Each site (the host, and `:<port>` but for 443) is decided once for the job's worker, in this order:

1. **The tool's own services, on 443**, go through, unrecorded: Claude Code's `anthropic.com`, `claude.ai` and `claude.com`; Codex's `openai.com` and `chatgpt.com`; Cursor's `cursor.sh` and `cursor.com`; each with its subdomains (their model APIs, and the settings and feature flags the CLIs ask their vendor for).
2. **Telemetry to anyone else** (`datadoghq.com`, `sentry.io`: Claude Code sends Datadog its logs) is a site like any other (below): the job's rules, its mode or the owner's card decide it (docs/contracts/permissions.md, PERMISSIONS-2).
3. **Another Obi's review job** reaches nothing more: it only reads, and never asks.
4. **In Sandbox mode, a package registry** goes through on 443, recorded in `answered`: `registry.npmjs.org`, `registry.yarnpkg.com`, `repo.yarnpkg.com`, `repo.maven.apache.org`, `repo1.maven.org`, `plugins.gradle.org`, `services.gradle.org`, `cdn.cocoapods.org`; exactly these hosts. They are only registries whose edge answers just the host the TLS hello named (Cloudflare's: each answered `403` to a hello naming it with `Host` naming another site of its edge, 2026-10-26). `pypi.org`, `files.pythonhosted.org`, `crates.io`, `index.crates.io`, `static.crates.io`, `static.rust-lang.org`, `rubygems.org` and `index.rubygems.org` (Fastly's), and `proxy.golang.org` and `sum.golang.org` (Google's), were on the list until 2026-10-26 and aren't (`ROUTED_BY_HOST`): their edges answered such a request with the other site, and the proxy doesn't read the `Host` inside a tunnel. They are decided as any other site (5., below), so `pip install`, `cargo fetch`, `gem install` and `go mod download` in Sandbox mode wait for the owner's card, or a `WebFetch(domain:…)` rule, the first time in a job (`only_registries_whose_edge_answers_its_own_host_go_through_by_default`).
5. **Any other site is a fetch from it** (`WebFetch` of `https://<site>/`), answered as a fetch the agent asked for: the repository's rules, then the job's mode (`bypass` lets it through), else the owner's `permission` card, "Fetch <site>", `why` "It reaches the network beyond the model's API.", its `detail` ending "Allowing it lets this task reach <site> until it ends.", with Allow, Always allow (which saves `WebFetch(domain:<site>)` for the repository) and Deny. A `WebFetch(domain:<site>)` deny covers the site and its subdomains on every port; an allow, the port it names (none: 443). Allow lets every later connection to that site through until the worker ends, Deny refuses them, without another card. Every connection to a site being asked about waits for that one card, at most 5 minutes (then `403`, and the card keeps waiting: its answer holds for the next); at most 3 of a job's sites wait for the owner at once (counted as the card is put), and a 4th is refused this once (`403`, "Other sites are waiting for the owner"), with no card. A deny rule is checked at every connection, so one saved later stops a site the owner had let through.

What a mode or the rules decided is decided again when the job's mode changes (`set_mode`, `POST /v1/jobs/{id}/mode`) or a rule is saved or forgotten (for every job), a waiting card such a change settled included; the owner's own answers to cards stay. Only the owner's own yes to a call's card opens sites besides: the `http(s)://` addresses of a fetch, and of the commands in it that reach the network as obid reads them (`curl https://…`, `git clone https://…`), until the worker ends, and its card says which (`detail`, as above). A comment (`git fetch origin # https://…`), an `echo` and a saved rule's or a mode's allow open nothing: the proxy decides those sites itself.

A connection has 5 seconds to send its request, and at most 128 wait to (another is closed at once); one whose token checks out takes one of 1,024 places every job's tunnels share (none left: `503`), and at most 64 of a job's tunnels are open at once (another gets `429`), so no job can hold the places another's model calls need; obid raises its own limit of open files to what macOS allows (10,240) at start, since each tunnel holds two. A tunnel nothing went through for 10 minutes ends. A refused connection gets `403` with the reason as its text, a site that can't be reached `502`. Refusals are logged at debug, never at info. The proxy reaches a site through the proxy obid itself is behind, when there is one: obid's own `HTTPS_PROXY`, an `http://` one (its login percent-decoded, `NO_PROXY`'s domains straight, `NO_PROXY=*` every host; another scheme, `https://` or `socks5://`, is said once in the log and the proxy connects straight), else the Mac's https proxy (`scutil --proxy`: `HTTPSProxy`, `HTTPSPort`, the `ExceptionsList`'s domains straight), read again after a minute; loopback always goes straight. Codex runs with `-c features.plugins=false`: at every start it clones its curated plug-ins from github.com with `git`, which would ask, and a job's `CODEX_HOME` has none installed. `permissions_2_the_egress_proxy_lets_through_asks_and_refuses_by_site` shows the rule's site tunnelled with a hello naming it and closed for another name, an encrypted hello or no TLS; no token refused; a deny on its port and another; one card for two connections; Deny and Allow each holding; the 4th site refused while 3 wait; the tool's API on 443 only, a registry, telemetry decided as any site and a plain http request forwarded alone; a site the owner allowed a fetch from going through; a comment's and a rule's allow opening nothing; Bypass's decisions decided again in Sandbox mode; and the token dead once the worker ends.

Checked on this Mac on 2026-10-26, each CLI as obid starts it in a job, in the box, with a made-up login in a scratch home: Claude Code 2.1.302 reached `api.anthropic.com` through the proxy, Codex 0.162.1 `api.openai.com` and `chatgpt.com`, cursor-agent 2026.10.01 `api2.cursor.sh`, each sending the proxy's login and a TLS hello naming the host, and each heard its API refuse the made-up login. Without the proxy's variables, under a profile that denies the same, Codex only says it's waiting for the network.

What it doesn't hold back:

- **Loopback, and what listens.** A test's own servers, obid's MCP servers and the proxy are there, so the agent reaches the person's own services on `localhost` too, as before: one that sends things on (a local HTTP or SOCKS proxy, a DNS forwarder, a database linked elsewhere) is a way out. And a server the agent starts on `0.0.0.0` serves the network: Seatbelt's only hosts are `*` and `localhost`, its `localhost` takes a listen on `0.0.0.0` too, and its inbound rules hold only at the listen, so refusing it would refuse a test's own server on 127.0.0.1 as well (tried 2026-10-26). macOS's firewall (System Settings › Network › Firewall) is what holds it.
- **What an allowed site is sent.** The proxy sees names, not what goes inside the tunnel (no TLS inspection). A tool's vendor and the default registries take uploads (`npm publish`, `cargo publish`, `gem push` go to the same hosts) with a login the agent brings, a token planted in a repository, say.
- **The `Host` inside a tunnel.** The TLS name is checked; the HTTP `Host` inside the tunnel isn't read (no TLS inspection). Some edges pick the site they serve by `Host`, not by the hello's name: Fastly's and Google's did (2026-10-26), Cloudflare's, Vercel's, CloudFront's and Cursor's own answered `403`, `404` or `421`. So the default registries are only Cloudflare's (4., above), and every tool's own service tried answered so (Anthropic's, Claude's, OpenAI's and ChatGPT's on Cloudflare, `cursor.com` on Vercel, `api2.cursor.sh`, the status pages on CloudFront); those are a sample of the subdomains each tool's domains cover, not all of them. A site the owner allows on a card, or a rule or Bypass allows, is tunnelled as it is: when its edge picks by `Host`, the job reaches that edge's other sites too.
- **An allowed site that doesn't speak TLS.** Only TLS goes through a tunnel, so Postgres, ssh or plain HTTP to a site the owner allowed fails all the same.
- **The system's daemons that fetch for a caller**, like trustd's certificate checks and nsurlsessiond's background downloads: they're outside the profile.
- **The Apple check.** `oby-check apple` has a Mac that follows the runner build and test the job's commit with Xcode (Apple check, above), outside this box and with the network: a job's tests run there. It's off by default since the launch build.
- **Linux.** Not yet, and nothing above changes there (the registries' list included): the agent keeps slirp4netns, the whole network and the host's loopback at `10.0.2.2`, and gets no proxy variables. The next step: no slirp4netns, the agent's namespace with its own loopback only, and a forwarder in it from a loopback port to the proxy over a Unix socket bound into the box; the proxy then refuses a name that resolves to the host's loopback.
- **The brain, a conversation's agent and a Sphere answering run** keep the network as before.
