### obid only: routines (#395)

A routine is a saved request with a schedule: "every weekday at 9, review the open pull requests in obi". On each run obid starts an ordinary job from it, routed, checked, published and reviewed exactly like a job the owner asked for, and the run shows up in the routine's conversation. obid runs as a login item, so routines run while the Mac is awake: a closed lid sleeps the Mac (`keepAwake` holds off idle sleep while a job runs, never a lid's), and a Mac asleep at a run's time catches up once it wakes (below). The Swift runner has none. Triggers on events ("when CI finishes", #135) come later.

A routine, as `GET /v1/routines` lists it and the `routine` event sends it:

```json
{"id": "a1b2c3d4", "name": "Review open PRs", "repo": "obi-ai-bot/obi", "kind": "review",
 "task": "Review every open pull request in obi-ai-bot/obi and say what each needs.",
 "agent": "auto", "account": "auto", "mode": null, "check": null, "rounds": 1,
 "schedule": {"every": "weekdays", "at": "09:00"}, "zone": "America/Sao_Paulo",
 "when": "Weekdays at 9:00", "enabled": true, "created": "2026-10-19T12:00:00Z", "createdBy": "chat",
 "conversation": "5b0e2c4d-…", "nextRun": "2026-10-20T12:00:00Z", "failuresInARow": 0,
 "graceMinutes": 1440,
 "lastRun": {"scheduled": "2026-10-19T12:00:00Z", "at": "2026-10-19T12:00:20Z", "outcome": "started",
             "reason": null, "job": "9f08fd10", "catchUp": false, "ended": "done"}}
```

- `id`: 8 lower-case hex characters. `name`: what Home, Settings and the run's job call it, one line of 1 to 60 characters. `repo`, `kind`, `task` (1 to 2,000 characters), `agent`, `account`, `mode`, `check` and `rounds`: the job each run starts, with the rules of `POST /v1/jobs` (an unknown repository, kind, tool, account or mode is `422`, with why). `agent` and `account` are `auto` unless the routine pins them: then routing picks for each run, as for any job. `mode` null is Settings' default at each run. `rounds` is 1 when left out, and a run of a routine with 1 gets obid's own default (3 for a `fix`, `build` or `test` with a check, #958).
- `schedule`: one of `{"every": "hourly", "minute": 15}`, `{"every": "daily", "at": "09:00"}`, `{"every": "weekdays", "at": "09:00"}` (Monday to Friday) or `{"every": "weekly", "days": ["mon", "thu"], "at": "08:30"}` (`mon` to `sun`, at least one). `at` is `HH:MM`, 24-hour, in `zone`. So no routine runs more often than once an hour: every run spends an account's window. No cron yet.
- `zone`: the IANA time zone the times are in (`TimeZone.current.identifier`), never the runner's own: `422` for one obid doesn't know. A time the clocks skip (02:30 when they spring forward) runs once, right after the jump; a time they go through twice (when they fall back) runs once, the first time.
- `when`: obid's words for the schedule, to show as they are: `Every hour at :15`, `Every day at 9:00`, `Weekdays at 9:00`, `Mondays and Thursdays at 8:30`.
- `enabled`: false while paused. `nextRun`: when it runs next, or null while paused. `createdBy`: `chat` (only a routine the owner confirmed from chat; a client that sends `chat` gets `app`), `mac` or `iphone` (anything else reads `app`). `conversation`: where its runs show up: the conversation it was asked for in, or one obid starts for it, titled with its name, at its first run. A deleted one is started again at the next run.
- `failuresInARow`: runs in a row whose job ended `failed` (or couldn't start). At 3, obid pauses the routine and says so in its conversation; a run that ends `done` sets it back to 0, a stopped one leaves it, and a `skipped` or `missed` run never counts (docs/contracts/routines.md).
- `graceMinutes`: how late, in minutes, its latest time still runs (docs/contracts/routines.md, ROUTINES-3): the routine's own, or 60 for an hourly routine and 1440 for the rest when it names none.
- **Paused by itself** (docs/contracts/alerts.md, ALERTS-5): that pause also puts a card in the inbox, kind `routine`, id `routine-paused-<id>` (one per routine: a later pause raises it again), `job` empty, sorted `needs_you`, so it alerts as any such item: `title` `Routine paused`, `text` `<name> failed 3 times in a row, so it's paused.`, `options` `["Turn back on", "Dismiss"]` (proposed words, Sangam's to change). `POST /v1/inbox/{id}/answer` with `Turn back on` resumes it exactly as `PATCH` `{"enabled": true}` does, with the same signature rule (none), and settles the card; when the routine can't run as it is (`422` with why, as `PATCH`'s), the card stays open. `Dismiss` settles it and leaves the routine paused. Turned back on anywhere else, or deleted, the routine's card settles with no answer. A routine the owner paused raises none.
- `lastRun`: the latest run, or null. Each run: `scheduled`, the time it was due; `at`, when obid acted on it; `outcome`, `started`, `skipped`, `missed` or `failed` (it couldn't start); `reason`, why it was skipped, missed or failed, or null; `job`, the job it started, or null; `catchUp`, true for a run started late because obid wasn't running at its time; `ended`, its job's end (`done`, `failed`, `stopped`, `interrupted`) once it ended, else null. The job's own status and summary say how it went: a green run isn't a finished task.

At most 20 routines (the owner's `limits.routines`). Each keeps its last 50 runs, in a private file of its own (`home/routines/<id>.json`, 0600).

**Running.** obid checks every minute, and once when it starts. A routine is due when its next time after its last one has come. A check starts at most one routine's job: another one due then waits for the next check and runs for the same time, as late as it was at the first check, so that wait never makes it `missed` or a catch-up (ROUTINES-4); one skipped, missed or failed doesn't count.
- **Never twice.** obid saves the time it's acting on before it starts the job, so a restart or a second check in the same minute doesn't run it again. A due run and Run now are started one at a time, from the busy check to the run's record, so they never both start. When the clock goes back past the time it last acted on, that time becomes now: nothing waits for a time that seems done already.
- **Missed.** When more than one time passed while obid wasn't running (the Mac asleep or off), it runs once, for the latest, with `catchUp` true, and records one `missed` run for the others (`reason`: `Missed 3 runs while Oby wasn't running.`). Times more than 7 days old aren't caught up: they're one `missed` run, and the routine goes on from now. A latest time older than the routine's `graceMinutes` isn't run either: it's counted in that `missed` run, and the routine goes on to its next time (ROUTINES-3).
- **No overlap.** While the job of its previous run waits, the run is `skipped`, starts no job and never counts toward `failuresInARow` (docs/contracts/routines.md): `The previous run still waits for you.` when that job waits on the owner (`interrupted`, a `permission` open, an `accountLimit` decision, or held for a ChatGPT yes), isn't dismissed and has no follow-up (`followUpOf`) carrying it on (ROUTINES-2); `The previous run still waits for an account with room.` when it's `queued` for room (`resumesAt`, or `waiting` for room; ROUTINES-1); else `The previous run was still going.` while it's queued or running. Run now waits only for the last. The previous run's job is kept on the routine itself (`lastJob` in its file), so the hold outlasts the 50 runs kept.
- **Same rules as any job.** The job is made as `POST /v1/jobs` makes one (`Jobs::create`): routing, the weekly reserve, `maxRunning`, the files claim, the permission mode, the checks, the secret scan and the review all apply unchanged. A routine never widens what a job may do, and its stored task can't approve anything during the run. A run that can't start (its repository or account is gone, no account can take it) is `failed`, with obid's reason.
- The job has `request` and `task` the routine's task, `title` its name, `conversation` the routine's, and `routine`: `{"id": "a1b2c3d4", "name": "Review open PRs", "scheduled": "2026-10-19T12:00:00Z", "catchUp": false}` (null on every other job).

**In the conversation.** Each run adds one Oby turn to the routine's conversation (a skipped run only the first time for the job that holds it, not at every due time), in obid's own words, with `routine`, a key only these turns have: `{"id", "name", "outcome", "scheduled", "catchUp"}`. A started run's turn lists its job (`jobs: [<id>]`), so the apps show its card there, as a task in Home's Routines group: `Review open PRs started its 9:00 run.` (`… its 9:00 run, which it missed while Oby wasn't running.` for a catch-up), `Review open PRs skipped its 9:00 run: the previous run was still going.`, `Review open PRs couldn't start its 9:00 run: <why>`, `Review open PRs missed 3 runs while Oby wasn't running.`, and, after the third failure in a row, `Review open PRs failed 3 times in a row, so it's paused. Turn it back on in Settings › Routines.`. How the job ended then comes as for any job a conversation started (#351). Missed runs older than 7 days, and a run now, say so too.

**In chat.** The conversation's brain has `oby_routines` (lists them, with their ids), `oby_routine` (a new one) and `oby_change_routine` (`pause`, `resume`, `run`, `delete` or `reschedule`, by id).
- `oby_routine` never saves anything. It checks the routine as `POST /v1/routines` would and puts a `confirm` item in the inbox, `Make the routine Review open PRs (Weekdays at 9:00, review obi in Bypass mode, on Claude Code · Personal)`: the job each run starts as obid describes a planned job (kind, repository, mode, tool, account, check), its next 3 times in its zone, and the task, quoted. A Bypass routine's card also says plainly that every run's job never asks the owner anything. Only the owner's Confirm saves it (the confirm action `create_routine`). The brain says the zone the owner is in when it knows it, and obid's own zone otherwise.
- Only `pause` happens on the owner's words, as stopping a job does: it can only make less happen. `resume`, `reschedule`, `delete` and `run` each put a `confirm` item in the inbox (`Resume the routine …`, `Reschedule the routine …`, `Delete the routine …`, `Run the routine … now`, with a Bypass routine's plain line), carried out only on the owner's Confirm (the confirm action `change_routine`, `target` the routine, `payload` `{"action", "schedule", "zone", "mode", "agent", "account", "check"}`). The card keeps the routine's mode, tool, account and check as it named them: when one changed before the Confirm, the Confirm does nothing (`409`, `The routine's mode, tool, account or check changed since Oby asked: ask again.`), and the item closes saying so. Words in a conversation may be an agent's (a job's summary in the turn that says it ended, a job's step), so none of them can resume, reschedule, delete or run a routine by themselves, and none starts a job that never asks. After a turn read what others wrote (the web, the repositories, an attachment), pausing one is a Confirm too (`change_routine` with `action` `pause`, TASKCONV-11).

**`GET /v1/routines`**: every routine, by name. `[]` when there's none.

**`POST /v1/routines`** with a routine's fields (`name`, `repo`, `task`, `schedule`, `zone`; `kind` (left out, `investigate`), `agent`, `account`, `mode`, `check`, `rounds`, `graceMinutes` (at least 1), `createdBy` and `conversation` optional) answers `201` and the routine. `422` with why: a field that breaks the rules above, an unknown zone, a conversation that isn't there, or 20 routines already. `400` for a body that isn't that JSON.

**`GET /v1/routines/{id}`**: the routine, with `runs`, its runs newest first (up to 50). `404` for an id that isn't there.

**`PATCH /v1/routines/{id}`** with any of `name`, `task`, `schedule`, `zone`, `enabled`, `agent`, `account`, `mode`, `check`, `rounds`, `graceMinutes`: changes them, checked as on `POST`, and answers the routine. `{"enabled": false}` pauses it, `{"enabled": true}` resumes it. Resuming, or a new `schedule` or `zone`, counts from now: what was due meanwhile doesn't run. `422` as for `POST`, `404` for an id that isn't there.

**`DELETE /v1/routines/{id}`**: `204`; `404` for an id that isn't there. The jobs its runs started stay, with their `routine`.

**`POST /v1/routines/{id}/run`**: Run now, paused or not, without changing when it runs next. `201` with `{"routine": …, "job": …Job}`; `409` while its previous run's job is still queued or running; `422` when the job can't start, with why.

**Events.** A `routine` event comes with the routine as listed whenever it changes (made, changed, paused, run, a run's job ended). When one is deleted, it's `{"id": "<id>", "deleted": true}`.

**Through the gateway.** All of these are on obid's gateway allowlist, so a paired iPhone lists, pauses, resumes, runs and deletes routines.

**In the apps.** Home has a Routines group (Sangam's design, `design/app`'s `tasks.ts`): its page lists each routine waiting for its next run as he draws it, `Starts Monday at 9:00 AM`, then the jobs its runs started (`routine` set), and a job's page says `From routine: Review open PRs`. Settings › Routines, on the Mac and the iPhone, lists every routine with `when`, its next run and its last outcome, a switch (`PATCH` `enabled`), Run now and Delete (with a confirmation). Settings › Routines isn't in Sangam's design: his has no screen to manage routines yet, so this one is ours until his comes.

### obid only: check-ins (#1116)

Oby checks in by itself only when the owner asked for it in a conversation ("check in with me every weekday at 9"), and stops the same way ("stop checking in"). A check-in is Oby's own turn in that conversation, so it comes as an ordinary `turn` event (`who: "oby"`) and the apps notify it as they notify any answer that comes while their window is closed. It never starts, approves or answers anything. The Swift runner has none.

- **Morning summary.** At the check-in's time, at most once a day, Oby posts one to three sentences: what finished, what needs the owner, and what it would do next once the owner says so. It covers what happened since the owner last looked (the latest of the check-in's previous time, the owner's last message or tap, and Oby's last check-in), with the facts and the one background call of the recap above (same fence, same vault and secret scan, same quick model, one attempt), and its own instructions. The turn lists the jobs it names (`jobs`, at most 10, the latest) for their cards. Nothing happened since: nothing is posted.
- **Away recap.** While check-ins are on, when the owner has been away more than 30 minutes and something finished or came into the inbox since they were last seen, Oby posts the recap in that conversation instead of waiting for their return: once per stretch away (the morning summary counts as that stretch's one), and the recap on their return covers only what came after it. Quiet hours: it posts only in the 12 hours after the check-in's time on its days (09:00 to 21:00 for weekdays at 9), so nights and days off wait for the next summary. obid keeps when the owner was last seen in memory only: until their first message or tap after obid starts, there's no away recap.
- **When the call can't write it** (no Claude account, a vault that can't be read, a failed call, an answer that isn't one to three sentences), obid posts its own count instead, with no title in it: `Since you last looked: 2 jobs done and 1 item waits in your inbox.`
- **Never twice.** obid checks every minute, on routines' loop, and once as it starts. It keeps the time it's acting on before it posts, so a restart or a second check doesn't post it again. A time missed by more than 12 hours (obid wasn't running) is skipped: the next one covers it; one missed by less posts late. Changing the time, or turning check-ins off and on again, on a day that already had its summary doesn't send a second one; a summary posted late, past midnight, counts for its own day.
- **The conversation.** The one the owner turned it on in; when that one is deleted, obid starts one titled `Check-ins` and posts there from then on.

**In chat.** The conversation's brain has `oby_check_in`: with `schedule` (`{"every": "daily", "at": "08:30"}`, `{"every": "weekdays", "at": "09:00"}` or `{"every": "weekly", "days": ["mon", "thu"], "at": "09:00"}`, as routines take them; never hourly) and `zone` (the owner's IANA zone; left out, the Mac's), it turns check-ins on or changes them, in the conversation it's called from, and answers what it saved so the brain says it back; with `{"off": true}` it turns them off; with neither, it says how they are. It saves at once, with no Confirm, since a check-in only posts in its conversation; but after a turn read what others wrote (a repository's files, a page, the inbox), turning them on or changing them waits for the owner's Confirm (`set_check_in`, TASKCONV-11). Off works from any of the owner's turns.

**Kept** in `home/settings.json` (0600) as `checkIn`, left out while off, and `checkInSent`:

```json
{"maxRunning": 6,
 "checkIn": {"schedule": {"every": "weekdays", "at": "09:00"}, "zone": "America/Sao_Paulo",
             "conversation": "5b0e2c4d-…", "from": 1792411200},
 "checkInSent": 1792411200}
```

`from` is what its next time counts from (when it was set, or the latest time it was due). `checkInSent` is the due time of the last summary posted (not when it posted, so one posted late, past midnight, still counts for its own day), kept while check-ins are off, so turning them off and on again, or changing the time, never sends a second one that day. Both are seconds since the epoch. An older obid reads the file as before and keeps neither when it saves it. There's no endpoint for it yet: Settings shows nothing until one comes.

**What reaches the model, and from where.** Only obid's own records: each job's title (else the start of its task), repository and id, and how it ended; pull requests merged; each waiting inbox item's title and kind (not those sorted `ignore`); accounts a job found out of usage. Inbox titles can come from GitHub, Slack, alerts or other Obys, and job titles from what the owner or the brain wrote: they're one line each, quoted between the call's nonce fences as data, never instructions, every secret obid and the vault know taken out and each line the secret scan flags left out; a vault that can't be read sends nothing. No agent output, report, diff, file or summary is read. What the model writes is cut to one to three sentences of at most 600 characters, and is Oby's turn as the recap is.
