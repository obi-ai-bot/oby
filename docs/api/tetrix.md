### obid only: Tetrix

The owner connects Tetrix once, in Oby, and every agent on every account (Claude Code, Codex, Cursor) uses it with no sign-in of its own (the owner's decision of 2026-10-18, AGENTS.md). obid is Tetrix's OAuth client and holds the login; agents reach Tetrix only through obid, with a credential that works for their own job and dies with it. None of these endpoints is on the gateway's allowlist, and no other Oby can reach them: a paired phone never signs the Mac in to Tetrix (the iPhone shows the state through the accounts' `tetrix` and the jobs' `tetrix`).

**`GET /v1/tetrix`** answers:

```json
{"connected": true, "url": "https://tetrix.example/mcp", "preset": "team",
 "presets": [{"id": "team", "name": "Our Tetrix", "url": "https://tetrix.example/mcp"}],
 "scopes": ["graph:read", "sessions:write", "hitl:write", "offline_access"],
 "connectedAt": "2026-10-18T14:02:11Z", "signIn": null, "error": null}
```

- `connected`: obid holds a login for `url` that it can use or refresh. `url` is the MCP server it signed in to (or last tried), `preset` the preset's id or null for a URL the owner typed. `presets`: what Settings offers before a URL field, `config.json`'s `tetrixPresets`; `[]` when it names none.
- `scopes`: what the authorization server granted, or null when signed out. `connectedAt`: when the sign-in finished, or null.
- `signIn`: the sign-in under way, as `POST` answers it, or null. `error`: why the last sign-in or refresh failed, in a sentence (`Tetrix signed Oby out: sign in again.`), or null; it clears on the next sign-in, or the next refresh that works. With `connected` still true, it's a refresh the sign-in server didn't answer (below): Settings › Connectors shows Tetrix as needing attention, with Reconnect.
- No token, code, verifier or client secret is ever in an answer, an event, a log line, a report or `config.json`.

**`POST /v1/tetrix/sign-in`** with `{"preset": "<id>"}` (one of `presets`) or `{"url": "https://<host>/mcp"}` starts a sign-in and answers `{"url": "https://<authorization server>/…/authorize?…", "server": "https://<authorization server>/…", "expiresAt": "…"}`. `server` is the authorization server's issuer (where the person signs in), as the MCP server's metadata named it and its own metadata confirmed; `url` is always on its host (obid refuses a server whose authorization endpoint is elsewhere, `502`). The app opens `url` in the person's browser; when they finish there, the browser lands on obid's loopback page, which says `Oby is signed in to Tetrix. You can close this tab.` The app follows it with `GET /v1/tetrix` (every 2 seconds while `signIn` isn't null) or the `tetrix` event.

- The URL follows a connection's rules (Connection, above): HTTPS, with no login, query or fragment; plain HTTP only on 127.0.0.1 or localhost. The one query it may carry is Tetrix's own `?org=<uuid>` (a hyphenated UUID, nothing after it), which obid writes in lower case as Tetrix matches it: which organization a login in several answers for, as the owner's other Tetrix clients have it; Tetrix refuses such a login every call (`400`) until its address says (#1667, SIGN-IN-14). A preset's `url` may carry it too. Any other query is `422` saying the one query it takes is `?org=<your organization's id>`; anything else, or an unknown preset, is `422` naming what's wrong.
- How obid finds the authorization server (the MCP authorization spec): the server's protected-resource metadata (where an unauthenticated call's `401` says, `WWW-Authenticate: Bearer … resource_metadata="…"`, else `/.well-known/oauth-protected-resource/<path>`, then at the root) gives `authorization_servers`, `resource` and `scopes_supported`; the server's metadata is RFC 8414's (`/.well-known/oauth-authorization-server/<path>`), else OpenID discovery (`<issuer>/.well-known/openid-configuration`, then `/.well-known/openid-configuration/<path>`), whose `issuer` must be the one asked for. Redirects aren't followed. When none answers JSON, `502` says so.
- The client: a public client with PKCE (S256) and no secret. A preset may name its client id; otherwise obid registers one by dynamic client registration (`registration_endpoint`, `token_endpoint_auth_method` `none`, redirect `http://127.0.0.1/callback`) once per authorization server and keeps its id. Neither: `502`.
- The metadata must be for the server obid was given (RFC 9728 3.3): its `resource` has the URL's origin and its path, or a prefix of it at a `/`; else `502` and no sign-in. That `resource` is the resource indicator obid sends. Plain-HTTP endpoints on 127.0.0.1 are taken only when the URL itself is on 127.0.0.1. Answers from the sign-in server are read up to 256 KB.
- Scopes: the resource's `scopes_supported`, else `graph:read sessions:write hitl:write`; plus `offline_access`, so obid can refresh. The request carries `resource` (RFC 8707), the `state` and the PKCE challenge.
- The redirect is `http://127.0.0.1:<port>/callback` on a port obid opens for this sign-in alone, on 127.0.0.1 only. It answers that one path (`GET /callback`), takes the first request whose `state` matches, and then closes; a request whose `state` doesn't match gets `400` and changes nothing.
- One at a time: a second `POST` ends the one under way (and waits up to 5 seconds for its page to close, so a registered client's port is free again) and starts another. A sign-in ends when the token exchange does, after 10 minutes, with `DELETE`, or when obid stops.
- The login (access token, refresh token, expiry) goes into obid's vault as `oby.tetrix.access` and `oby.tetrix.refresh` (a connection can't name an `oby.` secret), so it lives where the vault lives (`home/vault/secrets.json`, a Mac's too since 2026-10-30) and is taken out of every answer, log line and push like every vault secret (obid only: the vault). Everything else (`url`, the client id, the endpoints, the expiry, the granted scopes) is in `home/tetrix.json` (0600).
- Until a sign-in finishes, the login before it stays in use. One that finishes on another sign-in server than the login it replaces (another token endpoint: another Tetrix's) has the old one take that login back, as `DELETE /v1/tetrix` does (its `revocation_endpoint`, the refresh token), in the background once the new login is kept; a failure there is only logged. On the same sign-in server nothing is taken back: there the old and new logins can share one session (Keycloak's client session), and revoking the old would end the new.
- obid refreshes the access token itself when it has less than a minute left, or when Tetrix answers `401`, and keeps the rotated refresh token. A refresh Tetrix refuses (`invalid_grant`) signs Oby out (`error` says so). One the sign-in server doesn't answer (it can't be reached, or answers 5xx) while the token can't be used (it ended, or Tetrix answered `401`) keeps the login, fails that call, and says so in `error` (`Oby couldn't refresh its Tetrix login: Tetrix's sign-in server answered HTTP 503. It tries again at the next call.`); the next call refreshes again.

Its `422`s carry `reason` `badAddress`; its `502`s `noSignIn`, but `didNotStart` when registering a client with the sign-in server failed or was refused. A sign-in that ended without a login shows as `connected` false and `signIn` null.

**`DELETE /v1/tetrix/sign-in`** ends the sign-in under way, if any: `204`.

**`DELETE /v1/tetrix`** signs Oby out: it asks the authorization server to revoke the refresh token when it offers `revocation_endpoint` (and goes on if that fails), removes both vault secrets, and keeps `url` and `preset`: `204`. Jobs that are running lose Tetrix at their next call (`Oby isn't signed in to Tetrix.`).

**The `tetrix` event** comes on `/v1/events` with the same body as `GET /v1/tetrix` whenever any of its fields change. The gateway leaves it out of a phone's event stream.

**What agents get.** While Oby is signed in, every owner's job's agent gets one MCP server named `tetrix` that is obid itself: `POST /v1/agent/tetrix/{job}` on obid's port (on Linux, through slirp4netns's 10.0.2.2, as for the broker), with the job's token (the broker's: Connection, above), which works for that job alone, only while it runs, and dies with it. Claude Code gets it in its `--mcp-config` file and one `--allowedTools` rule per tool (`mcp__tetrix__<tool>`); Codex as `mcp_servers.tetrix` with the token in its environment (`bearer_token_env_var`, as the broker); Cursor in `session/new`'s `mcpServers` when it says `mcpCapabilities.http`. The agent never sees Oby's Tetrix token, and Tetrix sees obid's token, never the job's.

- `tools/list` lists only the tools agents may call (`TOOLS` in core/crates/obid/src/tetrix.rs: the graph reads, the earlier sessions' digests and `save_session`); `tools/call` of any other (`resume_session`, admin, write and diagnostics tools) is refused before it leaves obid. Every call's arguments go through the secret scan first (`crate::scan`, as a push's do, in obid's own `home/tmp`, never the job's folder, which its agent can write): a finding, or a scan that can't run, is refused (`Oby didn't send this to Tetrix: the secret scan found something in it.`) and nothing leaves. Every result is scrubbed like a connection's.
- One Tetrix error never takes the tools away. obid keeps a job's listing only once Tetrix gave it whole: one that failed, or that a timeout cut off (a context question's 10 seconds), is asked again, in a new MCP session, at the job's next call. An agent lists its tools once, as it starts, so while Tetrix doesn't answer `tools/list` gets Tetrix's last listing for any job (else the allowed tools' names alone, with an open `inputSchema`), never an error or none. Each call tries Tetrix again (refreshing the login when it ended); one that can't reach it answers `isError` with `Oby couldn't reach Tetrix: <why> Ask again later: each call tries Tetrix again.`
- A call Tetrix refuses with an HTTP status other than `401` fails with its reason when its JSON body gives one (`detail`, `error_description` or `message`: one line, at most 200 characters, known secrets taken out): `<host> answered HTTP 400: multiple organizations in token; org query param required.`, to which obid adds `Add ?org=<your organization's id> to Tetrix's address and connect again.`. Every connected MCP server's refusals read that way. That refusal also shows as the connection's `error` (`GET /v1/tetrix`), still `connected`, and new jobs get no Tetrix server until it's connected again, which clears it; a token refresh doesn't (FIELD-3).
- A session the agent saves (`save_session`'s answer) is listed in the job's `outgoing` as `{"action": "tetrixSession", "repo", "id": "<session id>"}`.
- Each call is recorded in the job's `connectionUses` as connection `tetrix`, secret `oby.tetrix.access`, host Tetrix's (never a value), and counted in the job's `tetrix`.
- Without Oby signed in to Tetrix, agents get no Tetrix: the plug-in that gave a Claude Code agent Tetrix on its tool's own login went with plug-ins (2026-10-27), and obid logs how to sign in when `home/plugins.json` still has it on.
- Reviews another Obi asked for get no Tetrix.
- **A conversation's turn** (obid only: the conversation harness) gets the same server while Oby is signed in, at `POST /v1/agent/tetrix/conversation-<id>` with its turn's token (the one its `oby` server takes, good only while one of its turns is under way): Claude Code in its `--mcp-config` file, Codex as `mcp_servers.tetrix`. Signed out, its session has no `tetrix` server, and its orientation says nothing of Tetrix. It lists and calls `TOOLS`, the reads and `save_session` (TASKCONV-12: what it saves passes the secret scan and is in the connection-use log as a `write`; a conversation keeps no `outgoing`), and any other call is refused before it leaves obid. The same secret scan and scrubbing; every answer comes between the turn's fences with the line that says it's data, and a call that leaves obid makes the turn count as having read something untrusted (its jobs start marked `untrusted`, and the conversation keeps none of the owner's declared secrets). A Claude Code waiting for its next turn may `initialize`, `ping` and `tools/list` with its token; a `tools/call` answers a JSON-RPC error (`-32600`), and one from a turn that was stopped answers `isError` (`The turn was stopped: nothing more happens for it.`) and leaves nothing. Whether a turn gets Tetrix is decided once, as it starts, for both its server and its orientation. Oby's Tetrix login never reaches the turn. Each call goes in obid's connection-use log with job `conversation-<id>` (there's no job to list it on), and every conversation's calls share one upstream session with Tetrix.

**Context first.** Before a job's agent starts (its first turn, and the first after obid restarted it), obid asks Tetrix with its own login about the job: `search_entities` for the issue or pull request (`<repo>#<n>`, else the job's title) and `repo_sessions` for the repository, 10 seconds at most each, each through the secret scan first (one it doesn't pass isn't asked). After two questions in a row that can't reach Tetrix, the rest aren't asked, and the agent starts. What comes back is written to `.obi/context/tetrix.md` with the plug-ins' context (obid only: plug-ins), quoted as data, and the prompt says to start there, to ask Tetrix before reading many files, and to end with `save_session` and a `Tetrix-Session: <id>` trailer on every commit.

**Decisions before publishing** (Trail-Code's `trail check`, the idea only). When a job's check has passed and before it publishes, obid reads what the change does in its own clone, as the secret scan reads it (`git diff -U0` with the scan's options and configuration, never the worktree's git), and keeps the lines whose only change is a number (`retries = 4` to `retries = 6`), with the name it's assigned to (`MAX_RETRIES`, `"retries"`, `retry(4)`). A number inside a name (`u32`), a reference (`#12`, `main.rs:40`), a date or time (`2026-10-18`, `10:30`) or a version's later parts isn't one, and lock files and other generated files (`*.lock`, `*-lock.json`, `go.sum`, `*.min.*`, `vendor/`, `node_modules/`, `dist/`, …) are left out. It reads the first 8 MB of the diff, the first 10 files with such a change, and at most 200 changes in them. With none, Tetrix isn't asked.

Otherwise obid asks Tetrix with its own login, each question through the secret scan first (one it doesn't pass isn't sent), 10 seconds at most each and 30 seconds in all, and a stop ends it at once. The questions, as Tetrix's tools take them (deskree-inc/tetrix-collectors, `mcp_service/app/tools/`):
- `repo_sessions` with `{"name": "<owner>/<name>"}`: the sessions on the repository, `sessions[].session_id` (graph ids).
- `session_context` with `{"session": "<graph id>"}`, for the first 10 sessions of the first page. Tetrix orders them by edge type (`produced`, `references`, `worked_on`), then title, never by date, and which ones changed the files is only known from each one's digest, so on a repository with more than 10 sessions the rest aren't read and an older decision can be missed. It gives each one's `natural_key`, `session:<owner>/<uuid>`. One whose `digest_summary.decisions` is 0, or whose uuid is one of the job's own (`saved`, and the graph gaps obid saved for it), is skipped.
- `session_digest` with `{"session": "<natural key>", "format": "structured"}`: its `digest`. It is kept, at most 5, when its `projects[]` for this repository list one of the changed files in `paths_modified`. Its `decisions[].statement`s are read, not the `reverted` ones.

A decision that names the old number and not the new one, and a word of the assigned name (`retries` for `MAX_RETRIES`; the same stem, never a prefix), is a **conflict** (at most 20, one per line).

- **The author's round.** The first time there's a conflict, the author gets one more round, as for a push the secret scan blocked (even with no rounds left). Each conflict and its decision are quoted in `.obi/inputs/decisions.md`, fenced as data from Tetrix. The round's message names only the file, the line, the two numbers of the agent's own diff and that file, and tells it to put the value back and commit, or keep it and say why in its summary, which goes into the pull request's description. The job's step reads `Round 2 of 2: a change goes against an earlier decision`. Its check runs again after it, and the decision check once more. A job had its round once `decisions.asked` is true, after a restart too.
- **Never a block.** What's still a conflict after that round (or, when the check after it runs out of time, what the first one found) publishes all the same, listed in the pull request's description: ``- Earlier decisions: this changes 1 value(s) an earlier Tetrix session decided on: ` src/net.rs:12 ` (4 → 6), session 5b0e…. The agent's summary says why.`` The decision's words aren't in it. No second round.
- **On the job**, in its `tetrix`: `"decisions": {"sessions": ["5b0e…"], "conflicts": [{"file": "src/net.rs", "line": 12, "was": "4", "now": "6", "session": "5b0e…", "decision": "Keep retries at 4: …"}], "asked": true, "error": null}`, from the latest check:
  - `sessions`: the sessions whose decisions were read;
  - `conflicts`: what was found (`decision` at most 300 characters, scrubbed like every answer);
  - `asked`: whether the author got its round;
  - `error`: `Tetrix didn't answer within 30 seconds: nothing was checked.` when it ran out of time, else null.

  The whole field is null when the check didn't run.
- **Without Tetrix** (Oby not signed in, or the job's agent didn't get it through Oby) nothing changes. Questions to Tetrix aren't outgoing actions; the pull request that lists the conflicts is.
- What it doesn't catch yet: an approach an earlier session ruled out coming back, or a decision changed in other words. Those need a reviewer reading the digests whole: obid's own review (#525) doesn't read them yet.

**Jobs' `tetrix`** (Job, above) on obid is filled for jobs whose agent had Tetrix through Oby, and stays null otherwise:

```json
{"connected": true, "calls": {"search_entities": 2, "get_entity": 1, "save_session": 1}, "rounds": null,
 "reminded": null, "stamps": {"commits": 2, "stamped": 2, "sessions": ["8f2a…"]}, "author": null,
 "context": true, "saved": ["8f2a…"],
 "gaps": {"noResults": ["acme/shop#12"], "missing": ["repo:acme/legacy"], "unknownFiles": ["src/new.rs"],
          "failed": [{"tool": "code_impact", "error": "Tetrix said: …"}],
          "sent": "2026-10-18T14:40:02Z", "session": "c41d…", "notSent": null},
 "decisions": null, "unreachable": null}
```

- `calls`: every call the agent made through obid, by tool, counted by obid itself (it is the server). `rounds` and `reminded` are null on obid. `stamps`: as above, read when the job's last round ends. `context`: whether `.obi/context/tetrix.md` was written. `saved`: the session ids Tetrix's `save_session` answered the agent.
- `unreachable`: while Tetrix couldn't be reached the last time the job tried (the agent's listing or call, or obid's context questions), in plain words: `Tetrix wasn't reachable, so this job ran without the graph: Tetrix's sign-in server answered HTTP 503.`, or `Tetrix stopped answering during this job: <why>.` when it had answered the job before. An error Tetrix itself gave (`Tetrix said: …`, a tool it doesn't have) isn't one. Null once Tetrix answers again. The summary's Tetrix line says it too, after the calls.
- `gaps`, the report back to Tetrix of where the graph fell short (null until the job ends): `noResults`, searches (`search_entities`, `query_graph`) that found nothing, by their query; `missing`, entities `get_entity` (or another lookup) didn't find, by what was asked; `unknownFiles`, files the job changed that no Tetrix answer named; `failed`, calls that failed, with the error's first 200 characters. At most 20 of each, each at most 200 characters.
- When the job ends with any gap, obid sends them to Tetrix with its own login as a `save_session` of its own (`client` `oby`, `title` `Oby: graph gaps in <job title>`, `repo_hint` the repository, `summary` the counts, `state` `{"kind": "oby.graphGaps/1", "job": "<id>", …the four lists, "agentSessions": […]}`), after the secret scan passes on exactly what goes; a finding, or a scan that can't run, sends nothing (`notSent` says why). `sent` and `session` say when and as which Tetrix session; the send is listed in the job's `outgoing` as `{"action": "tetrixGaps", "repo", "id": "<session id>"}`.
- The summary's last line (not on review jobs) reads as above, followed by `Graph gaps sent to Tetrix: 1 search with no result, 1 file it didn't know.` when there were some.

**Accounts' `tetrix`** (Account, above) on obid is `true` for every Claude Code, Codex and Cursor account while Oby is signed in to Tetrix, else null; `tetrixJobs` and `tetrixUsed` count the account's latest 50 ended jobs with a `tetrix`, and those whose agent called it.
