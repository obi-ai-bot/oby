### obid only: Obi-to-Obi review jobs

The business contract is [docs/contracts/teammate-review.md](contracts/teammate-review.md) (TEAMREVIEW-1 to 8).

What obid does when it accepts a `review_request` (by the owner's answer or a decision):

1. It starts a job: `kind` `review`, `repo` the request's, `title` like `Review for ernesto: fixture-app`, and two keys only obid sends on jobs: `obi` (`{"correlationId", "from", "fromOwner", "requestId"}`, null on other jobs) and `worktree` (the job's worktree, an absolute path, null before it exists; the gateway nulls it). It runs on an account Routing picks.
2. It fetches `head_branch` and `head_sha` from the repository's `remote` into its clone (whose push URL is invalid, as the runner's is), and makes a fresh worktree, `home/worktrees/<job id>`, detached at `head_sha`. When `head_sha` can't be fetched, the job fails. So does a request with `approve_on_host` whose `base_branch` doesn't fetch, or that obid can't compare `head_sha` with (`Couldn't fetch the base branch <base> from <repo>, so obid didn't review a change it was asked to approve: …`): its approval would cover what the review couldn't see. When the commit holds a symbolic link that leads out of the worktree, followed as the system would open it (`x -> ../../accounts`, `x -> /`, an absolute path, a chain that ends outside, or one obid can't follow), the job fails before the agent starts, naming the link (`The branch commits a link that leads out of the review's worktree ("x"), so obid didn't review it: …`): Claude Code reads inside its working folder without asking, so a link out would let the agent read what the job sandbox lets it read, its own account folder included. A link that leads to a file inside the worktree, existing or not, is fine.
3. It writes the request as data to `.obi/inputs/obi-request.json` in the worktree, and the change as data to `.obi/inputs/change.diff` (what `head_sha` changes against the fetched `base_branch` from their merge base, the files it touches listed first: `git --no-replace-objects diff --no-color --no-ext-diff --no-textconv --find-renames --patch-with-stat --src-prefix=a/ --dst-prefix=b/ origin/<base_branch>...<head_sha>`, cut at 8 MiB with a line saying so; when the base didn't fetch, a line saying obid couldn't compare), and the repository's rules as the base has them, quoted, to `.obi/inputs/base-rules.md` (`AGENTS.md` and `CLAUDE.md` on `origin/<base_branch>`, each or `(<base> has no <name>.)`): never the change's own, which its author wrote. The request is `{"from", "from_owner", "type", "body"}` with `body` exactly as received. obid excludes `.obi/` in the worktree's `info/exclude`, and writes both files itself, outside the sandbox, into a worktree that holds whatever the other Obi's branch commits, so it follows no link: when `.obi` or `.obi/inputs` is there and isn't a real folder (a link out of the worktree, or a file), the job fails, saying so, and nothing is written; a link or file named `obi-request.json` or `change.diff` is removed, not written through, and the file is made new.
4. It runs the agent in the worktree with a fixed prompt that names only the commit, the conditions' kinds and the two files, never a field the other Obi wrote words into: the repository's and the branches' names (`repo`, `head_branch`, `base_branch`) reach the agent only inside the quoted file, and the prompt refers to them there by name; with the account's binary and `-p --input-format stream-json --output-format stream-json --verbose --permission-prompt-tool stdio --permission-mode default --setting-sources "" --strict-mcp-config --restricted --json-schema <the review output schema> --tools Read`, the environment cleaned as for any Claude Code job (no `CLAUDECODE`, `CLAUDE_CODE_*`, `ANTHROPIC_*`, `GH_TOKEN`, `GITHUB_TOKEN`), and the job sandbox below. `--restricted` keeps Claude Code from loading a `CLAUDE.md` of the worktree as instructions (`--setting-sources ""` keeps settings files out, not instructions): an `AGENTS.md` or `CLAUDE.md` the change adds is part of what it reviews, and the prompt says every file of the worktree is data. The agent has Read and nothing else (`--tools Read`): Claude Code doesn't ask before every call (it runs read-only shell commands such as `ls`, `grep -r`, `grep -R` and `find -L`, and reads inside its working folder, without a permission prompt), so obid gives it only a tool that is safe to run unasked. Claude Code 2.1.204 has no Grep, Glob or LS in this mode; the agent reads the diff from step 3 and the files it touches. obid answers the agent's permission prompts itself and never asks the owner: after its fixed rules, only Read, and every path input must lead inside the worktree once symlinks are followed (`path`, `file_path` and `notebook_path` resolved as the system would open them, relative ones from the worktree); a path starting with `~`, a link that leads out, and an input obid doesn't know that may name a path are refused. Claude Code asks before reading outside its working folder, and before reading through a link that leads out of it. The sandbox lets the agent read its own account folder (it signs in with it), so these together keep the account out of the review: Read only, no link out of the worktree (step 2), and obid's answers for what Claude Code asks. The publish gate in step 8 is not a barrier against an account's contents: it catches what looks like a known secret, including one written spaced out, backwards, or split with dashes or zero-width characters, not every way to encode one. It closes the agent's stdin after the turn's `result` line. A review job that makes a commit fails.
5. It reads `structured_output` from the `result` line; when that is missing, the last fenced code block labeled `obi-review` in `result`, holding the same JSON. Neither, or one that doesn't match the schema, fails the job.
6. It runs the repository's `check` in the worktree, **in the same job sandbox as the agent** (the test-run limit applies): `tests_pass` is met when it exits 0. Without a `check`, `tests_pass` is not met. The check runs code from another Obi's branch, and with a remembered decision it does so without the owner looking first, so it gets nothing the agent doesn't.

7. It builds the result body (spec `protocol.md` 5.7): each finding gets the spec's recommended id (`f-` + 16 hex of SHA-256 of `file\nline\ntitle`), and findings are de-duplicated **by that id**: when two have the same id (same file, line and title, whatever their severity or detail), only the first the agent reported is kept, so ids are unique in the result as the spec requires; each acceptance condition its `met` (`custom` conditions are not judged by obid yet: not met), and `outcome` is `approved` when every condition is met, else `changes_requested`; a job that failed gives `failed` with no findings. A finding that doesn't match the spec's schema (a path outside the repository, a title on two lines) is dropped, and the summary says how many were; when one dropped would have failed a condition (a `blocker` under `no_blocker_findings`, or one at or above a `no_findings_at_or_above` severity), the result can't say so and stay consistent, so it is `failed`, never an approval that hides it.
8. **Publish gate.** Every text field of the reply (finding titles and details, the summary) goes through the secret scan Publish uses (its rules, the vault's secrets, their encoded copies). Clean: it sends the `result`. A finding, or a scanner that can't run: it sends a `result` with `outcome` `failed`, `findings` `[]` and no text, and records that in the exchange's `publishScan`.
   When the request has `approve_on_host` and the review came out `approved`, the result's `host_review` says what obid did about approving it on GitHub, before the result goes ([teammate approval](#obid-only-teammate-approval)).
9. The job ends `done` (or `failed`) and publishes nothing: no push, no pull request, no check run, no comment, `outgoing` stays `[]`, but for the one approving review [teammate approval](#obid-only-teammate-approval) allows (`pullRequestApproval`).
10. **Its worktree is kept** after the job ends, unchanged, so the owner (and the e2e scenario's steps 5.2, 6.3 and 8.4.3) can look at what was reviewed. The cleanup pass (`cleanup`, above) removes the worktree of a review job from another Obi (a job whose `obi` isn't null) only once that job ended more than 24 hours ago, like a settled job's, and never earlier: the rule that removes an Oby review job's worktree as soon as it has a verdict doesn't apply to it. A runner restart keeps it too.

**The job sandbox** (steps 4 and 6), bubblewrap on Linux and a Seatbelt profile (`sandbox-exec`) on macOS. It holds for the process and everything it starts:

On macOS the box also hides `/private/tmp`, `/Users/Shared` and the user's Darwin
temporary folder (`TMPDIR`), restoring the job's own paths within them, the `ps` copy it
runs (`oby-tools-<uid>` in that temporary folder, read only, #1789) and Claude Code's own
`/tmp/claude-<uid>` by itself, never what is in it. Unboxed Claude
login refresh keeps its scratch configuration under obid's hidden home.

- **Writes** go only to the job's worktree (`home/worktrees/<job id>`), the worktree's own git directory (`<common dir>/worktrees/<name>`: its `HEAD`, `index`, logs), and the job's own temporary folder, which is its `HOME` and `TMPDIR` (for the agent also its own login folder, `home/logins/<job id>`). Never an account's own folder (`configDir`, #655): no box mounts it, so nothing a job writes is ever read by an unboxed process (the tool's own sign-in, the person's own `claude`); every configured account's folder is also hidden from every box, so none reads it either, wherever it is. At its start obid looks at each configured account's folder once and logs anything there that would run something or redirect a tool the next time it runs unboxed (Claude Code's `hooks`, `env`, `apiKeyHelper`, `statusLine` and `mcpServers` in `settings.json`, `settings.local.json` or `.claude.json`; Codex's `notify`, `mcp_servers`, `model_providers` and `profiles` in `config.toml`; Cursor's `mcp.json` and a non-empty `permissions.allow` in `cli-config.json`), since a box of an older obid could have put it there. On macOS, when the Keychain holds an account's login, it takes out a `.credentials.json` an older obid copied into that folder (one with no refresh token), whether `claudeKeychain` is on or off now (#646: left there, it showed the account `signedIn` and was copied for its runs); one the Keychain doesn't hold, or one with a refresh token, may be the login itself and stays. A `configDir` that holds obid's home is refused. Nothing else is writable, the clone included: a review job makes no commit.
- **Reads, from `obid`'s `home`**: the worktree, and the clone's git common directory (`home/clones/<owner>/<name>/.git`: objects, refs, `packed-refs`, `config`, `info/`), which git needs to work in a linked worktree, read-only. Nothing else of `home`: not the database, `keys/`, `api-token`, the delegation, `plugins/`, `plugin-data/`, other clones or other worktrees.
- **Reads elsewhere**: the system's files and the tools it runs (read-only), as for any job; not the person's real `HOME`. Of it, only the person's Rust toolchain, read-only: rustup's home (`RUSTUP_HOME`, else `~/.rustup`) and cargo's own `bin` (`CARGO_HOME/bin`, else `~/.cargo/bin`), never the rest of the cargo home (its `credentials.toml`, its registry).
- **On macOS, `ps` runs.** macOS runs no setuid program in a sandbox, whatever its profile says, and `/bin/ps` is one, so a repository's tests that look at processes could never pass in a job. A box's `PATH` starts with a folder in the person's own temporary folder holding a copy of it without setuid, signed ad hoc, which sees the same processes of the same person (#1789). Other setuid programs stay refused.
- **Environment**: cleaned as in step 4, with no vault secret, no code-host login (`GH_CONFIG_DIR` empty), no `obid` API token and no Obi key. `HOME`, `TMPDIR` and, on macOS, `CFFIXED_USER_HOME` are the job's temporary folder: Foundation takes its home from the password database whatever `HOME` says, so without it SwiftPM's caches and Xcode's DerivedData went in the person's hidden `~/Library` (xcodebuild: `You don't have permission to save the file "repositories"`). `RUSTUP_HOME` is the person's, and a job's `cargo clippy` and `cargo fmt` are the ones the person's shell runs: cargo looks for `cargo-*` in its own `bin` before `PATH` only when that `bin` isn't on `PATH`, and otherwise in `PATH`'s order (cargo#11020), so when the person's cargo `bin` isn't on their `PATH`, the job's own cargo home (`<temp>/.cargo/bin`) holds a link to each of its `cargo-*`, and when it is, the box's `PATH` (the person's) decides as theirs does (2026-10-24: with neither, the box found Homebrew's older clippy where the person's cargo found rustup's, and their lints differ). obid makes or takes out the links before each run, never through a link the job left (`.cargo` and its `bin` must be real folders, and a link of the same name is replaced, not followed). `a_jobs_cargo_is_the_persons` shows the box and the person's shell print the same `cargo clippy -V`, `cargo fmt --version` and `rustc -V`. Builds are sized to memory (obid only): the agent and the check get `CARGO_BUILD_JOBS`, `RUST_TEST_THREADS` and `OBY_BUILD_JOBS` (for the repository's own scripts: this repository's `scripts/oby-check.sh` passes it to `swift test -j` and `xcodebuild -jobs`), all the same number, one for each 1.5 GiB (about what one rustc of a big crate holds) of the room memory leaves the build (Jobs run side by side, above): what's spare (`available`, less a fifth of `total` kept free for the person's own apps), less what the other running jobs' agents here may still take (each one's budget less what it holds now), each at least what its turn was told to build with (N × 1.5 GiB for N, the whole turn: the width given is room taken), and, for an agent, one of the other running jobs' checks (any of them may start its check during the turn; its own can't); a check isn't held back from itself. Memory only narrows a build this way: it never keeps a job or a check waiting. At most half the machine's cores, at least 1. It's worked out at every turn (each starts the agent again) and every check, so a turn that starts next to others builds narrower. With memory unreadable, none is set and builds keep their own defaults. A command can still say otherwise for itself. A committing job's `GIT_OBJECT_DIRECTORY` and `GIT_ALTERNATE_OBJECT_DIRECTORIES` hold for every git it runs, in any repository (git has no setting that scopes them to one), so a process that runs git in another repository, a test's fixtures, takes both out, as obid's own git does and its tests do.
- **Agents can't publish** (docs/contracts/lanes.md, LANES-2), in either lane, by one rule (`process::no_publish_env`, given to every agent's run: a job's, boxed or in Claude Code's own sandbox, a conversation's and the brain's): an empty `GH_CONFIG_DIR` (no GitHub login), `GIT_TERMINAL_PROMPT=0`, git reading no settings but the repository's (`GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`) with an empty `credential.helper` on top (`GIT_CONFIG_PARAMETERS`, never `GIT_CONFIG_KEY_0`, which a Codex that drops `*KEY*` variables would leave git counting and refusing to run), and `remote.origin.pushurl` set to an invalid URL (`git::NO_PUSH_URL`): in the clone, and again in the same `GIT_CONFIG_PARAMETERS` after an empty value (`process::no_publish_git`). Two layers hold it. Each time obid gets a clone ready (`git::ensure_clone`) it sets the clone's push URL with `git config --replace-all`, so the clone holds only obid's, whatever push URLs it named before, and no job's sandbox writes the clone's settings. On git 2.46 and later, the environment's empty value resets git's list, so its reset alone covers a clone whose own settings name another push URL. On older git (Ubuntu 24.04's 2.43) the empty value is one more entry: the clone's own setting comes first, and git stops at obid's URL there. obid has no minimum git version for this. The egress proxy's environment carries the same value, so a proxied job's last word for it is still this one. No agent gets a name that pushes or signs in (`process::agent_withheld`): obid's withheld ones (`GH_TOKEN`, `GITHUB_TOKEN`, `ANTHROPIC_*`, …) and `SSH_AUTH_SOCK`, `GIT_ASKPASS`, `SSH_ASKPASS`, `GIT_SSH`, `GIT_SSH_COMMAND`, `GH_*` and `GITHUB_*`; obid's own gh and Publish keep `SSH_AUTH_SOCK`, so Publish over SSH works. Only Publish pushes. This covers obid's own paths: the owner's own MCP servers in the own lane are the owner's (LANE-12). `lanes_2_neither_lane_can_publish` and `lanes_2_an_agents_push_never_reaches_the_clones_push_url` check it.
- **Network**: the check has none (`--unshare-net`; a profile that denies network, and the DNS resolver's socket to anything without the network: Seatbelt kept that socket's allow over the profile's `(deny network*)`, so until 2026-10-24 a check, a review's or a no-network command resolved host names, and a lookup carries what it names out), but a check of the owner's own job whose agent ran here (never another Obi's review, nor a job that ran on a teammate's Mac, whose commits came from there: `Job::check_keeps_loopback`) keeps loopback, for the servers its tests start on 127.0.0.1. bubblewrap's network namespace has a loopback of its own with nothing of the host's on it; Seatbelt can't make one, so on macOS that check reaches the host's loopback (`localhost`, IPv4 and IPv6) and Unix sockets in its own folders, as the job's agent does anyway, and still no resolver (no host name but `localhost` resolves) and nothing beyond loopback: `an_owners_check_keeps_loopback_and_nothing_more`. On macOS an agent reaches nothing but loopback, and no resolver: its model's API, and any other site, only through obid's egress proxy ([obid only: the egress proxy](#obid-only-the-egress-proxy-616)). On Linux the agent has a network namespace of its own too, with `slirp4netns` so it still reaches its model's API (on Linux obid needs `slirp4netns` installed, Ubuntu: `sudo apt install slirp4netns`; without it no agent job and no answering run can start, and an answering run's log says only `obid couldn't answer by itself (the model's answer wasn't JSON)`) (in the stub's case, a local HTTP endpoint, at `10.0.2.2` from inside the namespace). An abstract-namespace Unix socket on the host is not in that namespace. `an_agent_reaches_its_api_but_not_an_abstract_socket` shows both. Inside the namespace the host's `/etc/resolv.conf` can't serve (on Ubuntu it names systemd-resolved's stub, `127.0.0.53`, the namespace's own loopback there, and the confined form has no `/run` for its link to lead into), so obid binds a file of its own over the one file it leads to, naming only slirp4netns's DNS forwarder, `10.0.2.3` (the host's `search` and `options` lines aren't carried over). That file is in a folder only obid's user can open and no sandbox shows (`/run/user/<uid>/obid-resolver-<uid>`, else the same name in the temporary folder), never in a folder a job writes, and it's replaced with a rename, never written through what is at its path. `a_run_with_the_network_resolves_a_host_name` resolves the model API's host in both forms, and `a_link_a_job_leaves_is_never_written_or_read_through` shows a link a job leaves is neither written nor read through.
- **No terminal, no one to run things for it.** The process leads a session of its own (`obid __session`, `setsid`; bubblewrap's `--new-session`), so it has no controlling terminal to push keystrokes into. On macOS the first process in the sandbox starts the job's program and, when that program exits or the process is signalled, kills every process in the sandbox (`kill -1`, which the profile allows only inside the sandbox). A descendant that called `setsid` ends with the job, on stop and when obid stops. On Linux, bubblewrap's PID namespace and `--die-with-parent` do the same. On macOS the profile also denies what would run or write something for the job outside its sandbox: LaunchServices opening an app (`lsopen`), Apple events, launchd jobs (`job-creation`), posted input events (`hid-control`, the window server's services), and every Unix socket but the job's own and, for a process with the network, the DNS resolver's.
- **On macOS, no preferences, pasteboard or keychain.** cfprefsd reads and writes the person's preferences for whoever asks, whatever the asker's `HOME`, `CFFIXED_USER_HOME` or file rules, so the profile denies `user-preference-read` and `user-preference-write` and the lookup of cfprefsd's services: a job has no preferences at all (CoreFoundation's writes fail; its reads find only what the job may read as files, and the person's home is hidden). It denies the pasteboard server's services (`com.apple.pasteboard.1`, Universal Clipboard's), secd's (`com.apple.securityd.*` and `com.apple.security.*`: the data protection keychain and iCloud Keychain, which secd reads and writes for whoever asks), the system keychain's securityd and SecurityAgent (which would ask the person for a keychain's password). The person's login keychain is a file in their home, which is hidden, and a client reads a file-based keychain's file itself, so it is out of reach too. Claude Code's login for a job is a `.credentials.json` in the job's own login folder, not the keychain: for an account with a `configDir`, a copy of that folder's login (the Keychain item's with `claudeKeychain`, else its `.credentials.json`) without the refresh token, in a folder that is the job's `CLAUDE_CONFIG_DIR`, with the account's `.claude.json` trimmed to what keeps it signed in (copied once); when `configDir` is null, the copy of `~/.claude/.credentials.json`. Claude Code 2.1.296 no longer writes it when the Keychain is denied, so with `claudeKeychain` on (obid only: configuration) obid copies Claude Code's own Keychain item instead (`security find-generic-password -s <service> -a <user> -w`, where the service is `Claude Code-credentials` for the default folder and `Claude Code-credentials-<first 8 hex digits of the folder's SHA-256>` for an account's `configDir`): into the job's private login copy as `.credentials.json` (removed when the run ends, like a copied file). The copy carries exactly what calls the API: `{"claudeAiOauth": {accessToken, expiresAt, scopes, subscriptionType, rateLimitTier}}`, and nothing else the item holds (no refresh token, no MCP logins, plug-in secrets or device tokens). Anthropic rotates refresh tokens, so a boxed run that refreshed with a copy revoked the Keychain's own and signed the Mac's own `claude` out (2026-10-17). Instead the Mac's own Claude Code refreshes the default login (`configDir` null), and the login of each account obid added itself (#877: its `configDir` is obid's own `home/accounts/<id>`, which the Swift engine never runs on), unboxed: `<absolute path of claude> -p /usage --model haiku --max-turns 1 --tools "" --strict-mcp-config --setting-sources "" --no-session-persistence` (Claude Code's own `/usage` refreshes an ended login and asks no model: 2.1.302 answered `num_turns` 0 and `total_cost_usd` 0; a Claude Code without its own `/usage` takes it for a one-turn Haiku prompt, which refreshes before it asks, as the earlier `-p ok` did; #1626), with `CLAUDE_CONFIG_DIR` and `TMPDIR` set to a new empty private folder of obid's (Claude Code applies a `.claude.json`'s `env` from its config folder whatever `--setting-sources` says), `CLAUDE_SECURESTORAGE_CONFIG_DIR` set to empty (it names the Keychain item: empty is the default one), `PATH=/usr/bin:/bin:/usr/sbin:/sbin`, the kept variables and `HOME`, and no `CLAUDECODE`, `CLAUDE_CODE_*` or `ANTHROPIC_*`, within 60 seconds, its output discarded. Claude Code 2.1.302 has no command that only refreshes (`claude auth status` reads the login without refreshing it), and it refreshes only in a token's last 5 minutes, so that is when obid asks, and only right before a boxed run starts (KEYCHAIN-10: no keeper looks at logins in the background): a token that ends within 5 minutes or doesn't say when is refreshed first, then the run's copy is made from the Keychain again. Nothing writes a running copy again. A login far from its end takes no lock; else one refresh at a time per Keychain item, at most one per 4 minutes, so many runs starting at once refresh it once and a failed refresh isn't hammered; never on obid's async runtime. After a refresh the old access token stays a secret obid redacts, next to the new one. Claude Code keeps the item's refresh lock, write lock and plaintext fallback in `CLAUDE_SECURESTORAGE_CONFIG_DIR`, which is the account's folder, so an added account's refresh runs only while its `.credentials*` files there are the person's own and no link. (Codex said: …)` and the account stays signed in; a revocation after `exp` still ends the login (`run codex login`) (ACCOUNTS-18). A job or the brain on an account with a `configDir` gets the same copy of that folder's `auth.json` (and never its `config.toml`, whose MCP servers would start inside the box with whatever tokens they carry) in a `CODEX_HOME` of its own, never the account's folder (#655); the owner refreshes it by running `codex` on that account.
- **Cursor's login is copied too, without its refresh token.** A Cursor job's `HOME`, `XDG_CONFIG_HOME` (`<it>/.config`) and `CURSOR_CONFIG_DIR` are its own login folder, never the account's. Cursor runs with `AGENT_CLI_CREDENTIAL_STORE=file`, so it keeps its login as a file, never the macOS Keychain, which the box denies: `~/.cursor/auth.json` on macOS, `$XDG_CONFIG_HOME/cursor/auth.json` elsewhere (cursor-agent 2026.10.01's own store; `{accessToken, refreshToken, apiKey, bedrockCredentials}`). Before every start the job gets a copy of the account's holding only `accessToken` and `apiKey` (an allowlist: never the refresh token, which a box could rotate away from the account as #651 found for Claude Code, nor Bedrock's keys), its tokens learned as secrets; for Cursor's own login with no login file, the same two read from its macOS Keychain items with `cursorKeychain` (obid only: configuration), the refresh token never asked for; a copy whose access token has ended makes the run say it isn't signed in. Once, it also gets the account's `cli-config.json`, then obid's settings over it (allow nothing ahead of obid), written inside the folder as obid opened it, never through a link put in its place (#645: the rewrite fails instead); never its `mcp.json`, whose MCP servers would start inside the box with their tokens. The account's sign-in writes that file too ([obid only: accounts](#obid-only-accounts)).
- **A repository's hooks wait for the owner, but in Bypass (#1570).** Cursor runs hooks from the worktree's `.cursor/hooks.json`, and Claude Code's from `.claude/settings.json` and `.claude/settings.local.json` (Cursor's "Include third-party configs", on by default), as its own children: they're inside the box, but outside obid's permission prompts, and no flag or `cli-config.json` key of Cursor's turns them off. So before a Cursor job starts, obid reads those files in its worktree, and with any hook a job that isn't in Bypass waits on a `RepositoryHooks` permission ([`POST /v1/jobs/{id}/permission`](#post-v1jobsidpermission)); a no starts nothing (docs/cursor.md, "A repository's hooks"). obid writes nothing for this: not the repository's files, the account's folder, the person's `~/.cursor`, nor the job's own folder copy.

What the sandbox can't hold back, and is known:

- **macOS: other processes' arguments and environment.** Any process of the same user can read another's arguments (`KERN_PROCARGS2`), and its environment when the kernel still includes it; Seatbelt has no rule for it. So `obid` keeps every secret out of its own and its children's arguments and environment (above, "obid only: configuration"). `a_sandboxed_job_reads_other_processes_but_finds_no_secret` shows a sandboxed job reads a marker in another process's arguments and finds neither the API token nor a vault secret kept only in a file. `a_sandboxed_plugin_reads_other_processes_but_finds_no_secret` shows the same for a plug-in.
- **macOS: a keychain file outside the person's home.** securityd's file-based keychains stay reachable (above), so a keychain file the job can read, outside the hidden homes and unlocked by the person, gives up the items whose access list lets the reading program in. `a_job_reaches_no_preferences_pasteboard_or_keychain` shows the person's login keychain and secd are out of reach.
- **macOS: a job's own preferences.** cfprefsd keeps preferences in the person's home whatever the job's `HOME` says, so the profile can't give a job preferences of its own; tools that keep settings there start from their defaults every time. The same test shows preference reads and writes fail.
When `obid` can't make this sandbox on the machine, it runs neither: the job fails, and its summary says why. On macOS it tries once when it starts (`sandbox-exec` with a small profile, as bubblewrap is tried on Linux).

- **macOS: the Apple apps don't build in a job's sandbox.** Tried in a box made as a job's agent's and as its check's (`a_command_in_a_jobs_box`, 2026-10-24), with Xcode 27: SwiftPM evaluates every package manifest (Sparkle's, when it resolves and on every build after) in a `sandbox-exec` sandbox of its own, and Seatbelt can't make one inside another (`sandbox_apply: Operation not permitted`); `swift` takes `--disable-sandbox`, but xcodebuild has no switch for it on its command line, and the default it reads (`IDEPackageSupportDisableManifestSandbox`) can't be set in the box, which has no preferences. Resolving outside the box first doesn't help, since the build evaluates the manifests again. Foundation also downloads a package's binary artifact (Sparkle's xcframework) through the person's temporary folder (`/private/var/folders/<…>/T`, which ignores `TMPDIR`), which no box may write: `Operation not permitted` (curl, which writes where it's told, downloads it). Letting a job write that folder, shared with the person's other apps, or run unboxed would weaken the sandbox, so the Apple apps are built and tested outside it: by the Mac check before merging, and for an agent by the Apple check (above). A repository's check that builds them should say so in a job's sandbox rather than fail (scripts/oby-check.sh does: a no-op `sandbox-exec` fails inside a sandbox). SwiftPM itself (`swift`) takes `--disable-sandbox`, and it fetches source packages with git in the box once a committing job's `GIT_OBJECT_DIRECTORY` is out of its environment (it clones each package from a cache of its own, which that variable leaves empty: `Could not read from remote repository`); but a cold `swift test` in the job's `HOME` doesn't fit the check's 20 minutes, so this repository's check leaves it to the Mac check too.
- **macOS: obid inside a job (its own tests).** A job that changes obid runs `cargo test -p obid` in its job sandbox, and those tests start an obid whose jobs run a fake agent. Seatbelt can't make a sandbox inside another (`sandbox_apply: Operation not permitted`, whatever the profile), so that obid's trial run is refused. When it is, and the sandbox it is in has the job profile's fingerprint, that obid runs what it starts inside the sandbox it inherited: the job's, which every process keeps and none can leave. The fingerprint, each part tried without a side effect (libsandbox's `sandbox_check` would need `unsafe`, which obid forbids): the person's home (from the password database, not `HOME`) can't be listed; a Unix socket that isn't the resolver's can't be connected to (syslog's, nothing sent); and the pasteboard server can't be reached (`pbpaste -pboard ruler`, its output discarded). Inside any other sandbox (an App Sandbox, a sandboxed launcher), or refused for any other reason, obid makes no sandbox and nothing runs, as above. Such an obid logs, when it starts, `obid runs inside a job sandbox, which Seatbelt can't nest in: what it starts stays in that sandbox`. So the test's agents write only where the job may, read nothing of the real obid's home or the person's home (no login, no Keychain), and have the job agent's network, no more; what they don't get is that obid's own narrower box (its home hidden from them, no network for its checks), which only matters to the tests that check those fences: they prove them outside a job's sandbox only. Those that need a sandbox of their own (tests/sandbox.rs's fences, and the plug-in tests whose plug-in host makes its own) find they're inside a job's (`Sandbox::encloses`) and fail, `not verified: inside a job's sandbox, where Seatbelt can't make this test's own; run it outside one`: there they'd prove nothing, and a pass would read as one. A job's check that runs them fails, so a job that changes them needs the owner, whose run outside a box (the merge wave's obid suite) verifies them; the Mac check runs no cargo. Its first process never kills the sandbox's other processes (`kill -1` would reach the job's own agent): one that called `setsid` ends with the job. The check of an owner's job keeps loopback, so it runs them too (this repository's check, scripts/oby-check.sh). `a_jobs_agent_and_its_check_run_obids_integration_tests` runs one that makes git fixtures, serves on 127.0.0.1 and runs its own job's check, in a box made as a committing job's agent's and as its check's. `a_fake_agent_test_runs_inside_a_jobs_sandbox` runs a fake-agent job test inside a sandbox made as a job's agent's and finds that log line; `a_fake_agent_inside_a_jobs_sandbox_stays_in_it` shows that test's fake agent can't list the person's home or the outer obid's, nor write outside its worktree and temporary folder; `inside_another_sandbox_a_fake_agent_test_runs_nothing` shows a sandbox that doesn't hide the person's home, and one that hides it without the job profile's other fences, run nothing.

The review output schema obid passes with `--json-schema`:

```json
{"type": "object", "additionalProperties": false, "required": ["summary", "findings"],
 "properties": {
   "summary": {"type": "string", "maxLength": 4000},
   "findings": {"type": "array", "maxItems": 50, "items": {
     "type": "object", "additionalProperties": false, "required": ["severity", "file", "line", "title", "detail"],
     "properties": {
       "severity": {"enum": ["blocker", "major", "minor", "nit"]},
       "file": {"type": "string", "maxLength": 500},
       "line": {"type": "integer", "minimum": 1},
       "end_line": {"type": "integer", "minimum": 1},
       "title": {"type": "string", "maxLength": 200},
       "detail": {"type": "string", "maxLength": 4000}}}}}}
```

Whatever the agent wrote must still pass the spec's schema before it is sent, and obid makes it so; what the agent wrote never fails the job once it matches the output schema above:

- **Findings.** A finding that doesn't pass the spec's schema for findings (a valid path, a one-line title, no control or bidirectional characters, the lengths) is dropped. Call the number dropped N.
- **The summary.** The result's `summary` is the spec's `block_text`, 1 to 4,000 characters (counted in Unicode code points, as JSON Schema counts them). obid builds it from the agent's `summary` in this order:
  1. Each CR LF, then each remaining CR, becomes LF.
  2. Every other character `block_text` forbids is removed: U+0000 to U+0008, U+000B to U+001F, U+007F, U+202A to U+202E and U+2066 to U+2069.
  3. When N is more than 0, the note is `obid dropped N finding(s) that didn't match the spec's schema.`, with N as a number; otherwise there is no note.
  4. The summary is the cleaned text, then (when there is a note and the cleaned text isn't empty) a blank line, then the note. When that is longer than 4,000 characters, the cleaned text is cut to the first `4,000 − 1 − (the rest's length)` characters and followed by `…` (U+2026), so the summary is exactly 4,000 characters and the note is whole.
  5. An empty summary (the cleaned text and the note both empty) is left out of the result: the field is optional.

  The publish gate (step 8) scans the summary as built here. With nothing to clean and nothing dropped, the summary is exactly the agent's.

**What obid sends in an exchange it was asked in, and in what order.** First `accept` (body `{}`, or `{"by_rule": "<decision id>"}` when a remembered decision accepted it) or `decline`; after an `accept`, any number of `status` with `state` `queued` or `working` and no `note`; then one `result`. obid never sends a `status` before its `accept` or `decline`: a request waiting in the owner's inbox sends nothing back. The protocol allows a `status` there (spec `protocol.md` section 4); obid doesn't send one, so the asking Obi learns nothing about the owner's inbox, and the e2e scenario's steps 5.4 and 7.3 rely on that order.

### obid only: teammate approval

The business contract is [docs/contracts/teammate-review.md](contracts/teammate-review.md) (TEAMREVIEW-1 to 8).

Some repositories merge only once another person approved the pull request on GitHub (a branch rule asking for an approving review from someone other than the author, as Tetrix's does), which neither Oby's own review nor its reviewer account can give. Then the owner's Oby asks a teammate's Oby over the Sphere, and that Oby, when its own review of the exact head passes, approves it on GitHub as its owner (spec `protocol.md` section 11, "Approving on the code host"): with its owner's own tap on that exchange at that commit, or, under its owner's standing permission, next to approvals of that commit by the people who own every file it changes. The sender's owner is asked nothing unless something goes wrong.

**Asking (the sender).** The merge step calls `Link::ask_teammate` (crate::sphere::approval) with the pull request, its base and head branches, its head commit and the owner's title, whenever it finds GitHub waiting for an approval it can't get otherwise; each call looks at what was asked before and sends at most one request:

- It asks one teammate at a time: an active member of the Sphere other than this Obi whose card accepts `review_request`, those whose Obi said it approved on that repository before first, then the rest by Obi id. The Sphere's directory says nothing of GitHub logins, so who can approve there is known only from what a teammate's Obi answers: one whose login can't push there says so (`host_review` `unable`) and the next is asked.
- The request is a `review_request` with `pr`, `approve_on_host: true`, the head commit as `head_sha`, `goal` the title's first line (`Review pull request #<n>` when it has none), two conditions, `tests_pass` (the teammate's own check passes on it) and `no_blocker_findings`, and two hours to answer, so a teammate whose Oby is away holds the merge that long at most. It goes through `POST /v1/obid/sphere/requests`'s path: the spec's schema, the secret scan, the signature.
- While a request for that head is on its way or being reviewed, while the result says `approved` and less than 10 minutes passed (GitHub shows it soon), or `asked` and the request hasn't expired (the teammate's owner may still say yes), it waits (`Waiting`, with words like `Waiting for ernesto's Oby to review it and approve it on GitHub.`). A decline, a failed review, `unable`, an expiry or an approval GitHub never showed asks the next teammate.
- A review that asked for changes is the owner's to settle: no other teammate is asked (`NeedsYou`: `ernesto's Oby reviewed it and asked for changes.`, or `ernesto's Oby didn't approve it: its checks didn't pass on it, or it has none for <repo>.` when `tests_pass` wasn't met). So is having nobody left to ask (`No teammate's Oby could approve it on GitHub.`, or `No teammate's Oby in the Obysphere takes reviews.`), or not being in a Sphere (`Oby isn't in an Obysphere, so no teammate's Oby can approve it.`); each then says what the owner can do instead (`Invite a teammate who can push to <repo> to your Obysphere, or get their approval on GitHub yourself.`, `… to an Obysphere with you, …` out of one).
- A new push is a new head: what was asked for the old one doesn't count, and it asks again.
- The merge itself stays the merge step's, by the repository's workflow, once GitHub shows an approval of the head it merges.

**Approving (the receiver).** An incoming `review_request` is accepted as any other (an inbox answer, or a remembered decision), and reviewed in a fresh worktree at exactly `head_sha` ([review jobs](#obid-only-obi-to-obi-review-jobs)). When it has `approve_on_host` and the review comes out `approved` (after the publish gate), before the result goes, it holds the review to its own bar first, whatever conditions the request listed: its own check passed on the head (a repository with no `check` never passes) and its agent reported no `blocker`, kept in the result or dropped. Below that bar the result says `host_review: "unable"`, and nothing is approved or asked. At or above it:

Either way, obid's approval counts only as the spec's rule says (`obi_protocol::host_approval::decide`, judged by the spec's `host_approval` conformance cases): with the owner's confirmation of this exchange, or next to code owners' approvals under a standing permission. Nothing else approves: no answer through the API token, no tap on another exchange's ask or for another commit, no tap older than two minutes or used before, nothing received.

- **With the owner's standing permission** for the sender's owner and the repository (a `host_approval` decision, exact repository or `*`: [remembered decisions](#obid-only-remembered-decisions)), obid first reads what GitHub shows with the owner's own `gh` (`approval::code_host`): the owner's login (`gh api user`), the repository's `CODEOWNERS` on `base_branch` (the first of `.github/CODEOWNERS`, `CODEOWNERS`, `docs/CODEOWNERS`, `gh api repos/<repo>/contents/<path> --method GET -f ref=<base_branch>`, raw), every file the pull request changes (`gh api repos/<repo>/pulls/<pr>/files --paginate`, a renamed file's old path too) and whether that's all of them (the pull request's `changed_files`, `gh api repos/<repo>/pulls/<pr>`), its reviews in order (`…/reviews --paginate`), all read as GitHub's API answers them, and, for the people whose approval may count, their access to the repository (`gh api repos/<repo>/collaborators/<login>/permission`, its `permission`; a 404 is none) and whether they're in each team `CODEOWNERS` names (`gh api orgs/<org>/teams/<team>/memberships/<login>`, `active`). Only when every changed file has owners and one of them approved `head_sha` itself does obid approve it now, by itself: its approval stands next to theirs. An approval counts as the person's last approving, changes-requesting or dismissed review; only from someone with `write` access or more (GitHub ignores the others' code-owner approvals too); never from an account GitHub marks as a bot, never one whose words carry Oby's marker `by Oby:` in any case (every review obid posts carries it: this approval, Oby's verdict on the owner's own pull request, the reviewer account's approval), and never the owner's own login, which obid posts with. A team counts only of the repository's own organization, and logins match in any case. Anything short of that (no `CODEOWNERS`, a file with no owners, a list GitHub can't give in full, an approval of an older commit, a `CODEOWNERS` pattern with `!`, `[`, `]` or `\`, or `gh` failing) and the owner is asked, as below. The decision's `uses` counts the approvals it let obid post.
- **Approving it** (by itself, as above, or on the owner's tap, below): obid reads the pull request (`gh pr view <pr> -R <repo> --json state,headRefOid,baseRefName,url`) and goes on only while it is open, it is `repo`'s own (its URL is `https://github.com/<repo>/pull/<pr>`), it goes into `base_branch` (the branch the review compared it with) and its head is still `head_sha`, and only when the owner's login can push to `repo` (`gh api repos/<repo> --jq .permissions.push`: an approval without that wouldn't count); then, once more checked that obid is still in its Sphere and the request hasn't expired, the same post the reviewer account's reviews use, as the owner (`gh api -X POST repos/<repo>/pulls/<pr>/reviews -f commit_id=<head_sha> -f event=APPROVE -F body=@<file>`), the commit named so a later push isn't approved by it. The body is obid's own words, `Approved by Oby: its review of <12 hex> passed.`, never a word of the request, and passes the secret scan first. The job's `outgoing` lists it (`pullRequestApproval`). Right after, obid reads the pull request again (`gh pr view`, and for an approval next to code owners', their approvals as above): when its head moved, or the code owners' approvals no longer hold, obid dismisses its own approval at once (`gh api -X PUT repos/<repo>/pulls/<pr>/reviews/<id>/dismissals -f message=… -f event=DISMISS`, the message obid's own, `Dismissed by Oby: …`), lists that too (`pullRequestApprovalDismissal`) and the result says `unable`. A read that `gh` fails is tried once more before anything is dismissed; one that fails twice is dismissed too. When GitHub doesn't let obid dismiss it (a branch rule that keeps the login from dismissing reviews), a `failed` item tells the owner to remove it: id `approval-dismissal-<correlationId>`, title `Remove Oby's approval of <repo> pull request #<pr> on GitHub`, its text the approval's URL and "remove this approval on GitHub", its one answer `Dismiss`, which only closes it. Otherwise the result says `host_review: "approved"`; when anything stops it (no `gh`, the pull request moved on, closed or goes into another branch, the login can't push there, GitHub refused it, the scan), nothing is approved and the result says `unable`. A request whose exchange was settled by a revoke meanwhile approves nothing either.
- **Otherwise**, the result says `host_review: "asked"`, and a `confirm` item asks the owner, one per exchange:

```json
{"id": "obi-approve-5f0e8c1a-…", "kind": "confirm", "job": "",
 "title": "Approve ernesto's pull request #12 on obi-ai-bot/tetrix at 6d20146 on GitHub, as you",
 "text": "Your Oby's review of obi-ai-bot/tetrix pull request #12 at 6d20146 passed. ernesto's Oby (obi-ernesto) asks you to approve it on GitHub, as you, so it can merge. Your Confirm approves this commit only, for this request.",
 "options": ["Confirm", "Cancel"],
 "details": ["Approve ernesto's pull request #12 on obi-ai-bot/tetrix at 6d20146 on GitHub, as you.", "Don't approve it: nothing is posted on GitHub."],
 "confirm": {"action": "approve_on_host", "target": "obi-approve-5f0e8c1a-…",
             "payload": {"correlationId": "5f0e8c1a-…", "from": "obi-ernesto", "fromOwner": "ernesto",
                         "repo": "obi-ai-bot/tetrix", "pr": 12, "baseBranch": "dev", "headSha": "6d20146f366b9fac8907b5066c30ee39aaec09b3",
                         "expiresAt": "2026-10-24T14:00:10Z", "job": "9f08fd10"}}}
```

  Its `Confirm` is the owner's tap, as every Confirm is ([inbox items](#post-v1inboxidanswer), #776): a registered device signs `oby-confirm\n<item id>\n<title>\n<signedAt>`, so the tap names this exchange (the item's id) and this commit (its title), within two minutes, used once. Then obid checks it again as the spec's rule does, against the exchange as it keeps it (that exchange, the commit its request named, the request still open, obid still in its Sphere, the device's signature made no more than two minutes before, nor more than 30 seconds after, by obid's clock) and approves it as above; the claim is on disk before GitHub is asked, so two at once, or a stop mid-post, approve once. A Confirm without the device's signature, or with one that doesn't hold (another item's, stale, used), is `403` and the item stays open. An approval that fails, or that obid dismissed right after posting it, closes the item with `It couldn't happen: No approval stands: <why>.` and answers `502`; a request that lapsed answers `409` (`That request lapsed: nothing was approved.`). `Cancel` or `{"done": true}` approves nothing. The yes lapses with the request: at its `expiresAt` the clock closes the item (`It lapsed when the request expired: nothing was approved.`), and a revoke closes every one (`This Oby left its Obysphere: nothing was approved.`). Oby's brain can't confirm it: a `confirm` item never confirms another. An `obiRequest` ask obid made before this (`Accept`, `Accept, and remember for this repo`, `Decline`) approves nothing on an answer: `Accept` turns it into this `confirm` item, the same id, and is refused (`403`).

The standing permission is asked for through `POST /v1/obid/decisions` ([remembered decisions](#obid-only-remembered-decisions)); no answer to an ask keeps one.

A request without `approve_on_host`, a review that isn't `approved`, or one that failed gets no `host_review`, and nothing is approved anywhere.
