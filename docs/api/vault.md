### obid only: the vault

A connection receives a credential from the same checked snapshot already learned by obid's
redactors. If Keychain Access changes an item between checks, the broker never gets a newer
credential from an unchecked second read. An unreadable store still refuses the request.


The owner's secrets for connections they make (#457), kept and used as the Swift runner keeps them (Engine/Vault.swift):

- **Where.** `home/vault/secrets.json`, everywhere, a Mac included. `obid` never reads or writes the Keychain for its own secrets (#1679, the owner's word of 2026-10-31), so it makes macOS ask for no password, on a start or an upgrade. Before 2026-10-30, on a Mac whose `obid` ran in the Mac app's runner home (`~/Library/Application Support/Oby/Runner`), the vault was the Swift runner's own Keychain items (service `com.deskree.oby.runner.vault`); from 2026-10-30 to #1679 an `obid` starting there with no `secrets.json` copied them into the file, and macOS asked the owner's password once per item while `obid` answered nothing. Those items now stay in the Keychain, unread: a connection whose login only they held is made again once. Once obid answers, it lists their names (`security dump-keychain`, attributes only: no value, no prompt, 10 seconds at most) and logs each one the file doesn't hold, with how to add it back (`… is still in the Keychain, where obid no longer reads its secrets, and not in the vault's file: add it again with obid vault --config <path> add NAME`; Tetrix's: connect Tetrix again). Tetrix says so itself: a saved Tetrix connection whose `oby.tetrix.access` isn't in the file is no longer connected, and `tetrix.error` (`GET /v1/status`, the `tetrix` event) is `Oby's Tetrix login isn't in its vault any more: connect Tetrix again.`, or, once obid found that item still in the Keychain, `Connect Tetrix again: Oby no longer reads its logins from your Keychain, so the one kept there didn't carry over.`, until the owner connects it. The file is `home/vault/secrets.json` (`{"secrets": {"<name>": "<value>"}}`) as the Swift runner's file vault keeps it: a folder only `obid`'s user may open (0700), the file readable only by that user (0600), each save a new file written 0600 and renamed into place under a lock (`home/vault/.lock`), so two `obid vault add` runs at once each keep their secret. No file is an empty vault, which everything reads.
- **Putting secrets in.** On the machine, as `obid`'s user: `obid vault --config <path> add NAME` takes the value on stdin (typed without echo at a terminal, with echo back if the command is stopped, or piped in), `obid vault --config <path> list` prints the names, `obid vault --config <path> remove NAME` removes one. A value is never an argument (`add NAME VALUE` is refused with the usage line) or an environment variable, and nothing the command prints holds one. A name is 1 to 64 letters, digits, `.`, `_` or `-`, starting with a letter or digit; a value is 8 bytes to 64 KB, with the whitespace around a paste dropped. A common word or a weak pattern (`postgres`, `changeme`, `00000000`: fewer than 6 different characters, a common word with or without digits after it, or under 50 bits by its length and kinds of characters) is refused, since every push holding it would be refused and every answer would have it taken out. No endpoint takes or returns a value.
- **While obid runs.** `obid` reads the vault at start and again whenever it changed (the file's inode, size or time), so a secret `obid vault add` puts there is taken out from then on, without a restart. A removed secret stops being taken out. At start the log says where the vault's file is and how many secrets it holds, never a name or a value.
- **Answers.** Every `/v1` answer has the vault's secrets taken out of every string, keys too, plain and in every encoded form `obid` knows (base64, standard or URL-safe, at any offset in a longer run, or wrapped over lines as GNU base64 writes it, also behind a diff's `+` or a quote's `> ` and with the line breaks written as `\n` inside one JSON string; hex in either case; URL-encoded, a form's `+` for spaces too), each as `[vault: <name>]`; a string that still holds one some other way becomes that marker whole. An answer with no secret in it goes as it was, byte for byte. The event stream and `/wait` are scrubbed a frame at a time. When the vault can't be read, a request isn't carried out: nothing reaches an agent, the brain, a plug-in or another Oby (no job is made, no words join the conversation). The exceptions only stop work and send nothing anywhere: `POST /v1/stop-all`, `POST /v1/jobs/{id}/stop`, `POST /v1/jobs/{id}/dismiss`, and `POST /v1/jobs/{id}/permission` denying without words (`message` absent, null or blank); those are carried out, so the owner can always stop work. Either way the answer is then `503` with `{"error": "The vault can't be read, so obid answers nothing until it's fixed: <why>"}`, `<why>` naming the file or folder, never a value, and what to do (`run chmod 600 on it`, `move it aside, then add the secrets again with obid vault …`). Two answers start no work and come even then: `GET /v1/status`, which says why in `vaultProblem` (`the vault can't be read: <why>`, left out while it reads), and, once obid has read the vault at least once, `GET /v1/events`, scrubbed of the secrets it last read (before any read it's `503` like the rest, since nothing could be taken out of it). An open event stream goes on the same way. A check's bundle (`application/octet-stream`) goes as it is.
- **Agents.** Every prompt `obid` hands an agent's turn (a job's task, the owner's words for it, a publish-fix round, an Obi-to-Obi review) has the vault's secrets taken out the same way, and so do the files an Obi-to-Obi review hands its agent (the request and the diff in `.obi/inputs/`). When the vault can't be read, the agent gets nothing: the job fails with `The vault can't be read, so obid gave the agent nothing: <why> Once it's fixed, tell the job to go on.`
- **What goes out.** The publish gate and every scan (`crate::scan`: publishing, Obi-to-Obi replies and review results) look for the vault's secrets in those same forms, in every file a push sends, read whole (base64 wrapped over lines joined), and in each commit message; when the vault can't be read, the scan can't run and nothing goes out (`publishError` `Not published: the secret scan couldn't run (the vault can't be read: …).`).

### obid only: secrets a check declares

A repository says which secrets its check needs in `secretspec.toml` at its root ([SecretSpec](https://secretspec.dev)), names only, never values (oby-plan E1, "Secrets you declare"). The owner keeps each value in their vault ([obid only: the vault](#obid-only-the-vault)) as `check.<NAME>`: `obid vault --config <path> add check.STRIPE_TEST_KEY`, the value on stdin. Only names starting `check.` ever reach a check, so a connection's secret or obid's own never does.

- **Which names.** The keys of `[profiles.default]` (`NAME = { description = "…" }`, one inline table on one line) and the tables `[profiles.default.NAME]`, at most 32. A name is an environment variable's (letters, digits and `_`, not starting with a digit, at most 64), never one obid sets for every check (`PATH`, `HOME`, `TMPDIR`, `GH_CONFIG_DIR`, …) or starting `GIT_`, `LD_`, `DYLD_`, `OBY_`, `OBID_`, `OBI_`, `CLAUDE`, `ANTHROPIC_`, `CODEX_`, `SSH_` or `BASH_FUNC_`. Other profiles, defaults and every other part of the file are left to the repository. A file obid can't read this way (a multi-line string, a name twice, a line it can't read in that profile) gives the check nothing, and says why.
- **From the base branch only.** The file is read from the job's base branch (its `base`, else the repository's `defaultBranch`) as obid's own clone has it (`refs/remotes/origin/<base>`, in a git folder every sandbox reads only), never from the worktree or the job's own branch: a commit that adds a name, the agent's or anyone's, changes nothing until it is merged.
- **Only into the check.** The values go into the check process's environment, after everything obid sets there, and nowhere else: never an agent's environment, prompt, transcript, a message, the chain, a log line, an answer or a pull request. The log says how many of the declared names the check got, never a name's value.
- **Taken out at once.** Each value, plain, JSON-escaped (`\"`, `\\`, `/` as `\/`, `\uXXXX` in either case) and in every encoded form obid knows (as for the vault), is taken out of what the check printed before obid keeps any of it (`check.log`, the job's `checks` and their failing tests, the agent's next prompt), as `[check secret: <NAME>]`; when only the end of a long output was kept, its first line, which a value may have been cut in, goes too. This catches a value a check prints by accident, not one its code turns into something else on purpose: that is why only the owner's own code gets values (below).
- **In a checkout of its own.** A check that gets values runs in a checkout obid makes from the commit the gate passed (`git worktree add` in obid's clone at `home/checks/<job>-<id>`, the job's commits since its base copied into the checkout's own object folder as one pack), with a temporary folder (`HOME`, `TMPDIR`) of its own, neither anywhere the job's sandbox can write, both removed after it. What the check writes never reaches the job; what the job left outside its commits (a file left uncommitted or hidden by a `.gitignore`, a rewrite after the gate) never reaches the check. A check without values runs in the job's worktree as before. Its builds start without the job's caches.
- **The threat model.** The values protect against other people's code reaching the check: teammates', pull request authors', received work, and content that steered the agent. An agent that never read foreign input counts as the owner's own, as the owner running the tests on their own laptop would. Commit metadata can't tell where a tree came from, so obid controls the inputs, and **fails closed**: a job is eligible only if every input it ever received came from an allowlisted channel. The channels:
  - **The owner's own words typed in Oby's apps**, signed by the app ("Words the owner typed", below): a job started through `POST /v1/jobs`, the owner's words sent to it (`POST /v1/jobs/{id}/messages`, a permission's words), and what Oby's conversation plans from them while it's clean. Anything else holding obid's token (oby-mcp's `dispatch`, `message` and `ask`, a script, an agent, an older app or one that doesn't sign, such as the Watch) sends words that aren't: a job they start, and one they reach, gets nothing. Not a job an event, a routine, the Lead or an inbox offer started, nor words from an event or a Confirm of what Oby proposed (obid's own Try again aside).
  - **Oby's conversation, while clean.** Each conversation keeps the first thing it read or heard that isn't on this list, for good (kept in its file; one kept before this, or one obid doesn't keep, counts as marked). It stays clean on the owner's signed words, Oby's own answers, its room's files outside the repositories' checkouts and attachments, its own task list, Oby's tools that answer in obid's words (`oby_dispatch`, `oby_offer`, `oby_tasks`, `oby_routine`, `oby_check_in`, `oby_artifact`), the ones that name a job that is clean throughout (`oby_tell_job`, `oby_stop_job`, `oby_continue_job`, `oby_archive_job`, `oby_delete_job`, `oby_change_job`), `oby_jobs` while every job it lists is, and a clean job's end. Anything else marks it: words no app signed, turns its client wrote, attachments, a recap or check-in, a routine's run, `oby_job`, the inbox, past conversations, a command, the web, a helper, and any tool it doesn't know. A job a marked conversation starts is someone else's code from the start and runs in a clone apart; its words (a tell, a continue, a permission's no) make the job they reach someone else's.
  - **The text of an issue or pull request the owner alone wrote**: its body, title and every comment, edit, rename, review and review comment, every list read whole, read as the job starts and again at its check (what's deleted in between still reached it). What obid posts under the owner's login is signed `by Oby:` and never counts as the owner's, but a pull request's own description that obid wrote only for jobs that are clean throughout (the jobs whose record says they opened or described it).
  - **The base repository's code.**
  - **Tool calls of kinds obid knows are safe**: a file read, write, edit or search, a command inside the job's sandbox, its to-do list, obid's own question to the owner.

  Anything else, a channel nobody listed included, makes the job someone else's code the moment it arrives, and marks the owner's clone: a vendor's own web search or fetch, any MCP tool or resource, a helper agent, any tool kind an agent adds later or obid doesn't parse (Claude Code's unparsed blocks, Codex's helper threads and unknown items, Cursor's unknown kinds and its `search`, which its web search reports as too), and egress to its vendor's other hosts or to a host that serves anyone's source code (2). Egress to any other site but the tool's API hosts, Codex's `chatgpt.com` (which takes the check's values away instead) and the default registries takes the values away too, and marks the owner's clone, but as a reach (the job's `reached`), not as someone else's code: it needs one review, not two; its check doesn't stand for the Mac's (merging.md MERGING-31, the owner's decision of 2026-11-06, "Split it"). Being given an MCP server's tools at launch (Tetrix's) doesn't (MERGING-30). A check gets the owner's values only when all of these hold too, none otherwise:
  1. **The machine is a Mac.** On Linux a job's agent still has a network of its own until oby#616, so it could fetch anyone's code itself (oby-plan E1: macOS only until then). On a Mac every agent's only way off the machine is obid's egress proxy, and every turn's sandbox watcher kills what the turn started, a process that called `setsid` included, when it ends.
  2. **obid's clone holds only what obid knows is the owner's.** A clone is made with only the default branch (`git clone --single-branch`; it carries `obid.narrow`); a clone made before holds every branch of its remote and gives no values until it's moved aside and made again. Only the owner's own jobs write to it: a job that's `untrusted` or someone else's code when it's made keeps to a clone apart (`home/apart/clones/<repo>`, its follow-ups too), and a review another Oby asks for to its own (`home/received/clones/<repo>`). Anything else comes into the owner's clone only by obid's own fetch: a job's base, a pull request's head. One that isn't a reviewed branch (3) and whose commits aren't all in obid's record of the owner's jobs (4) notes it in the clone's own settings (`obid.foreign`, which no sandbox can write), as does a job there that turns someone else's code; from then on no check in that repository gets values. An agent can't fetch anything itself: it has no code host's login (an empty `GH_CONFIG_DIR`, an invalid push URL), and the proxy lets its tool's own services through and decides every other site. A job's reach to its own tool's API hosts on port 443 (`egress::tools_api`: Claude Code's `api.anthropic.com`, `statsig.anthropic.com` and `console.anthropic.com`; Codex's `api.openai.com` and `auth.openai.com`; Cursor's `api2.cursor.sh`, `api3.cursor.sh` and `api4.cursor.sh`), by the CLI or by anything in its box, leaves the job the owner's, and so does being given Tetrix's tools before any call; Codex's `chatgpt.com` doesn't mark it either, but its own check gets no values from then on, and where its base declares some, its merge is the owner's, as for any check that went without them (`Job::check_withheld`): that job's only, never its follow-ups', and its conversation isn't marked for reading it (the owner's decisions of 2026-11-06 and 2026-11-08, merging.md MERGING-30). The job is marked `reached` for any site the proxy lets through but its tool's API hosts, Codex's `chatgpt.com` and the default registries (`egress::REGISTRIES`: npm, Yarn, Maven Central, Gradle's plugins and services, CocoaPods' CDN), which serve only published, immutable versions on an edge that answers only the host the TLS hello named. Its vendor's other hosts, and every other tool's vendor hosts but that tool's API hosts, on any port (`egress::vendor_page`), make it someone else's code: they serve pages people write (shared chats, forums), so its pull request needs two reviews (merging.md MERGING-14 and MERGING-31). Another tool's API host is a reach. The proxy reads that name, not the HTTP `Host` inside the tunnel, so a registry whose edge serves whichever of its sites `Host` names (`egress::ROUTED_BY_HOST`: Fastly's PyPI, crates.io and Rust's toolchains, RubyGems; Google's Go checksum database; the Go module proxy, which serves any public repository's commit by its path, is a code host: two reviews) could carry anyone's code, and the proxy can't tell such a registry from another site on its edge: those no longer go through by default, and when a rule or an owner's card lets one through, the job is marked `reached`, as for any other site: one review. A `reached` job's check, and every check in its clone, gets no values, and no follow-up counts its commits as the owner's (4), but it needs one review, not two; its check, run without the values, doesn't stand for the Mac's (MERGING-31). A reach to a host that serves anyone's source code (`secretspec::site_is_code_host`: GitHub's, GitLab's, Bitbucket's, Codeberg's, their pages and jsDelivr, each with its subdomains; never an artifact registry such as `ghcr.io`) makes the job someone else's code instead, two reviews (MERGING-14). A follow-up of a `reached` job marks the owner's clone again as it starts. The job turns someone else's code for every channel that brings content past the proxy: its vendor's own web search or fetch, or any MCP server's answer (obid's connected apps, Tetrix's), as a tool call in its turn; a connected app's answer through obid's broker; the context obid gives it in `.obi/context` (Tetrix's, teammates' pull requests). A marked owner's clone whose base declares a `secretspec.toml` is made again before the next job uses it, once no job of the repository runs in it: the old one moves to `home/marked/<when>` with the jobs whose worktrees belong to it, and their follow-ups; one whose base declares none stays as it is, marked (PUBLISHING-21). obid's start removes each `home/marked/<when>` no work lives in: no worktree's `.git` file points into it (every job's and every one in `home/worktrees`), git's record in it names no worktree still there, and no job keeps to it that is queued, running, has a worktree, or isn't merged, dismissed or not; a job file or `.git` that doesn't read keeps them all (PUBLISHING-21).
  3. **The base is reviewed, and so is the default branch:** a branch the repository lets in only through a pull request with at least one approving review that a later push can't slip past, that no one can bypass, as GitHub says through obid's own `gh`: an `active` ruleset whose `pull_request` rule has `required_approving_review_count` 1 or more and `require_last_push_approval` or `dismiss_stale_reviews_on_push`, that the login can't bypass (`current_user_can_bypass` `never`, which counts its teams), and whose `bypass_actors` (obid's login must be able to read them) is empty or holds only teams with no members (a break-glass team kept empty), or classic protection with `required_approving_review_count` 1 or more and `require_last_push_approval` or `dismiss_stale_reviews`, `enforce_admins` on, and no bypass allowance for the login, any team or any app. Never an `oby/` branch or the job's own branch. The repository's default branch, in every clone, must be one too.
  4. **Defence in depth:** every commit between that base and the commit is in obid's own record of what the job (and the follow-ups it continues) made, kept in the job's file in obid's home: after each of an owner's job's turns, the commits it added, each made then (author and committer the same, both no more than 5 minutes before the turn began) and none with the same change (`git patch-id --stable`) as a commit on any other branch the clone has, other jobs' own included; obid's rebase of recorded commits; and its "work left uncommitted" commit. A turn that brings in a commit made elsewhere makes the job someone else's code.
  5. **The job is the owner's:** started from the owner's own words, signed, through the jobs API or a clean conversation, and not another Oby's review, not a follow-up of a job that got none (carried to every follow-up), not `untrusted`, and not one that works from an issue or pull request anyone but the owner wrote in (members of the owner's organisation still count as the owner for what a conversation trusts, not for this). A job that's someone else's code (one of these, or marked above) marks the owner's clone; a job that's only not the owner's own words (a brain's, an event's) gets no values but leaves the clone as it is, and obid records its commits as it does the owner's.

  Its output starts `obid: secretspec.toml on <base> declares <names>; obid gave this check none of its owner's secrets: <why>.` Out of scope, and said so: a package anyone may publish to a registry the job installs from (the owner's own tests would install the same), and foreign code an agent writes out, as its own new commit, from what its model already knows.
- **What's missing.** A declared name the vault doesn't have as `check.<NAME>` is left unset, and the check's output starts with a line saying which (`obid: secretspec.toml declares X, which the owner's vault doesn't have as check.X: obid left it unset.`). When the vault can't be read, the check gets none of them and says so.
- **Words the owner typed.** Oby's Mac, iPhone and Android apps sign every request but a read (`GET`, `HEAD`) with the device's approval key, the one a Confirm uses (it signs on the owner's click, asking for no Touch ID or Face ID), in the header `X-Oby-Words: <device> <signedAt> <signature>`: ECDSA P-256 with SHA-256, DER, base64, over `"oby-words\n<METHOD>\n<path>\n<SHA-256 of the body, hex>\n<signedAt>"`, the path from `/v1/` on, without its query, and an empty body's hash when it has none. obid takes the words as the owner's own, for these secrets only, when the device is registered, the signature is its key's over exactly that request, `signedAt` (to the second, or to the millisecond as the apps sign, so two of the same request in one second differ) is within two minutes, and that signature was never used before (kept with the approvals, ten minutes). The Electron app signs in main, with its device key, only right after a real Enter or click main saw itself (one request each, within 2 seconds), only words the owner's own keystroke or click held, and only its own words requests in exactly the shape it sends them: `POST /v1/plans`, `POST /v1/jobs/{id}/messages`, `PATCH /v1/jobs/{id}` (a title), `POST /v1/inbox/{id}/answer`, `POST /v1/jobs/{id}/permission`, `POST /v1/spheres/{sphere}/room`, `POST /v1/obid/sphere/peers/{owner}/ask`, `POST /v1/accounts/{id}/background` (a yes), `POST /v1/jobs/{id}/mode` and `PUT /v1/settings/permissions` (exactly `{mode}`, by the mode's label); a body with any other key, or with working folders the owner didn't choose in the app's own dialog that run, goes unsigned (docs/contracts/signed-words.md). A trusted native select change holds its chosen option's text for Default mode, under the same two-second, one-input limit. A click on the Default mode menu signs within the two-second window, once per input. A change made only with the keyboard, or after the window, goes unsigned; obid will refuse a widening mode change with words explaining why (SIGN-5). The gateway and the phone relay pass the header on. It decides nothing else: a request without it does everything it did, and only its job, its follow-up or its conversation gets no values.
