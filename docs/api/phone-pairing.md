## LAN gateway (#284)

A Mac runner (below) keeps its API on loopback and starts one more listener, the gateway, on every interface at `:8810` (`OBY_GATEWAY_PORT`), advertised over Bonjour as `_oby._tcp` under the Mac's name so the iPhone finds it without an address. A tailnet runner has `tailscale serve` instead and binds nothing else. On the local network the gateway is plain HTTP plus a device token; away from home the Mac's tunnel carries the same requests.

- **Pairing.** The Mac app makes an invitation on the loopback API, with the runner's own token: `POST /v1/pairing/invite` with `{"url": "https://oby-….tetrix.pro", "name": "<the Mac's name>", "hostname": "oby-….tetrix.pro"}` answers `{"url", "name", "hostname", "link", "secret", "code", "expiresAt"}`: a high-entropy one-time `secret` (in the QR code, with the `url` and the `link`), a six-digit `code` to type instead, both good for two minutes and once; five wrong tries end the invitation. These endpoints exist on a Mac runner only and are never reachable through the gateway: nothing that reaches the gateway can mint an invitation, and no file on the Mac stands for the app. Settings › Remote access › Pair a device advertises a route the phone can reach over HTTPS: Remote access's hostname while it's on, else the gateway as `tailscale serve` publishes it on the tailnet (the app runs only `tailscale serve status --json`, from `/usr/local/bin/tailscale`, `/opt/homebrew/bin/tailscale` or `/Applications/Tailscale.app/Contents/MacOS/Tailscale` (with `TAILSCALE_BE_CLI=1`, so the app's binary acts as the CLI), its output capped at 1 MiB, and takes the `host:port` whose `/` proxies, or whose TLS-ending TCP forward goes, to `127.0.0.1:<the gateway's port>`; when any Funnel `host:port`, in the background config or a foreground session's, reaches the gateway on any path, there's no tailnet route and the screen says to turn Funnel off first), then `{"url": "https://mac.tail0000.ts.net:8443", "hostname": "mac.tail0000.ts.net:8443"}`. With both, Remote access is chosen and the user can pick the tailnet instead; the screen says which route the QR uses. With no `gateway` in obid's configuration, neither works, and it says so. With neither, it says to turn on Remote access or run `tailscale serve --bg --https=8443 http://127.0.0.1:8810`.
- **Redeeming.** The phone sends `POST /v1/pairing` to the gateway with `{"credential": "<the secret or the code>", "name": "<the phone's name>"}` and gets `{"token": "<device token>", "deviceID": "…", "expiresAt": "…", "link": {"name": "<the Mac's name>", "hostname": "oby-….tetrix.pro"}}`. The token is shown once: the runner keeps only its SHA-256 digest, with the device's name, in `gateway-devices.json`, and the phone keeps it in its keychain. Tokens last 30 days from their last use (PAIRING-6): a request with a token that has under 15 days left gives it 30 more, saved in `gateway-devices.json`, and `expiresAt` in Paired devices moves with it; a request refused for coming the wrong way (a relay-paired token unsealed, or a listener-paired one through a relay) doesn't extend it; one unused for 30 days stops working. A device not paired through the Obysphere (no relay: the local network, Remote access, the tailnet) stops at 90 days from pairing (its `created`) however it was used, and must pair again (PAIRING-7): the slide never takes it past day 90, and its `expiresAt` in Paired devices is never later. The `expiresAt` redeem answered is only the pairing-time date. The `link` lets a phone that typed the code link the Mac as the QR code would.
- **Paired devices.** `GET /v1/pairing/devices` on the loopback API lists them, `[{"id", "name", "created", "expiresAt"}]`, never a token or digest; `DELETE /v1/pairing/devices/{id}` revokes one (`204`), and the phone must pair again; on `obid` its FCM push tokens and its iPhone relay registration go with it (`POST /v1/notifications`). Settings › Remote access › Paired devices on the Mac shows this list with Revoke.
- **Every other gateway request** sends `Authorization: Bearer <device token>`. Besides `Content-Type` and `X-Oby-Words`, the gateway forwards the request's `Idempotency-Key` (obid only, R02-04), so a phone's retried `POST /v1/jobs` gets its first job back (docs/contracts/receipts.md). The gateway checks the method and path against an explicit allowlist (Runner/Routes.swift: exactly the routes the iPhone uses, and the Watch through it) before forwarding to the loopback API with the runner's own token. A route not on the list is `404` whatever the token; a missing, wrong, expired or revoked token is `401`. Adding a route to the loopback API doesn't open it through the gateway: that's a change to the list, on purpose. Off the list: `/v1/checks/…` and `/v1/agent/…` (the Mac's own and an agent's own calls, over loopback), `/v1/connections…` (managed on the Mac) and the pairing endpoints. `PATCH /v1/accounts/{id}` and `PUT /v1/settings/jobs` are on it (obid, the owner's decision of 2026-11-01), so the iPhone's Settings › Agents changes an agent's model and efforts and the account new tasks go to, as the Electron app's does; the paired phone is the owner's own app, so it may send that route's other keys too (`maxRunning`, `accountFailover`, `limits`), each within obid's own bounds.
- **Scrubbing.** Before an answer or an event leaves the Mac, the gateway nulls every `session` (an agent's session id, which resumes its conversation) and every `resumeCommand` (which names it, LANES-9), replaces the accounts' home paths with `[home]` in every string, and runs the vault's redaction over the text (`[vault: name]`), the same that cleans the runner's logs. Event streams are scrubbed a frame at a time, so a secret split across chunks never goes out in pieces.

- **Base URL:** `https://<the runner's tailnet name>:8443` (set in the app), or `http://127.0.0.1:7777` for the runner on the Mac itself (below). Everything is under `/v1`.
- The runner listens on `127.0.0.1:7777` only. `tailscale serve --https=8443` publishes it on the tailnet with a real HTTPS certificate, so iOS needs no exceptions, and nothing is reachable from the internet. Port 443 on tetrix-lab belongs to the Tetrix stack's own proxy, so Oby uses 8443, one of the ports Tailscale serves HTTPS on.
- **Who you are:** `tailscale serve` adds `Tailscale-User-Login` to every request. The runner answers only its owner's login (set when it's installed) and returns `401` to anyone else. The app sends no token and stores no secret for this. The one exception is `/v1/agent/…`, which agents call from their sandbox on the runner itself (`oby-check apple`, Apple check below): those requests carry their job's token instead, `Authorization: Bearer <token>`, and answer nothing else.
- **JSON** everywhere, camelCase keys, dates as ISO 8601 strings (`2026-10-09T21:43:30Z`). Errors are `{"error": "One line a person can read."}` with a 4xx or 5xx status. obid's sign-in routes add `"reason"`, a stable word an app shows its own sentence for ([Sign-in reasons](#obid-only-sign-in-reasons)); an app that doesn't know a reason shows its own plain sentence.
- **No vault secret** in an answer or an event: every string has the vault's secrets, plain or encoded, taken out. When the runner can't read its vault, answers are `503` with the reason, and events aren't sent.
- **The Apple Watch** reaches obid only through its iPhone: the Watch's own API, the Swift runner's, is gone ([Routes obid does not serve](#routes-obid-does-not-serve)).

### obid only: the gateway

obid serves the LAN gateway's pairing and forwarding (LAN gateway (#284), above) as the Swift runner does, with these differences (`core/crates/obid/src/gateway.rs`, #446):

- **Where it listens.** Only where the configuration's `gateway` says, an address on `127.0.0.1` like `127.0.0.1:8810`; with no `gateway` there's none. Any other address is refused when obid starts (`gateway is "0.0.0.0:8810": it must be an address on 127.0.0.1 with a port…`), and a busy one doesn't stop obid: it serves the API without a gateway, logs `no gateway: can't listen on 127.0.0.1:8810: …`, and `GET /v1/status` says `"gateway": {"state": "down", "address": "127.0.0.1:8810", "detail": "can't listen on 127.0.0.1:8810: Address already in use (os error 48)"}` until it starts again (`{"state": "listening", "address": …}` while it listens; the key is left out with no `gateway` configured). Once it listens, obid prints a second line on stdout after its first, `obid gateway listening on http://127.0.0.1:8810`. It isn't advertised over Bonjour: phones reach it through the owner's tailnet, with `tailscale serve --bg --https=8443 http://127.0.0.1:8810` (never `tailscale funnel`, which would put it on the internet), and pair at `https://<the Mac's tailnet name>:8443`.
- **Invitations** come from `POST /v1/pairing/invite` on obid's API with its API token, as above. The Mac app adds `"approval": {"device", "signedAt", "signature"}`, its registered key's signature (ECDSA P-256 with SHA-256, DER, base64) over `"oby-pair-invite\n<signedAt>"`, within 2 minutes, once, made on the owner's click: only the phone such an invitation pairs may add its publishing key (`POST /v1/devices`). One without an `approval` pairs a phone that can read and answer through the gateway but approves nothing; an `approval` that doesn't hold is `403` and makes nothing. `name` defaults to the machine's name and `hostname` to the `url`'s host and port. A Tailscale hostname is a link's `hostname` as it is, port included (`mac.tail0000.ts.net:8443`). While obid is a member of an Obysphere, every invitation is one through it too, and `url` is optional ([the phone relay](#obid-only-the-phone-relay), below); with no Obysphere, an invitation needs a `url`, and without one it's `409` (`Join or host an Obysphere first (Settings › Obysphere).`).
- **Paired devices** are kept, by their token's SHA-256 digest only, in `home/gateway-devices.json` (0600), not in `devices.json`: a phone paired with the Swift runner pairs again with obid.
- **Forwarding** happens inside obid: an allowed request with a paired device's token goes to obid's own API router with obid's API token and a loopback `Host`, carrying only its method, path, query, body (at most 4 MiB) and `Content-Type`. The answer has passed through the API's own layers, so the vault's secrets are already out; the gateway then nulls `session` and `resumeCommand` and puts `[home]` for the accounts' `configDir` paths and for `home/logins` (where a job's copy of its login lives), as above, and sends only the status, `Content-Type`, `Cache-Control`, and an artifact's `Content-Security-Policy`, `X-Content-Type-Options` and `Referrer-Policy`. An answer that isn't text (not `text/…`, JSON or `…+json`: an artifact's image or PDF) goes byte for byte, as the API's own layer sends it. An answer of known length goes whole; any other (the event stream, `GET /v1/jobs/{id}/wait`) goes chunk by chunk as obid sends it, so a wait's first space reaches the phone at once. A stream ends at its first chunk after its device is revoked.
- **Redeeming** takes only what a phone sends: a request with an `Origin` (a browser) is `403` and one that isn't `application/json` is `415`, before it counts as a try, so a web page can't use an invitation up. A device's name keeps no control characters.
- **The allowlist** is Runner/Routes.swift's, plus `GET /v1/conversations`, `PATCH` and `DELETE /v1/conversations/{id}` (obid only: conversations), `GET /v1/obid/sphere` and `GET /v1/obid/sphere/members` (the iPhone's side panel, docs/contracts/ios-new-oby.md), `GET /v1/obid/sphere/peers/{owner}` (obid only: a member's thread), `GET /v1/artifacts`, `GET /v1/artifacts/{id}` and `GET /v1/artifacts/{id}/{version}/{*path}` at any depth (obid only: artifacts), `GET /v1/jobs/{id}/report`, `GET /v1/jobs/{id}/transcript`, `GET /v1/jobs/{id}/transcript/{n}`, `POST /v1/jobs/{id}/delete` (the apps' Delete task, which asks before losing work), `GET /v1/github/work`, `POST /v1/github/work/refresh` and `POST /v1/github/work/{id}/start` (obid only: GitHub work), and `GET /v1/repos` (obid only: repositories). Routes obid doesn't serve answer `404` through the gateway as they do on loopback ([Routes obid does not serve](#routes-obid-does-not-serve)).

### obid only: the phone relay

A phone reaches obid through its owner's own Obysphere (the obi-sphere spec, `sphere-api.md` section 9), so the Mac opens no port and needs no tunnel: the Sphere passes frames between them, and every frame is an envelope the phone and obid seal end to end (#1277; `core/crates/obid/src/relay/`). Deskree's Obysphere relays for its members only; a Sphere anyone hosts works the same way.

- **When.** While obid is a member of an Obysphere (`GET /v1/obid/sphere` says `joined`) and at least one phone is paired through it or invited to, obid keeps one WebSocket on `GET <the Sphere's URL>/v0.1/relay/{relay}` with its member Obi's access token, and makes the Sphere's list of that relay's devices the paired ones: when the socket opens, when a phone is invited, paired or forgotten, and every minute (an invitation or a device whose time is up is taken off). After a drop it opens again after 1 second, doubling to 60, or when the Sphere's `Retry-After` says. 45 seconds before its token ends it opens a new socket with a new token, which replaces the old one (the Sphere closes that one with `4003`) and the phones see nothing: first a `pong` on the old socket says the Sphere has had all obid sent on it, and what the old socket still holds is read before anything on the new one, so nothing is lost or reordered either way. Once obid leaves its Sphere, or learns its membership was revoked, the socket ends. It sends `ping` every 30 seconds, and keeps under 4,000 frames and 56 MiB in any minute, below the Sphere's limits. It opens no listener for this: what comes in goes to the gateway's router inside obid.
- **What obid keeps.** `home/keys/relay.json` (0600): the relay's id (32 random bytes, base64url) and the Mac's X25519 private key, made the first time a phone is invited through a Sphere. The key never leaves obid: no answer, event or log has it. In `home/gateway-devices.json`, a device paired through the relay has `relay`, its relay token's SHA-256 (hex). The relay token itself is only in the QR code and on the phone.
- **Inviting.** While obid is a member of an Obysphere, `POST /v1/pairing/invite` makes a relay token for the phone (32 random bytes, base64url: 43 characters), and registers the relay and the token's SHA-256 with the Sphere (`PUT /v0.1/relay/{relay}`, then `PUT /v0.1/relay/{relay}/devices/{hex}`) before it answers, so the phone's first call can come through. The answer has everything the gateway's has, plus `relay`:

  ```json
  {"url": "https://obysphere.deskree.com", "name": "Studio", "hostname": "studio.local", "secret": "…", "code": "123456",
   "expiresAt": "2026-10-23T21:02:00Z",
   "relay": {"sphere": "https://obysphere.deskree.com", "id": "<relay id>", "token": "<the phone's relay token>", "key": "<the Mac's X25519 public key, base64url>"},
   "link": "{\"hostname\":\"studio.local\",\"name\":\"Studio\",\"relay\":{…the same…}}"}
  ```

  `link` carries `relay` too, so the QR code the Mac already makes from the answer (`{"url", "link", "secret"}`) has it as it is. Such an invitation pairs only through the Sphere: its `url` is the Sphere's (a `url` asked for is left out) and `hostname` the machine's name unless given, and its secret and code are refused on the gateway's listener (`401`, a wrong try), so a phone can't fall back to plain HTTP. `504` when the Sphere can't be reached, `502` when it refuses (`Your Obysphere relays 16 phones for this Mac at most: revoke one first.` at its limit); nothing is invited then. An owner with no Obysphere pairs as before, through Remote access or the tailnet, with a `url`; once obid is a member of one, every phone pairs through it.
- **Pairing through it.** The phone opens `GET <sphere>/v0.1/relay/{id}` with `Authorization: Bearer <relay token>`, starts a session (the envelope, below) with the QR's `key`, and sends `POST /v1/pairing` sealed in it: `{"credential": "<the secret>", "name": "<the phone's name>"}` with `content-type: application/json`. The answer is the gateway's. The device it pairs is bound to that relay token: an invitation made with a relay token is redeemed through the relay only on that token's socket (any other is `401`, and counts as a wrong try).
- **Requests.** Every other request is sealed the same way, with `authorization: Bearer <device token>`, and goes to the gateway's router in process: the same allowlist, device tokens, scrubbing and streams as on the listener; `POST /v1/hooks/{id}/deliver` is `404` through the relay. A device paired through the relay is reached only so: its token on the gateway's listener is `401` (`This phone reaches obid sealed, through its Obysphere.`), and inside another phone's envelopes `401` (`That device token isn't this phone's.`): which phone sent a request is its device token, sealed, and that device's relay token must be the socket's; the device id the Sphere routes by is never trusted for it. At most 32 requests open at once per phone (`429`), across its sessions: a write still running after its session ended counts until it's done; its requests' bodies at most 4 MiB until each is whole (`413`). Each phone's answers wait in a lane of their own, at most 64 frames (a refusal past that is dropped), and the lanes take turns, so one phone's download doesn't hold up another's events. A hello from a device the Sphere wasn't told of (forgotten, or made up) starts nothing, and a phone's new hello within a second of its session's start is ignored.
- **Forgetting.** `DELETE /v1/pairing/devices/{id}` ends that phone's session at once (its event stream too), and deletes its token's SHA-256 at the Sphere, which closes its socket (`4001`): from then on its relay token opens nothing.

#### The envelope (version 1)

Each WebSocket binary message between the phone and the Sphere is one envelope, at most 262,144 bytes; obid gets it after the 32 bytes of the phone's device id and sends its own after them (`sphere-api.md` 9.3). X25519 is RFC 7748, HKDF is HKDF-SHA256 (RFC 5869) with 32 bytes out, and seal is ChaCha20-Poly1305 (RFC 8439) with its 16-byte tag after the ciphertext. `‖` joins bytes; `nonce(n)` is 4 zero bytes and then `n` as 8 bytes, big-endian. In CryptoKit: `Curve25519.KeyAgreement`, `HKDF<SHA256>.deriveKey(inputKeyMaterial:salt:info:outputByteCount: 32)`, `ChaChaPoly.seal(_:using:nonce:authenticating:)`.

| Envelope | Bytes |
|---|---|
| hello, phone to Mac | `01 01` ‖ E ‖ seal(k_hello, nonce(0), aad: `01 01` ‖ E, the versions offered) |
| welcome, Mac to phone | `v 02` ‖ M ‖ seal(k_welcome, nonce(0), aad: `v 02` ‖ M, `v`) |
| sealed, either way | `v 03` ‖ n ‖ seal(k, nonce(n), aad: `v 03` ‖ n, a frame) |

- **Keys.** S is the Mac's public key, the QR's `key`, pinned at pairing. E is a new X25519 public key the phone makes for each session, M one the Mac makes for its welcome. es = X25519(the phone's new private key, S) = X25519(the Mac's private key, E); ee = X25519(the phone's new private key, M); either all zero is refused. k_hello = HKDF(salt: S ‖ E, ikm: es, info: `oby relay v1 hello`). The rest are HKDF(salt: SHA-256(the hello as sent ‖ M), ikm: es ‖ ee, info): k_welcome with `oby relay v1 welcome`, the phone's key with `oby relay v1 phone>mac` and the Mac's with `oby relay v1 mac>phone`.
- **Versions.** The hello seals one byte per version the phone speaks (1 to 16); this obid speaks `01`. The Mac picks the highest it speaks as `v`, in the welcome's header and sealed in it. The phone refuses a welcome with a `v` it didn't offer, or one that doesn't open (not from the Mac with the pinned key). Every sealed envelope carries `v` under its tag, and one with another `v` than its session's doesn't open: no downgrade, and nothing unsealed is ever taken from a phone paired this way.
- **Counters.** `n` is 8 bytes, big-endian: each side's first sealed envelope is 0, then 1, 2…, and each side takes exactly the next one, every time. One already taken (replayed, older) and one that doesn't open (changed, made up, sent back the other way, another session's) are dropped and spend nothing. One that opens with an `n` past the next proves an envelope before it is missing: nothing is skipped silently, and the session is over. When obid sees that, it sends the phone, sealed in that session, a `reset` on stream 0 (`The session is over: send a new hello.`) and keeps nothing of the session; when the phone sees it in obid's envelopes, or gets that `reset`, it sends a new hello. A new hello from the phone replaces its session: nothing of the old one opens in the new one. obid answers nothing to a hello or an envelope it can't open; a phone whose request goes unanswered for long sends a new hello, on a new socket if it must.
- **Frames.** Stream 0 is the session's own: only obid's `reset` that ends it. What a sealed envelope holds is a frame of the job channel's shape (obi-sphere `protocol.md` section 13): a stream (4 bytes, big-endian), a kind (one byte: `0` open, `1` data, `2` end, `3` reset) and its payload. A request opens a new stream, whose id is above every earlier one in the session (the first is 1), with `{"method", "path", "headers"}` (the path with its query; header names lower case), then its body in `data` frames and an `end`. obid answers on the same stream: `open` with `{"status", "headers"}` (the gateway's: `content-type`, `cache-control`, an artifact's `content-security-policy`…), the body in `data` frames of at most 65,536 bytes (an event stream's as its events come), then `end`, or `reset` with one line when the answer broke off. The phone sends `reset` on a stream to stop its answer (an event stream it no longer shows). That, and its session's end, stops only the answer: a request other than `GET` (a Merge, a Confirm, a Publish) runs to its end all the same, and the phone reads what came of it in its next session.
- **Known answer.** With the Mac's private key the bytes 0 to 31 (`00 01 … 1f`), the phone's new private key 32 to 63 and the Mac's 64 to 95, a hello offering version 1, then the phone's request on stream 1 (`open`, `{"method":"GET","path":"/v1/status","headers":{"authorization":"Bearer test-device-token"}}`, as its first sealed envelope) and the Mac's answer (`open` `{"status":200,"headers":{"content-type":"application/json"}}`, `data` `{"ok":true}`, `end`), every value in hex. obid's `relay::envelope` tests give exactly these, and CryptoKit on macOS 26 makes the same hello and request and opens the welcome and the answer.
  - S: `8f40c5adb68f25624ae5b214ea767a6ec94d829d3d7b5e1ad1ba6f3e2138285f`
  - hello: `0101358072d6365880d1aeea329adf9121383851ed21a28e3b75e965d0d2cd166254a2b39ce6bc8467ffdd094cfa4ea2258b59`
  - welcome: `010279a631eede1bf9c98f12032cdeadd0e7a079398fc786b88cc846ec89af85a51a0944396b30ca3b9834e5d232b1f803e05b`
  - the request: `01030000000000000000f5727141453120bc5930b45fc6041dd63ff38849669a6597b32e0126a0a47e5b8fe24aa92a12c8cb0b0d802d00b9b406da400b17143ce5eb2c2ec1d382aea99104e3927783310d114581bd85e058d1ebfe3852a2b3daf14baac186d5bb8a9459923c8d5f80fc14bc380ab04ace824f10`

#### What the Sphere sees

- **The Sphere** sees the relay's id and its Mac (the member's Sphere and Obi id), each phone's relay token (in its socket's `Authorization`; it keeps only the SHA-256), and for each frame its size, its time and which phone it comes from or goes to. It never sees a request, an answer, an event, a device token, the pairing secret, the Mac's public key or a login: those are only in the QR code and inside the envelopes. Dropping or changing an envelope ends that phone's session (it starts over); it never goes unnoticed.
- **Someone with a phone's relay token alone** (the Sphere itself, or whoever copied the token) can open a socket as that phone, which closes the phone's own (`4003`) until its person opens it again, send frames obid drops, use up that phone's share of the Sphere's limits, and see the size and timing of what obid sends to that socket. They can't read or change anything, act as the phone (that needs its device token, which never leaves an envelope), pair (that needs the QR code's one-time secret within its two minutes), or reach any other phone. Forgetting the phone ends all of it.
- **The Mac's private key** (`home/keys/relay.json`), if it were stolen, would let its holder answer as the Mac to new sessions; sessions recorded before stay closed to it (ee: each session's keys die with it), and a hello holds only the versions it offers.
