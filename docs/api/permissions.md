### `POST /v1/jobs/{id}/permission`

Answers the job's waiting `permission`:

```json
{"id": "p1a2b3c", "decision": "allow" | "always" | "deny", "message": "optional words for the agent"}
```

- `allow`: it goes ahead, once (Claude Code's `control_response` allow with its `updatedInput`; Codex's `accept`).
- `always`: it goes ahead, and the permission's `rule` is saved for the repository in `oby.sqlite` (`GET /v1/permissions/rules`): later prompts it covers, in this job and every other in that repository, go through without asking. The agent itself gets a plain allow (Claude Code's allow without `updatedPermissions`, Codex's `accept`, never `acceptForSession`): a rule of its own would let later calls through without asking the runner, past the user's deny rules and a rule they forgot, so every call still comes to the runner and its saved rules answer it. Only for a permission with a `rule` (`422` otherwise).
- `deny`: it doesn't happen, and the agent hears `message` as why (Claude Code's deny `message`; Codex's `decline`, then the words as a message to its turn), or a plain no without one. The user's own no never counts toward the runner's limit on denials in a row.

On obid, the agent's question (`permission.question`, #858) is answered with `{"id": "p1a2b3c", "answer": "SQLite"}` (no `decision`): an option by its label in any case, several labels separated by commas for a `multiSelect` question (`"Unit, Lint"`), or the owner's own words, up to 2,000 characters. With more of the call's questions left, the next one takes its place; after the last, Claude Code's `control_response` is an allow whose `updatedInput` is the call's input with `answers`, each question's whole text to its answer (`{"questions": […], "answers": {"Which store?": "SQLite", "Which checks?": "Unit, Lint"}}`). A `deny` with a `message` (the Mac's and the Watch's typed reply) answers it with those words, as `answer` does; a `deny` without one declines the question, the agent hearing `The owner didn't answer: decide yourself, and say in your summary what you chose and why.`; `allow` and `always` are `422`. The answer reaches the agent with the vault's secrets and the others obid knows taken out, and none goes while the vault can't be read. Telling the job something while a question waits answers it with those words (only the owner's own words: the brain's `message_job` and `oby_tell_job`, and other untrusted words, are refused with `It waits for the owner to answer its question, in their inbox.`).

On obid, `allow` and `always` need the owner's signed words (`X-Oby-Words`, a registered device's key; PERMISSIONS-15): without them it's `403` (the words under `POST /v1/inbox/{id}/answer`) and nothing changes. `deny` and a question's answer need none.

Returns the `Job`, with the next waiting permission or null. `404` for an unknown job, `409` when `id` isn't the permission waiting now, `422` for another `decision`, a `message` over 2,000 characters, or `always` without a rule. A job interrupted with its permission kept picks its session up again, the agent told what it asked and the answer. Telling a job something (`POST /v1/jobs/{id}/messages`) while a permission waits is a deny with those words.

**Parked** (obid only). The Electron app's Settings › General › "Permissions on this Mac" shows and sets it, with the saved rules below it: it offers Sangam's four modes, and `sandbox` only while it's the one saved.

### `GET /v1/permissions/rules` and `DELETE /v1/permissions/rules/{id}`

The saved rules, oldest first:

```json
[{"id": "r1a2b3c4d", "rule": "Bash(swift test:*)", "repo": "deskree-inc/oby", "decision": "allow", "created": "2026-10-11T09:12:00Z"}]
```

`decision` is `allow` or `deny`; deny beats allow. "Always" on a permission saves one. `DELETE` forgets one and answers with the rules left; `404` for a rule the runner doesn't know.

### obid only: permissions answered without the owner (#586)

A job should never ask the owner about anything that stays inside its sandbox ("The job sandbox", under obid only: Obi-to-Obi review jobs: it writes only to its worktree and temporary folder, has no code-host login, no vault secret and a clone whose push URL is invalid). The owner's decision of 2026-10-17: the agent takes most decisions, and the owner is asked only when it is extremely necessary. So `obid` has a fifth permission mode, **`sandbox`**. It was the default until #1570: a new install (no `permissions.json`, or one with no saved mode) now starts in `bypass`, as Sangam's Settings and the owner's decision of 2026-10-27 say (Settings › Permissions, `GET /v1/settings/permissions`); a mode the owner saved stays, `sandbox` too. The apps no longer offer it: only the owner's API calls set it. The Swift runner doesn't have it and its default stays `bypass`.

| In `sandbox` | |
|---|---|
| **Answered by obid's rules, recorded on the job** | File edits in the worktree; commands and tests (`cargo test`, `npm test`, `git commit`); reads and searches inside the worktree; the agent's own bookkeeping (its to-do list, a helper agent) and the MCP tools of enabled plug-ins, as in every mode. |
| **Refused** (the fixed rules, in every mode) | Pushing or posting (only Publish does, or the owner's word), a path outside the worktree, a background subagent (but in Bypass), other MCP tools. The agent hears why and how the owner gets it done. |
| **Asked** (a `permission` on the job and a `permission` inbox item, the card saying `why`) | The network beyond the model's API: a web fetch or search, a download or an install (`curl`, `wget`, `ssh`, `npm install`, `cargo add`, `pip install`, `python3 -m pip`, `git clone`, `git fetch`, `docker pull`, a bare `yarn` or `bundle`, `go mod`, `pipx`, `uvx`, `deno`, `gradle`, `mvn`, `rustup`, `swift package resolve`, `npx` or `bunx` of a tool the repository didn't install, …), a service's client (`psql`, `redis-cli`, `kubectl`, `aws`, `gcloud`, `terraform`, …), bash's `/dev/tcp` and `/dev/udp`, and what obid can't read: a program named by a variable or a substitution (`$c`, `$(echo curl)`), inline code (`python3 -c`, `node -e`, `perl -e`, `ruby -e`) and `find -exec`. Secrets, logins and the vault: a well-known secret file or folder by its name (`~/.ssh`, `.aws`, `.kube`, `.docker`, `api-token`, `auth.json`, `.credentials.json`, `.netrc`, `.npmrc`, `.env` but not `.env.example`, and a glob that could match one, like `.cred*`; the keys and patterns of `git config` are not files, only what follows its `-f`, `--file` or `--blob`), the agent's own login (the job's real account folder, its login copy and the links to it in the job's `HOME`, and `$CLAUDE_CONFIG_DIR`, `$CODEX_HOME`, `$CURSOR_CONFIG_DIR`), the tokens obid gives a job (`$OBY_MCP_TOKEN`, `$OBY_CHECK_TOKEN`), printing the environment (`printenv` with no name, a bare `env` or `set`, `export -p`, `/proc/*/environ`; `printenv NAME` prints only that variable, as `echo $NAME` does, and asks only for a secret's name), a keychain's passwords (`security find-…`), `gh auth`, or a value the vault keeps, in any form, anywhere in the call. A committed `.env.test` or `.env.development` in the worktree (git has it) is read without asking. A read or search outside the worktree and the job's temporary folder, and a command that names a file outside them and the system's folders (`/usr`, `/etc`, `/opt`, `/dev`, `/System`, `/Library`, …), like `cat /Users/someone/notes.txt` or `ls /tmp`. A tool obid doesn't know stays inside the sandbox, and a Cursor call that gives only a title for its command, or no place for its read. |

- **On macOS the OS holds the network; on Linux the questions are still best-effort.** A job's agent on macOS reaches nothing beyond loopback and no DNS resolver: whatever leaves the Mac goes through obid's egress proxy, which decides each site and asks the owner about a new one ([obid only: the egress proxy](#obid-only-the-egress-proxy-616)). So a program that opens a socket itself, bash's `/dev/tcp`, `python3 -c` or `find -exec curl` gets no further than the proxy lets it, whatever the reading of its command made of it. The reading stays, as the better prompt: it asks before the command runs. On Linux the agent still has slirp4netns, which reaches the whole network and the host's loopback at `10.0.2.2`, so there what reaches the network beyond the model's API is caught only by reading the command, and a program that opens a socket itself isn't caught (#616's next step).
- Matching a command's words is best-effort, like publishing's (obid only: publishing). `python -c` counts as inline code only before `-m` or a script (`python3 -m pytest -c setup.cfg` doesn't), and `find -exec` reaches the network only when what it runs does (`-exec rm {} +` doesn't). obid reads a command the way a shell does: each simple command between `|`, `;`, `&`, `(`, `)` and new lines outside quotes, through the shell's grouping words before it (`{`, `if`, `then`, `while`, `do`, `!`, `function f`, `coproc`, #1811) and the wrappers (`sudo`, `timeout 5s`, `env FOO=1`), and the code inside it too: `$(…)` and backticks (also inside double quotes and in a here-document whose end word isn't quoted), what `bash -c`, `sh -ec`, `eval`, `trap` or `find -exec` runs, and a here-document or here-string fed to a shell. A quoted argument, any other here-document's text, a commit's message (`git commit -m`) and the pattern of `grep` or `rg` are words, not commands or files, so a commit whose message says "curl" or "~/.ssh" goes through. Code nested more than four levels deep asks, as a secret does. A script that opens a socket itself isn't caught by its words: on macOS the box and the egress proxy hold it (above), on Linux nothing does yet. A command's network use is asked about before it runs, and the owner's yes covers the sites its addresses name: the proxy lets the agent reach them without a second card.
- **Secrets wait for the owner in every mode** (the re-review of #586). What touches secrets, a login or the vault asks in `ask`, `acceptEdits`, `plan` and `bypass` too, reads included, and no mode or saved rule lets it through: only the owner's own answer to its card does (the brain can't, even once). A waiting secrets card is never settled by a change of mode or a new rule, so neither the brain's `set_mode` nor `POST /v1/jobs/{id}/mode` answers it. This narrows `bypass` on obid: it answers everything but secrets.
- **Paths are read where the command runs.** A relative word is a path from the worktree, or from where a `cd` (or `pushd`) earlier in the same command line leaves it, with links followed: a committed link to the account's folder (`cat link/settings.json`) is a secret, and `cat ../../x` is outside. A subshell's `cd` (`( … )`, `$(…)`, backticks) ends with the subshell: after `(cd sub)` the folder is the one before. A command's own folder is read like a `cd` for that command: `git -C <dir>` (before git's subcommand), `make -C <dir>` or `--directory=<dir>`, `tar -C <dir>`, `env -C <dir>` or `--chdir=<dir>`; it is outside like any path, and its relative words are paths from there. A folder counts as a system folder only when it is one both as written and after links (on macOS `/home` leads into `/System`). A `cd` from an earlier call isn't known, so `../docs` after a previous call's `cd core` asks.
- **A folder obid can't tell makes the rest of the line `Outside`** (#636). When obid can't tell where a `cd` lands, every later simple command of the same line is outside, whatever it names: `cd -`, `cd $OLDPWD` or any folder named by a variable or a substitution (`cd "$(git rev-parse --show-toplevel)"`), `popd`, `pushd` with no folder or a place in its stack (`+1`), a bare `cd` when obid doesn't know the job's `HOME`, a `cd` inside code obid reads out of a word (`bash -c`, `eval`, a here-document fed to a shell), and a `cd` in a pipeline or in the background (a shell may run it in a subshell of its own). Likewise a command whose own folder (`git -C "$D"`, above) obid can't tell is outside. The commands before it aren't.
- **git settings that run a program ask** (`Unknown`). A command may give git exactly these, as written, and nothing else: the variables `GIT_EDITOR=true`, `GIT_SEQUENCE_EDITOR=:`, `GIT_PAGER=cat` and `GIT_TERMINAL_PROMPT=0` (before the program, or after `env`), and `git -c core.editor=true` and `git -c commit.gpgsign=false` before git's subcommand (#636). Each keeps git from opening an editor, a pager, a prompt or a signing program. Who a commit is by and when (`GIT_AUTHOR_*`, `GIT_COMMITTER_*`, `GIT_PAGER_IN_USE`, `-c user.name=…`, `-c user.email=…`) and colours (`-c color.*`) go through whatever their value: they run no program. Any other `GIT_*` variable (`GIT_SSH_COMMAND`, `GIT_PAGER=less`, `GIT_CONFIG_PARAMETERS`) and any other `-c` setting (`core.sshCommand`, `core.pager`, `alias.*`, `gpg.program`) ask, as do `--config-env` and `--exec-path=`. `busybox` and `toybox` count as network, like the other multi-call tools.
- **Known gaps of the reading**: what a shell works out only as it runs isn't read: code it reads from a pipe (`echo printenv | bash`), brace expansion (`{printenv,}`), a glob or a variable that spells a secret's path, a program a variable or an escape names, which counts as the network, not as a secret (docs/contracts/permissions.md, PERMISSIONS-7). Programs that run code they're given without a flag obid reads, like `awk` (its `system()`), `lua` and `Rscript`, aren't treated as network: asking for every `awk` would block normal work (on macOS the egress proxy still decides any site they reach). And these ask though they're harmless, by design: a write to `/tmp` (outside the job's folders; the sandbox refuses it anyway), a `sed` whose text names `GITHUB_TOKEN`, and `"$PYTHON" -m pytest` (a program named by a variable). `/Library` stays readable, like the other system folders.
- **The owner's rules still apply**, in this order: a deny rule refuses; a saved allow rule lets through what would ask for the network or a read outside the worktree (the owner's own earlier decision), but **never secrets**: a card about secrets has `rule` and `always` null, so it can only be allowed once. "Always" covers what was asked about, not the whole tool: a fetch saves `WebFetch(domain:<site>)` (that site and its subdomains), a search outside the worktree `Grep(<place>)` (likewise `Glob`, `LS`). A job whose `mode` this obid can't read (one a newer obid wrote) is treated as `ask`; a job from before modes is still `bypass`. Then `sandbox` answers or asks as above. In `plan` and the other modes nothing changes.
- **Standing rules stay confirm cards** (the owner's decision of 2026-10-16). `sandbox` is not a standing rule the brain can create: the brain's plan can't name it (`set_mode` and a dispatch's `mode` take `ask`, `acceptEdits`, `plan`, `bypass`), `bypass`, "always allow" and accepting another Obi's request are `confirm` items as before (obid only: the brain), and the agent's own questions (#448) are asked as before: Claude Code's `AskUserQuestion` waits for the owner in `sandbox` and every other mode (#858, `permission` above). Only the owner's API calls (`PUT /v1/settings/permissions`, `POST /v1/jobs/{id}/mode`) set `sandbox`.
- **The owner can go back to asking for commands**: set Settings › Permissions to `acceptEdits` (edits go, every command asks) or `ask`. Jobs already dispatched keep their mode.
- **The record.** Every permission obid answers itself in a job of the owner's own, the refused ones too, is kept on the job: `answered`, the latest 50, oldest first, and `answeredCount`, how many obid answered in all (the agent's bookkeeping calls, `TodoWrite`, `Task` and `Agent`, aren't counted; what the owner answers themselves isn't obid's). A waiting prompt that a new mode or a new rule answers is counted when it is answered.

  ```json
  {"answered": [{"id": "p1a2b3", "tool": "Bash", "title": "Run cargo test", "detail": "cargo test --workspace",
                 "decision": "allowed", "at": "2026-10-17T09:12:00Z"},
                {"id": "p4d5e6", "tool": "Bash", "title": "Run git push", "detail": "git push origin HEAD",
                 "decision": "refused", "reason": "Agents have no code-host login, so pushing and posting go through obid: …", "at": "2026-10-17T09:12:03Z"}],
   "answeredCount": 2}
  ```

  `decision` is `allowed` or `refused`; `reason` is what the agent heard, only on a refusal; `detail` is cut to 300 characters, with a login in an address (`https://user:pass@host`) and every word that looks like a token (the secret scan's rules) taken out. The `permission` a job waits on may also carry `why`, one sentence saying why it asks when `sandbox` would otherwise have answered ("It reaches the network beyond the model's API.", "It touches secrets or the vault.", "It reads outside the job's worktree."). The Swift runner sends neither key.
- Acceptance, as the API tests show it: a job that edits files, runs tests and installs nothing ends `done` with no inbox item and `answered` listing each; one that tries to push is refused and says so in `answered`; one that installs, fetches a page, reads `~/.ssh` or lists `/etc` waits with a `permission` and `why`.
