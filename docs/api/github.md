### obid only: GitHub's sign-in

The owner signs obid's `gh` in to GitHub from the Mac (Settings › Connectors › GitHub, and the setup's GitHub step), with GitHub's own device sign-in; nobody types `gh auth login` (the owner's decision of 2026-10-18). obid never reads, holds or passes the token: gh keeps it in its own Keychain item, as `gh auth login` always does. None of these endpoints is on the gateway's allowlist: a paired phone never signs the Mac in to someone's GitHub.

**`GET /v1/github`** answers `{"gh": true, "signedIn": true, "user": "well-prado", "signIn": null, "reviewer": {"signedIn": true, "user": "oby-reviewer", "signIn": null, "error": null}}`:

- `gh`: whether obid has a GitHub CLI (the one Oby.app carries, else the login shell's).
- `signedIn` and `user`: the active github.com account in `gh auth status --hostname github.com --active --json hosts` whose `state` is `success` (never `--show-token`); signed out otherwise. `user` is a GitHub login name or null. Read again at most every 30 seconds, and after a sign-in ends.
- `signIn`: the sign-in under way, as `POST` answers it, or null.
- `reviewer`: the reviewer's login (below), read the same way from its own settings folder: `signedIn`, `user`, its sign-in under way (`signIn`), and `error`, why its last sign-in kept no login (the owner's own account), or null; cleared by the next sign-in or a sign-out.

**`POST /v1/github/sign-in`** starts gh's own sign-in, or answers the one under way: `{"url": "https://github.com/login/device", "userCode": "AB12-CD34", "expiresAt": "…"}`. The app opens `url` and the person types `userCode` there (gh also puts it on its machine's clipboard).

- It runs `gh auth login --hostname github.com --git-protocol https --web --skip-ssh-key`, unboxed (it must reach the Keychain and the network), by its absolute path, with obid's kept environment (no token, no agent variable), the person's `HOME` (where gh keeps its settings), `GH_BROWSER` and `BROWSER` set to `true` (nothing opens on the runner), prompts off, and `GIT_CONFIG_GLOBAL` a file in the sign-in's own folder (`home/tmp/github-sign-in-…`, removed when it ends), so gh never changes the person's global git settings. obid needs no `gh auth setup-git`: it gives git gh's login itself (obid only: publishing).
- obid reads what gh prints only for its one-time code (`! One-time code (AB12-CD34) …` or `! First copy your one-time code: AB12-CD34`); nothing else is kept, answered or logged. The page is always GitHub's device page.
- One at a time. It ends when gh does (signed in, or not), after 15 minutes (a device code's life), with `DELETE`, or when obid stops; its process group is killed with it. `502` when gh gave no code within 30 seconds; `503` without a gh.

The `503` carries `reason` `notInstalled`, the `502` `didNotStart`, and the `409` while a sign-in is starting `busy` (the reviewer's sign-in too). A sign-in that ended without a login shows as `signedIn` false and `signIn` null: `GET /v1/github` reads the sign-in before the status, and a sign-in's end forgets the status before it shows as ended, so a status read that began before the end keeps nothing and a login that just succeeded never shows that way.

**`DELETE /v1/github/sign-in`** ends the sign-in under way, if any: `204`.

#### The reviewer

The reviewer is a second GitHub account that Oby posts its review of the owner's own pull requests as (the owner's decisions of 2026-10-24: Oby carries a task the whole way, and GitHub lets nobody approve their own pull request). Settings has no row for it yet; these endpoints are for the app to add one.

**`POST /v1/github/reviewer/sign-in`** starts the reviewer's sign-in, or answers the one under way, exactly as `POST /v1/github/sign-in` does (`{"url", "userCode", "expiresAt"}`, the same device page, one at a time, the same limits and errors), with these differences:

- `409` (`Sign in to GitHub first: …`) until the owner's gh is signed in: the reviewer must be another account.
- gh signs in to a settings folder of the sign-in's own (`GH_CONFIG_DIR` in `home/tmp/github-sign-in-…/gh`, 0700) with `--insecure-storage`, so its token is a file there, never a Keychain item, and is kept away from the keyring altogether: on macOS it runs under a Seatbelt profile that denies `/usr/bin/security` (how gh reaches the Keychain), and everywhere with a D-Bus session that isn't there (how it reaches a Secret Service). gh keeps a host's active token in the keyring's one shared slot whatever its settings folder, so a sign-in that reached the keyring would clear the owner's, and a call whose own file lost its token would go as the owner. Where neither holds, the reviewer's gh doesn't run. Inside a job sandbox, which denies the Keychain already and can't nest another, it runs as it is.
- When gh ends signed in, obid reads that folder's account (`gh auth status`, as above) and the owner's. When they're the same account (in any letter case), nothing is kept and `reviewer.error` says why (`<login> is your own GitHub account: …`); likewise when the owner's gh is signed out by then (`Sign in to GitHub first: …`). Otherwise its login is first kept for good among the reviewer accounts Oby has used (`home/github/reviewers.json`, 0600: obid only, merging), and then the folder becomes the reviewer's, `home/github/reviewer` (0700), in place of the one before. A login obid can't keep there keeps nothing either (`reviewer.error`: `obid couldn't keep the reviewer's login: …`): its approval could otherwise pass for a teammate's once it signed out.

**`DELETE /v1/github/reviewer/sign-in`** ends the reviewer's sign-in under way, if any, and signs the reviewer out: `home/github/reviewer` is removed, token and all, and `204`. Its login stays in `home/github/reviewers.json`. A sign-in that was still ending keeps nothing afterwards. obid never runs `gh auth logout` for it (it clears the keyring's shared slot, the owner's). As after `gh auth logout`, GitHub keeps the token valid until it's revoked in the reviewer account's settings (Applications › Authorized OAuth Apps › GitHub CLI).

What the reviewer's token can do and where it lives:

- It's gh's own OAuth token for the reviewer account, with the scopes gh's sign-in asks for (`repo`, `read:org`, `gist`): whatever that account may do in the repositories it can reach. Give the account write access only to the repositories Oby should approve in.
- It lives only in `home/github/reviewer/hosts.yml` (0600, in a 0700 folder): obid's home, which every job's and conversation's box hides. obid learns it as the secret `github reviewer` at start, after a sign-in and at every read of the reviewer's status (gh may refresh it), so it's taken out of every answer, log line and push like obid's other secrets, and the secret scan stops a push that holds it.
- It never reaches an agent: jobs keep their empty `GH_CONFIG_DIR`, no job's environment, prompt, file or argument has it, and the reviewer's gh is started only by obid itself, for one thing: posting Oby's review of the owner's own pull request (obid only: GitHub work, "Oby's verdict"). Every other GitHub call stays the owner's.
- None of these endpoints is on the gateway's allowlist.

### obid only: repositories

A job works in a repository the configuration lists (`repos`) or in one of the GitHub repositories the owner's gh can push to ([obid only: GitHub's sign-in](#obid-only-githubs-sign-in)), so a fresh obid with no `repos` works in the owner's repositories once gh is signed in, with no file edited.

- **GitHub's list.** obid asks gh at start, every hour, and as soon as a GitHub sign-in ends signed in: `gh auth status`, then `gh api user/repos?per_page=100&sort=pushed&affiliation=owner,collaborator,organization_member --paginate`, keeping each repository whose `permissions.push` is true and that isn't archived, newest push first. The list is the signed-in account's only: when gh says it's signed out, or signed in as another account (at each read, and whenever `GET /v1/github` reads gh's status), the list is dropped at once, so no job starts in, or adds, a repository of an account gh no longer uses. A read that fails while the same account is signed in keeps the list. A configured repository with a GitHub remote whose `defaultBranch` (`main` when the entry has none) differs from what the read lists, and is gone from GitHub, takes GitHub's: `gh api repos/<repo>/branches/<branch>` answers with another branch (GitHub renamed it and redirects to the new name, which gh follows) or 404 (it was deleted). GitHub's default is written to `config.json`'s `defaultBranch` too, so later jobs branch from it; this holds on every read, the first after a restart included. One whose branch still exists is the owner's pin (`dev` while GitHub's is `main`) and is never changed, whatever GitHub's default becomes; so is one GitHub's answer doesn't settle (a rate limit, a timeout) until a later read, and one with another remote. That's one `gh api` call per such repository per read. Each is cloned from `https://github.com/<owner>/<name>.git` with gh's login, as any GitHub remote is (obid only: publishing the owner's work).
- **A review request's repository, on the owner's tap.** A review requested of the owner in a repository neither listed nor among GitHub's above (one their login can read but not push to, say) is added only by the owner's signed Confirm (#776). A tap on its card in the feed (`POST /v1/github/work/{id}/start`) or `Review it` on its inbox offer makes a `confirm` item, `Add acme/other and review #12` (action `add_repository`), and answers `422` (obid only: GitHub work), so obid's API token alone (an agent, oby-mcp, a script) never adds one. On the Confirm, obid checks the name (`owner/name`), reads `gh repo view <repo> --json nameWithOwner,defaultBranchRef` with its own gh, and gives `{"repo", "remote": "https://github.com/<repo>.git", "defaultBranch"}`, with no `check`, to that review's job alone: no other job sees it before. The remote is built from the checked name, never taken from GitHub's answer. It's kept, as below, only once that job is made; a start that fails adds nothing. Never the brain or anything GitHub says.
- **The first job adds it.** A job in one of GitHub's (`POST /v1/jobs`, the brain, the conversation, GitHub work, a plug-in's event) adds `{"repo", "remote", "defaultBranch"}` to the configuration file's `repos`, every other key and entry kept (the file is written again as JSON through a temporary file, 0600, its keys sorted). From then on it's listed like the rest: conversations' rooms check it out, its clone is tidied, routines and rules may name it. When the file can't be written, obid logs why and lists the repository until it stops.
- **The first clone.** obid's clone of a repository (`home/clones/<owner>/<name>`, made in a `.<name>.cloning` folder and moved into place) and every fetch into it through `git::fetch` run `git` with `--progress` (never `--quiet`), and obid cuts one only once git's stderr has said nothing new for 5 minutes (`git clone … made no progress for 300 seconds, so obid stopped it`) or it has run 6 hours in all (`… was still running after 21600 seconds, obid's ceiling for a clone or fetch`), so a repository too big to clone in 10 minutes is still used (docs/contracts/recovery.md, RECOVERY-13). Every other git call of obid's is cut at 600 seconds (`git … took more than 600 seconds`), Publish's fetch of the base too. The clone is whole: never partial, shallow or sparse, since a job's box can't fetch what's missing.
- **What the brain is told.** The conversation's orientation names every listed repository and up to 100 of GitHub's, newest push first; a job may start in any of GitHub's.
- **Letter case.** Names match letter case aside, as GitHub's do and the Mac's disk, where two would share one clone: a listed repository first, with its settings (its `check`), and the job takes that name; GitHub's spelling of a listed one is never added again.
- **Never for another Obi.** A review another Obi asks for (obid only: Obi-to-Obi review jobs) is taken only in a listed repository.

**`GET /v1/repos`** answers the repositories a job may start in, the listed ones first, then GitHub's not listed yet (`listed` false), newest push first:

           {"repo": "octo-cat/app", "defaultBranch": "dev", "listed": false, "check": null, "noCheck": false}]}

`check` is the command its jobs run (null: none), and `noCheck` whether the owner answered No check when Oby asked (Job, #1062). Older obids don't send them.

**`POST /v1/repos/check`** (obid only, #1062), `{"repo": "acme/app", "check": "make test"}`: the owner's own check for a repository, from Edit on Oby's ask or Change check on a task's page. It never keeps anything by itself: it asks, as Oby does, with the same `confirm` item (action `set_check`, `job` empty), in place of any open one for that repository (those are done, unanswered), and only the owner's signed Confirm of that item keeps the command. Its text says what Cancel keeps: with a check there, `acme/app's check is \`npm test\` now. With \`make test\` instead, every task there that starts after your answer runs it in its box, with no network, before anything goes out. Cancel keeps \`npm test\`.` `"check": null` starts over: a check kept there is taken out the same way, an item titled `Take \`npm test\` out as acme/app's check?` whose Confirm takes it out (the next job asks again); with none kept, the owner's No check is forgotten at once, so the next job asks again, and there's no item. Answers `200` with the repository as `GET /v1/repos` lists it and the item, `{"repo": {…}, "ask": {…} | null}`; `422` for a repository obid doesn't know, or a `check` that isn't one line of up to 200 characters with no control character. Not on the gateway: a paired phone doesn't change a check.

### obid only: GitHub work

What GitHub wants from the owner, so Oby can show it and do it for them: the open issues assigned to them, the open pull requests waiting for their review (asked of them or of a team they're on), and their own open pull requests. obid reads it with its own `gh` login, as the Lead reads the board: `gh` signs in with its own login (gh's device sign-in from the Mac, or a token the owner gave gh's own store), and obid never reads, holds or passes a token (no file, argument, environment variable, log or event of obid's has one). No webhooks: obid is local and self-hostable, so it asks, every 3 minutes.

- **How it reads.** One `gh api graphql` query per read, with three searches of up to 100 items each (`is:open is:issue archived:false assignee:@me`, `is:open is:pr archived:false review-requested:@me`, `is:open is:pr archived:false author:@me`, newest update first), each item's boards (`projectItems(first: 5, includeArchived: false)`, with its `Status` field) and its milestone's title, GitHub's `rateLimit` (`cost`, `remaining`, `resetAt`, read on every read: 9 points with boards, 6 without, measured 2026-10-20) and `viewer`, so the feed is always that of whoever `gh` is signed in as now (after `gh auth switch` too). Every 3 minutes while obid runs, the first right after it starts. A `403` or `429` (GitHub's rate limits, the secondary ones included) waits 3 minutes, then doubles, up to 30 minutes, until a read succeeds; a read that leaves fewer than 50 points waits until `rateLimit.resetAt`. Other failures (no network, a `5xx`) keep the last lists and try again at the next tick. An answer with GitHub `errors` besides its `data` (an organization whose SAML the login isn't authorized for, say; `gh` fails it) still counts: its lists are shown, and `error` says what GitHub left out.
- **Boards need `read:project`.** Reading an item's boards needs gh's login to have the `read:project` scope (or `project`). Without it GitHub fails the whole query, so obid reads again at once without boards: the lists are as always, every `board` is null, `error` is `Board columns need gh's read:project scope: run gh auth refresh -s read:project`, and the log says so once until boards read again. For the next hour a tick reads without boards (one call per read), then tries boards again; a refresh (`POST /v1/github/work/refresh`), or a read as another login, tries them at once, so a refresh right after `gh auth refresh -s read:project` brings them back. Once they read, `error` clears.
- **Not signed in.** When `gh` isn't installed or isn't signed in, two reads in a row (one that passes, a 401 GitHub gives once, keeps the lists and reads again at the next tick), the lists are empty and `signedIn` is false: the apps show Connect GitHub. After those two, obid doesn't ask `gh` again for 30 minutes of the Mac awake (its clock stops while the Mac sleeps; while a job runs obid keeps it from idle sleep, `keepAwake`): signing in through Oby (`POST /v1/github/sign-in`) reads at once, as does a refresh, and signing in from a terminal (`gh auth login`) shows the work within those 30 minutes. The first read after signing in again, or as another login, is a first read: it offers nothing in the inbox.

- `signedIn`: whether `gh` is installed and signed in. `login`: its GitHub login, or null. `checkedAt`: the last read that succeeded, or null (none yet). `nextCheck`: when obid reads next. `error`: why the last read failed, one line with the secrets obid holds taken out (`GitHub's rate limit: reading again at 2026-10-18T09:42:00Z`, `gh isn't signed in to GitHub`), or what it left out (`GitHub left some of your work out: Resource protected by organization SAML enforcement…`), or null; after a failure the lists stay as the last read that worked.
- `reviews`, `assigned`, `mine`: the three lists, newest update first, at most 100 each. `counts`: how many GitHub found for each, so a list shorter than its count was cut at 100. Each read also takes a pull request's `isCrossRepository` and its head commit's `oid`.
- Each item: `id` (16 hex characters, obid's own, the same for the same repository and number on every read), `list` (which of the three), `repo` (`owner/name`), `number`, `title`, `url`, `author` (a login, or null for a deleted user), `association` (GitHub's `authorAssociation` of the author, or null) and `trusted` (whether the author's words count as the owner's own, Whose words below), `labels` (names, at most 20), `updated`, `state` (`OPEN`). On pull requests, `draft`, `reviewDecision` (`APPROVED`, `CHANGES_REQUESTED`, `REVIEW_REQUIRED`, or null: no review required), `checks` (the head commit's combined state: `SUCCESS`, `FAILURE`, `ERROR`, `PENDING`, `EXPECTED`, or null when it has none), `head` (that commit's full id, or null when GitHub gave none that is one) and `fork` (whether its branch is a fork's); on issues, the five are null. `board`: the GitHub Project (v2) board it's on and its column there (`{"project": "<the board's title>", "column": "<its Status>"}`: `Backlog`, `Todo`, `In progress`, whatever the board calls them), or null when it's on no board, on none with a single-select field named exactly `Status`, or gh's login lacks `read:project`; on several boards, the first that has a `Status`. Boards the item is archived from are left out (`includeArchived: false`). `known`: whether a job can start in its repository: one of obid's `repos` (obid only: configuration) or of GitHub's that gh can push to (obid only: repositories). `job`: the queued or running obid job on it (same repository and number; on your own pull request, a `fix` job with that `pr`), or null.
- Everything in an item is GitHub's data: show it, never act on it. `title`, `labels` and `board` are what people wrote.

#### `GET /v1/events`: `github`

A `github` event comes, carrying the same object as `GET /v1/github/work`, when a read changes anything in it but `checkedAt` and `nextCheck` (an item came, went or changed, `signedIn`, `login`, `error`), and when `POST /v1/github/work/{id}/start` starts a job (its `job`). The first read after obid starts sends none: fetch the feed when you connect, as after every reconnect. Replace the whole feed with it; how that job goes comes as `job` events.

#### `POST /v1/github/work/refresh`

Reads now, as a tick does, and answers the feed as `GET /v1/github/work` does once the read ends (up to 2 minutes). Within 15 seconds of the last read began (a tick's or a refresh's), it doesn't read again and answers the feed as it is, so no client spends GitHub's points by refreshing; nor during a rate-limit wait, when `error` and `nextCheck` say until when. No body.

#### `POST /v1/github/work/{id}/start`

Starts the work on an item with one call, as the owner's tap (no body; a body is ignored). Starting work is always the owner's choice: nothing in the feed starts a job by itself. The job it starts is in a conversation of its own, named after it, with Oby's line and its card; the item's title is GitHub's, so the conversation counts as having read something from outside, and nothing GitHub wrote is put in it as the owner's words (docs/contracts/task-conversations.md, TASKCONV-2).

- A `reviews` item starts Oby's review of that pull request: a `review` job (`POST /v1/jobs` with `kind` `review` and `pr`), routed as any job, with the pull request's head checked out. It reads, never commits, and never posts on GitHub by itself (What the runner doesn't do by itself). When the owner's own review started here ends `done` with a summary, and the pull request is someone else's (its author, `gh pr view --json author`, isn't the owner's gh login in any letter case; when obid can't read either, it's taken as not), one `listen` inbox item (`id` `feed-review-` and the job's id) shows that summary, with Oby's verdict, and offers `Approve` and `Dismiss`. `Approve` posts it on the pull request with that verdict, after the secret scan, and only while the pull request's head is still the commit the review started from. A summary the scan flags, or a scan that can't run, offers only `Dismiss` and posts nothing. Another Oby's review is not this item. A review asked for any other way (`POST /v1/jobs` with `kind` `review`, a conversation), and one of the owner's own pull request, raises no item: GitHub refuses the owner's approval of their own, and its verdict is on its job's page (docs/contracts/merging.md, MERGING-42). obid knows a review started here by the quote of the pull request it keeps for it, under its `attachments/github`.

  **Oby's verdict.** A review job's prompt asks the agent to end its summary with a line that is exactly `VERDICT: APPROVE` or `VERDICT: REQUEST CHANGES`. obid takes the last such line out of the text and keeps the verdict in the item's `watch.verdict`: `approve`, `requestChanges`, or `comment` when the agent gave none. What `watch.review` shows, and Approve posts, starts with obid's own line saying what was decided (`Oby's verdict: approved.`, `Oby's verdict: changes requested.` or `Oby's verdict: comments only.`), then the review. It's posted as a review of the commit reviewed with the event `APPROVE`, `REQUEST_CHANGES` or `COMMENT` (above), from the owner's login: Oby decides, the owner's Approve posts it. GitHub lets nobody approve or request changes on their own pull request, so on the owner's own (its author, `gh pr view --json author`, is the owner's gh login, in any letter case) an approval or a change request goes as the reviewer when one is signed in (obid only: GitHub's sign-in, "The reviewer"): obid first checks with the reviewer's login that it can push to the repository (`gh api repos/<repo>` → `permissions.push`), because an approval from an account without write access doesn't count toward the required ones. Without it nothing is posted and the item is settled with why (`502`, `Nothing was posted: the reviewer, <login>, can't push to <repo>, so its approval wouldn't count: …`); a reviewer signed in as the owner's own account is never used, nor one whose login gh can't read now or that isn't signed in any more (`Nothing was posted: obid couldn't read the reviewer's GitHub login …`), so it's never posted another way. Likewise when obid can't read the owner's login or the pull request's author. With no reviewer signed in it goes as the owner's comment, its first line still saying the verdict, as it does wherever GitHub says `your own pull request`. A comment is always the owner's. An item from before this has no `watch.verdict` and posts a comment.

  **Posting it.** Once a review's job ends `done`, its `listen` item (`Review ready: obi #835`) shows the review, its job's summary after the secret scan, under `watch.review`, offers `Approve` and `Dismiss` (`job` the review job, `watch.pr` the pull request and the head commit reviewed). A review the scan flags isn't shown and offers `Dismiss` only. `Approve` (the owner's own answer, on the Mac, where the review is shown: the conversation's brain is refused (the kind keeps its name from the Slack listener this flow outlived), and a phone's `Approve`, through the gateway, is `403`, `Answer it on your Mac, where what it sends is shown`, until the phones show the review: the answer endpoint checks the item itself, found by its id as decoded, so no spelling of the path gets by; their `Dismiss` and later go through) posts exactly that review on the pull request with Oby's verdict, signed `by Oby: Oby wrote this review.` (Whose words, below), with obid's `gh` (`gh api -X POST repos/<repo>/pulls/<n>/reviews -f commit_id=<the commit reviewed> -f event=APPROVE|REQUEST_CHANGES|COMMENT -F body=@…`, from a folder of its own each time; see "Oby's verdict" below), after the secret scan again and only while the pull request's head is still the commit reviewed: obid reads the head before it decides who posts, and again after, just before posting, and the review names the commit reviewed (`commit_id`), never whatever the head is when GitHub gets it (`gh pr review` can't name one), so a push while obid asks around never gets an approval meant for the commit before it. Whenever nothing was posted (a moved head, `out of date`; a finding; a scan that can't run; GitHub refusing it), the answer is `502` (`Nothing was posted: …`) and the item is settled with no answer, that sentence kept in its `watch.answerError` (an optional string, set only then) and in obid's log, so the app says it once: it never opens again by itself, nor when the same review is offered again, and a new review is the way to try again (MERGING-43). The claim is kept on disk before `gh` is asked (`watch.posting`): a second `Approve` meanwhile, or one after obid stopped mid-post, is `409` (`Oby was posting this review when it stopped, or still is: check the pull request on GitHub, then Dismiss it.`), so a review is never posted twice; when the claim can't be kept on disk, nothing is posted (`500`). A review the owner dismissed while it was being posted stays dismissed when the post fails. A review that's empty, or that the scan flags or can't check, says which and offers `Dismiss` only. Nothing is ever posted any other way. A review whose job didn't end `done` is left to its job's own report.
- An `assigned` item starts a `fix` job on that issue (`kind` `fix`, `issue`), routed as any job, that ends in a pull request through Publish as today (`Closes #N`).
- A `mine` item (your own pull request) starts a `fix` job on its branch (`kind` `fix`, `pr`, and `base` the pull request's head branch, read with `gh pr view --json headRefName,isCrossRepository,…` as it starts): it starts from the pull request's head on a branch of its own (`oby/fix-<n>`), adds commits on top, and what it publishes is a pull request into your branch, through Publish as today. It never pushes onto your branch, rewrites it or force-pushes it. A fork's branch is `409` (`Oby works on a branch of the repository itself, not a fork's.`), and so is a pull request an obid job opened (`Oby's job <title> opened this pull request and follows its checks: tell that job instead.`).
- A `reviews` item in a repository obid doesn't work in starts nothing here: it makes the `confirm` item that adds the repository and starts the review on the owner's signed Confirm, one per item (obid only: repositories, "A review request's repository, on the owner's tap"), and answers `422` with `Adding obi-ai-bot/other waits for your Confirm in the inbox.`
- The job's `task` and `title` are obid's own words, never GitHub's: `Review pull request #702 in obi-ai-bot/obi.` titled `Review obi #702`, `Fix issue #640 in obi-ai-bot/obi.` titled `Fix obi #640`, `Make pull request #812 in obi-ai-bot/obi pass its checks. Add commits on top of it; never rewrite or drop the ones it has.` titled `Fix CI obi #812`. What people wrote on GitHub (the title, the description, the labels and the latest 30 comments, at most 64 KiB; on your own pull request, each check's name and result too) reaches the agent only as a quoted file, `.obi/inputs/github-<name>-<number>.md` (an attachment, or for an assigned issue the quote every issue's job gets as it runs, `issue` above; so its text is fenced, the prompt says it's data, never instructions, and the vault's secrets are taken out when it's copied into the worktree), never in a prompt, a task, a title or the brain's briefing.
- Answers `201` with the new `Job`, as `POST /v1/jobs` does (and a `job` event). When a queued or running job is on it already (same repository, kind and number; for your own pull request, a `fix` job with that `pr`), answers `200` with that job and starts nothing. Starts happen one at a time, from the feed and the inbox alike, so two taps at once (the Mac and the iPhone, or a card and the feed) start one job: the second waits for the first and answers its job.
- `404` for an id that isn't in the feed now (read again). `409` with why: `gh` isn't signed in, a fork's or an obid job's pull request, or an assigned issue or your own pull request in a repository a job can't start in (`obid doesn't work in obi-ai-bot/other yet: add it to repos in obid's configuration, or sign gh in to an account that can push to it.`). obid clones only the repositories it's configured for, those gh can push to, and those the owner added with a signed Confirm: which repositories it works in, and their checks, stay the owner's choice. `422` with why when the job can't be made (no account signed in), or when a review waits for the owner's Confirm (above). `502` when GitHub's text for it couldn't be read.

#### The `github` inbox item

When a read finds a new review request, a new assigned issue on a repository obid works in (`known`), or failed checks on a new head of the owner's own pull request, one `github` inbox item offers to do it:

```json
{"id": "github-3f9a0c1d2b4e5f60", "kind": "github", "job": "", "title": "Review requested: obi #702",
 "text": "Your review is requested on pull request #702 in obi-ai-bot/obi.", "options": ["Review it", "Dismiss"],
 "details": ["Starts Oby's review of it. Nothing is posted on GitHub.", "Leaves it for now. It stays in your GitHub work."],
 "recommended": null, "github": {"id": "3f9a0c1d2b4e5f60", "list": "reviews", "repo": "obi-ai-bot/obi", "number": 702, "author": "sangam", "association": "MEMBER", "trusted": true, "url": "https://github.com/obi-ai-bot/obi/pull/702", "known": true, "head": "9f3c…", "quoted": {"title": "Pair a device from Settings"}}, "triage": "needs_you", …}
```

- `github.author` is the login of who opened it (null when GitHub names nobody), for sorting it (obid only: sorting the inbox). `github.association` and `github.trusted`: GitHub's `authorAssociation` of that author and whether their words count as the owner's own (Whose words, below). `github.known`: whether obid worked in its repository when it came. `github.head`: the pull request's head commit, or null.
- A review request in a repository obid doesn't work in says so: `Your review is requested on pull request #12 in acme/other. Oby doesn't work in acme/other yet.`, and offers `Review it` (`Adds acme/other to the repositories Oby works in, with no check, then starts Oby's review of it. Nothing is posted on GitHub.`). Answered with obid's API token alone, it adds nothing: obid makes a `confirm` item, `Add acme/other and review #12` (action `add_repository`, one per offer), answers `422` with `Adding acme/other waits for your Confirm in the inbox.`, and the offer stays open. The owner's signed Confirm adds the repository and starts the review, and the offer is done with `Review it`. A tap on the item's card in the feed does the same. Oby's brain never answers a `github` item either: its answer is a `confirm` item too (obid only: confirm items).
- Failed checks on your own pull request (`checks` `FAILURE` or `ERROR` on a head that wasn't red at the last read, or a pull request that wasn't there) are titled `CI failed: obi #812`, say `Checks failed on your pull request #812 in obi-ai-bot/obi.` and offer `Fix CI` (`Starts a fix job on your pull request's branch. It never pushes onto your branch: when its check passes, it opens a pull request into it.`) and `Dismiss`. Its `id` is `github-ci-`, the item's `id`, `-` and the head's first 12 characters: one offer per red head, across restarts too. None for a draft, a fork's branch, a repository obid doesn't work in, a pull request an obid job opened (that job follows its checks), or one with a queued or running fix job on it. No offer of any kind comes while the job it would start is queued or running already (a review on that pull request, a fix job on that issue). Only typed fields decide (list, repository, number, head, checks, draft, fork): no title, label or check name.

- An assigned issue's item is titled `Assigned to you: obi #640`, says `Issue #640 in obi-ai-bot/obi is assigned to you.` and offers `Fix it` (`Starts a fix job on it, which opens a pull request when its check passes.`) and `Dismiss`. `title` and `text` are obid's own words; GitHub's title is quoted under `github.quoted`, for the card only.
- `Review it`, `Fix it` or `Fix CI` starts the work as `POST /v1/github/work/{id}/start` does, and the item is done, its `job` the job's id (or the job already on it). The answer claims the item first, so a second answer meanwhile is `409` (`That item is done already.`) and nothing settles it by itself under way; when it can't start, the answer is the same error and the item is open again. `Dismiss`, done or later settle or put it off; nothing is sent to GitHub.
- One per item, ever: its `id` is `github-` and the item's `id` (`github-ci-…` per head for failed checks), so an item that's done never comes back, across restarts too. It's done by itself, with no `answer`, once its item leaves the feed (reviewed, merged, closed or unassigned), and a `CI failed` one once its pull request's head moves or its checks pass (a re-run's pending checks keep it, so a second failure on the same head is still that offer); a new red head is a new offer. Nothing settles by itself after a read GitHub cut or left something out of.
- No flood, none lost: the first read with no earlier read on record (a new obid, one that never read GitHub, or the first after signing in again or as another login) offers nothing, it only notes what's there. After that, at most 5 items per read, the newest first; the rest wait for the next reads (kept in `home/github-work.json`, at most 100, across restarts), each while it's still in the feed and still offered, so a burst arrives 5 a read. Assigned issues on repositories obid doesn't work in, and your own pull requests whose checks didn't fail, get no inbox item: they're in the feed only.

#### Who reaches it

- On loopback, with obid's API token, like every endpoint.
- Through the gateway, a paired phone can `GET /v1/github/work`, `POST /v1/github/work/refresh` and `POST /v1/github/work/{id}/start` (obid only: the gateway). The list is read-only, and a start does no more than `POST /v1/jobs`, already on the allowlist, would, with obid's own task. The phone gets the feed scrubbed as any answer is.
- Another Obi never does: nothing in Obi-to-Obi exchanges reads the feed or starts work from it, and its typed actions are unchanged.

#### Whose words: the owner's, or untrusted

Issues, pull requests and comments written by the owner or by members of the owner's GitHub organizations count as the owner's own words, not as untrusted (the owner's decision of 2026-10-24); text from anyone else stays untrusted. Either way it's still quoted data, never instructions, and trust changes only whether a turn is untrusted (so whether the work it starts may run in Bypass), never what an agent is told (`github_work.rs`, `Owner::trusts`).

- **Who counts.** The owner's own login, on any repository; or `OWNER` or `MEMBER` of a repository whose owner is the owner or one of the owner's organizations. Never `COLLABORATOR`, `CONTRIBUTOR`, `FIRST_TIME_CONTRIBUTOR`, `FIRST_TIMER`, `MANNEQUIN` or `NONE`, and never a member or the owner of another organization's repository (a `MEMBER` of `acme/app` is a member of `acme`, not of the owner's organizations).
- **The owner.** obid's own `gh` login (`gh api user`) and its organizations (`gh api user/orgs --paginate`; gh's `read:org` scope shows private memberships), kept for 10 minutes, and only while GitHub says the read at hand was made as that login: after `gh auth switch` the old login's organizations never count; organizations that couldn't be read are read again next time.
- **Never the owner's words.** What Oby wrote, under whoever's login: a pull request an obid job opened, and any text carrying Oby's signature `by Oby:` (what a teammate's Oby publishes under a member's login too; text that only forges it is untrusted, which fails closed). Every review obid posts on GitHub (Oby's review the owner approves, the reviewer account's approval, a teammate Oby's approval) carries it: one that doesn't already ends with `by Oby: Oby wrote this review.` Every issue Oby files under the owner's login with a model's or agents' words is signed so: an `oby-failure` issue (`by Oby: Oby's post-mortem of a failure, filed by the runner.`), a review follow-up issue (`by Oby: Oby's reviews of [pull request #N](…) found these items worth doing later:`) and a research job's proposed issue (its body, then `by Oby: a research job proposed this issue, and it was filed from Oby.`). A pull request's lookup (`view_pr`), whoever opened it: anyone who can push to its branch writes its files, branch and commits under its author's name. Labels, which whoever triages sets: a trusted issue's lookup leaves them out.
- **What an issue's lookup checks** (`view_issue`), with one more query after gh's answer (`gh api graphql`: who wrote, edited and renamed it, and as which login gh read it), so an edit made in between counts: its author and every comment's count; every edit of its description and of each comment (`userContentEdits`) was made by that text's author or the owner (a collaborator can edit a member's words, which keep the member's association); every rename of its title (`RenamedTitleEvent`) was made by its author or the owner; and no text carries `by Oby:`.
- **Fail closed.** An association, editor or renamer obid couldn't read, a list GitHub didn't give whole (more than 20 edits of one text or renames, more than 100 comments), a comment gh showed that the check didn't read, organizations it couldn't read (then no organization's member counts), a login it couldn't read, or a check that didn't end within the lookup's 10 seconds (gh's view and every read of the check share them): untrusted.
- **Where it shows.** Each feed item has `association` (GitHub's word, or null) and `trusted` (its author counts, as of the read that found it, and no obid job opened it), and its `github` inbox item carries both under `github`. The quoted file a job gets (`.obi/inputs/github-<name>-<n>.md`) names each author as `@login (MEMBER)` (just `@login` when GitHub didn't say), inside the same `GitHub, written by people` fences: never whether their words count as the owner's.
- **What it changes.** A conversation's `oby_inbox` doesn't taint the turn when everything waiting is a `github` offer with `trusted` true (an offer's text is obid's own sentence from typed fields); anything else waiting still does. A plan-loop `view_issue` that passes the check above doesn't make the turn count as researched; a `view_pr`, any other lookup, a refused one, or one that didn't run still does. That holds for everything the turn's `work.md` quotes, not only the plan at hand: a "continue" turn quotes the last turn's lookups, so one that carries anything but a trusted `view_issue` counts as researched from its first step, even when it looks nothing up itself. Reading files, a command's output, the web, attachments and a job's words taint exactly as before.
