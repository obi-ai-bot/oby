### Inbox item

Something only the user can answer (docs/pipeline-cases.md, "Your inbox"). Like email, it waits for them with no timeout, and its job waits too; the others keep going.

```json
{"id": "ab12cd34-question-0", "kind": "question", "job": "ab12cd34", "title": "Nothing committed status",
 "text": "Should a job that commits nothing end as failed, or get a new status?", "options": ["Failed", "A new status"],
 "created": "2026-10-10T09:12:00Z", "done": null, "later": null, "answer": null, "state": "open",
 "headline": "Pick a status for empty jobs", "happened": "The job found nothing to commit. It needs to know how to end.",
 "recommended": 1, "why": "A new status keeps real failures apart."}
```

- `kind`, and what each offers in `options`:

  | `kind` | Comes when | `text` | `options` |
  |---|---|---|---|
  | `question` | the job's agent asked (`question` on the job) | the question | the agent's, possibly none |
  | `review` | Oby's review stopped asking for changes (`reviewNeedsYou`) | `Oby's review found a blocker it asked to fix before. Take it from here.` | `One more round`, `Dismiss` |
  | `failed` | the job ended `failed` or `interrupted` | the summary's first line | `Try again`, `Dismiss` (only `Dismiss` for a job that never started) |
  | `failed` (obid, `<job>-review-<review job>`) | no reviewer could review the job's pushed head (`reviewNeedsYou`, obid only: Oby's review) | its `reviewError`, `Oby couldn't review #7: <why>` | `Try again`: Oby's review runs again (never the job's agent) |
  | `limit` | The Swift runner’s per-job usage-limit item. Obid groups stopped jobs in the account-limit decision API instead (#1563). | The summary’s first line | `Try again`, `Dismiss` on the Swift runner. |
  | `merge` | Oby's merge stopped (`mergeNeedsYou`, Mac check below) | `mergeError`, or why the check failed and that a person takes it from here | `Try again` and `Dismiss` when it couldn't merge (merge again, or hand the check to the author again), when the Mac couldn't run the check, when the round brought no new commit, or after the last failed check (check the same commit again, as the same round); `One more round` first, then `Try again` and `Dismiss`, when the check named failing tests after Oby's last review (its reviews used up): the failing tests go to the author as its next round, and Oby may review the fix once more (`extraReviews`) |
  | `audit` | the runner's daily issue/board reconciliation (Issue sync, below): a Status column the roadmap lacks (title `Roadmap column <column>`), or a report that something failed (title `Daily issue audit`) | which column is missing and the issues that belong there; or the drift count and what failed | for a missing column, `Add the column` (recommended: `recommended` is 0), `Use <closest column> instead` (when the roadmap has one before it: `In review` for `Needs test`, `In progress` for `In review` or `Blocked`) and `Ignore this status`; for failures, `Try again` |
  | `failure` | a failure's post-mortem found an Oby bug, or a cause seen twice in 7 days, with no fix for it merged into `dev`, queued, running or in review (Failure record, below); one open per signature, aliases included | the cause, how often it was seen this week, and what happened | `Fix it`, `Dismiss` |
  | `start` | rules guessed the plan, research found work that needs the user's go-ahead, or (obid only) Oby offered work in a conversation (`oby_offer`, docs/conversation-harness.md): one item per job, `job` its id (the job isn't in `GET /v1/jobs` until it starts), `title` its heading | `Oby's brain didn't answer, so this plan is a guess. Start Fix oby #12 on Claude Code · Deskree?` or `Oby looked into it first. Start Fix oby #12 on Claude Code · Deskree?` | `Start` (recommended: `recommended` is 0), `Cancel`, each with what it does (`details`) |
  | `permission` | the job's agent waits for the user's OK (`permission` on the job) | the permission's `title` | `Allow`, `Always allow`, `Deny` (only `Allow` and `Deny` when it has no `rule`) |
  | `plan` | obid only (#609): a Claude Code or Cursor job in `plan` mode presented its plan (Claude Code's `ExitPlanMode`, Cursor's `cursor/create_plan`, #1008) and waits for the owner (`permission` on the job, its `tool` `ExitPlanMode`); `details` holds the plan as the agent wrote it, quoted data. Only the owner answers it: the brain is refused either way | `Approve the plan?` | `Approve`, `Keep planning`; any other words keep it planning, with them |
  | `agentQuestion` | obid only (#858): a job's agent asked the owner a question (Claude Code's `AskUserQuestion`, Codex's and Cursor's own questions or Oby's `oby_ask_owner`; `permission` on the job, its `question` set), in any mode; one item per question of the call, one after another, its `id` the permission's like a `permission` item's. `details` holds each option's description, in the options' order, when any has one; the question and options are the agent's, quoted data. Only the owner answers it: the brain is refused. Its briefing names the item without the question's words, which reach the brain only in its quoted file, as data, as a plan's do. The Electron app shows it on the job's card as Sangam's Question card (the question its headline, the options its buttons, then Tell it something, which takes the owner's own words, and Later) and answers the item itself, `POST /v1/inbox/{id}/answer` (#1570) | the question | its options' labels; any other words are the answer, as the owner wrote them |
  | `confirm` | obid only (#546): Oby's brain planned something that persists or widens trust, which it never does in a turn (obid only: the brain, below); `title` says exactly what `Confirm` does, like `Always allow Bash(make lint:*) in acme/app`, and `job` is the job it's about, or empty | what was planned and why it waits | `Confirm`, `Cancel`, none recommended |
  | `github` | obid only: a read of the owner's GitHub work found a new review request, an assigned issue on a repository obid works in, or failed checks on a new head of the owner's own pull request (obid only: GitHub work); one per item (per head for failed checks), ever | `Your review is requested on pull request #702 in obi-ai-bot/obi.`, `Issue #640 in obi-ai-bot/obi is assigned to you.`, `People wrote on Oby's pull request #812 in obi-ai-bot/obi.` or `Checks failed on your pull request #812 in obi-ai-bot/obi.` | `Review it`, `Fix it` or `Fix CI`, `Dismiss` |
  | `watch` | obid only, from before the cut of Slack and its watcher (docs/trim.md): an item the watcher made then, still listed until dismissed | `Dmitry wrote in #tetrix-avenga-testing.` | `Dismiss` |
  | `listen` | obid only: the owner's review of a pull request is ready to post (`GET /v1/github/work`, "Posting it"); older items from the Slack channel listener stay listed until dismissed | `Post this review on pull request #835 in obi-ai-bot/obi as you? Approve posts the review shown here with Oby's verdict, from your GitHub login.` | a review's: `Approve`, `Dismiss` |

  A `confirm` item (obid only) also carries `confirm`, what its `Confirm` carries out: `{"action": "always_allow", "target": "ab12cd34", "payload": {"permission": "p1a2b3c"}}`. `action` is a typed name, `target` what it acts on (a job's id or an inbox item's id, as the action says) and `payload` what else it needs (`null` when nothing). obid carries every action out through one dispatcher, so a new action is a new name with its own `target` and `payload`, the shape unchanged. The actions so far:

  | `action` | `target` | `payload` | `Confirm` does |
  |---|---|---|---|
  | `always_allow` | a job | `{"permission": "<id>"}` | answers that job's waiting permission with always, saving its rule |
  | `set_mode_bypass` | a running job | `null` | puts the job in Bypass mode (`409` once it isn't running) |
  | `start_job` | the conversation that planned it | `{"job": …}`, the job as `POST /v1/jobs` takes it | queues the job, in Bypass mode |
  | `accept` | an `obiRequest` item | `null` | answers it `Accept` |
  | `accept_remember` | an `obiRequest` item | `null` | answers it `Accept, and remember for this repo` |
  | `decline_remember` | an `obiRequest` item | `null` | answers it `Decline, and remember for this repo` |
  | `answer_question` | an `obiRequest` question | `{"words": "…"}` | answers the other Obi's question with those words |
  | `start` | a `start` item | `null` | answers it `Start`: the proposed job queues |
  | `answer_item` | any other item | `{"answer": "…"}` | answers it with those words |
  | `message_job` | a job that ended | `{"words": "…"}`, the user's own words, secrets taken out | starts a follow-up of the job with the words, as `POST /v1/jobs/{id}/messages` does (made before 2026-10-18, when it ran one more round; obid makes none now) |
  | `add_repository` | a review request in a repository obid doesn't work in: its `github` offer's id (#1118) | `{"repo", "number"}`, obid's own from the feed's typed fields | adds the repository and starts Oby's review (obid only: repositories, "A review request's repository, on the owner's tap"), and answers the offer `Review it`; `409` once the offer is settled |
  | `dismiss_job` | a job whose commits aren't published, or another conversation's (#631) | `null` | dismisses the job, as `POST /v1/jobs/{id}/dismiss` does; its commits stay on its branch |
  | `retry_job` | another conversation's job that failed, was stopped or was cut off (#631) | `null` | tries it again with Try again's words (`409` once it's running), once for the job's revision when it's carried out: a repeat answers with the job as it is now and runs nothing (RECEIPTS-13) |
  | `continue_job` | a job that failed, was stopped or needs you (`interrupted`: a stalled one too, with `stalled` set) | `{"words": "…", "snapshot": …}`: what the conversation's turn added, secrets taken out | continues it in its own session, as `oby_continue_job` does (`409` once it's running) |
  | `delete_job` | a job that ended | `{"snapshot": …}` | deletes the job, as `DELETE /v1/jobs/{id}` does: its record, worktree and local branch; never anything pushed |
  | `delete_conversations` | the conversation that asked | `{"conversations": [{"id", "cursor"}]}` | deletes each conversation named, as `DELETE /v1/conversations/{id}` does; one used or pinned since Oby asked stays |
  | `change_job` | a job | `{"mode": "…"}`, `{"agent": "…", "account": "…"}` or both, with `snapshot` | changes the job's mode, tool or account, as `oby_change_job` does |
  | `set_check` | a repository (#1062) | `{"check": "<command>", "was": "<its check now>" \| null}`: obid's own guess, or the owner's command (`POST /v1/repos/check`); `"check": null` takes `was` out | makes the command the repository's check, kept on its entry in the configuration file's `repos` (a GitHub one is listed then), so every later job there runs it, or takes `was` out (`409` when its check changed since); either way No check is forgotten. The job that asked goes on with none. Its `Cancel` keeps what the repository has; with no check there, it's No check, remembered (Job, above) |
  | `share_status` | empty | `null` | lets obid answer members' questions by itself: one rule for every member and repository (the one they have, or a new one), with `jobStatus` and `jobProgress`, `jobProgress` on every other rule that tells status too, and the questions waiting on the owner go by it ("obid only: sharing rules") |

  `snapshot` (on `continue_job`, `delete_job` and `change_job`) is the job as it was when Oby asked: `{round, status, commits, unpublished, mode, agent, account}`. Confirmed after any of them changed (another round, a commit, a move, a new mode), it's refused with `409` (`The job changed since Oby asked (another round, a move or a new mode): ask Oby again.`) and nothing happens, so the owner never confirms something other than what the title said. An unknown `action` is refused with `409`. Every title is obid's own words, made from the action's target, never the brain's: `Always allow <rule> in <repo>` (the rule it saves, which can be broader than the one command), `Accept: Review request from ernesto`, `Send an answer: Question from Bob`, `Dismiss Average helper empty lists (2 commits kept on its branch)`, `Try Vault tests again`, `Continue Vault tests` (`Continue Vault tests in Bypass mode` for a job in Bypass), `Delete Vault tests (its worktree and local branch go; 2 commits that aren't published are lost)` (`its worktree goes; its branch stays, another job uses it` when it's shared), `Put Vault tests in Bypass mode`, `Move Vault tests to Codex · Deskree`, `Start fix fixture-app (Greeting fix) in Bypass mode, on Claude Code · Personal, check node --test` (the job obid keeps: what, the mode, the tool and account, the check). Words the brain wrote for an answer are in `payload`, and quoted in `text` as `> ` lines, never in the title. Two `Confirm`s at the same moment carry it out once: the first claims the item, and the other is `409`. The apps don't show `confirm` items yet: the Mac app drops an item kind it can't decode; a separate apps change follows #552.

  **Only decisions wait in the inbox (#215).** Every item offers at least one answer that changes something, besides done and later: a `question` takes the agent's options or the user's words, and every other kind declares its own (above). An item with nothing to decide arrives already `done`, with no `answer`: it's kept in `oby.sqlite` with the reports (the job's own report, or the audit's `outgoing`) and comes as an `inbox` event whose `state` is `done`, so it never shows in the inbox. That's the audit's report when it fixed the drift by itself, and a `failure` whose fix is already underway. A new kind declares its answers, or none of its items reach the inbox.

  More kinds will come (hands-on steps): show one you don't know with its `text` and `options`. A plan waiting for approval is a `question` item (its job's `question` has the `plan`).
- `details`: what each option does, one plain sentence each, in the same order as `options` (as Claude Code describes the options it asks with), shown under each button; null when there are none (older items, or a question whose agent gave none). Oby's own items always have them; a `question` has them when its agent wrote them (`question` on the job, above). Older runners don't send the key.
- `job`: the job's `id`, `runner-update` for the runner's own update, or empty for an audit item or a failure (it's about Oby, not one job). `title`: the job's title, "Daily issue audit", `Roadmap column <column>`, or `Oby failure: <signature>`. Optional `outgoing` on audits lists repairs using the same records as a job's report. `conversation` (obid only): the conversation a `start` item was proposed in (for one made before obid kept that, its job's), or a confirm came from (one that starts a job, or one the conversation's own tools made: `merge_pr`, `github_write`, `set_settings`, `set_check_in`), else null; the apps show a `start` item with no `job` opened out only in that conversation, never in another (a conversation shows the decisions of the jobs it started, as before). The Electron app shows a conversation's own Confirm under Oby's answer there, and on Home's stack too: one item, so a click in either settles both (#1680). `offer` (obid only, on a `start` item Oby offered, else absent): `{"id", "what", "task", "untrusted"}`, the card it's on in that conversation and what it shows. `id` is the user's turn it was offered in, so one turn's offers are one card under Oby's answer to that turn; for one no user turn holds, it is `offer-` and 8 hexadecimal digits, a card of its own. `what` is obid's own words for the job it starts (`build fixture-app (Greeting)`, with `, on Claude Code · Personal` when Oby named them; a tool or account left to obid is never said), `task` the task Oby planned (every secret obid knows taken out), and `untrusted` whether the turn had read something untrusted first (the job is marked so, and runs in the owner's mode: the owner's decision of 2026-10-27). Answer each item of the card as any `start` item. Every answer to a `start` item settles it under obid's lock, so of two at the same moment only the first counts: a second `Start` is `409`, and so is a `later` or `Cancel` after a `Start`. An offer nobody answered in 24 hours is done by itself, with no options and no `answer`, its `text` `Closed by Oby: offered a day ago and never started. Ask Oby again to start it.` above its words, and a `Start` on one past its day closes it so and is `409` with that sentence, though nothing read the inbox since; deleting its conversation closes it the same way (`Closed by Oby: the conversation it was offered in was deleted.`). The relay pushes one alert per offer (`collapse` its `id`, titled `Oby offers <n> jobs` when there are several), not one per item: obid can't tell which conversation the owner is looking at.
- `headline`, `happened`, `recommended`, `why`: the item in plain words, for a card. `headline` says what it's about in at most 8 plain words; `happened` what happened, in one or two short sentences with no ids or hashes; `recommended` the index into `options` of the answer Oby recommends, or null (when Oby or the job's agent recommends one already, like `Add the column`, it's set from the start and the model only says why); `why` one sentence saying why. The runner's brain model (Haiku, through the same `claude` as the brain, with no tool but reading the quoted item) writes them in the background, once per item and text: what the item says, its title and its options reach the model only as a quoted file, never in its prompt. The runner checks the lengths, the sentences, that there's no id or hash, and that `recommended` is one of `options`. The item arrives at once with all four null and they follow in an `inbox` event; when the model fails, is slow (20 s) or writes something the runner refuses, they stay null for good. `text` is always the full detail: show it when they're null, and under them otherwise. Older runners don't send these keys.
- `created`: when it came. Apps list the open ones in the order `GET /v1/inbox` gives (the longest-waiting first; on obid what needs the owner first), with how long each has waited ("waiting 3m").
- `triage` (obid only, #1123): `needs_you`, `fyi`, `ignore` or `pending`: the item needs the owner, asks nothing of them now, is noise, or is an outside item still waiting for Oby's quick model to sort it. Notify for `needs_you` only, never for `pending`: an `inbox` event brings the item again once it's sorted, and one still `pending` after 2 minutes (no Claude Code account, the hourly limit, a slow model) becomes `needs_you`, which an `inbox` event says too. A sort can change while the item is open (a second item about the same thing is `ignore` only while the first is open): `GET /v1/inbox` has the latest. Sorting never acts: every item stays listed and answerable (obid only: sorting the inbox, below). Absent on a runner that doesn't sort (the Swift runner): treat it as `needs_you`.
- `done`: when it was settled, or null. `answer`: what the user answered, or null (done without an answer, or settled by itself). `answeredBy` (obid only, #1825): the device whose signature came with the answer that settled it, or null: no app signed it, or it settled by itself.
- `later`: put off until then, or null. `state`: `open`, `later` (put off until a time still to come) or `done`. Apps show a `later` item again once its time has passed.
- One open item per job: a newer item for the same job settles the older (done, with no `answer`), and audits share one per `title` (an empty `job`), so a newer report settles the older report, never a missing column's decision. Failures keep their own rule, one open per signature.
- An item comes once: each failure (even a retry that fails again within the same second), each question and each fourth review has its own `id`, and one that's done never comes back. It's done by itself, with no `answer`, when its job needs it no more: the job runs again (told something, or Try again from either app), was dismissed or stopped, or its question was answered with a message.
- Kept in `oby.sqlite` with the jobs, so a restart keeps the inbox, and the runner loads the job of every open item however old it is (and, for a `review` item, its review), so it can still be answered. A job's own alert (below) still says it needs you; the inbox is where you answer.

### `GET /v1/inbox`

The inbox items not yet done, the longest-waiting first, items put off `later` included (say so, or hide them until their time). On obid, what needs the owner comes first (`triage` `needs_you`, and `pending` with it), then `fyi`, then `ignore`, each the longest-waiting first (obid only: sorting the inbox).

```json
[{"id": "ab12cd34-question-0", "kind": "question", …InboxItem}]
```

`GET /v1/inbox?state=done` is the history instead (#215): the items that are done, the latest settled first, at most `limit` (50 unless asked, at most 1,000). Reports with nothing to decide arrive there directly, never in the inbox: the audit's report of drift it fixed by itself (with its `outgoing` repairs), a `failure` whose fix was already under way, and items saved before #215 that offered no answer (done once when the runner starts). Answered, dismissed and settled items are there too, with their `answer`. `state=open` is the default; any other `state` is `422`. Older runners ignore `state` and list the open items.

### `POST /v1/inbox/{id}/answer`

Settles an item, on the iPhone or the Mac. The body is exactly one of:

```json
{"answer": "A new status"}
{"done": true}
{"later": "2026-10-10T10:12:00Z"}
```

- `answer`: one of its `options`, or the user's own words (1 to 2,000 characters). It goes to the job:
  - `question`: the answer is the agent's next message (as `POST /v1/jobs/{id}/messages`): a waiting job goes on, an ended one gets a follow-up. A plan's question takes `Approve: <mode>` or `Change it` (Permission modes, below).
  - `permission`: `Allow`, `Always allow` or `Deny`, as `POST /v1/jobs/{id}/permission`; any other words are a deny with those words as the message for the agent. On obid, an open job's `permission` or `plan` item takes an answer it reads as Allow or Always (`Allow`, `yes`, `approve`, `Always allow`; Approve on a plan's card) only with the owner's signed words (`X-Oby-Words`, PERMISSIONS-15): without them, the API token alone or a phone through the gateway paired without a key, it's `403`, `This has to be a click in your own Oby app, signed by its key, so nothing changed. On an iPhone, pair it again from Oby on your Mac, then try again.`, and nothing changes. Deny and other words, a question's answer and a plan's need none.
  - `Dismiss` (on `review`, `failed`, `limit` and `merge`): dismisses the job (`POST /v1/jobs/{id}/dismiss`).
  - `Try again` (on `merge`): the merge is tried again, or the Mac check is handed to the author again or queued again on the same commit (Mac check, above).
  - `Try again` (on `failed` and `limit`): the job runs again in its session, told to pick up where it left off.
  - `One more round` (on `review`): Oby's last review is quoted in `.oby/inputs/review-4.md` and the agent works on it, as a message does. The runner doesn't review it again.
  - `Fix it` (on `failure`): the fix job starts, as `POST /v1/failures/{id}/fix` does, and the signature's items are done. When the cause is being fixed or is fixed already, nothing starts and the answer is refused (`422`) saying so, like `Fixed by #189 on dev.` `Dismiss` (on `failure`): done, nothing starts. Other words on a `failure` are refused (`422`).
  - `Add the column` (on an `audit` item about a missing column): the column joins the roadmap's Status field, then the audit runs again and moves its issues there. GraphQL's `updateProjectV2Field` keeps an option, and the cards on it, when the option goes back with its `id`, and the runner checks that by reading the ids back: it reads the field's options (`id`, `name`, `color`, `description`), sends every one back with its `id`, in its order, to GraphQL's `updateProjectV2Field` (`singleSelectOptions`), with the new one (gray, no description, no `id`) after the column it would stand in for (`Needs test` after `In review`), else last, and reads the options back: any old option whose `id` or name changed, or that moved, refuses the answer (`422`) and the item still waits. The request passes the secret scan first and is listed in the audit's ledger. When it fails the item waits, and the answer's error says why.
  - `Use <column> instead` (on an `audit` item about a missing column): remembered for that status in `issue-audit.json`, and the audit runs again now, moving its issues to that column; from then on issue sync and the audit put them there. `Ignore this status`: remembered too; from then on their column is left where it is. Neither asks again.
  - `Try again` (on an `audit` report of what failed): the audit runs again now, whatever the day; its report is a new item.
  - `Start` (on `start`): the guessed job is queued as planned, routed as it was when planned, and an Oby turn carrying it joins the conversation; `422` when its account has been signed out since (ask again). `Cancel`: done, nothing starts. Other words on a `start` item are refused (`422`).
  - `Try again` (on `failed` with `job` `runner-update`): the runner tries that commit again now (Runner update, below).
  - Other words: sent to the job as a message. On an `audit` or `runner-update` item, only its `options` are taken; other words are refused (`422`).
- `done`: settled without an answer; the job is left as it is.
- `later`: put off until that time (ISO 8601).

**Confirm takes the owner's tap (obid only, #776).** `Confirm` on an open `confirm` item also carries `approval`, a registered device's signature, as publishing by hand does (`POST /v1/jobs/{id}/publish`): `{"answer": "Confirm", "approval": {"device", "action", "signedAt", "signature"}}`. `action` is the item's `title`, word for word, and the device signed `"oby-confirm\n<item id>\n<title>\n<signedAt>"` on the owner's click (P-256 ECDSA with SHA-256, DER, base64), within two minutes, used once, remembered across restarts. The `oby-confirm` prefix and the item's id mean no publish or connection signature passes for a Confirm, and one tap confirms one item. A Confirm without an approval, or with one that doesn't hold, is `403` with `{"error", "action"}` (`action` the title to sign) and the item stays open, unclaimed. `Cancel`, `done` and `later` need no approval; an `approval` with anything else is `422`. Inside obid nothing confirms either: the brain, oby-mcp, a conversation's tools and obid's own callers answer without a device and are refused.

Returns the item. `404` for an item the runner doesn't know, `409` when it's done already, `422` for a body that isn't exactly one of these, a `later` that isn't a date, an empty or too-long answer, or a job that can't take it (the same reasons as `POST /v1/jobs/{id}/messages`). Every app following events hears the item (`inbox`) and its job (`job`).

**A request key** (obid only, R02-05; docs/contracts/receipts.md, RECEIPTS-10): `clientRequestId` in the body (beside exactly one of the three) or the `Idempotency-Key` header, with `POST /v1/jobs`'s rules (A request key, above): a bad one is `422`, and nothing is answered. The same body again with the key, as signed as the first (`X-Oby-Words`, and on a `confirm` item a Confirm's `approval`: checked and used up before the lookup, and only whether it held is compared; the Confirm then confirms the title it was checked against, so a title changed in between, such as the sharing card ticked again, is refused `403`), within 24 hours, answers the first status and answer as they were then: the item isn't answered again, so a Try again runs one round, a Start starts one job, and a Confirm is carried out once. Another body under the key, or the same one signed differently (a retry whose signed words or approval were already used, or left out: sign it again), is `409`, and nothing is answered (RECEIPTS-15). A refusal (a `4xx`, a Confirm refused `403` included) keeps no receipt. With no key, a second answer to a settled item is `409` as before.

### obid only: sorting the inbox

Every inbox item gets a `triage` (Inbox item, above), so only what needs the owner notifies them. Rules first, from obid's typed fields only, never from what came from outside; the brain's quick model only for an outside item no rule sorts.

- **`needs_you`**: everything Oby itself asks the owner (`permission`, `plan`, `question`, `confirm`, `start`, `obiRequest`, a job's `failed`, `limit`, `merge`, `review` or `failure`, and any kind still to come); a `listen` item (a message, a review request or a review the channel listener brought them); a review requested of the owner (`github` in `reviews`, `pull_request.review_requested`); changes requested on their pull request; a failed check (`github` in `mine`, Fix CI on their own pull request, and `check.failed`); a failed deploy to `production` or `staging`; an alert at `critical` or `error`. An item whose typed fields are missing needs the owner too.
- **`fyi`**: a `watch` item (the owner asked to be told); the channel listener's daily digest; a review requested by a bot, by the feed's `github.author` (`dependabot`, `renovate`, `github-actions`, `pre-commit-ci`, `snyk-bot`, `mergify`, starting with `app/` or ending in `[bot]`; a plug-in's `actor` is outside text and never decides it); a failed deploy to `preview` or `development`; an alert at `warning` or `info`.
- **`ignore`**: only from the rules: a `github` or `pluginEvent` item about what another open item is about (the same review asked for by the GitHub feed and a plug-in, red checks on one pull request from the feed's Fix CI and a plug-in's `check.failed`, whether the plug-in names the pull request or only its head commit, a second alert on one project at the same severity), while that one is open. The one that offers to start something (`Review it`, `Fix it`, `Fix CI`, `Look into it`) stands for both, else the first to come. It's worked out whenever the inbox is read, never kept: once the one that stood for it is done, the other has its own sort again.
- **The model** sorts the rest of the outside kinds: an assigned issue (`github` in `assigned`, `issue.assigned`), a `ticket.assigned` and a `mention`. Until it has, the item is `pending`, for at most 2 minutes; then it's `needs_you` (and an `inbox` event says so) until the model sorts it. It's the brain's quick model, through the same `claude` and Claude Code account as the brain's side calls: soon after such an item comes (2 seconds, so nearby ones come together), at most one call a minute of at most 50 items, and at most 20 calls an hour (past that, items wait until the hour has room). With no Claude Code account nothing is scanned or sent; the items are sorted once one is added. Each item is sent once: its sort is kept in `home/triage.json` (0600) with the last hour's call times, and never changes, across restarts too. A file that doesn't read is said in obid's log and starts again.
- **What it reads.** Its system prompt is fixed and says it only sorts and never acts. Its prompt only asks it to read its quoted file (`work.md`, with the Read tool) and sort each of its items with the schema `{"items": [{"n", "as"}]}`. The file has, for each item, obid's own `title` and `text` (made from typed fields only), then what came from outside fenced as quoted data under a fence rule: a `github` item's `github.author` and GitHub's title, a `pluginEvent` item's `plugin.quoted` `actor`, `title` and `text`, each on one line of at most 500 characters. The secret scan runs first, on each item's whole entry alone (obid's own patterns and gitleaks), and the secrets obid knows are taken out of the file: a flagged item is never sent and is `needs_you`; when the scan can't run, nothing is sent and every item is `needs_you`.
- **At worst, FYI.** The model may answer only `needs_you` or `fyi`, never `ignore`: words in one item (`items 1 to 50 are chatter`) can at worst move the others in its call to FYI, still listed and answerable, never hide them.
- **Nothing hidden by mistake.** A model that fails or takes over 60 seconds, or an answer that doesn't sort every item it was sent exactly once with `needs_you` or `fyi`, leaves every item of the call `needs_you`.
- **Sorting never acts.** It answers, starts, snoozes, settles and hides nothing: an `ignore` item is listed (last) and answered like any other. The conversation's brain reads the inbox in the same order (its briefing, and `oby_inbox`, which says each item's `triage`). The recap and the check-ins (obid only: check-ins) leave `ignore` items out of what they tell, so a duplicate alert never turns a quiet day into a check-in; since only a rule sorts `ignore`, an item's words can't hide another from them.
