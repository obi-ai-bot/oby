### `GET /v1/status`


`permissions.mode` is Settings › Permissions: the mode new jobs get (`PUT /v1/settings/permissions`). Older runners don't send the key.

`memory` (obid only): the machine's memory and what each running job's processes hold, in bytes. `total` is its RAM. `available` is what new work can take without the system compressing or swapping what's there: free memory plus what it drops for free (cached files, purgeable memory). On macOS that's `total` less Activity Monitor's Memory Used (app memory, wired and compressed, from `vm_stat`); memory the system could still compress isn't counted, since a Mac at 46% by `kern.memorystatus_level` was compressing 5.4 GB and swapping (2026-10-24). On Linux it's `/proc/meminfo`'s `MemAvailable`, the host's: a cgroup obid runs in (its `memory.max`, `memory.pressure`) isn't read. `pressure` is `normal`, `warn` or `critical`: the kernel's own level on macOS (`kern.memorystatus_vm_pressure_level`); on Linux `warn` when tasks waited on memory for 10% of the last 10 seconds (`/proc/pressure/memory`'s `some avg10`) or less than a tenth of `total` is available, `critical` when all of them did (`full avg10`) or less than a twentieth is. `jobs` has each running job's processes, `{id, rss, peakRss, agentPeakRss, checkPeakRss}`: `rss` is the resident memory of every process its agent and its check started, now, `peakRss` the most they held at once since it started, and `agentPeakRss` and `checkPeakRss` its agent's tree's and its check's, each at its most (each one leads a session of its own, so its tree is it, what descends from it and what's still in its group; memory two processes share counts in each). obid reads it every 5 seconds while a job runs (`sysctl`, `vm_stat` and `ps` on macOS, `/proc` on Linux; a few milliseconds each time) and not at all while none does; status asked then reads the machine's part afresh, at most every 5 seconds. A job's worker that ends keeps its `peakRss` on the job (Job, above). `waiting` is always `[]`: an obid before 2026-10-28 listed there each queued job it held back for memory (`{id, budget, since}`), and none is held back now (Jobs run side by side, above); the key stays for the apps that decode it. Left out when it can't be read. Older runners don't send the key.

`gateway` (obid only): the gateway's state, as "obid only: the gateway" says. Left out with no `gateway` configured. Older runners don't send the key.

`tunnel` (obid only): always `{"state": "off", "detail": null}` since the Cloudflare Tunnel went (2026-10-27), kept for the apps that decode it.

`vaultProblem` (obid only): why the vault can't be read, as "obid only: the vault" says; meanwhile every other `/v1` answer is `503`, but for the event stream once obid has read the vault. Left out while it reads. On obid the status looks again for a tool installed or signed in since it started at most every 2 seconds.

`availableLogins` (obid only): the tools' own logins obid found on this Mac that aren't accounts (looked for at start and again at every status, so a tool installed and signed in since, as during first launch, shows up without a restart), `[{"agent": "codex", "id": "codex", "name": "Codex"}]`; `POST /v1/accounts` `{"agent", "default": true}` lists one on the owner's word (obid only: accounts, "Logins already on the Mac"). Empty when there's none.

`scanner` (obid only): the secret scanner publishing needs, `{"gitleaks": true}`. `gitleaks` is `false` when obid has no gitleaks that runs: none in Oby.app or on its `PATH` (with the login shell's and the usual folders), or one that doesn't answer `gitleaks version` within 5 seconds. Then nothing with text is published (the scan couldn't run, Publishing), as before; this only says so from the start instead of at the first publish, and obid's log warns once when it starts. Each status looks for it again, as publishing does, so a gitleaks installed, removed or replaced since shows up without a restart; a run that worked is reused for at most 60 seconds, and only while the same file (path, size, modified time) is there, so one that stops running in place shows up within a minute. Older runners don't send the key.

`receipts` (obid only, R02-04): `true` when obid's receipt store opened, so `POST /v1/jobs` honours a request key (`clientRequestId`, `Idempotency-Key`; docs/contracts/receipts.md), and so do `POST /v1/jobs/{id}/messages`, `/stop` and `/move` and `POST /v1/inbox/{id}/answer` (R02-05); `false` when `home/receipts` couldn't be made, and a key is then only kept on the job. Older runners don't send the key: an app relies on a key only once it reads `true`.

`tools` (obid only, add-only, docs/contracts/cli-versions.md): each agent CLI's binary and version, one entry per tool in the order `claude`, `codex`, `cursor`. `path` is the absolute path of the binary the configuration's `bin` names, else the tool's default name (`claude`, `codex`, `cursor-agent`) as a run finds it, or null when none is found. `version` is the first version-looking word its `--version` printed (run with a 5 second limit, a cleared environment, the login `PATH` and an empty folder of obid's as its home: no account, login or token reaches it), or null when it exited non-zero, ran past 5 seconds, printed no version or no binary was found. obid reads at start, and again only when the binary's resolved path, size or modified time changed: status looks at that at most once a minute per tool, a round's start every time. A version that can't be read never fails status or a job. `versionStatus` (obid only, add-only) is that version's status in obid's table of tested and known-bad versions (`core/crates/obid/cli-versions.json`, CLIVERSIONS-7), a string: `tested` within the tool's tested range, `knownBad` when listed as known to break, `untested` otherwise (no version, one obid can't compare, or a tool the table doesn't name); a new value may come. `knownBadReason` (obid only, add-only) is the table's reason, present only when `versionStatus` is `knownBad`. Automatic routing ranks a known-bad tool's accounts last (CLIVERSIONS-8). Older runners don't send the key.

`unreadable` (obid only, add-only, R02-12, docs/contracts/home.md HOME-8 and HOME-9): the files obid didn't load, always present and `[]` when there are none. It covers every folder obid reads one `*.json` file per record from: `home/jobs` (and `home/jobs/groups`), `home/conversations`, `home/inbox`, `home/exchanges`, `home/routines` and `home/failures`. A file whose bytes don't parse is moved, with `rename` and its bytes unchanged, to `home/unreadable/<its folder>/<name>-<unix seconds>.json`; one obid can't read, or can't move (the folder can't be made, the name is taken), stays where it is. Each entry is `{"path", "error", "since"}`: `path` is the file's absolute path now, `since` when it was kept aside (the seconds in its name, else the file's last change), and `error` a short reason that never quotes the file: `not valid JSON at line L column C`, `not what obid expects at line L column C`, an I/O error's kind (`permission denied`), or `kept aside at an earlier start` for a file found in `home/unreadable/` at a later start. obid never loads, repairs or deletes a file under `home/unreadable/`, and a conversation whose file is there keeps its folders. Older runners don't send the key.

`folders` (obid only, #1572): `true` when obid takes working folders: `folders` on `POST /v1/plans`, on conversations and on `PATCH /v1/conversations/{id}` (obid only: working folders, below). Older runners don't send the key, and refuse `folders` with a `400`: an app sends none until it reads `true`. `folders-v1` in `capabilities` announces the same thing.

`capabilities` (obid only, add-only, R06-01, [docs/contracts/capabilities.md](contracts/capabilities.md)): the optional features obid serves, by stable name, sorted, with no duplicate, always present. A name means one behaviour forever: a changed behaviour gets a new name (`-v2`). The table below lists every name obid serves. A client hides an action whose name is missing. Older runners don't send the key: such a client falls back to that feature's own key (for example `folders`) or treats the feature as absent.

| Name | What it means | Since |
|---|---|---|
| `events-replay-v1` | `GET /v1/events` numbers its events with an `id: <epoch>-<seq>` line, and resumes a client that sends the last one it had (`?after=` or the `Last-Event-ID` header): it replays what the client missed, or sends one `resync` when it can't. | R06-02 |
| `folders-v1` | obid takes working folders: `folders` on `POST /v1/plans`, on conversations and on `PATCH /v1/conversations/{id}`, the same behaviour `folders: true` announces. | The behaviour since #1572, listed since R06-01 |

`cleanup` is the runner's job-worktree disk usage and cleanup status. `path` is the worktree folder, `bytes` is its allocated disk usage, and `lastRun` is when the last cleanup pass completed, or null before the first pass. The runner runs cleanup at startup and every three hours. It removes a worktree only for a settled job finished more than 24 hours ago (merged, closed, dismissed or stopped), or immediately after an Oby review job has a verdict; open pull requests, jobs needing the user, queued or waiting jobs, and worktrees in use by an agent, check, publish or merge are kept. Older runners don't send the key. obid answers before it has measured a big worktrees folder (it waits for the walk 200 ms at most) and leaves `cleanup` out until the walk ends, then sends it as the `cleanup` event.

obid's cleanup pass (`home/worktrees/<job id>`) runs 30 seconds after it starts, in the background (its first answers never wait for it), then whenever a job ends, is dismissed or archived, or Clear done is pressed, and every three hours. It removes a job's worktree once the job is settled: it ended and needs nothing (done, failed, stopped, or `interrupted` and dismissed), no worker or publish holds it, its pull request isn't open (merged or closed as obid last read it, or none), no follow-up on its branch is still at work, and it was put away (dismissed, archived, or finished by the last Clear done's `clearedAt`) or ended 24 hours ago; an Oby review job (`kind: review`, `obi` null) as soon as it ends. Even then a worktree stays when what's in it may exist nowhere else: a folder that isn't a git worktree (no `.git`) unless it's empty, one whose artifacts weren't all published (`artifactProblems`; `.obi/artifacts` is never a change git sees), one with uncommitted changes (untracked files too, ignored ones not), one whose HEAD is neither the job's `startCommit`, nor the commit it last pushed, nor on any of the clone's remote branches, and one git can't answer for. Each is in `kept`, `{job, why}`, as of the last pass. git looks at the worktree inside the job's sandbox, without the network, as for the `wip:` commit: the agent could have pointed the worktree's `.git` at a repository of its own, whose filters would otherwise run outside the box. obid runs git for a worktree (this pass, the `wip:` commit and taking it back out, keeping its commits, a run) only when its `.git` leads into obid's clone of the job's repository (its `.git`, and a folder directly in its `worktrees/` whose `gitdir` names this worktree, never another job's); else the worktree stays, `why` "Its .git doesn't point into obid's clone.", and a run fails. The job's own object folder is made only where nothing on the way is a link. The pass checks and takes the worktree away under the lock a job's worktree is made with, with `git worktree remove --force` and `git worktree prune` in obid's clone, and sets the job's `worktree` to null; its branch in the clone stays, so the job page, its diffs (kept on the job) and its artifacts (published when it ended) don't change, and a job that runs again (Try again) or a follow-up gets its worktree made again from its branch. A pass that removed one measures `bytes` again. obid sends `kept` (`[]` before the first pass); older runners don't.

A job that ended loses its builds on the next pass (obid only, [CLEANUP-1](contracts/cleanup.md)): one that ended (done, failed, stopped or interrupted) and no worker or publish holds, its pull request open or not, needing the owner or not, whether or not it was put away or ended 24 hours ago. Those are the folders git ignores in its worktree (`git ls-files --others --ignored --exclude-standard --directory`) and the folders of its HOME (`home/tmp/<job id>`) that a build makes again: a cache by its `CACHEDIR.TAG` (the Cache Directory Tagging convention, which Cargo's `target/` follows, a check's `CARGO_TARGET_DIR` too: a regular file of its own that begins with `Signature: 8a477f597d28d172789f06886806bc55`; a link, a pipe or another first line doesn't count), Xcode's `DerivedData`, cargo's and npm's caches (`.cargo`, `.npm`), and a `node_modules`'s `.cache`. A `node_modules`'s packages stay, and so does a Python virtual environment (a folder with `pyvenv.cfg`, which uv tags as a cache too), since a check runs without the network to install them again; so does anything in `.obi/`, anything reached through a link (the last part of the path included), the HOME's login copies and other files, and the worktree itself, for a follow-up, a fix round or Try again (which build again). A check that runs in a HOME whose `.cargo` or `.npm` went, with no agent run before it (Publish by hand), has no cached packages: the owner's choice of 2026-11-10. git lists the worktree's and `rm -rf` takes them all in the job's sandbox, without the network, so a link the agent left leads nowhere outside its worktree.

obid looks at the free space of the disk its home is on every 5 minutes (obid only, [CLEANUP-2](contracts/cleanup.md)). Under 20 GB free, the pass runs at once (and again every 5 minutes while it stays under) and frees the builds of every job that ended and no worker or publish holds, a check's since its last end included, oldest end first, until it freed what 30 GB free lacks; a queued or running job keeps them. `freed` in `cleanup` is what the last pass that freed builds freed, `{"bytes": 6436484096, "why": "Jobs ended."}`, or `"The disk had 12 GB free."` for a low disk; null before any did, and older runners don't send it. The job says what that freed in `buildFreed` (Job, below), measured before and after off the runtime's threads: an `rm` that stops partway still counts what went, and the log says why it stopped. A pass looks once per end, freed or not, and again after the job runs again and ends. A pass that freed space measures `bytes` again.

`runner.version` is the running API version. `runner.update` adds `{"commit": "<dev SHA>", "waiting": "<candidate SHA>", "phase": "draining"}` for Settings › Runner. `commit` is the running executable's dev commit, or null before its first self-install or after an untracked manual install. `waiting` is null when no update is pending. `phase` is `idle`, `building`, `ready` (built and tested, waiting for its turn to restart), `draining`, `restarting` or `failed`. Clients of older runners accept an absent `update`; refresh status to observe progress.

The runner checks `dev` every three minutes, using its own checkout in `OBY_HOME/updates/source`, outside agent sandboxes. It pins the fetched commit, runs `swift build -c release` then `swift test` (with a throwaway `OBY_HOME`, also as `TEST_RUNNER_OBY_HOME`, like a Mac check, so the tests never open the runner's own data), and drains only after both pass. Drain pauses new jobs, reviews and follow-up rounds while current rounds finish, for at most 30 minutes; a job waiting for the user's answer or OK doesn't hold it up. The drain covers the end of a turn too (#212): the runner restarts only between the steps that follow an agent's last turn, never inside one: counting a job's commits and publishing it, a review's verdict reaching its author (the verdict recorded, the `Oby review` check run posted, then the author's round started or the approval's Mac check queued), and posting a Mac check's results and merging. Past the 30 minutes it still waits for the step under way to end. Updates are batched: when `dev` moves while a tested commit waits (for its turn or for the drain), the newer commit is built and tested and replaces it, and the drain carries on meanwhile, so two merges in quick succession make one restart; if the newer commit fails, the one it was to replace still installs. The runner restarts for an update at most once every 15 minutes (`ready` until then, with no agent held back), unless the update brings the fix of one of Oby's own failures: a fix of an `oby-bug` failure of the last 7 days that merged into `dev` since the last update's restart installs at once. The tested executable is kept as `OBY_HOME/updates/candidate`; it atomically replaces the installed binary, then the runner exits with code 75 so the systemd user service (`Restart=on-failure`) restarts it. Its journal is `OBY_HOME/updates/state.json`, with when the last update restarted the runner.

After the restart, its jobs carry on like after any other restart ("After any restart", below). If `swift test` fails naming tests, the runner waits until the 1-minute load is below the machine's thread count, for up to 10 minutes, then reruns only those tests once with `swift test --filter`. If they pass, the update is tested and may install; Oby records a `flaky-test` failure with the test names and messages for its failure study, and adds no inbox item. If tests still fail, the old binary stays and one durable inbox item (`kind: failed`, `job: runner-update`, `options` `Try again`) names the failing tests and their messages. A failed build or install, or a test failure that cannot be identified by name, is reported immediately; compiler errors include their diagnostic lines. That commit is not retried on later polls or restarts, only by its Try again (#215); the next dev commit is tried. Each try that fails is its own item (`runner-update-<commit>`, then `…-try-2`, `…-try-3`), so a retry that fails again offers Try again again; while one is open, the same commit adds no other. A commit whose build or tests a restart cut short is tried again. A fetch failure adds one item per outage, however many polls or restarts it lasts; once a fetch succeeds, the next outage adds another. No unrelated build output or credentials enter the inbox.

**After any restart.** Whatever restarted the runner (a crash, a reboot, `systemctl restart`, a manual deploy or its own update), every job that was `queued` or `running` when it went down carries on once it's back, after its first refresh of the accounts: stopping the runner leaves them on disk as they were, not `interrupted`. A job with a session picks it up again in its own worktree, keeping its round. On obid (docs/contracts/recovery.md, RECOVERY-2) a job whose agent was at work, with a session, is told in a marked message what happened and to check what really ran before repeating anything, `step` `Oby restarted while this ran: continuing it (<n> of 3)`, then all its cut turn was sent (kept in the job's file until that turn ends well, never in the API), at most 3 times a job; a clean stop (`home/stopped-cleanly`, below) continues it the same way with no count in its `step` and costs no try; the fourth going down leaves it `interrupted`, `reason` `obid or the Mac went down 4 times while this ran, so Oby left it here. Try again carries it on.` and `nextStep` `Try again`, with a failure record (`crash`) and one `failed` inbox item (`Try again`, `Dismiss`) as below, until the owner's own words give it 3 more. A job that waited for the owner, was `queued` for a slot (it wasn't cut) or was cut checking or publishing isn't counted or told. On obid it picks up at the phase it was in: one cut short while it ran its check, or while it published, is `running` at once at that phase (so another restart cuts it there again) and runs its check again on what it committed (never its agent's turn, and no prompt is built for one; one with no check goes straight on to publish), and a pass goes on to publish as after its last round, a failure to the next round as any failing check does; words the owner sent meanwhile are its next turn instead. Its agent first hears `Oby's runner restarted while you were working…`, then the message it was about to get, if any: the next round's message, the user's words or answer, Oby's review hand-off or a failed Mac check's hand-off. That message is saved in `OBY_HOME/restarts.json` the moment Oby hands it over (while draining for an update too), and kept until the agent's turn ends, so a turn the restart cut short hears it again; the notice never replaces it. A queued job starts when its worktree is ready, when there's a free slot, oldest first; one whose worktree was set up before the restart is brought up to date with its base first, as a job that waited is. A job waiting on a question keeps waiting, `running` with its question and no agent, until its answer picks the session up (on obid, Claude Code's `AskUserQuestion` and Codex's and Cursor's questions, #858: `permission` above). A job waiting on a permission is `interrupted`, keeping it: its answer picks the session up, telling the agent what it asked and the answer. One stays `interrupted`: a job picked up twice in the last 30 minutes, when the runner keeps going down with it (the runner's own update restarts don't count: it notes them in `restarts.json` before it exits): its summary starts `Oby's runner restarted 3 times in 30 minutes while this ran…`, and it gets one `failed` inbox item with `Try again`. On obid nothing a job ran before the going down is still at work when it carries on: every process group obid starts for a job's run (each turn of its agent, Claude Code, Codex or Cursor, and its check; not the short git calls obid makes in its sandbox) is recorded while it runs in `home/jobs/groups/<pgid>.json` (0600: its leader's id, start time and executable, and the job; the start time is `ps`'s on macOS, the boot's id and `/proc`'s on Linux), and holds a lock in the worktree's own git folder (`obid-run`, the same record). When the start times can't be read (no `/bin/ps`), nothing is recorded and obid says so once in its log. After a going down that didn't end them (a crash, a kill, a panic), the next start ends every recorded group whose leader is still that very process (its id and its start time: an id another process took since is never signalled), SIGTERM then SIGKILL 0.4 seconds later, before any job is picked up again, and logs the job, the executable and the group, never a command line. A run that finds its worktree's lock held by a live run ends it first when obid recorded that run for the same job, and otherwise doesn't start, saying `an earlier run is still at work in this job's worktree (process <pgid>), which obid didn't start for this job`: the agent can write the lock, so it never makes obid signal another job's run. A group whose leader ended while its members still run isn't ended. On obid (#915) a stop that was asked for (SIGTERM or SIGINT, an update, the owner turning it off), however long its jobs take to end, leaves an empty `home/stopped-cleanly`, which the next start reads and removes; any other going down (a crash, a kill) counts against each job that was at work: running with an agent, or queued with nothing it waits for (a worker getting it ready), never one waiting on the owner's question or permission. A job picked up twice already in the last 30 minutes after such a going down stays `interrupted` at the next start, its `reason` `obid went down 3 times in 30 minutes while this ran, so Oby left it here. Try again carries it on.` (its `summary` that sentence, then the earlier summary), `nextStep` `Try again`, with a failure record (`crash`) and one `failed` inbox item (`Try again`, `Dismiss`); the count is kept in the job's file, never in the API, and emptied once the job ends any other way. Telling it something picks its session up with the message it was about to get, then the user's words. A job the user stopped stays `stopped`. Quitting Oby on the Mac still leaves its jobs `interrupted`.

End-of-turn work a restart cut short carries on too (a crash or `systemctl restart` can stop the runner anywhere; its own update waits for it). A review that ended while its author still shows it `reviewing` has its verdict applied now, as when it ends. A verdict on the author whose check run and hand-off didn't happen (the author's `review` is saved with `applying: true` until both are done) gets them now: the `Oby review` check run is posted (possibly a second time, if the restart came just after GitHub took it: never lost), then changes requested start the author's round with the quoted review, or an approval queues its Mac check. A restart after the round's message was saved but before the round was finds the review still `applying`: the round starts once, with that message. A merge whose check passed is finished on the first refresh ("Mac check", above), and a job that was publishing is still `running`, so it carries on and publishes when its agent ends.

`maxRunning` is how many jobs run at once (#237; Job, above), and `running` how many slots are taken now: jobs whose agent is running, reviews and rounds included. Older runners don't send them.

`defaultAgent` (obid only) is the agent new conversation tasks go to: `auto`, `claude`, `codex` or `cursor` (`PUT /v1/settings/default-agent`). Older runners don't send the key.

`talkAccount` (obid only, docs/contracts/conversation-agent.md) is the account conversations talk through unless one chose another, or null for Auto (`PUT /v1/settings/jobs`); `talkNext` is the account a new conversation's first turn would use now, or null when none can. Older runners don't send either.

`defaultAccount` (obid only, #1573) is the account new tasks go to (Settings › Agents › New tasks go to), or null for routing's own order (`PUT /v1/settings/jobs`). Older runners don't send the key; an app that sees it, even null, knows obid keeps Settings › Agents' choices (docs/contracts/agents.md).

`clearedAt` is when Clear done was last pressed, on any app (`POST /v1/clear`), or null when it never was. Every app hides the settled jobs that finished at that second or before (`finished` not after `clearedAt`): dismissed or stopped, with their pull request merged or closed, or ended with nothing to publish (`JobList.settled`, Shared/JobList.swift). Jobs still queued, running or waiting, needing the user, with their pull request open, or reviewing one that isn't settled stay, and so do finished ones that ran again since. Older runners don't send the key.

`github` is who the runner's own GitHub calls act as: `app` when the GitHub app is set up (`OBY_GITHUB_APP_ID` and its key, Runner/README.md) and its latest request for a token worked, `owner` otherwise (the owner's `gh` login, as before). Older runners don't send the key. Who does what:

- **As the app** (`oby-by-deskree[bot]` on GitHub), with an installation token in `GH_TOKEN` for that one call: reading pull requests, checks, issues, sub-issues and the board (the Lead, issue sync and its daily audit, a job's quoted issue and pull request, following published pull requests, Publish's lookup of the branch's open pull request), writing Oby's reviews and Mac check results as check runs, merging into `dev`, and the failure records. The token is the installation's for the account the call names (`-R owner/repo`, `--owner`, a `repos/…` path; a call that names none, like a GraphQL query by node ID, uses the app's only installation), minted with a JWT signed by the app's key and kept until five minutes before it expires. A call GitHub refuses with `401` gets a fresh token and runs once more.
- **As the owner** (their `gh` login): pushing branches, opening and editing pull requests, cloning, `gh api user` and `user/…` (the owner's name and email for agents' commits, the repositories the brain may pick), and anything that names `@me` (the owner's own projects). The calls above too, when there's no app, its key is missing or refused, or it isn't installed for that account.
- **Agents** get neither: `GH_TOKEN`, `GITHUB_TOKEN`, `OBY_GITHUB_APP_ID` and `OBY_GITHUB_APP_KEY` are taken out of their environment, and their gh has no login.

`checks` says whether Oby's review and Mac check go on pull requests as check runs (#198): `ok` when the app's installations have **Checks: Read and write** (read from GitHub at start) or the last check run went through, `missing permission` when they don't or GitHub refused the last one for it (the owner grants it on the installation, where GitHub shows the app's request; the next check run goes through by itself), `no app` when the runner's calls go as the owner, who can't write check runs. Until it's `ok`, reviews and Mac check results stay in Oby, and nothing goes on the pull request. Older runners don't send the key.
