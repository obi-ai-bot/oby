# obid only: other computers

The runner's side of "other computers" ([contracts/remote.md](../contracts/remote.md)): the owner's window on this Mac uses another Mac's or Linux box's obid, reached over any network they already have or an SSH tunnel, never through the Obysphere.

## `obid pair-computer`

What the person's own SSH runs on the other computer, as the user obid runs as there, when they add it from their Mac (COMPUTERS-7). It's placed with obid, never installed over SSH.

```bash
ssh -o BatchMode=yes -T -- <their alias> '/path/to/obid pair-computer --config /path/to/config.json' < name-and-key
obid pair-computer          # macOS, Oby.app's own obid: ~/Library/Application Support/Oby/obid/config.json
```

- **stdin:** the Mac's name on the first line, its device key on the second (P-256, X9.63 uncompressed, base64: the key the Mac app signs the owner's words with), and nothing else. Neither goes on the command line, where `ps` would show it. Anything else (no key, a key that isn't one, a third line, more than 4 KiB) prints `That isn't a device key.` on stderr and exits 2, having written nothing. So an `authorized_keys` line can make it a key's forced command (`restrict,port-forwarding,permitopen="127.0.0.1:<gateway>",command="…"`), and that key can do nothing but pair.
- **What it does:** names the key in obid's `home/pairing` (0600), the owner's presence as `POST /v1/devices` already takes it ([phone-pairing.md](phone-pairing.md)); registers it with `POST /v1/devices` on that obid's own API, with its API token, which stays on that computer; and makes a one-time invitation with `POST /v1/pairing/invite` `{"url": "http://<its gateway>", "name": <the Mac's name>, "computer": true, "presence", "device": <the key's id>}` (COMPUTERS-8: never through the Obysphere), its `presence` from `home/invite-computer` as `obid invite-computer`'s is, so redeeming it binds that key to the pairing (COMPUTERS-15).
- **stdout,** when it paired: one JSON line, `{"device": {"id": "…"}, "invite": {"url", "name", "hostname", "link", "secret", "code", "expiresAt"}}`. It goes back over SSH only. The Mac redeems `invite.secret` through its tunnel to the gateway (`POST /v1/pairing`, [phone-pairing.md](phone-pairing.md), "Redeeming") for its device token, and signs the owner's words there with its key, registered as `device.id`.
- **Where it reaches obid:** the addresses that obid bound when it last started, from `home/addresses.json` (COMPUTERS-9), a port the system picked included; the configuration's `listen` and `gateway` while that file isn't there.
- **Exit 1,** one line on stderr, nothing paired: the configuration doesn't read; obid has no `gateway` (`This obid has no gateway, so no other computer can reach it: …`); it never started there (no `api-token`); it doesn't answer (`obid doesn't answer on 127.0.0.1:<port>: is it running?`); or it refused a step (`obid refused /v1/devices (403 Forbidden): …`). After a refusal `home/pairing` is taken out again.

## Direct addresses

With `direct` in obid's configuration ([configuration.md](configuration.md)), obid serves its gateway's own router over HTTPS on those addresses too (COMPUTERS-10): the same `POST /v1/pairing`, device tokens and allowlist as the gateway's listener ([phone-pairing.md](phone-pairing.md)), and never the pairing endpoints, which stay on the loopback API. Without a `gateway` the configuration doesn't load.

- **Its certificate** is this computer's own: self-signed P-256 (subject `CN=<the machine's name>`, `notAfter` 99991231235959Z), made the first time obid serves a direct address and kept in `home/keys/direct-certificate.der` and `home/keys/direct-key.p8` (PKCS#8, both 0600). Its SHA-256 is its pin, which a window trusts in its place: no CA, no name. A start keeps it; it's made anew only when its files are gone or the key isn't the certificate's, and then every window that pinned the old one refuses it until the computer is added again.
- **`GET /v1/status`** names each address under `gateway.direct`: `{"address": "0.0.0.0:8443", "state": "listening", "pin": "sha256:<64 hex>"}`, or `{"address", "state": "down", "detail"}` when it can't listen there (a warning in the log, never a stop). obid's log says `obid direct listening` with each address and pin; stdout keeps only its two lines, which launchers read first.
- **A handshake** has 10 seconds; one that doesn't finish, or fails, is dropped and holds up no other.

## `obid invite-computer`

What the other computer's owner runs at it to add it to their Mac with a code (COMPUTERS-13), as the user obid runs as there.

```bash
obid invite-computer --config /path/to/config.json
obid invite-computer          # macOS, Oby.app's own obid
```

- **What it does:** reads the running obid's status for its direct addresses ([Direct addresses](#direct-addresses)), writes a one-time `home/invite-computer` (0600, good for 2 minutes and once) as the owner's presence at this machine, and asks for `POST /v1/pairing/invite` `{"url", "name", "computer": true, "presence"}`.
- **stdout:** one JSON line, `{"code": "123456", "link": "oby-computer:…", "name", "fingerprint": "ABCD 1234 …", "expiresAt"}`. `fingerprint` is the pin's first 16 bytes in groups of four hex digits, to compare by eye; the link carries the whole pin.
- **Exit 1,** one line on stderr: obid isn't running or never started here; or `This computer has no address another computer can reach. Set "direct" in obid's configuration, or add it over SSH instead.`; or obid refused.

## A computer's invitation

`POST /v1/pairing/invite` with `"computer": true` ([phone-pairing.md](phone-pairing.md)):

- **`computerLink`** in the answer, when obid serves direct addresses: `oby-computer:` and base64url JSON, `{"v": 1, "name", "routes": [{"id", "kind": "lan" | "tailnet" | "vpn" | "public" | "loopback", "via": {"type": "https", "host", "port", "pin": "sha256:<hex>"}}]}`. An address on every interface (`0.0.0.0`, `[::]`) is each of the machine's own addresses but loopback and IPv6 link-local; at most 8, in the owner's order.
- **Its own slot:** a computer's invitation replaces the computer's before it, never a phone's, and a phone's never replaces it. It lasts 10 minutes. A wrong code counts against every open invitation; the fifth ends it.
- **`presence`:** what `obid invite-computer` or `obid pair-computer` wrote in `home/invite-computer`. When it holds, or with the owner's device's `approval`, the computer it pairs may add its own key (`POST /v1/devices` through the gateway, for 10 minutes); otherwise it pairs one that can't.
- **`device`:** with `presence` or `approval` only, a registered key bound to no pairing that's still paired (`obid pair-computer`'s): redeeming the invitation binds it to the pairing it makes (COMPUTERS-15). Without either, or for a key that's another pairing's, `403` and nothing made.

## A computer's token

A pairing a computer's invitation made is a computer's (`"computer": true` in `GET /v1/pairing/devices`), and its device token differs from a phone's through the gateway and its direct addresses:

- **Its routes (COMPUTERS-14):** the gateway's list, as a phone's ([phone-pairing.md](phone-pairing.md)), and nothing past it, so every promise that a route stays on obid's loopback API holds for a computer too. Among them: the vault, all three routes ([vault.md](vault.md), VAULT-1 to 5; vault secrets go in only on the Mac, the owner's word of 2026-11-20); pairing (`/v1/pairing/devices`, `/v1/pairing/invite`); every sign-in, Tetrix's, ChatGPT's, GitHub's and an account's ([chatgpt-sign-in.md](../contracts/chatgpt-sign-in.md), core/AGENTS.md "Tetrix"); accounts but `PATCH /v1/accounts/{id}`, `PUT /v1/settings/agents/{agent}` and `/v1/settings/chatgpt` ([accounts.md](accounts.md), "Not on the gateway"); `POST /v1/accounts/{id}/background` ([chatgpt-sign-in.md](../contracts/chatgpt-sign-in.md)); adding folders and a conversation's workspace ([folders.md](folders.md)); attachments ([attachments.md](../contracts/attachments.md)); projects ([projects.md](projects.md)); `GET /v1/alerts` and `DELETE /v1/devices/{id}` ([alerts.md](alerts.md)); renaming and deleting artifacts ([artifacts.md](artifacts.md)); a job's changes and Undo ([jobs.md](jobs.md)); `POST /v1/repos/check` and `/v1/repos/setup` ([github.md](github.md)); `PUT /v1/obid/sphere/owner` and cancelling an exchange ([obysphere.md](obysphere.md), SPHERE-21, OBIREQ-5). Past the list is `404` (`That route isn't available through the gateway.`). A computer reaches what a phone does, and the routes on a computer's own list, each added by name with the screen of the window that needs it there (`COMPUTER_ROUTES`, gateway.rs): `GET /v1/skills` (the message box's `/` list), `GET /v1/connectors` (Settings › Connectors), `GET /v1/preview/tunnel` (a page's localhost, board 14: [The preview tunnel](#the-preview-tunnel)), and the window's browser (COMPUTERS-29, [browser.md](browser.md)): `GET /v1/browser`, `GET /v1/browser/events`, `GET` and `POST /v1/browser/relay`, `POST /v1/browser/tabs/{id}/take` and `…/giveBack`, `POST /v1/browser/asks/{id}/answer`, `GET /v1/browser/downloads`, `POST /v1/browser/downloads/{id}/saveCopy`, `GET` and `PUT /v1/browser/settings`. The agents' `POST /v1/browser/mcp`, the retired `…/stream`, `…/input` and `…/secret`, and `…/reload`, `…/back` and `…/dialog` stay `404`. A phone's token on those is `404`.
- **One route as written:** each segment of the path is decoded before the list is read, whoever's token it carries, and the list reads the decoded path (`/v1/%70airing/devices` is `/v1/pairing/devices`, off it). obid is sent that same path, encoded the one standard way (every byte but letters, digits, `-`, `.`, `_` and `~` as `%XX`), with the request's query: so `/v1/jobs/<id>/rep%6Frt` reaches the report, as the list read it, never another route. A segment that's empty, `.` or `..`, holds a backslash or NUL, or has an escape that isn't two hex digits, isn't UTF-8 or decodes to any of those, a `/` or a `%`, is `404` (`That route isn't available through the gateway.`).
- **The owner's words (COMPUTERS-15):** an `X-Oby-Words` header through it counts only signed by the key bound to that pairing: the key `obid pair-computer` named, or the one the computer added with `POST /v1/devices` through the gateway after a code. Any other key's, a registered one included, is `403` (`Those words aren't signed by this computer's own key. Add this computer again.`) before the route sees it.
- **Removing it (COMPUTERS-16):** `DELETE /v1/pairing` on the gateway (or a direct address) with its own token ends its pairing, as `DELETE /v1/pairing/devices/{id}` does on that computer's loopback, and forgets the key bound to it: `204`. Its token is `401` from then on, and the key needs the owner's presence there again. A phone's token is `404` there; none is `401`.

## Adding a computer with a code, the Mac's side

`obid::remote::code::redeem(link, code, name, key)`: it decodes the link, reaches its first route that answers (`GET /v1/status`) with that route's pin, then sends `POST /v1/pairing` `{"credential": <code>, "name"}` there and `POST /v1/devices` `{"name", "publicKey"}` with the token it got. No route reached is `Oby can't reach {name} right now. It tried …`, each route with why: a certificate not the pinned one says `another computer answered: its certificate is …`. The window's endpoint for it comes with the computers this Mac keeps.

## This Mac's computers

The computers the Mac's obid keeps for its window (docs/contracts/remote.md, COMPUTERS-17 to 25), on its loopback API with its token only, never on the gateway.

- **`GET /v1/computers`** → `{"current": "this" | "<id>", "computers": [{"id", "name", "os": "mac" | "linux", "state": "connected" | "lost" | "idle", "route": {"id", "kind", "address"}, "tried": [{"route", "what", "why"}]}]}`. `os`, `route` (while connected) and `tried` (while lost) are left out when there are none. Never a token. The event `computers` carries the same object whenever it changes.
- **`POST /v1/computers/link`** `{"link": "oby-computer:…"}` → `{"name", "fingerprint", "routes": [{"kind", "address"}]}`; `422` `not_a_link` with why.
- **`POST /v1/computers`** `{"link", "code"}`, with `X-Oby-Words` signed by a registered device (unsigned: `403`) → `201` with the computer as the list shows it. obid reaches a route of the link with its pin, redeems the code there (`POST /v1/pairing`), registers the signing device's key there with the token it got (`POST /v1/devices`, so its words count through that token) and reads the computer's `runner.os`. Refusals: `422` `wrong_code` or `code_ended` (obid's words from there), `502` `unreachable` or `refused_there`, `422` `not_a_link`. Kept in `home/computers.json` (0600): `{"current", "computers": [{"id", "name", "os", "routes", "pairing", "device", "signer", "added"}]}`; the token in the vault as `oby.computer.<id>`.
- **`POST /v1/computers`** `{"ssh": "<host>"}`, with `X-Oby-Words` (unsigned: `403`) → `202` `{"adding": "<id>"}` (COMPUTERS-25): adding over the person's own `ssh`, found on obid's `PATH`, with COMPUTERS-4's options. A host that isn't an SSH host or alias, or could be read as an option, is `422` `not_a_host`, and ssh doesn't run. ssh runs one command there, `obid pair-computer`, this Mac's name and the signing device's key on its stdin, never its command line; obid opens the tunnel to the gateway its invitation names, on that computer's own 127.0.0.1, redeems the invitation through it (`POST /v1/pairing`), and keeps the computer with the direct routes the invitation's `computerLink` holds, each pinned, first, and its SSH route `ssh` last; the window starts on the best that answers. Each step is the event **`computer.adding`** `{"id": <adding>, "step": "ssh" | "pair" | "routes", "state": "doing" | "done" | "failed"}`; the last `routes` `done` carries `"computer"` as the list shows it, and the event `computers` follows; a `failed` one carries `"trouble": {"trouble": <kind>, "say": <words>}` and keeps nothing: ssh's kinds (`hostKeyUnknown`, `hostKeyChanged`, `noKey`, `noSshServer`, `unreachable`, `forwardFailed`, `other`, COMPUTERS-5 and 17), `noObid` (no `obid` on the PATH ssh gets there), `refusedThere` (obid there said no: its words), `notKept`. A pairing made there that this Mac can't keep is ended there again.
- **`PUT /v1/computers/current`** `{"id": "<id>" | "this"}` → the list; `404` `no_such_computer`.
- **`PATCH /v1/computers/{id}`** `{"name"}` → the computer; on this Mac only. An empty name is `422`.
- **`POST /v1/computers/{id}/retry`** → the computer: each route probed (`GET /v1/status` there), best first, until obid answers on one: something else on the port, or a refused token, isn't an answer (COMPUTERS-18).
- **`DELETE /v1/computers/{id}`**, with `X-Oby-Words` (unsigned: `403`) → `{"removed": "<id>", "there": true | false}`: `DELETE /v1/pairing` there with its token (`there` is whether that computer said its pairing is over), then this Mac forgets it, its token and its SSH tunnels (each ssh ends), and the window is on This Mac if it was on it.
- **`POST /v1/computers/{id}/door`** → `{"proxy": "http://oby:<64 hex>@127.0.0.1:<port>"}` (COMPUTERS-28): the door a page's `localhost` on that computer goes through, in the shape main sets on a partition's proxy as `BOX_PROXY`, the same each time until the computer is removed ([egress.md](egress.md), "A computer's door"; [The preview tunnel](#the-preview-tunnel)). No signed words: it hands out a way, not an owner's act. Only obid's own token on loopback gets it: a broker token or none is `401` at obid's gate, a paired device's token through the gateway or the relay `404` there (no `/v1/computers` route is on either list), and a request that came through either is `403` `not_the_window` here too. An unknown computer is `404` `no_such_computer`. The door's token is in no event, log line or other answer.
- **The event `computer.route`** `{"id", "change": "moved", "from", "to"}` or `{"id", "change": "lost", "tried"}`, when a computer's route changes, from a retry or a forwarded request.

### A request for another computer

A request on the Mac's loopback API, with its token, carrying **`Oby-Computer: <id>`** of a computer the Mac keeps, is that computer's (COMPUTERS-22): obid sends it to that computer's gateway over its best route that answers (each tried for 5 seconds to connect; a direct one pinned, an SSH one through its tunnel, opened when a request needs it and dialed again no more than once a second after it's cut, COMPUTERS-18), with its device token, and brings back its answer as it comes (`GET /v1/events` too) with its status and its `Content-Type`, `Cache-Control` and `Content-Disposition`. It carries the request's body and its `Content-Type`, `X-Oby-Words`, `Idempotency-Key`, `Last-Event-ID` and `Accept`, and nothing else; never `Oby-Profile`, so the other computer answers for its own default profile. Words signed by the device whose key the Mac registered there name that key's id there instead (the signature is over the request and its time, not the id). `Oby-Computer` absent or `this`, and every `/v1/computers` route, stay this Mac's. It is decided on the Mac before anything leaves it. Refusals: `400` `not_the_window` (through the gateway or the relay, or with any token but obid's own, an agent's broker token too: nothing is sent); `404` `not_for_a_computer` for a route a computer's token doesn't reach there (the phone's list and `COMPUTER_ROUTES`, the path read as the gateway reads it), so the vault and pairing stay the Mac's; `404` `no_such_computer`; `409` `no_token`; `502` `unreachable` with the supervisor's words naming every route tried. A computer's device token is in no answer, event, log line or error, a failed one's included. A forwarded `GET /v1/events` carries only that computer's events and ends once `current` names another computer or the Mac removes it; a forwarded `GET /v1/browser/events` and `GET /v1/browser/relay` stream and end the same way (COMPUTERS-29), with no whole-answer limit.

## The preview tunnel

A page's `localhost` on another computer (COMPUTERS-26 and 27), ported from T3 Code's `PreviewTunnel.ts` and `LoopbackTunnel.ts` (pingdotgg/t3code@1d028248): the Mac's door ([egress.md](egress.md), "A computer's door") carries each connection to the other computer over a WebSocket of its own.

- **`GET /v1/preview/tunnel?port=<n>`**, on the other computer's gateway listener and each of its direct addresses, served there itself, never forwarded to its API. A WebSocket of raw bytes to that computer's own loopback port `n`.
- **Who reaches it:** exactly one `Authorization: Bearer <token>` of a paired computer's, on the listener (never a device paired through the relay), with no `Oby-Computer` header and not through the relay. Anyone else is `404` `{"error": "That route isn't available through the gateway."}`, the gateway's unlisted route, whatever the port or the headers: a phone's token, none, an expired or revoked one, a relayed request, one naming `Oby-Computer`. obid's loopback API doesn't serve it (`404`).
- **Its refusals,** in this order, after the caller and each before any upgrade, `{"error", "reason"}`: `400` `bad_port` for a `port` that's missing, empty, given twice, not digits, `0` or past 65535; `403` `own_port` for one of obid's own listeners' (its API's, its gateway's and its direct addresses', as obid bound them at start); `400` `not_a_websocket` for a request with no WebSocket upgrade; `403` `nothing_listens` when nothing answers (`403`, not `502`, so a proxy between can't swap it).
- **The dial:** `127.0.0.1:<n>`, then `[::1]:<n>`, both within 5 seconds, made before the upgrade so a dead port fails the handshake; never any other address.
- **The pump:** bytes both ways as binary frames, at most 64 KiB read at a time, each written before the next read on its side; the WebSocket's write buffer, message and frame each at most 1 MiB; text frames ignored, pings answered by the library. Either side closing or failing ends both; there's no idle limit.
- **Its end:** the tunnel closes, its socket and its WebSocket, once its pairing ends (`DELETE /v1/pairing` with its token, or `DELETE /v1/pairing/devices/{id}` on that computer) or its token's time is up (checked again at that instant), even while a write waits on a service that stopped reading: both are dropped at once and the socket reset, so nothing still queued reaches the service.

## `home/addresses.json`

obid writes it (0600) each time it starts, once its API, gateway and direct addresses are bound: `{"api": "127.0.0.1:<port>", "gateway": "127.0.0.1:<port>", "direct": ["0.0.0.0:<port>"]}`, `gateway` and `direct` left out when there are none. Only `obid pair-computer` reads it.

## `POST /v1/pairing/invite` with `"computer": true`

See [phone-pairing.md](phone-pairing.md): the invitation is for the given `url` only, never through the Obysphere, even while obid is a member of one; without a `url` it's `400` (`Another computer is invited to a url: its gateway's.`).
