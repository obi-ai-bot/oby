## Behavior

### Actors and ownership

- **GitHub** runs `.github/workflows/ci.yml` (CI-70 to 76) on its own `ubuntu-latest` runners; this repository's code only reads its result.
- **The check** (`scripts/oby-check.sh`) runs the route guard when a change reaches what it reads (below). No model call is involved, and nothing changes at runtime for obid or any client.
- **The check** counts and judges obid's tests' sleeps in its `rust` group: the block that reports the Rust core's line count and judges `jobs.rs`'s line limit, so it runs wherever they run, one group at a time under the installed `oby-check-blok` too.
- **The check** reads the flaky list, guards it in that same block, and retries a listed obid test in its `rust` group. **GitHub** retries a listed test through nextest's own override.
- **The check** measures the root `AGENTS.md` in that same limits block, so it runs wherever the Rust core's count is reported and `jobs.rs`'s limit judged, and also when `AGENTS.md` alone changed: that plans the `rust` group's limits with no cargo step.

### Rules

- **The route list.** `docs/api/routes.txt` lists every route obid serves, one `<METHOD> <path>` line per method, the path as axum declares it (`{id}`, `{*path}`), sorted by path, then method. It is rebuilt from every `.route(` under `core/crates/obid/src` whose path is a literal starting `/v1/`, outside test modules (`production_lines`' rule in `scripts/oby-check.sh`) and comment lines; each method router (`get`, `post`, `put`, `patch`, `delete`, or `axum::routing::` one) is a line, and a layer is skipped. A method router the guard doesn't know fails it, naming the file and the path. The routes `gateway.rs` declares itself (`POST /v1/pairing`, on the gateway's own listener) sit under their own heading. A new route commits its line with it; a route that goes shows as a deleted line in review.
- **The clients' calls.** The `/v1/` (or Swift's `v1/`) string literals of `apps/electron/src` (its `.ts` and `.tsx`, not under a `test/` folder, not `*.test.ts(x)`, not `renderer/src/mock.ts`) and `apps/shared` are paths the clients call. Each is compared, segment by segment and whatever the method, with every route in the list: an interpolated segment matches any, a route's `{x}` matches any one and `{*x}` one or more, and a literal ending in `/` matches when a route starts with it. A query is cut, and an interpolation glued to the end of the text (`/v1/jobs${q(..)}`) is dropped.
- **The known-dead list only shrinks.** `docs/api/dead-client-calls.txt` holds the calls that were already dead when the guard came, `<file> <path>` a line. A dead call not on it fails, and so does a line whose call is gone from its file or served again: delete that line.
- **The gateway's list holds only served routes.** Each `ROUTES` entry in `core/crates/obid/src/gateway.rs` (`*` one segment, a final `**` one or more) must reach a route of the API's with the same method; one that reaches none fails, and is deleted.
- **What sleeps count.** Each occurrence of `thread::sleep` or `time::sleep` (the pattern `(thread|time)::sleep`, written once in `tests_sleeps`) in a `*.rs` file under `core/crates/obid/tests`, however many share a line. No exemptions: `support::within`'s own 100 ms poll counts like any other. A missing folder counts 0.
- **The sleep limit.** `tests_sleep_limit` in `scripts/oby-check.sh`. It may only come down.
- **Shrink-only, as `jobs.rs`'s line limit.** A job's check runs the base's copy of the script on the commit (PUBLISHING-7). `pick_limit` holds a branch that lowered `tests_sleep_limit` since its merge base to its own number, but never to one higher than the running copy's; one that didn't gets the running copy's. When dev's limit changed since the branch started, the messages add "rebase onto dev".
- **Past the sleep limit** fails (CI-12). **Under it** fails too (CI-13), asking for the exact new count. **At it** passes, and says so in one line.
- **What AGENTS.md's limit counts.** The bytes (`wc -c`) of the root `AGENTS.md` in the checked tree, committed or not; no other `AGENTS.md` counts, or runs the limits by changing.
- **AGENTS.md's byte limit.** `agents_md_bytes_limit` in `scripts/oby-check.sh`, picked with `pick_limit` as the others are. Past it fails (CI-36). More than 512 bytes under it fails too (CI-37), asking to lower the limit to the file's exact size. At it, or up to 512 under, passes and says so in one line. A checked tree with no `AGENTS.md` fails (CI-38) and is never counted as 0 bytes.
- **The line count report** (CI-49, CI-50). Wherever the limits block runs (the `rust` group on shard 1 when Rust, the check or `AGENTS.md` changed, and `OBY_CHECK_ONLY=limits` whatever changed, `OBY_CHECK_PLAN` included), it prints one line on stdout, before `jobs.rs`'s: `oby-check: the Rust core has <N> production lines outside the Sphere, <D> since its base`. `<N>` is `obid_lines` on the checked tree, committed or not: every `*.rs` under a `src/` of `core/crates` but `obi-protocol`'s and the Sphere's (its `inbox.rs` and `link/inbox_actions.rs` count), each without its test modules (`production_lines`). `<D>` is `<N>` minus the same count of the merge base's `core/crates`, which git writes into a folder of its own under `TMPDIR`, removed after, signed as `printf '%+d'` writes it (`+451`, `-2000`, `+0`). When git can't give the base's `core/crates` (none in its tree, or an object it can't read), the line is `oby-check: the Rust core has <N> production lines outside the Sphere, the difference from its base unknown (its core/crates can't be read)`, with no error of git's. Neither the count nor the difference ever fails the check, in either direction or by any amount.
- **What a raise is.** `jobs_rs_limit` is raised when `limit_in` reads a number for it in the merge base's copy of the script and in the commit's (HEAD's), and the commit's is the greater. A cut, an unchanged limit, and a limit that moved only on `dev` after the branch started are not raises, and `pick_limit` still never takes a commit's higher number.
- **A raise names its payback** (CI-39). In the commit's copy, the line directly above the first `<name>=<digits>` line of a raised limit matches `^# payback: (#[0-9]+|[A-Z][A-Z0-9]*-[0-9]+)( .*)?$`: a GitHub issue (`#2131`) or a task key (`R05-02`), then optionally a space and words. Else the check fails, naming the limit, its old and new numbers, and the line to add.
- **A raise comes alone** (CI-40). A commit that raises it, and whose committed diff from the merge base (`git diff --name-only <base> HEAD`) names any file but `scripts/oby-check.sh`, fails, naming the limit and the other files (the first five, then how many more). Uncommitted and untracked files don't count.
- **Payback lines are printed** (CI-41). Whenever the limits block runs, `OBY_CHECK_ONLY=limits` included, each of the three limits whose line directly above it in the commit's copy is a `# payback:` line prints `oby-check: <name>'s payback: <the rest of the line>` right after its own message. Nothing reaches the network.
- **Not on combined code.** CI-39 and CI-40 aren't judged under `OBY_CHECK_ONLY=limits` (CI-35): in the merge queue a raise shares its diff with the pull requests queued beside it, and a pull request into `main` carries all of `dev`. The pull request's own check judges the raise against its merge base.
- **The flaky list's shape.** Every `[[profile.ci.overrides]]` in `core/.config/nextest.toml` is an entry of exactly four lines: `# <KEY>: <what the test waits on>`, the header, `filter = 'binary_id(<binary id>) & test(=<full test name>)'` and `retries = 2`. `<KEY>` is the key of the task that fixes it; `<binary id>` is `obid` for the lib's tests and `obid::<name>` for `tests/<name>.rs`; the name is the full one libtest prints (`codex::tests::…`), never a prefix or another filterset. One function, `flaky_list` in `scripts/oby-check.sh`, reads it, for the retry and the guard alike; an override in any other shape, or any other key or table naming overrides, is malformed. No file is an empty list.
- **The Mac's retry.** A run of obid's tests failed by named tests when its output has one or more libtest summaries (`failures:` and the indented names, then `test result: FAILED. … N failed`), every target it started ended (a `test result:` for each `running N tests`), and the names read are as many as the summaries' `N failed`. When every one of them is on the list at the merge base and in the checked tree, keyed by binary id and name, it runs once more with only those tests: a test binary, after every binary ended, one at a time from `core/crates/obid` with the same `RUST_TEST_THREADS`, as `<exe> --quiet --exact <name>…`; the lib step (which runs with `--no-fail-fast`, so every target runs to its end) as the same cargo command with its filters replaced by `--exact <name>…`. A passing retry passes that binary or step, shows both outputs, and prints `retried flaky: <binary id> <test name>` for each test. Anything else (a test not on the list, names that can't be read or don't add up, a crash, a build error, a stop) retries nothing, and the run fails as before.
- **The list only shrinks.** Against the merge base, removing an entry always passes. An entry whose binary id and name the base's list hasn't passes only when `factory/queue/tasks/<KEY>.md` is in the checked tree and wasn't at the base: the same change adds the task that fixes it. A run where the guard passes says so in one line.
- **AGENTS.md's rules** (CI-42 to 44). Each line of `docs/agents-rules-manifest.md` matching `` ^- `([^`]+)`: (.+)$ `` is an entry: a home and a sentence. Its home is `AGENTS.md`, `core/AGENTS.md` or a path the root `AGENTS.md` links (a Markdown link whose target isn't a URL or a bare `#anchor`, the target without its `#anchor` and leading `./`), or it fails (CI-43). The sentence and the home's text, in the checked tree, committed or not, are each compared with every Markdown link's target cut, leaving its text and closing bracket, and every run of whitespace made one space: the sentence must be a fixed substring of the text, or it fails (CI-42); a home that doesn't exist holds nothing. A changed `AGENTS.md`, `core/AGENTS.md`, `core/CLAUDE.md` or `docs/agents-rules-manifest.md`, a changed file the tree's manifest names as a home, and `OBY_CHECK_ALL` plan the block, in the `rust` group with no cargo step of its own (CI-44); `core/AGENTS.md` and `core/CLAUDE.md` plan no Rust. A checked tree with no manifest fails (CI-43).
- **What a change reaches on GitHub** (CI-72). `changes` reads `git diff --name-only` of the run's range: a pull request's `<base>...<head>` (from its merge base), the queue's and `dev`'s `<base>..<head>`. Each path takes the first row of `ci.yml`'s `case` it matches (bash's `case`, where `*` matches `/` too), and what it reaches only adds: `rust` is `full`, `guards` or `none`, `electron` `true` or `false`.

  | `apps/electron/*` | `electron`, and `rust=guards` unless already `full` |
  | `apps/shared/*`, `docs/runner-api.md`, `docs/contracts/*` | `rust=guards` unless already `full` |

- **The guards** (CI-74). `GUARDS` in `ci.yml`: `tests/routes_guard.rs`, `tests/state_owner.rs`, `tests/released_files.rs`, `tests/runner_api.rs`'s `caps_` tests, and obid's lib tests `prompt_budget_holds`, `unsafe_1_only_may_write_is_unsafe`, `keychain_1_the_vault_never_touches_the_keychain`, `merging_2_what_only_the_mac_tests_is_the_scripts`, `agentmcp_7_every_entry_names_every_gate`, `one_protocol_version_list`, `clean_docs_and_the_fixture_result_stay_clean` and `this_repositorys_names_are_clean_and_a_token_among_them_is_found`. Each keeps two places in agreement: obid's routes with `docs/api/routes.txt` and the apps' calls, who writes a job's state, what released obids wrote, `GET /v1/status`'s capabilities and their doc, the prompt budget, the one unsafe function, no Keychain in the vault, what only the Mac tests, the MCP tool list and protocol versions, and obid's secret scan against this repository's docs and names.
- **The test binaries at once** (CI-51). When `OBY_BUILD_JOBS` is unset (run by hand, by `factory/checks.sh` or by either nightly; obid always sets it), `test_binaries` runs half the Mac's cores (`sysctl -n hw.ncpu`, else `getconf _NPROCESSORS_ONLN`, else 4) of obid's test binaries at once, at least 2, each with `OBY_TEST_THREADS` (2) threads, whatever the load: they mostly wait on stand-ins, and on this Mac 2 at once ran past the full run's 60 minutes (25 of 58 binaries, a load average of 9 to 22) where 5 at once ran the Rust group in 2171 s (6 to 16). With `OBY_BUILD_JOBS` set it stays `(jobs + 1) / 2`; Cargo's jobs and the lib tests' threads stay `jobs`, 4 by hand.
- **The test binaries' times** (CI-52). `test_binaries` prints, before it starts them, `oby-check: <N> test binaries, <P> at once with <T> threads each (<cores> CPUs, a load average of <load>)`; each binary's output starts `     Running <name> (<s>s)`; and its last line is `oby-check: obid's test binaries took <S>s, the longest tests/<name>.rs at <s>s`. None of them ever fails the check.
- **The Mac's nightly** (CI-53). `scripts/oby-nightly.sh` fetches `origin/dev`, checks its commit out detached at `<results>/worktree` (the one kept from the last run, moved to the commit and cleaned with `git clean -ffdx` but for `apps/electron/node_modules`, else a new one), runs `npm ci` in `apps/electron` and that commit's `scripts/oby-check.sh <commit>` with `OBY_CHECK_ALL=1` and `CARGO_TARGET_DIR=<results>/target` (kept between nights), and writes `<results>/<stamp>.md` (`RESULT: PASS|FAIL`, `COMMIT`, `STARTED`, `SECONDS`, `LOAD` as it started and ended, the log's last 80 lines), `<stamp>.log` beside it and `latest.md` linking the newest. `<results>` is `OBY_NIGHTLY_DIR`, by default `~/Library/Logs/Oby/nightly`; `<stamp>` is the UTC start, `YYYY-MM-DDTHHMMZ`. A failure also shows a macOS notification. It exits 0 on a pass, 1 on a failure, 2 when it can't check out `origin/dev` (no result written). The worktree and the target folder stay for the next run: the check's shared caches (`~/Library/Caches/oby-check`) hold builds that name the folder they were built in, and once that folder was removed, every later check that reused them failed with `No such file or directory` (seen 2026-11-17, `tools/oby-check-blok`'s `workflow` tests). It never creates, deletes or checks out a branch, never pushes, and writes nothing in the checkout it was run from.
- **When it's due** (CI-54). A run is due when the newest `<stamp>.md` started more than 20 hours ago, or there is none; `--now` runs it anyway. `--install` writes `~/Library/LaunchAgents/dev.oby.nightly.plist` (every day at 03:30, the Mac's time, with the `PATH` it was installed from) and loads it; `--uninstall` unloads and removes it.
- **One run at a time** (CI-55). A run holds `<results>/.lock` (its pid inside); while a live run holds it, another says it's not due; one whose run is gone is taken over. The lock is removed after a pass, a failure or a stop alike; a stopped run (TERM, INT) writes no result, so it is due again.
- **The nightly's turn.** `factory/bin/nightly` is due when no other nightly run holds `factory/jobs/nightly/.lock`, no job's `job.json` is in `gate` or `merging`, and the newest result started more than 20 hours ago, or there is none. `job queue` asks it (`nightly --due`) and never repeats the rule.
- **The nightly's run.** It fetches `origin/dev`, checks it out detached at `.worktrees/nightly`, and runs the main checkout's `factory/checks.sh` there with `OBY_CHECK_ALL=1`: every suite, under the same check lock as a gate. Its result is `factory/jobs/nightly/<stamp>.md` (`GATE: PASS|FAIL`, `COMMIT`, `STARTED`, `SECONDS`, `TASK` on a failure, the log's last 80 lines), named by its UTC start time, with the full log beside it. Only exit 0 passes; a stopped run writes no result and is due again.
- **One fix task per failing commit.** On a failure it runs `factory/bin/job add "fix: the nightly full Mac check fails on dev at <sha7>"` with the commit, the result's path, the failing lines (`oby-check: failed: …`, `test … ... FAILED`) and the log's tail quoted as data. A failure on a commit an earlier result already has a task for reuses that task.
- **A node stops its own script past its limit** (CI-33). The host sends each step's limit to its node in the request (`max_ms`); a request without one has none. Past it, the node sends SIGTERM to the script's bash and every process descended from it, found from the system's process list by parent id, in the check's own process group (obid and `check-lock` stop a check by its group, so the node makes no group or session of its own). It relays what the script says until both pipes close or 30 seconds pass, then sends SIGKILL to whatever of that tree is left, and answers only once none of it runs. The node is `unjudged`, its reason `ran past its maxDuration of <N>s`, then `: tests/<name>.rs, … were still running` for each `oby-check: tests/<name>.rs was still running` line the script's `test_binaries` printed as it stopped. The host's own timeout is the limit plus 60 seconds, a backstop the node's answer comes before.
- **The limits on GitHub** (CI-35, CI-73). For a change that reaches all of Rust, GitHub's `rust` job runs `OBY_CHECK_ONLY=limits scripts/oby-check.sh <base>` on the checked commit (the merge group's combined code in the queue), with that commit's own copy of the script, measured against the run's base (`pull_request.base.sha`, `merge_group.base_sha`, or the commit before on `dev`), so `pick_limit` holds a commit that lowered a limit to its own number. It runs the script's limits block alone, with no `oby-check-blok` and nothing installed. Every rule of that block but CI-39's and CI-40's holds on the combined code, so more sleeps than `tests_sleep_limit` fails `Check`, and so do fewer sleeps than its limit and a malformed or unbacked flaky list entry: two pull requests that each cut a little can fail the queue together until one lowers the limit. That is the script's own rule, kept on purpose. The step prints the Rust core's line count and its difference from the base (CI-49) and never fails on them. `jobs.rs` past `jobs_rs_limit` is reported ("past its limit of N (reported, not a failure)"), never a failure (the owner's word, 2026-11-17); the other limits still fail.
- **A full run's Rust group** (CI-34). In `check` with `OBY_CHECK_ALL` set and not empty (the nightly's run), the `rust-affected-tests` step's limit is `FULL_RUN_RUST_LIMIT` in `tools/oby-check-blok/src/lib.rs`, 60 minutes: 1.5 times the Rust group of a full run measured on the Mac (2,306 seconds at `9eb7d431`, with `OBY_BUILD_JOBS` and `OBY_TEST_THREADS` unset, beside a gate's check), rounded up to a whole 15 minutes, and never under 45 minutes or over 2 hours (PUBLISHING-29's ceiling for a test run). Every other step, a gate's check (no `OBY_CHECK_ALL`), obid's checks and the shadow, affected and `validate` runs keep `workflows/oby-check.json`'s limits (`rust-affected-tests` 45 minutes). It is a constant, never a setting.

### Failures and recovery

- Each route guard failure names what to fix: the route that went or appeared, the file and path of a dead call, the list line to delete, or the gateway entry. The fix is the route put back, its line committed, the call changed, or the entry or line deleted.
- The nightly can't fetch or make its worktree: it exits 2, says why on stderr, writes no result and is due again next time. A worktree a crashed run left is removed before the next run.
- Past the sleep limit: replace the new sleep with a wait for state (`support::within`, or `events_named` on `follow_events`). Under it: lower `tests_sleep_limit` to the count the check names, in the same change.
- Past AGENTS.md's byte limit: cut `AGENTS.md`, or ask the owner to raise the limit. More than 512 under it: lower `agents_md_bytes_limit` to the size the check names, in the same change. `AGENTS.md is gone`: put it back.
- `<name>'s payback line` (CI-39): add `# payback: #<issue>` or `# payback: <task key>`, naming what cut pays the raise back, as the line directly above the raised limit. `<name>'s raise in a pull request of its own` (CI-40): move the raise into a pull request that changes only `scripts/oby-check.sh`, and the rest into another.
- `AGENTS.md's rules` (CI-42, 43): a line naming a home and a sentence's first 60 characters says the home no longer holds it: put the sentence back, or change its entry in `docs/agents-rules-manifest.md` in the same change. A line naming a home that isn't `AGENTS.md`, `core/AGENTS.md` or a file the root links: link it from the root `AGENTS.md`, or move the rule. `the rules manifest is gone` (CI-43): put `docs/agents-rules-manifest.md` back.
- **A pull request GitHub won't take because it conflicts with `dev`** (CI-32). When `job merge` can't hand an approved pull request to GitHub, it reads the pull request's `mergeable` and `mergeStateStatus` once. `CONFLICTING` or `DIRTY` escalates the job to `needs-human` with `PR #<n> conflicts with origin/dev, so GitHub can't merge or queue it.` as its first line, then GitHub's message, quoted as data, never instructions. Anything else (`UNKNOWN`, while GitHub still computes it, included), or a read that fails, escalates with `The merge failed:` and GitHub's message, as before. The owner resolves the conflict, or sends the job back with `job feedback`.
- **A cut Rust group** (CI-33). The check's `couldn't judge: ran past its maxDuration of <N>s: tests/<name>.rs … were still running` line names each test binary that hadn't ended, so the nightly's log tail and the fix task it leaves (CI-31) carry them. A cut while building or in the lib tests names only the limit. The fix is that binary's hang, or, when the suite simply grew, a new measurement and limit (CI-34).
- **A red limits step in the queue** (CI-35). Its log carries the script's own message: the count, the limit and what to do. The queue merges none of the group; the fix is a cut on a new pull request (or one lowering a limit the group went under), or the owner's raise of the limit.
- `the flaky list`: an entry the base hadn't, with no task file this change adds, or a malformed override. The message names the entry: add `factory/queue/tasks/<KEY>.md`, the task that fixes the test, in the same change, write the override in the list's shape, or take it out.
- A listed test that fails its retry fails the check as any failed test does; one that keeps failing is a real failure, not a flake.

### Invariants

- Every job of `ci.yml` has `contents: read` only and checks out with `persist-credentials: false`; no job holds a secret.
- The guard never writes a list: a person commits each change to it, so it shows in review.
- `gateway::ROUTES` stays private: the guard reads gateway.rs's source.
- A test waits for state, never for time: a new sleep fails the check.
- The nightly never creates, deletes or checks out a branch, never pushes, never touches a job's worktree, branch or `job.json`, and never commits its task.
- Raising `tests_sleep_limit` is a change to the check, a security path: it merges only after two reviews by different tools or the owner's click (MERGING-13 to 16).
- Raising `agents_md_bytes_limit` is the owner's word, and a change to the check, a security path: it merges only after two reviews by different tools or the owner's click (MERGING-13 to 16).
- A test is retried on the Mac only when it was on the flaky list at the merge base and still is: a change can't list its own failing test and pass its own gate with it.
- The list is one file, `core/.config/nextest.toml`; the Mac keeps no second copy.
