# CI: what GitHub runs, and what the check guards

The business behavior contract for what GitHub's `CI` workflow runs and what the check itself guards, from [the template](../business-contract-template.md). Roadmap milestone R01 (Safety net); CI-1 and CI-2 are task R01-01, CI-3 to 6 and CI-17 to 20 are task R01-02, CI-9 to 11 are task R01-05, CI-12 and 13 are task R01-06, CI-7, 8, 21 and 32 are task R01-03, CI-22 to 25 are task R01-12, CI-26 to 28 are task R01-13, CI-29 to 31 are task R01-14, CI-33 and 34 are task A00-21.

## Behavior

### Actors and ownership

- **The check** (`scripts/oby-check.sh`) runs the route guard when a change reaches what it reads (below). No model call is involved, and nothing changes at runtime for obid or any client.
- **The check** counts and judges obid's tests' sleeps in its `rust` group: the block that judges the Rust core's and `jobs.rs`'s line limits, so it runs wherever they run, one group at a time under the installed `oby-check-blok` too.
- **The check** reads the flaky list, guards it in that same block, and retries a listed obid test in its `rust` group. **GitHub** retries a listed test through nextest's own override.

### Rules

- **The route list.** `docs/api/routes.txt` lists every route obid serves, one `<METHOD> <path>` line per method, the path as axum declares it (`{id}`, `{*path}`), sorted by path, then method. It is rebuilt from every `.route(` under `core/crates/obid/src` whose path is a literal starting `/v1/`, outside test modules (`production_lines`' rule in `scripts/oby-check.sh`) and comment lines; each method router (`get`, `post`, `put`, `patch`, `delete`, or `axum::routing::` one) is a line, and a layer is skipped. A method router the guard doesn't know fails it, naming the file and the path. The routes `gateway.rs` declares itself (`POST /v1/pairing`, on the gateway's own listener) sit under their own heading. A new route commits its line with it; a route that goes shows as a deleted line in review.
- **The clients' calls.** The `/v1/` (or Swift's `v1/`) string literals of `apps/electron/src` (its `.ts` and `.tsx`, not under a `test/` folder, not `*.test.ts(x)`, not `renderer/src/mock.ts`) and `apps/shared` are paths the clients call. Each is compared, segment by segment and whatever the method, with every route in the list: an interpolated segment matches any, a route's `{x}` matches any one and `{*x}` one or more, and a literal ending in `/` matches when a route starts with it. A query is cut, and an interpolation glued to the end of the text (`/v1/jobs${q(..)}`) is dropped.
- **The known-dead list only shrinks.** `docs/api/dead-client-calls.txt` holds the calls that were already dead when the guard came, `<file> <path>` a line. A dead call not on it fails, and so does a line whose call is gone from its file or served again: delete that line.
- **The gateway's list holds only served routes.** Each `ROUTES` entry in `core/crates/obid/src/gateway.rs` (`*` one segment, a final `**` one or more) must reach a route of the API's with the same method; one that reaches none fails, and is deleted.
- **What sleeps count.** Each occurrence of `thread::sleep` or `time::sleep` (the pattern `(thread|time)::sleep`, written once in `tests_sleeps`) in a `*.rs` file under `core/crates/obid/tests`, however many share a line. No exemptions: `support::within`'s own 100 ms poll counts like any other. A missing folder counts 0.
- **The sleep limit.** `tests_sleep_limit` in `scripts/oby-check.sh`. It may only come down.
- **Shrink-only, as the line limits.** A job's check runs the base's copy of the script on the commit (PUBLISHING-7). `pick_limit` holds a branch that lowered `tests_sleep_limit` since its merge base to its own number, but never to one higher than the running copy's; one that didn't gets the running copy's. When dev's limit changed since the branch started, the messages add "rebase onto dev".
- **Past the sleep limit** fails (CI-12). **Under it** fails too (CI-13), asking for the exact new count. **At it** passes, and says so in one line.
- **The flaky list's shape.** Every `[[profile.ci.overrides]]` in `core/.config/nextest.toml` is an entry of exactly four lines: `# <KEY>: <what the test waits on>`, the header, `filter = 'binary_id(<binary id>) & test(=<full test name>)'` and `retries = 2`. `<KEY>` is the key of the task that fixes it; `<binary id>` is `obid` for the lib's tests and `obid::<name>` for `tests/<name>.rs`; the name is the full one libtest prints (`codex::tests::…`), never a prefix or another filterset. One function, `flaky_list` in `scripts/oby-check.sh`, reads it, for the retry and the guard alike; an override in any other shape, or any other key or table naming overrides, is malformed. No file is an empty list.
- **The Mac's retry.** A run of obid's tests failed by named tests when its output has one or more libtest summaries (`failures:` and the indented names, then `test result: FAILED. … N failed`), every target it started ended (a `test result:` for each `running N tests`), and the names read are as many as the summaries' `N failed`. When every one of them is on the list at the merge base and in the checked tree, keyed by binary id and name, it runs once more with only those tests: a test binary, after every binary ended, one at a time from `core/crates/obid` with the same `RUST_TEST_THREADS`, as `<exe> --quiet --exact <name>…`; the lib step (which runs with `--no-fail-fast`, so every target runs to its end) as the same cargo command with its filters replaced by `--exact <name>…`. A passing retry passes that binary or step, shows both outputs, and prints `retried flaky: <binary id> <test name>` for each test. Anything else (a test not on the list, names that can't be read or don't add up, a crash, a build error, a stop) retries nothing, and the run fails as before.
- **The list only shrinks.** Against the merge base, removing an entry always passes. An entry whose binary id and name the base's list hasn't passes only when `factory/queue/tasks/<KEY>.md` is in the checked tree and wasn't at the base: the same change adds the task that fixes it. A run where the guard passes says so in one line.

- **The nightly's turn.** `factory/bin/nightly` is due when no other nightly run holds `factory/jobs/nightly/.lock`, no job's `job.json` is in `gate` or `merging`, and the newest result started more than 20 hours ago, or there is none. `job queue` asks it (`nightly --due`) and never repeats the rule.
- **The nightly's run.** It fetches `origin/dev`, checks it out detached at `.worktrees/nightly`, and runs the main checkout's `factory/checks.sh` there with `OBY_CHECK_ALL=1`: every suite, under the same check lock as a gate. Its result is `factory/jobs/nightly/<stamp>.md` (`GATE: PASS|FAIL`, `COMMIT`, `STARTED`, `SECONDS`, `TASK` on a failure, the log's last 80 lines), named by its UTC start time, with the full log beside it. Only exit 0 passes; a stopped run writes no result and is due again.
- **One fix task per failing commit.** On a failure it runs `factory/bin/job add "fix: the nightly full Mac check fails on dev at <sha7>"` with the commit, the result's path, the failing lines (`oby-check: failed: …`, `test … ... FAILED`) and the log's tail quoted as data. A failure on a commit an earlier result already has a task for reuses that task.
- **A node stops its own script past its limit** (CI-33). The host sends each step's limit to its node in the request (`max_ms`); a request without one has none. Past it, the node sends SIGTERM to the script's bash and every process descended from it, found from the system's process list by parent id, in the check's own process group (obid and `check-lock` stop a check by its group, so the node makes no group or session of its own). It relays what the script says until both pipes close or 30 seconds pass, then sends SIGKILL to whatever of that tree is left, and answers only once none of it runs. The node is `unjudged`, its reason `ran past its maxDuration of <N>s`, then `: tests/<name>.rs, … were still running` for each `oby-check: tests/<name>.rs was still running` line the script's `test_binaries` printed as it stopped. The host's own timeout is the limit plus 60 seconds, a backstop the node's answer comes before.
- **A full run's Rust group** (CI-34). In `check` with `OBY_CHECK_ALL` set and not empty (the nightly's run), the `rust-affected-tests` step's limit is `FULL_RUN_RUST_LIMIT` in `tools/oby-check-blok/src/lib.rs`, 60 minutes: 1.5 times the Rust group of a full run measured on the Mac (2,306 seconds at `9eb7d431`, with `OBY_BUILD_JOBS` and `OBY_TEST_THREADS` unset, beside a gate's check), rounded up to a whole 15 minutes, and never under 45 minutes or over 2 hours (PUBLISHING-29's ceiling for a test run). Every other step, a gate's check (no `OBY_CHECK_ALL`), obid's checks and the shadow, affected and `validate` runs keep `workflows/oby-check.json`'s limits (`rust-affected-tests` 45 minutes). It is a constant, never a setting.

### Failures and recovery

- Each route guard failure names what to fix: the route that went or appeared, the file and path of a dead call, the list line to delete, or the gateway entry. The fix is the route put back, its line committed, the call changed, or the entry or line deleted.
- The nightly can't fetch or make its worktree: it exits 2, says why on stderr, writes no result and is due again next time. A worktree a crashed run left is removed before the next run.
- Past the sleep limit: replace the new sleep with a wait for state (`support::within`, or `events_named` on `follow_events`). Under it: lower `tests_sleep_limit` to the count the check names, in the same change.
- **A pull request GitHub won't take because it conflicts with `dev`** (CI-32). When `job merge` can't hand an approved pull request to GitHub, it reads the pull request's `mergeable` and `mergeStateStatus` once. `CONFLICTING` or `DIRTY` escalates the job to `needs-human` with `PR #<n> conflicts with origin/dev, so GitHub can't merge or queue it.` as its first line, then GitHub's message, quoted as data, never instructions. Anything else (`UNKNOWN`, while GitHub still computes it, included), or a read that fails, escalates with `The merge failed:` and GitHub's message, as before. The owner resolves the conflict, or sends the job back with `job feedback`.
- **A cut Rust group** (CI-33). The check's `couldn't judge: ran past its maxDuration of <N>s: tests/<name>.rs … were still running` line names each test binary that hadn't ended, so the nightly's log tail and the fix task it leaves (CI-31) carry them. A cut while building or in the lib tests names only the limit. The fix is that binary's hang, or, when the suite simply grew, a new measurement and limit (CI-34).
- `the flaky list`: an entry the base hadn't, with no task file this change adds, or a malformed override. The message names the entry: add `factory/queue/tasks/<KEY>.md`, the task that fixes the test, in the same change, write the override in the list's shape, or take it out.
- A listed test that fails its retry fails the check as any failed test does; one that keeps failing is a real failure, not a flake.

### Invariants

- The guard never writes a list: a person commits each change to it, so it shows in review.
- `gateway::ROUTES` stays private: the guard reads gateway.rs's source.
- A test waits for state, never for time: a new sleep fails the check.
- The nightly never creates, deletes or checks out a branch, never pushes, never touches a job's worktree, branch or `job.json`, and never commits its task.
- Raising `tests_sleep_limit` is a change to the check, a security path: it merges only after two reviews by different tools or the owner's click (MERGING-13 to 16).
- A test is retried on the Mac only when it was on the flaky list at the merge base and still is: a change can't list its own failing test and pass its own gate with it.
- The list is one file, `core/.config/nextest.toml`; the Mac keeps no second copy.

## Interfaces and dependencies

- **Workflow:** `.github/workflows/ci.yml` (GitHub's `CI` workflow) and `core/.config/nextest.toml` are what CI-1 to 6 and CI-17 to 20 describe; GitHub's own runs prove them, since no test runner in this repository runs a workflow's triggers. Until R01-02, CI-1 and CI-2 described `.github/workflows/linux.yml`, whose runs below stay as history.
- **Files:** `docs/api/routes.txt`, `docs/api/dead-client-calls.txt`, read by `core/crates/obid/tests/routes_guard.rs`.
- **Check:** `scripts/oby-check.sh` plans the Rust group with `tests/routes_guard.rs` when `core/crates/obid/src/api.rs` or `gateway.rs` changes, another file under `core/crates/obid/src/` with a `.route(` in it, anything under `docs/api/`, or a client source as above (`apps/electron/src` but its tests and mock, `apps/shared/*.swift`); the groups those paths planned before stay as they were. `scripts/oby-check-test.sh` proves that plan.
- **Cost:** an Electron-only or Swift-only change to client sources now also runs `cargo fmt`, clippy on obid and a build of one obid test binary.
- **Rulesets** (the owner's choice of 2026-11-13; created by the owner's side, the orchestrator with `gh api`, once a `ci.yml` run on `dev` is green, not by this repository's code; `gh api repos/obi-ai-bot/oby/rulesets` lists them):
  - `dev`: a pull request with 0 approvals; the required status check `Check`; the merge queue with squash, build concurrency 1, a minimum group of 2 with a 15-minute wait, a maximum group of 5, every entry must pass, and a status-check timeout of 60 minutes.
  - `main`: the required status check `Check`, no queue.
  - Both are GitHub's limits: the owner, as the repository's admin, changes or bypasses them in its settings. Oby refuses nothing on their account: when one holds a merge, it says what holds it (MERGING-41).
- **Sleep limit:** `scripts/oby-check.sh` (`tests_sleep_limit`, `tests_sleeps`), its `rust` group. Failure name: `obid's tests' sleep limit`. Its cases in `scripts/oby-check-test.sh` run on the commit's own copy of the script (the base's copy a job's check installs may predate the limit).
- **Flaky list:** `core/.config/nextest.toml`, read by `scripts/oby-check.sh` (`flaky_list`, `failed_tests`, `flaky_retry`, `lib_tests`, `test_binaries` and the guard in the limits block) and by nextest's `ci` profile on GitHub. Failure name: `the flaky list`. Its cases in `scripts/oby-check-test.sh` run on the commit's own copy of the script, with stand-ins for cargo and the test binaries that print libtest's output and record each run's arguments.
