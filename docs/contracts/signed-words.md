# The owner's words, signed

The business behavior contract for the Electron app signing what the owner types or clicks ([#1611](https://github.com/obi-ai-bot/oby/issues/1611)), from [the template](../business-contract-template.md). Scenarios are numbered `WORDS-n`; the tests that prove them are named after them: the app's in `apps/electron/src/renderer/src/test/words.test.ts` and `apps/electron/scripts/test-core.mjs` (`npm run test:core`), obid's in `core/crates/obid/tests/secretspec.rs` (`words_5_…`).

## Feature and status

- **Outcome:** Words the owner types or clicks in the Electron app (Home's box, a conversation, a task's page, a task's new name, a question's answer, a permission's Allow or Deny) count as the owner's own in obid, as the Swift apps' do. Their conversation isn't marked, the tasks it starts keep their check's declared secrets, and the owner's Bypass carries on to the follow-ups their words start (BYPASS-7). Words the owner didn't type or click stay unsigned, and obid marks them as before.
- **Status:** **Implemented** (#1611). obid already checked `X-Oby-Words` (docs/runner-api.md, "Words the owner typed"); the Electron app signed only a limit-stopped job's continuation. Since #1632 a task's words open its conversation, so unsigned words marked every conversation the app started.
- **Scope:** the Electron app (main, the preload, the page's Content-Security-Policy, the window's sandbox). **Out of scope:** Publish by hand, whose push is signed only on Publish in main's own dialog, never on the page's say (docs/contracts/publishing.md, PUBLISHING-14); obid's verification (unchanged), the Swift apps (they sign already), offers' Start and Cancel, Later, `POST /v1/jobs` and `POST /v1/memory/suggestions/{id}/remember` (the app sends neither: each gets its exact shape here when it does).

## Behavior

### Actors and ownership

- **The owner** presses Enter in a box, or clicks (Send, an option, Allow).
- **Main** (`src/main/words.ts`, `device.ts`, `index.ts`) decides. It signs with this Mac's device key only when all of these hold:
  1. it saw a real keystroke (Enter) or mouse-down reach the window itself (`before-input-event`, `before-mouse-event`), less than 2 seconds before, not used by another signature (each one signs once);
  2. the request is one of the app's words requests, in exactly the shape the app sends it (`wordsOf`, `src/shared/words.ts`): `POST /v1/plans` (`said`; an answer's `question` and `option`; `conversation` or `new`; `folders`, `id`, `attachments`, `jobs`), `POST /v1/jobs/{id}/messages` (`text`, `attachments`, `conversation`), `PATCH /v1/jobs/{id}` (`title` only), `POST /v1/inbox/{id}/answer` (`answer` only), `POST /v1/jobs/{id}/permission` (`id`, `decision`, `message`), `POST /v1/spheres/{sphere}/room` (`text` only: the owner's `say`, [room-app.md](room-app.md)), `POST /v1/obid/sphere/peers/{owner}/ask` (`text` only: the owner's question from a member's thread, [peer-thread.md](peer-thread.md); the signature covers the path, so it names to whom), `POST /v1/accounts/{id}/background` (`given: true` only, by its own button's label: the owner's yes to work nobody's watching using that ChatGPT login, [chatgpt-sign-in.md](chatgpt-sign-in.md); the signature covers the path, so it names which). The task's `POST /v1/jobs/{id}/mode` and Settings' `PUT /v1/settings/permissions` sign exactly `{mode}`, by `modeLabel`. Any other key (a check, a repository, a base, an account) and it signs nothing. Working folders (`folders`) go signed only when every one is a folder the owner chose in main's own dialog this run (`pick-folders`): a recent folder from an earlier run, or one the page made up, sends the words unsigned;
  3. the preload asked for it.
- **The preload** (`src/preload/index.ts`) asks only when the request's words are text the owner's own event held: the box they pressed Enter in, and for a click, the boxes of the form clicked in (Send) and the label of the `<button>` clicked (never a card's text). Only `isTrusted` events count, and a box or button that isn't visible (`checkVisibility` with opacity and CSS visibility) holds nothing. A trusted, visible native select's change holds its chosen option's text too. Each held text signs once, within 2 seconds.
- **Native notifications** deliver actions directly to main. Their Allow/Deny callbacks sign their fixed request with the same device key and exact-shape validation, without `takeInput`; they are not window requests.
- **obid** checks the signature as it does the Swift apps' and decides what the words may do.

### Decisions and invariants

- **Nothing is signed because the page asks.** Before #1611 main signed no ordinary words on purpose: the page shows text from outside (agents' output, GitHub, other people's words), and a script that got into it could have had main sign any words as the owner's, so the tasks they start get the check's declared secrets. The page still can't: main signs only right after a keystroke or click it saw itself, one request each, and only the app's own shapes.
- **The window is sandboxed** (#1641): `sandbox: true`, with `contextIsolation` and no `nodeIntegration`, and `app.enableSandbox()` for any window added later; a packaged app refuses `--no-sandbox` (it exits). The page's process, the preload's world included, has no Node (no `process`, `require`, files or programs) and runs in Chromium's sandbox; the preload is CommonJS and requires only `electron`'s `contextBridge` and `ipcRenderer`. Before it, a script that took the renderer over had Node, the Mac's files and programs, already worse than the ceiling below. Now it reaches only what the preload hands main over IPC, and main checks each sender (`trusted`) as before; escaping takes a Chromium sandbox escape.
- **What a compromised page can still do.** The preload still shares the page's process (in a world of its own), so a script that takes the whole renderer over can pass the preload's check. What it still can't pass is main's: within 2 seconds of each real Enter or click of the owner's in Oby's window, it can have one request of its own choosing signed, words of its choosing in one of the shapes above. Those words count as the owner's: words to Oby that ask for a task, with a check of their choosing, start a vetted task whose check gets the owner's declared secrets; so can that one request be the yes to work nobody's watching using a ChatGPT login, on any real input. It can't sign without the owner's input, more than once per input, or a body with any other key. **The owner accepted this ceiling on 2026-10-30** (Wellington, merging #1638), as he accepted `claudeOwnSandbox`'s race on 2026-10-27: it closes only with words read in a UI main owns. The window's sandbox (above) doesn't change it: the ceiling is what's left inside the sandbox. Keeping script out of the page stays the first line: React's escaping, no remote content, the window's own frame only (`trusted`), and a Content-Security-Policy in every build (`vite.config.ts`: the page's own scripts only, no network).
- **Exactly the words held.** Spaces don't count (the box's lines come back as the page joins them). Anything more, less or else goes unsigned, a repository put in front of the words (`In owner/name: …`, the design's `?everything` only) too. One label also stands for other words, as a permission's button stands for its decision: `Give it another round` signs exactly obid's Try-again words to a job (`POST /v1/jobs/{id}/messages`, `TRY_AGAIN` in `src/shared/words.ts`), the one message whose words needn't be the text the click held. Those words typed in a box sign as any words do. Another round on a task that never started sends its title and request, a card's text, and goes unsigned. Main can't tell which job a request is for, so the app keeps this off a job an account limit stopped: no card offers it, and a click on a card drawn before the limit sends nothing (#1563's grouped choice decides).
- **An answer to Oby's question** sends again the words it answers (`said`): those may be words to Oby this app signed before; its `option` must be held now.
- **Unsigned is never refused by the app.** Words that aren't signed (a rename that ends when the window loses focus, a send obid didn't answer and that goes again later, words that wait for their files' upload) go unsigned, and obid marks them as it always did. Only a limit-stopped job's continuation needs the signature (docs/runner-api.md, `accountLimit`), as before, and so do the words that are only ever the owner's: the room's `say`, a question from a member's thread, and an answer or Decline to another Oby's question ([peer-thread.md](peer-thread.md), PEER-33). There obid refuses unsigned words, and the box keeps them with obid's words over them: a Mac whose device key can't be read can't answer from this window until it can, and its paired phone still can.

- **A Confirm that tells someone something (`share_status`, `share_room`, `answer_question`, `decline_remember`: [peer-thread.md](peer-thread.md), [rooms.md](rooms.md)).** A Confirm isn't words: main signs obid's own sentence for the open item (`oby-confirm`, `obid-confirm` in `device.ts`), reading its title from obid. Most Confirms sign on the page's say. The first two let the Oby tell other people things by itself, and the others answer another Oby as the owner, so main signs them only when the preload saw the owner's own event (`isTrusted`, a visible button) hold the label `Confirm` within 2 seconds, by a click, Enter or Space on the focused button, and main itself saw a real click, Enter or Space within 2 seconds (`mayConfirm`). Space counts only here: it signs no words. **What this stops, and no more:** a script acting on an input it didn't arrange. The DOM is shared, and the preload reads a button's `innerText` and checks only that it's visible, so a page script can put a transparent full-window button labelled Confirm over the page, or relabel the one the owner is about to press, and confirm on that real click. That stays inside the ceiling above: one signature per real input of the owner's in the window. It closes only with a question in a UI main owns.

### Failure and recovery

- The device key can't be read or the device can't register (the Keychain unavailable, obid refuses it): the words go unsigned, never dropped, and main logs why. The device registers once a run, one registration at a time (`home/pairing` is written by one at once).
- A signature obid doesn't take (the clock, a device it removed) leaves the words marked, as unsigned ones are; obid logs why.

## Interfaces and dependencies

`X-Oby-Words: <device> <signedAt> <signature>` (docs/runner-api.md, "Words the owner typed"), signed to the millisecond over the body as main sends it. No change to obid's API.

## Acceptance scenarios

- **WORDS-1** Main signs the app's words requests only, in exactly their shapes: a job body, a message or plan with a mode or check, a title with a base, settings outside the exact default-mode shape, a task's mode with extra keys, a check, a conversation's title, Later and any non-text field are never signed.
- **WORDS-2** Words the owner's keystroke or click held are signed, each held text once (with spaces joined differently); words the page made up, nothing held, more than was held, or a repository put in front are not. A permission is signed by its own button's label. `Give it another round` also signs exactly obid's Try-again words to a job, and nothing else that isn't its own text; those words are signed otherwise only when held, as any words are.
- **WORDS-3** An answer to Oby's question signs the words it answers when they were signed before and the option is held; neither alone, and words signed before don't go signed to a task.
- **WORDS-4** Main's signature verifies with the device's key over `oby-words\n<METHOD>\n<path without query>\n<SHA-256 of the body>\n<signedAt>`.
- **WORDS-5** (BYPASS-7, through obid's real routes) A signed `POST /v1/jobs` in Bypass is vetted; a signed message starts a vetted follow-up in Bypass; the same words unsigned start one that isn't vetted, in the owner's default mode.
- **WORDS-6** In the real app against a scratch obid: the task Home's box starts is vetted, and so is the follow-up the owner's words on its page start. The page's Content-Security-Policy blocks nothing the app loads.
- **WORDS-8** Words with working folders are signed only when the owner chose every one in main's own dialog this run; one more, or one never chosen, sends them unsigned.
- **WORDS-10** The owner's `say` in the Sphere's room signs in exactly its shape, its words held: `text` alone, never with an `about`, a `replyTo` or a `kind`.
- **WORDS-12** The owner's question from a member's thread signs in exactly its shape, its words held: `text` alone, never with an `about`, `choices` or a `to` (`words_12_ask_signs_its_exact_shape`).
- **WORDS-11** (PEER-17, ROOMS-17, PEER-33) Main signs a `share_status`, `share_room`, `answer_question` or `decline_remember` Confirm only on a press of Confirm the preload held and an input main saw, one each; a script's call, or a press with no input, is `403` and nothing reaches obid. A Space signs no words (`words_11_…` in `device.test.ts`, `preload.test.ts` and `words.test.ts`).
- **WORDS-13** The yes to work nobody's watching on a ChatGPT login signs only by its own button's label (**Yes, it can**: a permission's Allow doesn't stand for it), in exactly its shape, `given: true` alone. A no goes unsigned, as obid keeps it either way.
- **WORDS-14** A task's mode and Settings' Default mode sign exactly `{mode}`, by the mode's label from `modeLabel`. A task's button holds its label; a trusted change on a visible native select holds its chosen option's text. Unknown modes and extra keys sign nothing. The two-second window and one request per real main input still apply.
- **WORDS-15** A notification's Allow/Deny signs in main on macOS's native action, without consuming window input. Each callback holds exactly the job and permission id or inbox item and answer its button names; the signature covers that path and body. No notification signer is exposed to the page over IPC.
- **WORDS-7** Main signs once per real keystroke or click it saw, within 2 seconds; in the real app, words the page's script sends with no keystroke or click start a follow-up that isn't vetted.
- **WORDS-9** In the real app, the window's process runs sandboxed (`app.getAppMetrics()` says `sandboxed: true` for its process: that is the check that proves it, since the page lacks `process` and `require` with `contextIsolation` alone too), the page reaches neither, and the preload's bridge (`window.app`, obid through main) still answers. A packaged app refuses `--no-sandbox`.

### Test it when it's done (a real Mac)

1. Type a task in Home's box: it starts, and `home/jobs/<id>.json` says `"vetted": true`.
2. On its page, tell it something: the follow-up is vetted, and in Bypass when the task was.
3. Answer an agent's question with an option, and with Tell it something; Allow a command: the task stays vetted.
