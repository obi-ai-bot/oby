# Publishing: only the commit the check passed on

The business behavior contract for what a job's publish pushes, what its check runs on ([#1647](https://github.com/obi-ai-bot/oby/issues/1647)), and for which jobs may work on one branch ([#1635](https://github.com/obi-ai-bot/oby/issues/1635), both from the core audit of 2026-10-30), from [the template](../business-contract-template.md). Scenarios are numbered `PUBLISHING-n`; the tests that prove them are named after them (`core/crates/obid/tests/publish_api.rs`, `runner_api.rs`).

## Feature and status

- **Outcome:** Nothing goes out by itself unless its check passed (AGENTS.md, "Rules Oby never breaks"): what a job pushes is exactly the commit its check passed on, never commits another job put on its branch since, and two tasks on one issue never overwrite each other's commits.
- **Status:** **Implemented**, PUBLISHING-9 to 11 since 2026-10-31 (AGENTS.md, "Oby forbids nothing"; #1677), but for what PUBLISHING-4 does when the owner insists, and PUBLISHING-9's card words and pull request line, which are **proposed** (not built). Before #1647, the check ran in the job's own worktree, so an agent could rewrite the check's script to `exit 0`, or leave an ignored `.env` the tests read, and the check passed on what never went out. Before #1635, publishing pushed whatever the job's branch pointed to in obid's clone at publish time, so a follow-up that failed its check could move the branch and Publish on the first job pushed its failing commits; and only follow-ups were kept off a branch another active job used, so "fix issue 34" twice put two jobs on `oby/fix-34`.
- **Scope:** What publishing pushes, by itself and by hand, what the check runs on, and when a new job may start on a branch. **Out of scope:** the secret scan, the lease on a rebase, the pull request and the merge (docs/runner-api.md, "obid only: publishing the owner's work", and #1636), which stay as they are.

## Behavior

### Actors and ownership

- **obid** decides everything here: it makes the check's checkout and chooses which of its files come from the base, says why when nothing counts as checked, records the commit a job's check passed on, refuses a publish when the branch moved, and refuses a job whose branch an active job works on. Those refusals are Oby's defaults; the owner's signed Publish goes past them (PUBLISHING-9 to 11), and the owner's word past PUBLISHING-4's is proposed.
- **The apps** show obid's words: `publishError`, the `409` of `GET` and `POST /v1/jobs/{id}/publish`, and the `422` of `POST /v1/jobs`. They decide nothing.

### Triggers and decisions

- **Its check runs.** obid reads the worktree's HEAD and its `git status` (untracked files too, ignored ones not) first. The check passed on that commit only when nothing was uncommitted then and HEAD was still there after it.
- **Where it runs (PUBLISHING-6).** In the job's own checkout of that commit, which obid makes out of its clone's objects (`git worktree add --detach`, about half a second for this repository), apart from everything the job's sandbox can write: nothing the job's agent left in its worktree is there, untracked or ignored (a `.env`, `node_modules`, a build folder), and what the check writes or commits stays there, so it never reaches the job's branch. The job's next check uses the same checkout, reset to its commit, with everything the last check left removed, ignored files and any `.gitignore` it wrote included, but for the folders the repository keeps for its checks' builds (`checkKeep` on its entry in `config.json`, none by default; `core/target` here), so a job's second check doesn't build from nothing. What's left: a kept folder can carry what an earlier check's code (the agent's) wrote there. It's never another job's (cargo could run another checkout's binary), and it goes when the job's worker ends, or when obid starts again. A check that gets the owner's secrets has a checkout of its own, gone after it. obid's git on the agent's commit reads none of the person's own git settings (no `filter.lfs`, no `url.*.insteadOf`), so a `.gitattributes` or `.lfsconfig` the agent wrote reaches no host. The check's home is the job's, with the caches its agent filled (cargo's registry, npm's), since the check has no network; one that gets the owner's secrets has a home of its own. The commit is the one obid read as HEAD when the check started, the one it records as checked. The base its files come from is the job's base when that's the repository's default branch or the branch its remembered workflow merges into (`dev` here), else the branch its remembered workflow merges into, else the default branch: never a branch obid pushed (`oby/…`) or any other branch, which another task could have written. As its remote has it when the check starts (fetched then, when it isn't the job's own base, which was); when obid can't read it, nothing counts as checked (PUBLISHING-8). From that branch's head come:
  - **the check's scripts:** for each simple command (split at `&&`, `||`, `|`, `;`, `(` and `)`), past `NAME=value` words and `env`, `timeout`, `nice`, `time`, `exec` or `command` with their options: its program when that's a path (`scripts/oby-check.sh`, `./check.sh`), or what it hands an interpreter (`sh`, `bash`, `zsh`, `dash`, `python3`, `python`, `node`, `ruby`, `perl`, `deno run`): the first word that isn't an option or an option's argument (`bash -o pipefail s.sh` runs `s.sh`), a command string's first included (`sh -c 'scripts/x.sh'`); none after `-m` or `-e`. It counts when it's a path inside the repository (`./` taken off; never one with `..`, `.git`, `$`, a glob or `~`, or that starts with `/`) naming a file in the commit or on the base. The base's copy replaces the commit's; one the commit deleted is put back. This is the same reading of the command that tells which files are the check's own at merge (`crate::merge::check_files`, MERGING-15). What a command reads without naming it (`make check`'s Makefile, `npm test`'s `package.json`) is the commit's, a known limit: the check's output starts with `obid: no script found in this check, so the commit's own files run`.
  - **`.gitleaks.toml`:** the base's copy, or none when the base has none. A repository's first `.gitleaks.toml` isn't in the check until it's merged, so a check that names it (this repository's runs `gitleaks --config .gitleaks.toml`) fails until then.
  - The base's copies are read-only while the check runs, and so are the folders they're in, which can't be renamed or removed (a shell reads its script as it goes: rewritten under it, it would run what the rewrite says). What's left, and always is: the code under test can empty its own tests.
- **The base has no copy of a check's script (PUBLISHING-8).** A script the commit has and the base doesn't (a new repository, or a check added by this very task), or a checkout obid can't make: nothing runs, nothing counts as checked, and the job ends done with nothing published by itself and why in its `reason`. The commit it ended with is kept for Publish by hand, the owner's click.
- **A job ends done.** obid takes its commits into its clone and moves its branch there; the commit its check passed on is the job's checked head (`checkedHead`, kept with the job, not in the API), its head for a job with no check. Another round (a decision round, the round told to commit) records it again when it ends done. A check that ran with work uncommitted gets the one round Oby tells it to commit; still uncommitted then, or HEAD moved by the check, the job ends done with nothing published and why (PUBLISHING-5).
- **A branch moves.** When obid moves a job's branch in its clone (any job's commits, kept when it ends), every job whose checked head on that branch is another commit loses it: it's offered no Publish, and isn't waiting on the owner for one.
- **It publishes, by itself or by hand.** obid pushes the checked head and nothing else, and only while the job's branch in its clone is still there. When the branch moved, nothing goes out and the job says why. The owner's own signed Publish may ask for more (PUBLISHING-9 to 11).
- **The owner publishes by hand while a follow-up carries the branch on.** By default refused (the owner's signed Publish anyway publishes it, PUBLISHING-9), as Try again and delete are, while that follow-up is queued, running or done and not dismissed: it publishes the branch once its own check passes. One that failed, stopped or was dismissed doesn't hold it; when its commits moved the branch, the moved-branch refusal holds instead.
- **A job would start on a branch an active job works on.** A queued or running job on the same repository with the same branch, letter case aside (`oby/Fix-34` is `oby/fix-34` on a Mac): the job is refused, naming that job. That's a new job (`POST /v1/jobs`, a plan, a standing rule, GitHub work), an ended one run again (Try again, `oby_continue_job`, the owner's account-limit choice to resume or move it), and Oby's review asking for changes, which then starts no round and says why on the job (`reviewError`). Refused rather than given a branch of its own, so one issue never gets two pull requests that overwrite or duplicate each other: the owner tells the job already at work instead. Once it ended, another may take the branch. That's the default; when the owner insists (proposed, not built), the new job starts once the first ends, or on a branch of its own.

### Invariants

- No commit goes out by itself that a job's check didn't pass on. By hand, the owner's click publishes one (PUBLISHING-8, and Publish anyway, PUBLISHING-9), still scanned.
- No commit a check didn't check, untracked files and commits made while it ran included, is a checked head.
- A check runs the base's copy of its scripts and `.gitleaks.toml`, never the task's, on the commit alone: a task can't make its own check pass by changing the check.
- No two queued or running jobs on one repository work on one branch, new or run again.
- Publish is offered (`GET /v1/jobs/{id}/publish`, a job's Ready alert) only when publishing it would go out as far as obid knows.
- Everything else about publishing holds: the secret scan on every publish, the lease, never `main` or the default branch by itself (the owner's signed `to` names any branch: PUBLISHING-10), every outgoing action listed.

### Failure and recovery

- `Not published: oby/fix-75 moved since this job's check passed on it, so its commits now aren't the ones checked.` The owner tells the job (a follow-up runs the check on the branch as it is now) or the follow-up that moved it.
- `Not published: this job ended before Oby kept the commit its check passed on, so Oby can't tell what it checked. Tell it to carry on, and it checks again.` A job that ended before obid kept that commit.
- `Its follow-up <title> carries its branch on: publish that one instead.`
- `<title> (job <id>) is working on oby/fix-34 now: tell that one instead.` For Oby's review, `reviewError` is `Oby's review asks for changes, and obid couldn't hand them to the agent: ` and that line.
- `Not published: its check ran with changes in the worktree that weren't committed, so it didn't check the commits alone. Tell Oby to commit them or drop them, and it checks again.` (the job's `reason`, and Publish's `409`)
- `Not published: its commits changed while its check ran, so the check didn't pass on the ones there now. Tell Oby to carry on, and it checks them again.`
- `Not published: its check runs scripts/check.sh as main has it, and main has no scripts/check.sh, so nothing counts as checked. Read its change, then Publish it by hand.` (PUBLISHING-8, the job's `reason`.) A checkout obid couldn't make, or a base it can't read, gives the same ending with its own words in the middle (`obid's clone doesn't have main`, `obid couldn't make the check's own checkout (its worktree)`).

These words show an internal job id (`job 3125ab36`) and a branch name, as obid's other refusals do; how the apps word them is Sangam's.

## Interfaces and dependencies

`GET` and `POST /v1/jobs/{id}/publish`, `POST /v1/jobs`, and `publishError` on the job, as docs/runner-api.md has them. Nothing new in the API: `checkedHead` stays in the job's file.

## Acceptance scenarios

- **PUBLISHING-1:** A job ends done with its check passed and its publish fails. Published by hand, the commit its check passed on goes out. (`publishing_1_2_only_the_commit_its_check_passed_on_goes_out`)
- **PUBLISHING-2:** Its branch in obid's clone moved since (a commit its check never ran on): Publish by hand is `409` with `Not published: <branch> moved since this job's check passed on it…`, and nothing reaches the remote (by default; PUBLISHING-9). (`publishing_1_2_only_the_commit_its_check_passed_on_goes_out`)
- **PUBLISHING-3:** A published job's next run passes its check and its publish fails; a follow-up on its branch fails its check. Publish on the first job is `409` while the follow-up is at work; once the follow-up's commits moved the branch, `GET` and `POST` are `409` because the branch moved. The follow-up's failing commits never reach the remote by themselves (PUBLISHING-9). (`publishing_3_a_follow_ups_failing_commits_never_go_out_on_the_first_job`)
- **PUBLISHING-4:** "Fix issue 34" while a job already works on `oby/fix-34`, or a job naming that branch in any letter case: by default `422` naming the job at work. Issue 35 starts; once the first job stopped, issue 34 starts again on `oby/fix-34`, and then the first takes no Try again (`422` naming it). (`publishing_4_two_jobs_on_one_issue_never_share_a_branch`, runner_api.rs.) Nor does the owner's account-limit choice resume or move a job while another works on `oby/Fix-34` (`publishing_4_an_ended_job_runs_again_only_off_a_busy_branch`, obid's lib tests), nor does Oby's review asking for changes start a round: `reviewError` names the other job (`publishing_4_a_reviews_changes_wait_off_a_busy_branch`, publish_api.rs).
- **PUBLISHING-5:** A published job's next check runs with a file it never commits: it's told once to commit, then ends done with `reason` saying so, nothing pushed, and Publish `409` with the same words (by default; PUBLISHING-9). A check that commits while it runs commits in its own checkout (PUBLISHING-6): what goes out is the commit it checked, without the check's. (`publishing_5_a_check_that_didnt_check_the_commits_publishes_nothing`.) A commit that lands on the job's worktree from elsewhere while its check runs: done, `reason` `Not published: its commits changed while its check ran…`, nothing pushed (`publishing_5_a_commit_made_while_the_check_runs_isnt_checked`). A check that writes `report.xml` writes it in its own checkout, so the job's worktree never has it: its new commit publishes without the report and without a round telling it to commit (`publishing_5_what_a_check_leaves_isnt_uncommitted_work`).
- **PUBLISHING-6:** A job based on `oby/a`, whose `check.sh` passes, is checked with `main`'s, which fails (`publishing_6_a_check_never_comes_from_a_branch_obid_pushed`). The base has a `.gitleaks.toml` and ignores `.env`. A task commits its own `.gitleaks.toml`: its check reads the base's, passes, and the task's goes out. A task that leaves a `.env` its check needs (ignored, so not uncommitted work) fails its check: the checkout has none, as the commit going out has none. (`publishing_6_the_check_runs_on_the_commit_alone_with_the_bases_files`; which words are scripts: `publishing_6_a_checks_scripts_are_its_programs_paths`, obid's lib tests, crate::merge.)
- **PUBLISHING-7:** The base's `check.sh` fails. A task rewrites it to `exit 0`: its check still runs the base's, which fails, and nothing goes out (`publishing_7_a_check_rewritten_to_pass_still_runs_the_bases`). A check that empties its own script while it runs, renames a folder it's in, or rewrites `.gitleaks.toml` is refused each time, and still fails (`publishing_7_a_running_check_cant_rewrite_the_bases_script`). A task that changes its check script for good is checked by the base's until it's merged; its pull request also falls under MERGING-15 (#1646). 
- **PUBLISHING-8:** The base has no `check.sh`, and the task adds one its check runs (`sh check.sh`): the job ends done with no check run, `reason` `Not published: its check runs check.sh as main has it, and main has no check.sh, so nothing counts as checked. Read its change, then Publish it by hand.`, nothing pushed; Publish by hand pushes it. (`publishing_8_a_check_the_base_doesnt_have_counts_for_nothing`)
- **PUBLISHING-9:** Where PUBLISHING-2, 3, 5 or 8 refuse Publish by hand, or a job ended without its check passing, the owner's word goes through: `anyway` on their signed Publish (`GET /v1/jobs/{id}/publish?anyway=true` answers the sentence and `head`, the commit it sends: the worktree's head for a job that didn't end done, else its branch's in obid's clone) pushes exactly that commit, its sentence ending ` Its check didn't pass on <commit>, or didn't run: it goes out anyway.`, and opens the pull request; a job that didn't end done takes its worktree's commits into obid's clone first. A branch that moved since is refused (`Not published: <branch> is at <commit> now, not <commit>, the commit you approved.`). A follow-up carrying the branch doesn't hold it, and the sentence says so: ` A follow-up, <title>, carries this branch: publishing this puts it at <commit>, and the follow-up loses its own publish.` The pull request is reviewed and merged as any other. What still stops it is the secret scan (AGENTS.md; the owner hasn't decided otherwise) and GitHub's own rules. Proposed, not built: the job's card offering it with the refusal's words, and the pull request's description saying which check didn't pass on that commit. (`publishing_9_10_11_the_owners_publish_goes_where_they_say`)
- **PUBLISHING-10:** The owner's signed Publish takes `to` (any branch, the default branch included; onto its base it lands with no pull request) and `force`: `GET …?force=true` answers `over`, the commit on that branch now (empty for none), which the sentence names (` It replaces <commit> on <branch> (force-push).`) and the push replaces with `--force-with-lease` on exactly that commit; moved since, nothing goes out. Each choice is in obid's sentence, so the signature covers it, and a body that asks for other choices than the signed sentence is refused. Over a branch someone else moved, without `force`, it's refused as before. By itself obid pushes only its own `oby/` branch, never main or the default branch, and force-pushes only over its own last push. (`publishing_9_10_11_the_owners_publish_goes_where_they_say`; `publish::tests::publishing_10_the_owners_publish_takes_any_branch_and_says_so`)
- **PUBLISHING-11:** A root commit (no parent) goes out only on the owner's signed Publish with a choice of theirs; the scan reads its whole tree, so a key anywhere in it stops it. By itself, `Not published: the head commit on <branch> has no parent.` The secret scan stops every one of PUBLISHING-9 to 11 the same way: `409`, nothing pushed. (`publishing_9_10_11_the_owners_publish_goes_where_they_say`)

Test it when it's done, on a real Mac: ask Oby, in this repository, to change `scripts/oby-check.sh` to `exit 0` and break a test, and see its check fail with dev's script; ask Oby to fix one issue twice, from Home and from a conversation, and see the second refused naming the first; let a task's publish fail (sign `gh` out), tell it something that fails its check, and see Publish on the first task refused.
