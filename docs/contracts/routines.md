# Routines: work on a schedule or on GitHub events, by itself

The business behavior contract for how a routine's runs wait, and how a routine on GitHub events starts its jobs, from [the template](../business-contract-template.md). The API is [docs/api/routines.md](../api/routines.md); the code is `core/crates/obid/src/routines.rs`, its pure decision `core/crates/obid/src/routines/trigger.rs`, and `github_work.rs`'s routine start (`start_routine`, on the feed's Start's path, `begin`). The tests are `core/crates/obid/tests/routines_api.rs` (`routines_1_*` to `routines_17_*`), the unit tests `routines_2_*` and `routines_3_*` in `routines.rs` and `routines_10_to_16_each_rule_decides` in `trigger.rs`, and the Kani proofs in `trigger.rs`. Roadmap: OBY-84, OBY-88, R12-05.

## Feature and status

- **Outcome:** A routine runs on its schedule without piling work up or asking the owner anything. Since LIMITS-18 (#2124) `Jobs::create` never refuses for want of room: a job with no account that has room is made `queued` and waits by itself. The owner's word: work waits by itself, never asks about a limit; ask the human least. So a routine whose last run still waits (for room, or for the owner) doesn't start another one behind it, a run too late to matter is recorded, not run, and a Mac waking with many routines due doesn't start them all at once.
- **Outcome, GitHub events:** the owner confirms once "review every pull request that requests me in obi" or "fix red CI on my pull requests", and each matching event of the GitHub work feed starts one ordinary job. A second read or a restart never starts a second job.
- **Status:** **Implemented** (ROUTINES-1 to 21). The words of the reasons, a trigger routine's `when` and Settings › Routines' words are **proposed, Sangam's to change**: his design has no screen for a routine's runs or receipts yet (R12-06).
- **Outcome, Settings › Routines:** the owner sees every routine obid keeps in one place, the T3 Code way, and pauses, resumes, runs or deletes one without asking Oby in a conversation.
- **Scope:** When a scheduled run starts, is skipped or is missed, and which feed events a routine on GitHub events starts a job for. Outside it: the job a run starts (it's an ordinary job, `Jobs::create`, unchanged), pausing after 3 failures (`failuresInARow`, ALERTS-5, unchanged), Run now's own rules (the owner's own word, below), events the feed doesn't read, webhooks, and the apps' screens but the Mac's Settings › Routines (ROUTINES-18 to 21), which shows and changes routines through obid's routes and decides nothing itself. Making or editing a routine there is out of scope: a routine is still made by confirming Oby's card in a conversation.

## Behavior

- **Actors and ownership:** obid decides, at each check (every minute, and once as it starts), whether a routine that's due runs, is skipped or is missed, and keeps the run in the routine's file. Clients show `lastRun`, `runs` and `graceMinutes`, and send `graceMinutes` on `POST` and `PATCH`. No model call decides any of it.
- **Triggers:** a routine's next time comes (`due`), at a check.
- **States:** each run is `started`, `skipped`, `missed` or `failed`, as before. `skipped` and `missed` start no job and never count toward `failuresInARow`, so they never pause a routine.
- **The previous run.** What a new run looks at is the job of the latest run that started one. obid keeps that job's id on the routine itself (`lastJob` in its file, filled from its runs for a file kept before it), not only in its last 50 runs: skipped and missed runs are runs too, and would push the one that started the job out of the list. A skipped run is said in the routine's conversation once for the job that holds it, not at every due time; every skipped run is still kept in `runs`. Run now (`POST /v1/routines/{id}/run`) is the owner's own click: it waits only while that job is still `queued` or `running` (`409`, as before), never because it waits for the owner.
- **Failures and recovery:** a skipped or missed run moves the routine on to its next time, kept before anything starts, so a restart never runs a time twice. A previous job that ends, moves to an account with room, or is answered or dismissed by the owner lets the next due run start. Answered in words counts: an ended job the owner tells something stays `interrupted` and a follow-up carries it on (`followUpOf`), so it no longer waits for them.
- **Routines on GitHub events.** A routine has a `schedule` or an `on` trigger, never both or neither: `{"github": {"repo", "event", "label"?}}`, the repository the routine's own. The events come from the GitHub work feed's reads (every 180 s, docs/api/github.md), after a read that offers work, and match only the items that read kept (docs/contracts/github-work.md), so with `githubEveryRepo` off a routine's repository must be one of obid's listed ones; the first read on record, or the first as another login, starts nothing. For each enabled routine, an item matches when its repository is the routine's (letter case aside) and: `reviewRequested`, a review request; `assigned`, an issue assigned to the owner; `checksFailed`, one of the owner's own pull requests whose head's checks failed, not a draft and not a fork's; `labeled`, a review request (a `review` routine) or an assigned issue (a `fix` routine) carrying the label (ASCII case aside). A `reviewRequested` routine makes `review` jobs, `assigned` and `checksFailed` make `fix` jobs, `labeled` either; left out, the kind is the event's (`fix` for `labeled`). It has no next run and no Run now; a paused one matches nothing.
- **Receipts.** Each event a routine decides gets a receipt in the routine's file, keyed `<repo>#<number>@<event>@<marker>`: the marker is the head commit for `reviewRequested` and `checksFailed` (empty when GitHub gave none), the routine's label for `labeled`, empty for `assigned`. A receipt is `started`, `ignored`, `held` or `failed`, with a reason, the job's id and when its outcome was last set; it holds none of GitHub's text. One routine keeps one receipt per key.
- **What one event does.** At each read the routine decides, one at a time, each matching event whose key the previous read didn't hold, and each of its `held` receipts whose key this read still holds; each sees the receipts the ones before it left. `routines::trigger::decide`, in this order: a key with a `started`, `ignored` or `failed` receipt is done; an event Oby caused (a head an obid job pushed, or a pull request an obid job opened) is `ignored`; one with no marker it needs is `ignored`; one on an item where this routine's job is still `queued` or `running` is `held`; one on an item this routine started 3 jobs on in the last 24 hours is `held`; one when this routine started 10 jobs on any of its items in the last 24 hours is `held`; one after this routine started 3 jobs at this read is `held`; any other starts.
- **Starting.** A start keeps its `started` receipt in the routine's file before it asks for the job, so a crash between them starts nothing more; a file that can't be written makes the receipt `failed` in memory and starts nothing, its inbox offer left for the owner. The job is made on the feed's Start's path, so GitHub's text reaches it only through its quoted inputs file (ISSUETASK-1's for an issue), with the routine's agent, account, mode, check, rounds and mark, its task obid's sentence for the item and then the routine's task, and its own conversation, as a job started from the feed. A queued or running job already on the item makes the receipt `ignored`, `Another job is already on it.`. Either way the item's inbox offer is settled.
- **Expiry.** A receipt is kept 7 days from when its outcome was set, and as long as its item stays in the feed with the same marker.
- **From chat.** `oby_routine` may propose an `on` trigger instead of a schedule; it is a Confirm card, and nothing is saved until the owner confirms it.
- **Invariants:** a routine never asks the owner about a limit, a scheduled run never starts behind a previous run's job that still waits, and a routine never pauses for runs it skipped. Every job a run starts is made by `Jobs::create`, under every rule a job has.

## Interfaces

- `graceMinutes` on a routine (`GET`, the `routine` event): how late, in minutes, its latest time still runs; `60` for an hourly routine and `1440` for the rest when the routine names none. Optional on `POST /v1/routines` and `PATCH /v1/routines/{id}` (a whole number, at least 1; `0` is `422`). Add-only: an older client that never sends it gets the default.
- `on`, `receipts` and a trigger routine's `when` words, `schedule` and `nextRun` null on it: [docs/api/routines.md](../api/routines.md).
- A receipt's `reason`: `Oby's own push or pull request caused it.`, `GitHub didn't say which commit it's on.`, `This routine's job on it is still open.`, `This routine started 3 jobs on it in the last 24 hours.`, `This routine started 10 jobs in the last 24 hours.`, `This routine started 3 jobs at this read of GitHub.`, `Another job is already on it.`, `obid couldn't keep the receipt, so it started nothing.`, or the reason the job couldn't start.
- A skipped run's `reason`: `The previous run still waits for an account with room.` or `The previous run still waits for you.` (new), or `The previous run was still going.` (as before).

## Acceptance scenarios

- **ROUTINES-1** (`routines_1_a_run_whose_previous_job_waits_for_room_is_skipped`): a routine's previous run's job is `queued` and waits for room (a five-hour limit's reset, `resumesAt`, LIMITS-5 and 18; or `waiting` for room, #872). Its next due run is `skipped`, `reason` `The previous run still waits for an account with room.`, and starts no job. `failuresInARow` stays as it was; a routine skipped 3 times in a row stays on. However long it waits (`routines_1_a_run_stays_held_past_50_skipped_runs`): past 50 skipped runs, when the run that started the job is no longer among the runs kept, the next due run is still `skipped` and no second job starts; the conversation heard of the skip once.
- **ROUTINES-2** (`routines_2_a_run_whose_previous_job_waits_for_you_is_skipped`, and the unit test `routines_2_a_job_that_asks_holds_the_next_run_until_it_is_answered` for an open permission): a routine's previous run's job waits on the owner: `interrupted`, a permission or question open (`permission`), a #1563 limit decision (`accountLimit`), or held for a ChatGPT yes (CHATGPT-20). Its next due run is `skipped`, `reason` `The previous run still waits for you.`, and starts no job, with no count toward `failuresInARow`. Run now still starts one. It waits for them no longer, and the next due run starts, once they dismissed it (`routines_2_a_dismissed_previous_job_holds_nothing`) or a follow-up carries it on, as the app stops showing it then (`routines_2_a_followed_previous_job_holds_nothing`).
- **ROUTINES-3** (`routines_3_a_time_older_than_its_grace_is_missed_not_run`, and the unit test `routines_3_a_latest_time_past_its_grace_is_missed_not_run`): when a routine's latest due time is older than its grace (`graceMinutes`, else 60 for hourly and 1440 for the rest), it's recorded `missed` with the times before it (`Missed 1 run while Oby wasn't running.`), nothing runs, and the routine goes on to its next time. Within its grace it runs as a catch-up, as before.
- **ROUTINES-4** (`routines_4_a_check_starts_one_routine_at_most`): a check starts at most one routine's job. Another routine due at the same check waits for the next check, a minute on, and runs then for the same time, judged as it was at the check that put it off: that wait is obid's own, so it never makes the run `missed` (with `graceMinutes` 1 it still runs) or a catch-up. obid keeps which routines it put off in memory only: after a restart a time is as late as it is. A run that's skipped, missed or fails doesn't count: the check goes on to the next routine.
- **ROUTINES-9** (`routines_9_a_review_request_starts_one_job`, `routines_9_a_trigger_routine_is_checked_and_shown`, `routines_9_a_trigger_from_chat_waits_for_confirm`): given a routine on `reviewRequested` for a repository, when the feed reads a new review request there, then one job starts (kind `review`, the pull request, the routine's agent, account, mode and mark), its `started` receipt is in the routine's file, and the item's offer is settled. A routine with both a schedule and `on`, or neither, a label where it doesn't belong, a kind that doesn't fit, or another repository is `422`; `PATCH` `schedule` and Run now on one are `422`; from chat it's a Confirm card.
- **ROUTINES-10** (`routines_10_a_receipt_starts_nothing_twice`, the Kani proof `routines_10_a_receipt_never_starts_twice`): given a receipt for an item, when the feed reads it again or obid restarts and reads it as new, then no second job starts and the receipt is unchanged. A receipt that can't be kept starts no job, and the offer stays open.
- **ROUTINES-11** (`routines_11_a_later_event_waits_for_the_open_job`, the Kani proof `routines_11_an_open_job_holds`): given this routine's job on an item still `queued` or `running`, when a new event on the item comes, then it is `held` (`This routine's job on it is still open.`) and starts nothing; once that job ends, the next read with the item at that marker starts it.
- **ROUTINES-12** (`routines_12_a_fourth_run_in_a_day_is_held`, the Kani proof `routines_12_no_fourth_start_in_a_day`): given 3 `started` receipts on one item in the last 24 hours, when a 4th event arrives, then it is `held` (`This routine started 3 jobs on it in the last 24 hours.`) and no job starts.
- **ROUTINES-15** (`routines_15_a_read_starts_three_jobs_at_most`, the Kani proofs `routines_15_no_fourth_start_in_a_read` and `routines_15_a_capped_event_is_held`): given a routine on GitHub events, when one read offers more than 3 of its events, then 3 jobs start and each event past them is `held` (`This routine started 3 jobs at this read of GitHub.`), its offer left open; the held ones start by themselves at later reads, 3 at a time, and their offers stay open meanwhile. A start that ends `ignored` or `failed` doesn't count.
- **ROUTINES-16** (`routines_16_an_eleventh_start_in_a_day_is_held`, the Kani proofs `routines_16_no_eleventh_start_in_a_day` and `routines_16_a_capped_event_is_held`): given 10 `started` receipts of a routine on any of its items in the last 24 hours, when a new event arrives, then it is `held` (`This routine started 10 jobs in the last 24 hours.`) and no job starts; it starts at a later read once the routine is under 10 again. An item at its own 3 says ROUTINES-12's reason.
- **ROUTINES-17** (`routines_17_a_label_with_a_control_character_is_refused`): given a `labeled` trigger, when its label holds a control character (`\r`, a tab, NUL, U+0085 and the like) or U+2028 or U+2029, then making the routine is `422` (`label is one line of 1 to 50 characters.`); a label with a plain space is kept.
- **ROUTINES-13** (`routines_13_github_text_stays_quoted`): given a routine on GitHub events, when its job starts, then the item's text is only in the job's quoted inputs file, never in its task, and the routine's file holds no title, body, author or label but the routine's own.
- **ROUTINES-14** (`routines_14_obys_own_push_starts_nothing`, the Kani proof `routines_14_obys_own_events_start_nothing`): given an event Oby caused (a head an obid job pushed, or a pull request an obid job opened), then it is `ignored` with a reason and no job starts.
- Every rule of `decide`, branch by branch: the unit test `routines::trigger::tests::routines_10_to_16_each_rule_decides`.

### Settings › Routines (the Mac's Electron app)

The page is `apps/electron/src/renderer/src/RoutinesSettings.tsx`, its words `routines.ts`; obid owns every routine and its runs, and the page only shows them and sends the owner's clicks (docs/api/routines.md, "In the apps"). Tests: `apps/electron/src/renderer/src/test/routinesSettings.test.tsx`, named after each scenario.

- **ROUTINES-18** (`ROUTINES-18: lists every routine…`, `ROUTINES-18: Settings lists Routines…`): given obid keeps routines, when the owner opens Settings › Routines, then each shows as a group titled with its name: obid's `when` (its schedule in words), its repository and when it runs next in the Mac's time (`Next tomorrow at 9:00 AM`; `Paused` while paused; `Runs when its event comes` on GitHub events), and how its last run went (`Done · started today at 9:00 AM`, `Skipped today at 2:00 AM: The previous run was still going`, `Couldn’t start …: <why>`, `Hasn’t run yet`), in red when it failed. A routine on GitHub events has no Last run row: what its events did are its receipts. With none, `No routines yet`, and how to make one. The page reads obid as it opens, after each change and every 30 seconds while open.
- **ROUTINES-19** (`ROUTINES-19: Pause and Resume…`): given a routine, when the owner clicks Pause, then the app sends `PATCH /v1/routines/{id}` `{"enabled": false}` and shows it `Paused`; Resume sends `{"enabled": true}` and shows its next run. Nothing else about it changes.
- **ROUTINES-20** (`ROUTINES-20: Run now…`): given a scheduled routine, when the owner clicks Run now, then the app sends `POST /v1/routines/{id}/run` and shows the run obid answers (`Running · started today at …`); when obid refuses (`409` while its previous run's job is open, `422`), obid's words show under it and nothing else changes. A routine on GitHub events has no Run now.
- **ROUTINES-21** (`ROUTINES-21: Delete asks first…`): given a routine, when the owner clicks Delete, then nothing is sent yet: its group asks in the page, `Delete <name>?` and `The tasks its runs started stay.`, with Cancel and Delete (the app has no `confirm()` window). Cancel sends nothing; Delete sends `DELETE /v1/routines/{id}` and the routine goes from the page.
