# Permission modes: Bypass asks nothing

The business behavior contract for how much a job asks its owner, from [the template](../business-contract-template.md). Scenarios are numbered `BYPASS-n`; the tests that prove them name the scenario.

## Feature and status

- **Outcome:** The owner picks how freely their agents work, in Settings and on each task, with Sangam's four modes, and Bypass, the default, asks nothing (the owner's decision of 2026-11-04). On the 2026-10-28 call every task asked for permissions although Settings showed Bypass ([#1570](https://github.com/obi-ai-bot/oby/issues/1570)): obid wasn't in Bypass, and the app's Mode menu did nothing.
- **Status:** **Implemented** by [#1592](https://github.com/obi-ai-bot/oby/pull/1592) (Bypass holds where the brain, the conversation's shell and approved plans lost it; only what touches secrets asks) and by the change that added this contract (a new install starts in Bypass, the Mode menu, hooks, Question cards). Sangam's design (General › Permissions: Ask, Accept edits, Plan, Bypass · "Asks nothing", Bypass the default; the task card's Mode button) and the owner's decision of 2026-10-27 lead.
- **Scope:** obid's default mode, the modes the Electron app offers, what Bypass still asks, the agent's own questions. **Out of scope:** the words of the secrets card (Sangam's to design), the Swift apps (frozen; they keep decoding every mode), Linux's network reading.

## Behavior

### Actors and ownership

- **obid** keeps the default mode (`home/permissions.json`), gives each new job its mode, decides every call by its fixed rules, the owner's saved rules and the mode, and asks the owner what's left.
- **The Electron app** shows and sets the default (Settings › General › Permissions on this Mac) and a task's mode (its Mode menu), shows what a job asks on its card, and sends the owner's answers.
- **The owner** answers what's asked, from the app.

### The modes

| Mode | Asks the owner about |
|---|---|
| Ask | every edit and command |
| Accept edits | every command |
| Plan | a command or a site that doesn't only read (what only reads goes ahead; an edit is refused until the owner approves its plan) |
| Bypass | nothing: the job's box and obid's fixed denials hold there, not a card |
| Sandbox (obid's old default) | the network beyond the model's API, a read outside the worktree, what obid can't read, secrets |

The app offers the first four. Sandbox stays in obid's API, add-only, for the installs that saved it and the jobs that have it: Settings shows it only while it's the saved one, and a task in it shows `Sandbox` on its Mode button.

### Decisions

- **A new install starts in Bypass.** No `permissions.json`, or one with rules and no `mode`, means `bypass`. A mode the owner saved is never changed by an upgrade, `sandbox` included. An install that never saved a mode (most 0.4.x installs, which ran in Sandbox by default) is in Bypass after the upgrade too: the owner's decision of 2026-10-30, said in the release notes. A saved mode obid can't read (a newer obid's, a hand edit), or a file that doesn't read, fails closed: Ask, as a job whose mode obid can't read does.
- **Bypass asks nothing (the owner's decision of 2026-11-04, "I want the bypass", replacing secrets asking there).** A command naming a secret, a login or the vault runs inside the job's box, which gives it no real secret: reads from obid's home and the person's home stop at the job's own folders (`sandbox.rs`). An agent's own question still waits for the owner, since no mode can answer it. Commands, edits, the network, the conversation's shell, a repository's hooks (Cursor's), approved plans and the brain's own Bypass jobs all go ahead. What touches secrets, a login or the vault asks in every mode, Bypass too, and no mode change or rule settles that card. A repository's hooks are judged as the agent's commands are (`permissions::decide`), when the job starts and when its mode changes alike, so a hook that touches secrets asks in Bypass too, with no Always.
- **The agent's own question is not a permission.** Claude Code's `AskUserQuestion` (and Codex's and Cursor's questions) waits for the owner in every mode, because the agent chose to ask; the app shows it as Sangam's Question card, the question as its headline and the agent's options as buttons, never as a Permission card with Allow and Deny. His Tell it something follows the options and opens the card's field for the owner's own words, so a question with no options is answered too. A pick or the words answer the inbox item itself (`POST /v1/inbox/{id}/answer`), never the job's permission, which can lag behind the inbox between a call's questions.
- **What only reads never asks, Plan too.** A command whose every part only reads (`cat`, `grep`, `rg`, `ls`, `nl`, `od` with their reading options, `command -v`, `sed -n` with line numbers from a file or a pipe; git's `diff`, `log`, `show`, `status`, `rev-parse`, `ls-files`, `ls-tree`, `cat-file`, `blame`, the listing forms of `branch` and `tag` and the other reads of PERMISSIONS-9, from the worktree's top), inside the job's box, with nothing written to a file, runs without a card in every mode. So Oby's own review, which stays in Plan, reads the change (`git diff origin/dev...HEAD`) without leaving the owner a card. A write (`git commit`, `rm`), the network and secrets still follow the mode: in Plan they ask, an edit is refused, and a push is refused in every mode. The `rg` Codex ships beside its binary (its package's `pathDir`, first on its commands' `PATH`, out of the box's reach) counts as the system's.
- **A task's Mode menu changes that task only**, from now on (`POST /v1/jobs/{id}/mode`): a waiting permission the new mode allows is answered; a secret or a question keeps waiting.

### Failures and recovery

- A `permissions.json` that can't be read (its permissions, a folder in its place) or doesn't parse is logged and taken as no rules and Ask, until the owner picks a mode again. Only a missing file is a new install.
- A Mode or an answer obid refuses (an unknown job, a mode that isn't one, a question already answered) shows obid's words in the app, and the card stays.

### Invariants

- The box, the fences (the worktree only, no publishing by the agent, no background work) and the secret scan hold in every mode. Bypass changes what obid asks, never what the box allows.
- obid's API stays add-only for the Swift iPhone and Watch apps: `sandbox` stays a mode they may see.

## Interfaces

`GET`/`PUT /v1/settings/permissions`, `GET /v1/status` (`permissions.mode`), `POST /v1/jobs/{id}/mode`, the `agentQuestion` inbox item and `POST /v1/inbox/{id}/answer` ([runner-api.md](../runner-api.md)).

- **PERMISSIONS-2** A Claude Code job starts with its telemetry and error reports off (`DISABLE_TELEMETRY=1`, `DISABLE_ERROR_REPORTING=1` in its environment, in obid's box and in its own sandbox alike), so it sends nothing to Datadog or Sentry: no card for the owner, no foreign mark. Codex and Cursor document no environment switch for theirs. - **PERMISSIONS-3** Oby's own review (Plan) runs `git diff origin/dev...HEAD`, `git ls-tree`, `git cat-file -p`, `git blame`, `cat`, `grep` and `ls` with no card and nothing on Home; its edit and its push are refused, and a `git commit` or `rm` waits for the owner. Codex's own `rg` is a reader as the system's is. `jobs_api::permissions_3_a_review_reads_without_asking_and_a_write_still_asks`, `permissions::tests::a_command_that_only_reads_never_asks`, `permissions::tests::a_reader_the_agent_ships_never_asks`, `codex::tests::codex_ships_its_programs_beside_its_binary`.
- **PERMISSIONS-4** A `permissions.json` that doesn't read (a hand edit, a file a newer obid wrote) is Ask with no rules, as before, and the owner's next change (a mode, an Always) copies it aside to `permissions.json.unreadable-<time>` before writing: the rules it holds are never written over. When it can't be copied, nothing is written and the change fails. `permissions::tests::permissions_4_an_unreadable_file_is_kept_aside_never_written_over` (#1652).
- **PERMISSIONS-5** Plan asks before a command that doesn't only read, WebFetch included, and refuses an edit until the plan is approved (Sangam's "Plans first, and works once you approve the plan"); what only reads never asks. `permissions::tests::permissions_5_each_mode_allows_or_asks` (#1652).
- **PERMISSIONS-6** A shell's grouping words don't change what a command does (#1811). A job's `printenv` or `curl` inside `{ }`, `if`, `while`, `until`, `for`, `select`, `case`, `!`, `( )`, a function's body, a coprocess, a `trap`, or a `$(…)` in a here-document whose end word isn't quoted is judged as the plain command is: `printenv` asks in Bypass, `curl` is the network, and a saved deny rule for it holds. No allow rule covers, or is offered for, a command behind `!`, in `( )`, in a coprocess or in a `trap`. A word of another command (`echo if printenv`, `git log --grep '{ x'`), a parenthesis in quotes (`git commit -m "fix(obid): x"`, which keeps its rule and its Always) and a quoted here-document's lines stay plain text. `coproc curl if x` is read both ways, since bash takes `curl` for its name and zsh runs it. `permissions::tests::permissions_6_grouping_words_hide_nothing`, `permissions::tests::permissions_6_a_saved_rule_reads_grouping_words_too`. Where a `cd` in a branch leads is read as if the branch ran, as `cd a || cd b` is: the box holds the rest.
- **PERMISSIONS-7** The rest of what a line's words can hide (#1811). Where a redirect goes isn't an argument (`printenv 2>&1`, `set > o.txt`, `{ printenv > o.txt; }` print every variable; `printenv HOME > o.txt` still only one, and a file a redirect names is still a file it touches). `$'…'` is a quote (`echo $'\'' ; printenv ; echo ''`). `<<` in `(( ))` shifts, so the next line is a command. Nested backticks are code, `bash -c -- x` runs `x`, `find -exec` runs what follows it, and an option of a wrapper that takes a value isn't the program (`env -u FOO printenv`, `exec -a x printenv`, `xargs -I {} printenv`, `sudo -u root curl x`), zsh's `noglob`, `nocorrect` and `repeat 1` are wrappers, and its `{ printenv }` still prints everything. `set` alone prints every variable, and `set -e` asks nothing. A deny rule holds past a wrapper and a variable set before the program (`command curl x`, `{ FOO=1 curl x; }`), and for the wrapper it names (`Bash(sudo:*)`, `! sudo curl x`), and text in a here-document or in quotes is no command to it. A `>` or `;` in quotes keeps a command's allow rule and its Always (`git log --format='%h > x'`). `permissions::tests::permissions_7_only_what_runs_chains_a_command`. `permissions::tests::permissions_7_redirects_quotes_and_wrappers_hide_nothing`, `permissions::tests::permissions_7_a_deny_rule_reads_past_wrappers`.
  **Limits, on purpose:** obid reads a line's words and is no shell, so these aren't seen as what they run, and the box holds them (no secret is in a job's environment, the egress proxy decides each site, what it hides from reading is hidden from reading only): code a shell reads from a pipe (`echo printenv | bash`), brace expansion (`{printenv,}`, `cat {.env,}`), a glob or a variable that spells a secret's path (`cat ~/.a*/credentials`), a program a variable or an escape names (`c=printenv; $c`, `$'\x70rintenv'`), which counts as the network, not as a secret, zsh's short forms with no separator (`if [[ -n x ]] printenv`), and a saved deny rule with quotes in it on a chained line, read from the words without their quotes. Reading more of them would make harmless lines ask, and `echo if` and `git log --grep "{ x"` stay clean.
- **PERMISSIONS-8** What obid can't fully see never passes as allowed or read-only. A `<<` in `$(( ))`, nested `(( ))`, `$[ ]`, `${ }` or a first word's subscript (`a[1<<2]=3`) is a shift, as bash, zsh and sh run it, so the lines after it are read as commands and every check sees them (`echo $[1<<2]⏎curl y` is the network, and a saved `Bash(curl:*)` refuses it; this was a limit of PERMISSIONS-7). A here-document ends at the line a shell ends it at: `<<'E F'`, `<<E\ F`, `<<$'E'`, `$(cat <<E⏎…⏎E)`, and when its end word isn't quoted, after a shell joins a backslash and its new line (`<<E⏎E\⏎⏎rm y`, so `rm y` is a command). Even so a line with such a `<<`, or with a here-document that never ends (a shell may have ended it where obid didn't: `<<$'E\x41'`, `<<"E\"F"`, `<(cat <<E⏎x⏎E)`), counts as no read, in a job and in the conversation's shell, and no allow rule covers it or is offered for it; a here-document that never ends has its lines read as commands too, by a deny rule and the secrets check as well, at the cost of a question on a malformed line; and Bypass stays quiet unless what obid reads touches secrets. A `$'…'` with an escape can spell an option (`find . $'-\x64elete'`), so it's no read either. `ps` with the environment's letter (`ps e`, `ps auxe`, `ps -E`) prints the environment as `printenv` does and asks in Bypass; `ps -e` and `ps -o user` don't. A command whose card offers an exact rule shows all of it in its `title`, since the inbox card shows only that. A command longer than the 2,000 characters its card shows says how many are hidden (`… (345 more characters not shown)`, proposed words, Sangam's to change), in its `title` and `detail`, and offers no Always. `permissions::tests::permissions_8_what_a_shell_runs_is_what_obid_reads` runs each form in `/bin/bash` first. `permissions::tests::permissions_8_what_obid_cant_read_is_no_read_and_gets_no_rule`, `permissions::tests::permissions_8_a_cut_command_says_what_is_hidden_and_offers_no_always`, `permissions::tests::permissions_8_ps_with_e_prints_environments`, `permissions::tests::permissions_8_an_escaped_word_is_no_read`, `brain::shell::tests::permissions_8_a_line_obid_cant_read_is_no_read_here_too`.
  **Limits, on purpose:** a `<<` in `$(( ))` a shell takes for a real here-document, because the `$((` turned out to be a `$(` with a subshell in it, is read as a shift: the line is no read and has no rule, but a quote in its text could still hide a later line from a deny rule or the secrets check. `declare a[1<<2]=3` is a here-document in bash and zsh, and read so. What a shell spells into an option as it runs is still not seen by what counts as a read: `find . $(echo -delete)`, `find . ${x:--delete}`, `find . {-delete,}`, `git diff $(echo --output=x)`, a glob that matches a file named like an option. Refusing those would make `git diff $(git merge-base HEAD origin/dev)` ask in every review; the box holds them to the worktree and its git folder. On this Mac `ps e`, `ps E` and `ps -E` printed no environment when tried (macOS 26, for the same user's processes): the card is for Linux's procps and for other macOS versions, and costs a Mac only that question. Claude Code answers what it takes for a read by itself and never asks obid (seen on 2.1.302, `answered` empty, for `echo $[1<<2]` in Plan): obid's reading holds there for what it does ask about, such as `echo $[1<<2]⏎touch y`, which it asked obid about and got a card with no rule.
- **PERMISSIONS-9** More of git's reads never ask, Plan too: `git branch` listing (`-a`, `-r`, `-v`, `--show-current`, `--list`, `--contains`, `--merged`, `--points-at`, `--sort`, `--format`), `git tag` listing (`-l`, `--list`, `-n`, and the same), `git remote` (names only), `git reflog` (its `show`, `list`, `exists`, `HEAD`, or options), `git stash list`, `git stash show`, `git worktree list`, `git grep`, and `git config` reading one setting (`--get`, `--get-all`, `get`, or a key alone). Each is read form by form, so anything else follows the mode: a word after `git branch` makes a branch (`git branch -v x` does, on real git) unless an option lists, `git reflog expire`, `git stash`, `git remote update`, `git remote show` and `git ls-remote` (the network), `git remote -v`, `git remote get-url`, `git config --list` and `--get-regexp` (they can print a login: a remote's URL can hold one, `https://user:token@…`), and a setting whose name says it may hold one (`credential`, `token`, `pass`, `secret`, `key`, `auth`, `header`, `cookie`, `proxy`, `insteadOf`, `url`). `--textconv` has git run a repository's program and `git grep -O` the one it names (real git ran it for `-lOrm`, `--open=rm` and `--op=rm`), so no git read takes them, run together with other letters or cut short. Claude Code has its own table and answers these itself, so the reach is Codex and Cursor, in Ask, Accept edits and Plan (seen on real turns: `git branch -a` and `git reflog -n 1` on Codex 0.162.1, `git branch -a` on Cursor, allowed by obid with no card; `git grep -lOtouch fixture` and `git remote -v` a card on both). **Limit, on purpose:** in Plan, Claude Code 2.1.302 ran `git grep -lOtouch fixture` and `git remote -v` by itself and never asked obid (2026-11-03, `answered` empty): its own read table answers those, so obid can't stop them, and its box holds them to the worktree. `permissions::tests::permissions_9_gits_read_only_forms_never_ask`, `permissions::tests::permissions_9_git_grep_with_a_program_is_no_read_however_its_written`.
- **PERMISSIONS-10** A saved allow rule, and what Always offers, read past variables and wrappers that don't change what runs: `RUST_LOG`, `RUST_BACKTRACE`, `NODE_ENV`, `GOOS`, `GOARCH`, `LANG`, `LC_ALL`, `TZ`, `NO_COLOR`, `FORCE_COLOR`, `CI` set to a plain value, then `timeout`, `time`, `nice`, `nohup` and `stdbuf` with the options known to change nothing else. So `RUST_LOG=debug timeout 60 cargo test` is `Bash(cargo test:*)`. Nothing else is read past: `env`, `sudo`, `xargs`, `watch`, `command` or a shell, `PATH`, `IFS`, `LD_*`, a login's variable, a value with a quote or a `$`, `time -o f` (it writes a file), an option obid doesn't know, or a program with a folder. What follows them runs anything as it did (`timeout 5 bash -c x` has no rule), and a chained line stays chained. A deny rule read past them already. `permissions::tests::permissions_10_a_saved_rule_reads_past_harmless_wrappers_and_safe_variables`.
- **PERMISSIONS-11** A refusal says what happened and doesn't invite a way around it. The owner's no, a saved deny rule, the conversation's shell and Plan each tell the agent the call did not run and changed nothing, and not to reach the same result another way; a no says to do the rest of the work and to say in the summary what it needed; the owner's own words come quoted, and what they say goes (a no with `use the lockfile` is a way the owner chose). Words that aren't the owner's (a turn's after it read something untrusted, an event's) say `Oby said no.` and come quoted as data, not the owner's order, with no "go on as they say": text from outside is never framed as an order. All of it is obid's one helper, in proposed words, Sangam's to change. A words field on a permission card isn't on his screen, so it isn't here: words reach a card as they did. `permissions::tests::permissions_11_a_refusal_says_what_happened_and_invites_no_way_around`, `jobs::tests::permissions_11_words_that_arent_the_owners_never_speak_for_them`, `plans_api::permissions_11_a_turn_that_read_the_web_tells_a_job_no_as_oby_not_the_owner`, a parked call's in `jobs_api::a_parked_job_survives_a_restart_and_words_are_its_no` and `adapters::codex_and_cursor_park_and_resume_with_the_answer`.
- **PERMISSIONS-12** Always saves something narrow and says what it saves. A tool's subcommand keeps what follows it (`Bash(swift test:*)`); anything else saves that very command (`rm -rf build` is `Bash(rm -rf build)`, never `Bash(rm:*)`), so a tool with no subcommand asks more in Ask. A command a rule can't keep whole offers no Always: more than one line, one ending in `*` (read as a prefix), one holding a token or a login. `always` names what's saved, and the Mac's card shows it on hovering Always allow (proposed, Sangam's to change). A rule saved before keeps its reach until the owner removes it in Settings, one written with a variable too (`Bash(RUST_LOG=debug cargo test:*)`), and none reaches past a wrapper it names (`Bash(timeout:*)` isn't `timeout 5 rm x`). In the conversation's shell a lone command is compared as written, quotes included, so Always holds for what it saved and `Bash(rm a b)` isn't `rm 'a b'`; a part of a chained line is compared by its words without their quotes. An Edit card's Always is as it was: what his button does there is his to say. `permissions::tests::permissions_12_always_saves_something_narrow_and_says_what`, `brain::shell::tests::permissions_12_always_holds_for_what_it_saved_as_written`, `asks.test.ts` (`permissions_12_…`, the hover too).

Narrow: only that job's own login folder (and its temp `~/.codex` link into it), only reads, only under `.codex/skills/`, after links and `..`. `auth.json`, `config.toml` and anything else in that login still ask; a path that leaves skills (`..` into `auth.json`, a symlink out, `..` into another job's id under `logins/`) still asks; an Edit or `rm` of a skill file still asks; a compound command that also names a secret (`cat SKILL.md && cat auth.json`) still asks. `permissions::tests::permissions_13_a_read_of_the_jobs_own_codex_skills_is_not_secrets`.
- **PERMISSIONS-14** Oby's own review of published work (a `review` job with `reviewOf`, run in `plan`) has nobody watching it, so it asks nothing: what `plan` would ask the owner (a command that reaches the network, a secret or past its box, or writes, a file write, a site its agent reaches through the egress proxy, its AskUserQuestion) is refused at once, kept in its `answered`, with no card, no inbox item and no park, and its agent is told nobody is watching and to write `couldn't run <what>` in its review, where `<what>` is only the program (a command's first word past its variables), the site or the tool, never a command's arguments or an address's login, path or query (a question: to decide what it can and say what it couldn't settle without the user).
