# Teammate review: another Oby asks this Oby to review its pull request

The business behavior contract for one Oby asking a teammate's Oby to review a pull request and approve it on GitHub, and for that Oby doing it, from [the template](../business-contract-template.md). Scenarios are numbered `TEAMREVIEW-n`; the tests that will prove the proposed ones are named after them (`teamreview_<n>_…`). The API is `docs/runner-api.md`, "obid only: Obi-to-Obi review jobs" and "obid only: teammate approval"; the protocol is the spec's `protocol.md`, section 11, "Approving on the code host".

## Feature and status

- **Outcome:** Some repositories merge only once a person other than the author approved the pull request on GitHub (a branch rule, as Tetrix's). Oby's own review can't give that approval, and neither can its reviewer account. So the owner's Oby asks a teammate's Oby over the Obysphere. That Oby reviews the exact commit, and when its review passes, it approves the commit on GitHub as its owner. Obys talk to Obys, and each owner is asked only when something goes wrong or a yes is theirs to give ("Rules Oby never breaks", AGENTS.md).
- **Status:** TEAMREVIEW-1 and TEAMREVIEW-2 are **Implemented**. TEAMREVIEW-3 to 8 are **Proposed**, not built. The words in TEAMREVIEW-2 to 8 (cards, task lines, results) are proposed, and Sangam's to change: TEAMREVIEW-2's card is built, but its words are still proposed.
- **Scope:** both sides of one `review_request` with `approve_on_host`: the sender's Oby asking, one teammate after another, and the receiver's Oby reviewing, answering and approving on GitHub. Outside it: the merge itself, which stays the merge step's ([merging.md](merging.md)); a review request with no `approve_on_host`, which follows the same review job and approves nothing; questions between Obys ([ask-an-oby.md](ask-an-oby.md)); Oby's own review of the owner's own pull requests; and the owner's own jobs' recovery ([recovery.md](recovery.md)), which TEAMREVIEW-6 borrows from.

## Behavior

### Actors and ownership

- **The sender's obid** decides when a teammate is needed (the merge step finds GitHub waiting for an approval it can't otherwise get), whom to ask and when to give up. `Link::ask_teammate` (`core/crates/obid/src/sphere/link/reviews.rs`) sends at most one request per call. Its owner is asked nothing unless something goes wrong.
- **The receiver's obid** accepts or declines (from the owner's inbox answer, or from a decision the owner remembered), reviews in a fresh worktree at exactly the head, builds the result, scans it and sends it. It approves on GitHub only by the spec's rule: with the owner's own tap on this exchange at this commit, or, under a standing permission, next to approvals of that commit by the people who own every file it changes (`approve_on_host`, `crate::sphere::link::reviews`).
- **The review's agent** reads, and that's all. It can't commit, publish, run commands or ask the owner. The review job and its check run in Oby's box (the foreign lane, [lanes.md](lanes.md)).
- **The Obysphere** relays the request and its replies. Its policy, which only its admin changes, may refuse a request.
- **The apps** show the request, the Confirm card and the job, and send the owner's answers and taps. They decide nothing.

### Triggers and prerequisites

- The sender's Oby is in an Obysphere, and the pull request is published, Oby's. It waits for an approval that only another person can give. In a repository whose workflow Oby hasn't learned, the owner says yes once, on a card, to a teammate reviewing it, and Oby remembers that for the repository (`crate::merge::teammate_card`).
- The teammate is an active member of the Sphere whose card accepts `review_request`. Teammates who approved on that repository before are asked first, then the rest by Obi id.
- The receiver's owner, or a decision they remembered, accepts the request. Only their own `gh` login approves on GitHub, and only where it can push.

### States and transitions

The sender's side, for one pull request at one head (the [teammate approval](../runner-api.md#obid-only-teammate-approval) section has every rule):

| Where it stands | What moves it | What the owner sees |
|---|---|---|
| Asked, waiting (`sent`, `accepted`, an approval less than 10 minutes old that GitHub may still show, or `asked` and the request not yet expired) | The teammate's reply, the request's expiry (2 hours, `approval::REQUEST_LIFETIME`), a new head | Nothing today; the wait on the task with TEAMREVIEW-7 |
| Spent (declined, expired, failed, `host_review` `unable`, an approval GitHub never showed) | The next call asks the next teammate | Nothing |
| Changes requested | The owner settles it; no other teammate is asked | A card: `ernesto's Oby reviewed it and asked for changes.` |
| Nobody left, no teammate who takes reviews, no Sphere | The owner invites someone or gets the approval on GitHub | A card that says what to do instead |
| Approved and shown on GitHub | The merge step merges by the repository's workflow | The task merges |

A new push is a new head: what was asked for the old one doesn't count, and Oby asks again.

The receiver's side: the request waits in the inbox as an `obiRequest` (`Accept`, `Accept, and remember for this repo`, `Decline`, `Decline, and remember for this repo`), or a remembered decision answers it. Accepted, it's a `review` job ([review jobs](../runner-api.md#obid-only-obi-to-obi-review-jobs)): fetch, a fresh worktree at `head_sha`, the agent with Read only, the repository's check in the same box, the result, the publish gate. With `approve_on_host` and an approved result, held to the receiver's own bar (its own check passed, no `blocker` found): approved by itself under a standing permission next to code owners', or `asked` with one Confirm card for this exchange. The owner's Confirm approves this commit only, for this request, and the yes lapses with the request.

### Failures and recovery

- **Today:** a review that can't start after `accept` sends a `failed` result. A turn that ends on an error, or runs past 45 minutes, fails the review. A Sphere that refuses the sender's request is taken for one that can't be reached, and the sender asks again on its next look, saying nothing. TEAMREVIEW-3, 6 and 8 change these.
- A request the receiver's owner leaves unanswered expires in the inbox: the item closes by itself and obid sends `decline` with reason `expired`. Today the sender waits the request's whole two hours for that. TEAMREVIEW-7 moves on after 15 silent minutes.
- An approval obid posted is read back at once. When the head moved, or the code owners' approvals no longer hold, it's dismissed. When GitHub won't let it be dismissed, a `failed` item tells the owner to remove it.
- A restart starts a review again from a fresh worktree: nothing is picked up. A Confirm's claim is on disk before GitHub is asked, so two taps, or a stop during the post, approve once.

### Invariants and boundaries

- The review is of the exact head: the worktree is detached at `head_sha`. The approval names that commit (`commit_id`), and obid posts it only while the pull request is open, is `repo`'s own, goes into the `base_branch` the review compared it with, and its head is still `head_sha`.
- A request to approve is reviewed against its base as fetched, or not at all: a base that doesn't fetch, or can't be compared, fails the job.
- What the other Oby wrote is data: it's quoted in `.obi/inputs/`, never in a prompt, and the repository's rules are the base's, never the change's.
- Only the owner approves, by their own tap or a standing permission they gave with their own tap. Nothing received, no API token, no other exchange's tap and no stale or reused tap approves.
- Every word that leaves passes the secret scan first. A finding, or a scanner that can't run, sends a `failed` result with no text.
- The sender asks one teammate at a time, and never another after a review that asked for changes.
- Vendor agnostic (AGENTS.md, "The social contract"): the protocol names no agent, and TEAMREVIEW-5 adds Codex next to Claude Code.

## Interfaces and dependencies

- **API (implemented):** `POST /v1/obid/sphere/requests`'s path for the sender's request, exchanges and their `exchange` events, the `obiRequest` inbox item and `POST /v1/inbox/{id}/answer`, the `confirm` item with action `approve_on_host`, `host_approval` decisions on `POST /v1/obid/decisions`, and the job's `outgoing` (`pullRequestApproval`, `pullRequestApprovalDismissal`). TEAMREVIEW-2 to 8 add no key, status or enum value that the Swift apps decode as closed.
- **Code:** `Jobs::start_obi_review` and `Jobs::run_obi_review` (`core/crates/obid/src/jobs.rs`), `Link::accept_locked` (`sphere/link/follower.rs`), `Link::ask_teammate` and `Link::approve_on_host` (`sphere/link/reviews.rs`), `approval::REQUEST_LIFETIME` and the request's body (`sphere/approval.rs`).
- **External:** the Obysphere (relay and policy), GitHub through the receiver's owner's `gh`, and the review's agent CLI (Claude Code today; Codex with TEAMREVIEW-5).
- **Electron app:** it reads an `obiRequest` that's a question (`questionOf`) or a review request (`reviewOf`, `live.ts`). A review request that waits for the owner is a card on Home's stack (TEAMREVIEW-2, `ReviewBlock` in `AskStack.tsx`).
- **Open questions, for the owner:**
  - TEAMREVIEW-7: when Oby asks the next teammate after 15 silent minutes, does the silent one's request stay open until it expires (either approval merges it), or is it called off with `cancel` (spec 5.17)? This contract assumes it stays open.
  - TEAMREVIEW-4: a result with outcome `failed` carries no text today. Is obid's own fixed sentence allowed there?

## Acceptance scenarios

- **TEAMREVIEW-1** The owner's pull request on a repository whose branch rule needs another person's approval is published, and Oby is in a Sphere with two teammates whose cards take reviews. Oby asks one teammate at a time, for the exact head, with `approve_on_host`, the conditions `tests_pass` and `no_blocker_findings`, and a request that lives 2 hours (`approval::REQUEST_LIFETIME`, 7,200 seconds). It asks the next one after a decline, a failed review, `unable`, an expiry or an approval GitHub never showed, never after changes requested. A new head asks again. The teammate's Oby reviews in a fresh worktree at exactly `head_sha`, against its base as fetched. Holding the review to its own bar (its check passed, no blocker), `approve_on_host` approves by itself only next to code owners' approvals under a standing permission, else answers `asked` with one Confirm card (`Approve ernesto's pull request #12 on obi-ai-bot/tetrix at 6d20146 on GitHub, as you`). Only the owner's fresh tap on that card approves, that commit only, and only while the pull request still points there. **Implemented** (`sphere::approval::tests::the_request_for_an_approval_is_the_specs`, `what_a_request_came_to`, `requests_are_this_pull_requests_at_this_head`, `teammates_who_approved_there_before_come_first`, `only_the_change_reviewed_is_approved`; `sphere::link::tests::a_teammate_is_asked_once_and_never_after_changes_were_asked_for`, `only_the_owners_fresh_tap_on_that_exchange_at_that_commit_approves`; in tests/sphere_api.rs `an_approved_review_is_approved_on_github_only_as_the_owner_allows`, `an_approval_needs_the_receivers_own_passing_check_whatever_the_request_lists`, `a_request_that_expires_in_the_inbox_is_settled_and_declined`; in tests/review_job.rs `the_stub_agent_reviews_the_fixture_in_the_sandbox`, `a_change_to_approve_isnt_reviewed_without_its_base`, `a_commit_the_remote_doesnt_have_fails_the_job`; in tests/merge_api.rs `a_required_approval_goes_to_a_teammate_or_the_owner`, `a_teammate_workflow_asks_a_teammates_oby`, `a_yes_remembers_a_teammate_for_the_repository_and_asks_one`, `a_remembered_teammate_review_asks_a_teammate_with_no_card`). No test pins the two hours yet: TEAMREVIEW-7's test will assert the request's `expiresIn`.
- **TEAMREVIEW-2** A review request from ernesto's Oby that no remembered decision covers waits in the owner's inbox. On Home it shows as a card shaped like `QuestionCard` (`apps/electron/src/renderer/src/QuestionCard.tsx`). The card shows obid's `title` and `text` (typed fields only: `Review request from ernesto`, `ernesto's Obi (obi-ernesto) asks for a review of obi-ai-bot/tetrix: oby/fix-12 into dev at 6d20146. Conditions: tests pass, no blocker findings.`), the quoted goal, summary and every condition as text nodes, and its four answers as buttons: `Accept`, `Accept, and remember for this repo`, `Decline`, `Decline, and remember for this repo`. Later follows them, as on the question card. A click sends that answer once, as the button's label, which main signs (`POST /v1/inbox/{id}/answer`). A refusal keeps the card with obid's words for why. The words are obid's today and proposed for Sangam to change. **Implemented** (in apps/electron/src/renderer/src/test/personCard.test.tsx: `teamreview_2_a_review_request_shows_on_home_with_its_four_answers`, `teamreview_2_the_quoted_words_are_text_nodes`, `teamreview_2_accept_answers_the_item_once`, `teamreview_2_a_refusal_keeps_the_card_with_obids_words`); its words stay **Proposed**, for Sangam.
- **TEAMREVIEW-3** A request comes for a repository that isn't in obid's `repos` but that the owner's GitHub login can push to: it's reviewed, and the repository becomes one of obid's, as for the owner's own jobs (`config.repos.keep`). A request the review can't start for (no repository the owner can push to, no signed-in account that can review, no job sandbox on this machine) is answered with a `decline`, its note in obid's own words, and never with an `accept` followed by a `failed` result. An inbox `Accept` for one closes the item with that reason. **Proposed** (`teamreview_3_any_repository_the_owner_can_push_to_is_reviewed` and `teamreview_3_a_review_that_cant_start_is_declined_never_accepted`, tests/sphere_api.rs).
- **TEAMREVIEW-4** The receiver's Oby has no `check` for the repository. The review comes out as a `result` with outcome `failed`, no findings, and obid's own summary: `This Oby has no check for obi-ai-bot/tetrix, so it can't vouch that the tests pass.` The outcome is never `changes_requested`. The sender's Oby takes that as spent and asks the next teammate, never stopping at `its checks didn't pass on it, or it has none`. **Proposed** (`teamreview_4_a_reviewer_with_no_check_fails_saying_it_cant_vouch`, tests/review_job.rs, and `teamreview_4_the_sender_asks_the_next_teammate_after_no_check`, `sphere::link::tests`).
- **TEAMREVIEW-5** The receiver's only signed-in account that can review is Codex on a `codex login`. The review runs on it through the confined read-only reader that questions use ([runner-api.md](../runner-api.md), "Codex and Cursor confinement"): `app-server` and an ephemeral thread with fixed instructions, a dynamic `Read` that serves only files inside the worktree, the review output schema on `turn/start`, and every other tool request stopping the run. It runs in the job sandbox with a login copy that has no refresh token. A Sign in with ChatGPT account is never used for it. With both tools signed in, Routing picks either. The result is the same as Claude Code's for the same change. **Proposed** (`teamreview_5_a_review_runs_on_codex_through_the_confined_reader`, tests/review_job.rs).
- **TEAMREVIEW-6** The review's turn ends on a passing error (`API Error: 529`, a dropped connection, as RECOVERY-1 reads it): it's tried again after 1, 5 and 15 minutes (never longer than `stallAfter`), its step saying so, and the review finishes. A review with no progress for `stallAfter` (the quiet window, read as RECOVERY-12) is ended, not left stalled waiting for anyone's Try again. Its result is `failed` with obid's own summary of why, and the sender's Oby asks the next teammate. No try runs past the request's `expires_at`. **Proposed** (`teamreview_6_a_review_tries_again_after_a_passing_error` and `teamreview_6_a_review_that_hangs_ends_at_the_quiet_window`, tests/review_job.rs).
- **TEAMREVIEW-7** The teammate's Oby sends nothing back (no `accept`, `decline`, `status` or `result`) for 15 minutes after the request: the sender's Oby asks the next teammate, and the request keeps its 2 hours. All the while, the task's line shows the wait: `Waiting for ernesto's Oby to review it and approve it on GitHub (asked 6 minutes ago).`, then `ernesto's Oby didn't answer in 15 minutes: asked zoe's Oby.` Today the waiting words are dropped. **Proposed** (`teamreview_7_fifteen_silent_minutes_ask_the_next_teammate` in `sphere::link::tests`, and `teamreview_7_the_wait_shows_on_the_task` in tests/merge_api.rs).
- **TEAMREVIEW-8** The Sphere refuses the sender's request (`policy_denied`, or any other code it answers with). The owner gets a card in obid's words: for `policy_denied`, `This Obysphere's rules don't allow reviews between you and ernesto yet. An admin can change that.`; for another code, only that code when it is `[a-z0-9_]{1,40}`; never anything else the Sphere wrote. It isn't taken for a Sphere that can't be reached, which stays a wait and is asked again on the next look. **Proposed** (`teamreview_8_a_sphere_refusal_becomes_a_card`, tests/merge_api.rs).
