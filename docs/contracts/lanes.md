# Lanes: the owner's work on their own login, everyone else's in Oby's box

The business behavior contract for where a job's agent runs, from [the template](../business-contract-template.md). Scenarios are numbered `LANES-n`; the tests that prove them will be named after them.

## Feature and status

- **Outcome:** The work the owner asked for runs as it would in their terminal: their own Claude Code or Codex, on their own login, which refreshes itself, with their environment, gateways, settings, skills and MCP servers, under the CLI's own sandbox. Work another Oby asked for, or work marked untrusted, stays in Oby's box as it does today. AGENTS.md, "Dispatcher, not harness" (the owner's decision of 2026-11-05), names the two lanes; this contract says what each one does.
- **Status:** **Implemented** for LANES-1, 2, 3, 4, 5 (jobs), 6, 8, 9, 10, 12, 14 and 15 (LANES-16 on macOS, and LANES-17, implemented): `Jobs::own_lane` (`core/crates/obid/src/jobs/lanes.rs`) runs every Claude Code job of the owner's in the own lane, with no egress proxy and no login refresh by obid, and its check stays boxed with no network (LANES-1, 3, 6, 10); its Claude Code loads the owner's user settings, skills and MCP servers, never the repository's, under obid's `--settings` (LANES-5); one no-publish rule for both lanes, `process::no_publish_env` and `process::agent_withheld` (LANES-2, runner-api.md, "Agents can't publish"); the owner's login shell's environment, `process::login_env` and `process::with_owners` (LANES-4, runner-api.md, `claudeOwnSandbox`); an own Claude Code job's branches and stash in its worktree's own git folder, never the clone's (LANES-8, `own_refs` and `settle_own_refs` in `core/crates/obid/src/jobs/own_refs.rs`, runner-api.md, `claudeOwnSandbox`); the job's `resumeCommand` (LANES-9, runner-api.md); and the owner's Claude Code conversations in the own lane with their own Bash, the owner's user settings, skills and MCP servers, and no move back after an untrusted read (LANES-12, the owner's CONVO-1, 4 and 5; runner-api.md, "obid only: the conversation harness"). Still to come in LANES-6: a site a command reaches marking the job `reached`. Until then, an own Claude Code job's check gets no declared secrets. The rest is **Proposed**, not built (Codex comes next). The owner's decisions of 2026-11-09 lead, and are followed exactly:
  - only another Oby's job or an `untrusted` one is boxed, not every foreign mark;
  - Oby's own review stays boxed;
  - own runs skip obid's egress proxy;
  - the check stays boxed, with no network and declared secrets as today (the setup step has the network);
  - own jobs load Claude Code's user, project and local settings, as the terminal does; foreign ones load none; narrowed by "User settings only", LANE-6a (owner, 2026-11-10): own jobs load the owner's user settings, MCP servers and skills only, never a repository's own `.claude/`, `.mcp.json` or `CLAUDE.md`; project settings move to M3;
  - Tetrix is always wired;
  - Cursor stays boxed until a vendor sandbox is proven;
  - `claudeOwnSandbox` stays a key obid reads and ignores;
  - branches may land in the shared clone; a stash stays in the job's worktree (LANE-10), narrowed by "Keep them in the job", LANE-10a (owner, 2026-11-10): an own job's `git switch -c`, branches, commits on them and stash work but stay in its own worktree's git folder; the shared clone's refs (`refs/heads`, `refs/stash`, `packed-refs`), config, hooks and the worktree's pointers stay obid's alone and no agent writes them, so no job can steer or break another (obid bases follow-ups and retries on the clone's `refs/heads`, and a job's commits live in its own object store);
  - "Allow them", [LANE-12 (owner, 2026-11-09, issue #2044)](https://github.com/obi-ai-bot/oby/issues/2044), given after this contract's first draft and recorded in the owner's decisions and on that issue: own jobs and conversations keep the owner's MCP servers as configured, code-host tools included (a GitHub MCP server that can push and merge); obid strips none of them, and foreign jobs load none. "Agents can't publish" covers obid's own paths (LANES-2). This replaces the first brief's line that LANES-2 must say how code-host tools are kept from agents.

  **What runs today:** a Claude Code job of the owner's (not another Oby's, not `untrusted`, not Oby's own review) runs on its account's own folder under Claude Code's own sandbox, with the owner's login shell's environment and no egress proxy of obid's, whatever `claudeOwnSandbox` lists, with `--setting-sources user` and no `--strict-mcp-config` (LANES-5); every other job runs in Oby's box (`sandbox.rs`) with a private copy of its login, obid's egress proxy, `--setting-sources ""` and `--strict-mcp-config`; the owner's Claude Code conversation runs in the own lane with its own Bash and the owner's user settings, skills and MCP servers, while another Oby's conversation, Codex's, Cursor's and the brain's planner stay boxed; "Rules Oby never breaks" in AGENTS.md says what happens until each step lands, and each step changes those rules in the same pull request.
- **Scope:** which lane a job's and a conversation's agent runs in, and what each lane gives it: login, environment, settings, network, git, the check, a resume command. **Out of scope:** what Bypass and the other modes ask ([permissions.md](permissions.md)); how obid publishes, reviews and merges ([publishing.md](publishing.md), [merging.md](merging.md)); a Codex account obid signed in to ChatGPT itself ([chatgpt-sign-in.md](chatgpt-sign-in.md): its tokens never reach a run, in either lane); the words a person sees (Sangam's).

## Behavior

### Actors and ownership

- **obid** decides a job's lane when it launches the job's run, starts the agent there, keeps the lane on the job, and builds the resume command.
- **The agent's CLI** (Claude Code, Codex) enforces its own sandbox in the own lane and refreshes its own login.
- **The Electron app** shows the job as obid reports it, and its resume command. It decides nothing.

### The two lanes

| | Own lane | Foreign lane (today's) |
|---|---|---|
| Whose work | the owner's | another Oby's request, or a job marked `untrusted` |
| Sandbox | the CLI's own | Oby's box |
| Login | the account's own folder and Keychain item, refreshed by the CLI | a private copy with no refresh token |
| Environment | the owner's login shell's, with obid's git and `gh` settings on top | obid's allowlist |
| Claude Code settings | user, project and local | none |
| MCP servers | the owner's, as configured, and Tetrix | Tetrix only (none for another Oby's job) |
| Network | the CLI's sandbox, no obid proxy; Codex none | obid's egress proxy |
| Conversation shell | the CLI's own (Bash, Codex's shell) | obid's `oby_shell` |
| Cursor | Oby's box | Oby's box |

### Decisions

- **The lane comes from whose work it is, fixed at launch.** A job is in the foreign lane when another Oby asked for it (`Job.obi`) or it's marked `untrusted`; every other job is in the own lane. The other marks (`foreign` text from someone else's issue, `reached`, `unsigned`, `memory_from_others`) keep what they do today (reviews, no declared secrets) and don't move a job to the box. The lane is decided when a run launches and doesn't change while it runs: a mark that arrives during a run takes effect on the job's next run (a follow-up, Try again, the run after an answer), which launches boxed. A job that was foreign never goes back to the own lane. Oby's own review runs boxed in either case, as today (`review_may_run`).
- **Agents publish in neither lane, by obid's own paths.** Publishing is obid's: it pushes the job's branch and opens its pull request (Publish), and nothing obid gives an agent publishes. In the own lane that means:
  - `GH_CONFIG_DIR` is empty, so `gh` finds no login of obid's or the Mac's;
  - `remote.origin.pushurl` is an invalid URL, set in the run's environment (`GIT_CONFIG_COUNT`, beside the empty `credential.helper` `own_sandbox_env` sets today), so a `git push` from the worktree goes nowhere, whatever the clone's settings say;
  - obid's refusals of publishing commands (`policy::publishes`: `git push`, `gh pr`, `gh api` and the rest) hold as today, and Claude Code's sandbox keeps commands off `CODE_HOSTS`, as `own_sandbox_settings` does today;
  - only obid's Publish puts the job's branch on the code host.

  **The owner's own MCP tools are the owner's choice** (LANE-12 (owner, 2026-11-09, issue #2044), "Allow them"; "Oby forbids nothing"). An own job or conversation keeps the MCP servers the owner configured (Claude Code's settings, `.mcp.json`, plugins, Codex's `config.toml`) as configured, a code host's included, such as a GitHub MCP server that can push and merge: obid doesn't strip or disable them. A push or a merge such a tool makes is the owner's setup at work, not obid publishing, and the code host's own rules (branch protection, required reviews) are its limits. In the foreign lane none of them load, as today: Oby's box, no login, `--setting-sources ""`, `--strict-mcp-config`.
- **Own Claude Code runs on its own folder and refreshes itself.** `CLAUDE_CONFIG_DIR` is the account's `configDir` for an account with one; the default account runs with none and the owner's own `HOME`, as the terminal does, so Claude Code reads `~/.claude` and `~/.claude.json` (its MCP servers), and the login is the account's own Keychain item. obid writes no login copy for it and doesn't refresh it: Claude Code does, as in the terminal. Claude Code's sandbox keeps its commands out of obid's home, every other account's folder and the git pointers, as `own_sandbox_settings` does today. `claudeOwnSandbox` stays in `config.json` as a key obid reads and ignores: every own Claude Code job is in this lane, and a list there changes nothing.
- **Own runs get the owner's environment.** obid reads the owner's login shell's environment (the password database's shell, `-l`), as the terminal starts with it, and gives it to own runs, less obid's own variables (`OBY_*`, `OBID_*`), git's (`GIT_*`) and what pushes (LANES-2's `process::agent_withheld`: `SSH_AUTH_SOCK`, `GH_*`, …; its `ANTHROPIC_*` and `CLAUDE_CODE_*` are the owner's gateway). So a gateway reaches the agent as the owner set it (`ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, `AWS_*`, `OPENAI_BASE_URL`), and a provider's model id (Bedrock's `us.anthropic.…`, Vertex's) is passed to the CLI as written, never mapped to another name (`settings::valid_model` takes it). A job with no model picked (its own or its account's) passes no `--model` when that environment names one (`ANTHROPIC_MODEL`), so the owner's own default holds. obid reads the environment again when the owner's shell files change; a shell that doesn't answer in 10 seconds leaves own runs with obid's allowlist and says so on the job. The foreign lane keeps obid's allowlist (`process::sandbox_env`).
- **Own runs get the owner's settings, skills and MCP servers.** Claude Code gets `--setting-sources user` and no `--strict-mcp-config`, so it loads the owner's user settings, skills, plugins and MCP servers as the terminal does, but none of the owner's hooks (LANES-17), never the repository's own `.claude/`, `.mcp.json` or `CLAUDE.md` (LANE-6a), every server as configured (a code host's too, LANES-2), with obid's `obi-mcp.json` beside them. obid's command-line settings keep the sandbox on (`failIfUnavailable`, `allowUnsandboxedCommands: false`) and its permission mode; the owner's settings can't turn them off. Codex reads its own `config.toml`, skills and MCP servers from its `CODEX_HOME`, none disabled. Own conversations keep them the same way (`--setting-sources user`, with no `--restricted`, which would drop them), never their room's own settings, MCP servers or `CLAUDE.md`, which they can't write either. The foreign lane loads none of them, as today. **Tetrix is always wired**, as today: every job but another Oby's gets it, in either lane.
- **The own run's network, and its check.** Own runs skip obid's egress proxy: no `HTTP(S)_PROXY` of obid's. Claude Code's commands reach the network through its own sandbox, which obid's settings keep off the code hosts; the sites it asks about come to obid as any permission does and follow the job's mode. Codex has none (below). What the run reaches is still known: WebFetch, WebSearch, a site Claude Code's sandbox asks about past the package registries, and a call to an MCP server that isn't obid's mark the job `reached`, as the proxy does today, with the same consequences for its check (MERGING-31). **The check stays boxed** in Oby's box in both lanes, with no network (loopback only for a job no other Oby asked for, `check_keeps_loopback`) and declared secrets as today (`check_refuses_secrets`); the repository's setup step runs boxed with the network through the egress door, as today.
- **Own Codex runs on its own `CODEX_HOME` in `workspace-write`.** `CODEX_HOME` is the account's folder (`~/.codex`, or its `configDir`), its login the account's own `auth.json`, refreshed by Codex. obid sets `sandbox_mode = "workspace-write"` with `sandbox_workspace_write.network_access = false`, and the writable roots: the worktree and the worktree's own git folder (`<clone>/.git/worktrees/<name>`), which commit and stash need; `/private/tmp` is writable in `workspace-write` already. **Its network is off** because the spike of 2026-11-09 showed a command in `workspace-write` can read `~/.codex/auth.json`, refresh token included: with no network it can't send it anywhere, and the secret scan before publishing looks for the account's own tokens, read from its `auth.json` at scan time, in the change. Approvals still come to obid (`approvalPolicy`, as today).
- **Stash and branches work, and stay in the job; hooks and config stay closed** (LANE-10a, "Keep them in the job"). In the own lane:
  - `git stash`, `git stash pop`, `git branch`, `git switch -c`, `git checkout -b` and `git checkout` between its own branches work, and so do commits on those branches; all of it stays in the job's worktree's own git folder. The clone's refs (`refs/heads`, `refs/stash`, `packed-refs`) stay obid's alone and no agent writes them: a job never sees or pops another job's or the owner's stash, never sees another job's branch, and no branch of an agent's reaches the clone, where obid bases follow-ups and Try again (`refs/heads/<branch>`) and where a commit held only in one job's objects would break every other job's `--branches` walk, the secret check's copy and `gc`;
  - git keeps a worktree's branches and stash in the folder its `commondir` names, whatever `GIT_COMMON_DIR` says, so before an own Claude Code run obid points `commondir` at `oby-common` in the worktree's git folder: links to the clone's git folder but for its refs, which are the job's, beside it (`oby-refs`: its branches and stash, with links to the clone's remotes and tags, which it can't write; `oby-logs`; `oby-packed-refs`, a copy of the clone's packed refs but its branches and stash). Its commands can't write `oby-common`. After the run obid points `commondir` back at the clone's folder, so its own git calls on the job (keeping its commits, its branch `oby/…`, rebasing onto the base, publishing) see the clone's refs as before. A run cut short (obid killed, its task panicked, setting it back failed) is set back by obid's first git call on the job outside an own run, and if that fails obid reads none of the job's git: obid never reads a ref an agent wrote. A remotes or tags folder its commands left in `oby-refs` goes before the next own run; a HEAD left on one of the job's branches is detached at that commit for them, and the next own run is on that branch again while it's still at HEAD;
  - the clone's hooks (`hooks/`, `core.hooksPath`), its `config` and `config.worktree` (the worktree's too), and the pointers (`.git`, `commondir`, `gitdir`) stay read-only, so nothing an agent writes runs later in obid's or the owner's git. obid's own git calls keep `git::SAFE`.

  The foreign lane keeps today's: a detached HEAD, the clone read-only, objects in the job's own folder.
- **A resume command.** An own job with a session shows the command that continues it in the owner's terminal: `cd '<worktree>' && claude --resume <session>` (with `CLAUDE_CONFIG_DIR='<folder>'` first for an account that isn't the default) or `cd '<worktree>' && codex resume <session>` (with `CODEX_HOME`). obid gives it to the app on this Mac only: the gateway leaves it out, as it does `session`. A foreign job has none: its session lives in Oby's copy of the login, which the terminal can't open.
- **Foreign work is unchanged.** A job another Oby asked for or marked `untrusted` runs exactly as every job runs today: Oby's box, a private login copy with no refresh token, obid's egress proxy, obid's allowlisted environment, `--setting-sources ""` and `--strict-mcp-config`, Codex's `danger-full-access` inside the box, the conversation's `oby_shell`.
- **Cursor stays boxed**, in both lanes, with its login copy as today, until a sandbox of Cursor's own is proven to hold what Claude Code's and Codex's do (commands kept off obid's home, other accounts' folders, the git pointers and the code hosts). Proving it is a change to this contract.
- **Own Claude Code conversations get their own Bash.** A conversation the owner started runs its Claude Code turns on the account's own folder and login, with Claude Code's own Bash, under its sandbox, writing only the conversation's room (never its `repos/`) and its temporary folder, instead of `oby_shell`, and with the owner's settings, skills and MCP servers (CONVO-4). **A conversation that has read something untrusted stays in the own lane** (CONVO-1): it doesn't switch back to `oby_shell`; its untrusted mark (`read_untrusted`) stays, and with the owner's Confirm guards what goes out (the jobs it starts are marked `untrusted` and run boxed, Bypass waits for the owner's Confirm), and each call of the owner's own MCP tools counts as an untrusted read. Only a conversation with another Oby (ASK-16) runs foreign: `oby_shell`, as today. **The brain's planner stays boxed** with its login copy (CONVO-5), and **Cursor conversations stay boxed** with no shell (CONVO-2).
- **An own run asks obid about every call, whatever the owner allowed** (the owner's decision of 2026-11-11, LANES-ASK, "Yes, all of them"). Its tools run unboxed, and obid's rules (the worktree or the room, the job's mode, the room's rules) apply only to what Claude Code asks about; a skill's `allowed-tools`, an allow rule or a hook's `allow` of the owner's lets a call through without asking (measured with Claude Code 2.1.302: a skill granting `Write` wrote outside its folder, a hook's `allow` too). So obid's `--settings` list as `ask` rules every built-in tool of Claude Code's (2.1.302's, as its `init` event lists them, and the older names it takes: `CLAUDE_TOOLS`) and every MCP tool (`mcp__*`), which beat those (measured), and obid answers each by its rules, as before; what reaches nothing past the session (finding a deferred tool, its task list and background tasks, its agents' names, planning, a skill) runs at once (`Jobs::OWN_QUIET`), and so do the reads of its MCP servers' resources (`ListMcpResourcesTool`, `ReadMcpResourceTool`, `ReadMcpResourceDirTool`), which are the owner's MCP servers' as their tools are and mark the run as any MCP call does: the owner's skills, settings and MCP servers all stay (LANE-6a, CONVO-4, LANE-12); only what they let through without asking now asks. **And an own run has only the built-in tools obid answers** (`--tools`: an own job's `OWN_JOB_TOOLS`, an own conversation's `OWN_TOOLS`): one obid doesn't answer (`Monitor`, `EnterWorktree`, the `Cron*` and remote tools) or a later Claude Code adds isn't there at all, so no new tool skips obid; its skills and MCP tools stay (measured: `--tools` names built-ins only). Past the worktree or the room, obid lets an own run reach only what Claude Code reached by itself before: its commands' temporary folder (their background output, `CLAUDE_CODE_TMPDIR`) and `projects/<its working folder>` in a Claude Code account's folder (what it saved of a long output, its memory), to read, and in Plan mode its plan, `plans/<name>.md` there, never through a link or another name of a file (a hard link); a path in a call that's relative counts as the working folder's. **Every stored thread is out of reach too** (`conversations/<id>.json`, and `next-id`), denied by name as obid's other places are.
- **No hook of the owner's runs in an own run** (the owner's decision of 2026-11-11, LANE-6b, "No hooks in Oby runs"). Own jobs and conversations load the owner's skills, MCP servers and user settings, but none of their hooks: a hook runs outside Claude Code's sandbox with the owner's rights, and one a skill brings (`hooks:` in its frontmatter), or one a task fires (`TaskCreated`, `TaskCompleted`), could run a script the run itself wrote. obid's `--settings` set `disableAllHooks: true`, which outranks the owner's settings files (measured with 2.1.302: a settings file's hook and a skill's hook both run without it, neither with it, over a project file's `disableAllHooks: false`). Only Claude Code's managed settings outrank it, so an own run doesn't start when they would run a hook: when `managed-settings.json` or a `.json` in `managed-settings.d` (in `/Library/Application Support/ClaudeCode` on macOS, `/etc/claude-code` elsewhere), the account's `remote-settings.json` (the organization's) or a managed preferences plist (`/Library/Managed Preferences/com.anthropic.claudecode.plist`, and the person's own under their name) sets `hooks` or `disableAllHooks: false`, turns a plugin on (`enabledPlugins`: a managed plugin's hooks still run), or names a policy helper (`policyHelper`, `policyHelpers`: a program whose answer is more managed settings), or when obid can't read one; it says which document and key, and that whoever manages the Mac can take it out. With none of them there, nothing changes. **Claude Code's managed settings are the Mac's or the organization's administrator's, as Claude Code treats them** (the owner's decision of 2026-11-11, MANAGED-1, "Trust the admin, merge now"): obid refuses only what it can see before a launch, and an organization's policy Claude Code fetches from its server while a run runs is the administrator's, which obid doesn't override.
- **An own run's leftovers end with it** (LANES-16): a process its commands started that left its process group (`setsid`, `nohup` with a new session) still runs in Claude Code's sandbox for that run; it ends when the run's Claude Code does (a job's at its turn's end, a conversation's when its waiting session ends, a stop, a run dropped part way). obid finds it as macOS's `sandbox_check` answers: every process of the person's whose sandbox may write the run's commands' temporary folder but not its `env.sh`, which no other run's sandbox, nor any unsandboxed process, matches (`process::end_sandboxed`, the one call of obid's that is `unsafe`, the owner's decision UNSAFE-1 of 2026-11-11). **Implemented on macOS only.** On Linux, and for what an obid that crashed mid-run left, it's later work: obid's restart sweep ends the recorded process groups only.
- **A skill's `!command` lines don't run past obid** (measured with 2.1.302, for #2107's review): with obid's `ask` rule on `Bash`, a skill's ``!`command` `` is refused before it runs ("Shell command permission check failed"), whatever its `allowed-tools`, and obid isn't asked; without that rule Claude Code runs it when the skill's `allowed-tools` grants it and its own path check lets it.
- **Own Codex conversations get their own shell.** The same for Codex: its shell tool on, in `workspace-write` on the room, with no network (Codex's rule above).

### Failures and recovery

- Claude Code's sandbox unavailable (`failIfUnavailable`): the run fails before its first command and says so; obid never runs it unsandboxed or moves it to the box by itself.
- A Codex too old for `workspace-write`'s settings obid passes: the run fails and names the version it needs.
- An own account whose own login is signed out or expired: the run fails with the CLI's own words and how to sign in again ("run claude", "run codex login"); obid copies nothing and refreshes nothing.
- The login shell's environment unreadable: LANES-4's fallback (obid's allowlist), said on the job.
- obid restarts during a run: the run's lane is the one kept on the job; it's never decided again for that run.

### Invariants

- Nothing obid gives an agent publishes, in either lane (LANES-2); obid publishes. The owner's own MCP tools in the own lane are the owner's.
- A boxed job never gets an account's own folder (#655); only the own lane runs on it, and only under the CLI's own sandbox.
- Secrets in Oby's vault never reach an agent, in either lane. The owner's login shell's environment is the owner's, not the vault's.
- The secret scan, the merge rules (`merge::SECURITY_PATHS`, two reviews for an untrusted job) and the check's secret rules hold in both lanes.
- obid's API stays add-only: the lane and the resume command are new keys.

## Interfaces and dependencies

- `GET /v1/jobs/{id}` (and the job in its lists): proposed `lane` (`own` | `foreign`) and `resumeCommand` (a string, or `null`), added, never renamed; the gateway leaves `resumeCommand` out ([runner-api.md](../runner-api.md) gets them when built).
- `config.json`: `claudeOwnSandbox` read and ignored.
- Claude Code: `--setting-sources`, `--settings`, `--mcp-config`, its sandbox settings. Codex: `sandbox_mode`, `sandbox_workspace_write.network_access`, `sandbox_workspace_write.writable_roots`, `codex resume`. git: `remote.origin.pushurl` in the run's environment.

**Open questions:**

- Whether Claude Code in `-p` mode sends a sandboxed command's new site to the permission prompt tool, which LANES-6's `reached` needs; if it doesn't, obid lists only the registries in `allowedDomains` and an own run reaches no other site from a command.
- Whether a call to the owner's own MCP server should mark `reached` (LANES-6 says yes, the cautious reading of "as today"): with it, an own job that used one gets no declared secrets for its check.
- How a repository's own project settings, `.mcp.json` and `CLAUDE.md` could load safely in an own job (M3, LANE-6a): until then they never do, and the base's `AGENTS.md` and `CLAUDE.md` stay quoted in `.obi/inputs/base-rules.md`.
## Acceptance scenarios

- **LANES-1** The owner's task, another Oby's request and a job marked `untrusted` launch: the first is `own`, the other two `foreign`; a job marked only `foreign` (someone else's issue text) or `reached` is `own`. A mark that arrives while an own run works leaves that run own, and its next run is `foreign`. Oby's review of an own job runs boxed, and so does the owner's review of someone else's code (a `review` marked `foreign`: a pull request head with commits obid didn't record, or one anyone else wrote in; merging.md MERGING-36). **Implemented** (`lanes_1_the_owners_job_runs_in_its_own_lane_and_another_obys_stays_boxed`, `lanes_1_whose_work_picks_the_lane`, `merging_36_a_review_of_someone_elses_commits_asks_for_its_reads`); the job's `lane` key in the API is still proposed.
- **LANES-2** (**Implemented**, `process::tests::lanes_2_neither_lane_can_publish`: obid's own paths, the environment, git's settings and the push URL; an own job's MCP servers load since LANES-5) In each lane, the agent's `git push` and `gh pr create` publish nothing: `GH_CONFIG_DIR` is empty, `git config remote.origin.pushurl` in the worktree is obid's invalid URL, and the job's branch reaches the code host when obid publishes it. With the owner's Claude Code settings and Codex's `config.toml` giving a GitHub MCP server that can push and merge, an own job and an own conversation are offered its tools, as configured, and obid leaves its calls to the job's mode; a foreign job isn't offered them.
