# Lanes: the owner's work on their own login, everyone else's in Oby's box

The business behavior contract for where a job's agent runs, from [the template](../business-contract-template.md). Scenarios are numbered `LANES-n`; the tests that prove them will be named after them.

## Feature and status

- **Outcome:** The work the owner asked for runs as it would in their terminal: their own Claude Code or Codex, on their own login, which refreshes itself, with their environment, gateways, settings, skills and MCP servers, under the CLI's own sandbox. Work another Oby asked for, or work marked untrusted, stays in Oby's box as it does today. AGENTS.md, "Dispatcher, not harness" ([why](../decisions/2026-11-05-dispatcher-not-harness.md)), names the two lanes; this contract says what each one does.
- **Status:** **Implemented** for LANES-1, 2, 3, 4, 5 (jobs), 6, 8, 9, 10, 12, 13, 14 and 15 (LANES-16 on macOS, and LANES-17, 18, 19, 20 and 21, implemented; LANES-21 approves Oby's own MCP tools before an own Codex run, which asks nobody; LANES-20 lets an own Claude Code run's commands listen and connect on loopback; LANES-18 runs the owner's Codex jobs in Bypass in the own lane on macOS, the owner's CODEX-1, LANES-19 keeps one that builds in Oby's box, the owner's CODEX-BUILDS, and LANES-13 their Codex conversations in Bypass the same way, the owner's CODEX-2): `Jobs::own_lane` (`core/crates/obid/src/jobs/lanes.rs`) runs every Claude Code job of the owner's in the own lane, with no egress proxy and no login refresh by obid, and its check stays boxed with no network (LANES-1, 3, 6, 10); its Claude Code loads every settings source, the owner's and the repository's, as their terminal does, and obid refuses none of what they hold (LANES-5, LANES-22, LANES-23, the owner's decision of 2026-11-16, [why](../decisions/2026-11-16-own-lane-trusts-the-cli.md)); one no-publish rule for both lanes, `process::no_publish_env` and `process::agent_withheld` (LANES-2, runner-api.md, "Agents can't publish"); the owner's login shell's environment, `process::login_env` and `process::with_owners` (LANES-4, runner-api.md, `claudeOwnSandbox`); an own Claude Code job's branches and stash in its worktree's own git folder, never the clone's (LANES-8, `own_refs` and `settle_own_refs` in `core/crates/obid/src/jobs/own_refs.rs`, runner-api.md, `claudeOwnSandbox`); the job's `resumeCommand` (LANES-9, runner-api.md); and the owner's Claude Code conversations in the own lane with their own Bash, every settings source, skills and MCP servers, and no move back after an untrusted read (LANES-12, the owner's CONVO-1, 4 and 5; runner-api.md, "obid only: the conversation harness"). Still to come in LANES-6: a site a command reaches marking the job `reached`. Until then, an own Claude Code job's check gets no declared secrets. The rest is **Proposed**, not built. The owner's decisions lead, and are followed exactly ([why](../decisions/2026-11-09-own-lane-by-default.md)):
  - only another Oby's job or an `untrusted` one is boxed, not every foreign mark;
  - Oby's own review stays boxed;
  - own runs skip obid's egress proxy;
  - the check stays boxed, with no network and declared secrets as today (the setup step has the network);
  - own jobs load Claude Code's user, project and local settings, as the terminal does; foreign ones load none; LANE-6a, which narrowed it to the owner's user settings, is replaced for Claude Code by the owner's decision of 2026-11-16 ([why](../decisions/2026-11-16-own-lane-trusts-the-cli.md)): own runs trust the CLI as T3 Code does, every settings source, the owner's hooks, permissions, sandbox and environment as they set them, nothing refused;
  - Tetrix is always wired;
  - Cursor stays boxed until a vendor sandbox is proven;
  - `claudeOwnSandbox` stays a key obid reads and ignores;
  - branches may land in the shared clone; a stash stays in the job's worktree (LANE-10), narrowed by LANE-10a ([why](../decisions/2026-11-10-lane-10a.md)): an own job's `git switch -c`, branches, commits on them and stash work but stay in its own worktree's git folder; the shared clone's refs (`refs/heads`, `refs/stash`, `packed-refs`), config, hooks and the worktree's pointers stay obid's alone and no agent writes them, so no job can steer or break another (obid bases follow-ups and retries on the clone's `refs/heads`, and a job's commits live in its own object store);
  - CODEX-1 ([why](../decisions/2026-11-11-codex-1-bypass-only.md)): the owner's own Codex jobs run in the own lane in Bypass only, with Codex refusing to run a command outside its sandbox (`approval_policy = "never"`); Ask and Plan (and Accept edits and Sandbox) stay in Oby's box; no writes to the shared clone's refs or objects (LANE-10a); its commands read nothing of obid's home, the person's home or other accounts' folders (LANES-18);
  - CODEX-BUILDS ([why](../decisions/2026-11-15-codex-builds-in-the-box.md)): the owner's own Codex job that builds (`build`, `fix` or `test`) runs in Oby's box, in Bypass too, where it builds, while obid's home and the person's home stay hidden (LANES-19);
  - CODEX-2 ([why](../decisions/2026-11-12-codex-2.md)): the owner's own Codex conversation in Bypass runs in the own lane on macOS as an own Bypass Codex job does, its shell Codex's own in that sandbox, writing only its room; any other mode, off macOS, or another Oby's conversation stays boxed (LANES-13);
  - [LANE-12, issue #2044](https://github.com/obi-ai-bot/oby/issues/2044) ([why](../decisions/2026-11-09-lane-12.md)): own jobs and conversations keep the owner's MCP servers as configured, code-host tools included (a GitHub MCP server that can push and merge); obid strips none of them, and foreign jobs load none. "Agents can't publish" covers obid's own paths (LANES-2).

  **What runs today:** on macOS, a Codex job of the owner's in Bypass (not another Oby's, not `untrusted`, not a review, not on a ChatGPT login, not one that builds: LANES-19, not the rest of a run its approved Plan card resumed (its thread is in the box's `CODEX_HOME`)) runs on its account's own `CODEX_HOME` under Codex's own sandbox (LANES-18); a Claude Code job of the owner's (not another Oby's, not `untrusted`, not Oby's own review) runs on its account's own folder as the owner's terminal would, with the owner's login shell's environment, every settings source and no egress proxy of obid's, whatever `claudeOwnSandbox` lists, and no `--strict-mcp-config`; obid refuses none of what the owner's settings hold, and its `--settings` only pin obid's own variables and deny the file tools obid's secret places (LANES-5, LANES-22, LANES-23); every other job runs in Oby's box (`sandbox.rs`) with a private copy of its login, obid's egress proxy, `--setting-sources ""` and `--strict-mcp-config`; the owner's Claude Code conversation runs in the own lane the same way, with its own Bash, and their Codex conversation in Bypass with Codex's own shell under obid's profile (LANES-13), while another Oby's conversation, Codex's in any other mode or on a ChatGPT login, Cursor's and the brain's planner stay boxed; "Rules Oby never breaks" in AGENTS.md says what happens until each step lands, and each step changes those rules in the same pull request.
- **Scope:** which lane a job's and a conversation's agent runs in, and what each lane gives it: login, environment, settings, network, git, the check, a resume command. **Out of scope:** what Bypass and the other modes ask ([permissions.md](permissions.md)); how obid publishes, reviews and merges ([publishing.md](publishing.md), [merging.md](merging.md)); a Codex account obid signed in to ChatGPT itself ([chatgpt-sign-in.md](chatgpt-sign-in.md): its tokens never reach a run, in either lane); the words a person sees (Sangam's).

## Behavior

### Actors and ownership

- **obid** decides a job's lane when it launches the job's run, starts the agent there, keeps the lane on the job, and builds the resume command.
- **The agent's CLI** (Claude Code, Codex) enforces its own sandbox in the own lane and refreshes its own login.
- **The Electron app** shows the job as obid reports it, and its resume command. It decides nothing.

### The two lanes

| | Own lane | Foreign lane (today's) |
|---|---|---|
| Whose work | the owner's (Codex's: in Bypass only, and not one that builds) | another Oby's request, or a job marked `untrusted` (and the owner's Codex job in any other mode, or one that builds) |
| Sandbox | the CLI's own | Oby's box |
| Login | the account's own folder and Keychain item, refreshed by the CLI | a private copy with no refresh token |
| Environment | the owner's login shell's, with obid's git and `gh` settings on top | obid's allowlist |
| Claude Code settings | user, project and local | none |
| MCP servers | the owner's, as configured, and Tetrix | Tetrix only (none for another Oby's job) |
| Network | the CLI's own (the owner's settings), no obid proxy; Codex none | obid's egress proxy |
| Conversation shell | the CLI's own (Bash; Codex's shell, in Bypass) | none: it reads the room and runs no commands (CONVO-2) |
| Cursor | Oby's box | Oby's box |

### Decisions

- **The lane comes from whose work it is, fixed at launch.** A job is in the foreign lane when another Oby asked for it (`Job.obi`) or it's marked `untrusted`; every other job is in the own lane. The other marks (`foreign` text from someone else's issue, `reached`, `unsigned`, `memory_from_others`) keep what they do today (reviews, no declared secrets) and don't move a job to the box. The lane is decided when a run launches and doesn't change while it runs: a mark that arrives during a run takes effect on the job's next run (a follow-up, Try again, the run after an answer), which launches boxed. A job that was foreign never goes back to the own lane. Oby's own review runs boxed in either case, as today (`review_may_run`).
- **Agents publish in neither lane, by obid's own paths.** Publishing is obid's: it pushes the job's branch and opens its pull request (Publish), and nothing obid gives an agent publishes. In the own lane that means:
  - `GH_CONFIG_DIR` is empty, so `gh` finds no login of obid's or the Mac's;
  - `remote.origin.pushurl` is an invalid URL, set in the run's environment (`GIT_CONFIG_COUNT`, beside the empty `credential.helper` `own_sandbox_env` sets today), so a `git push` from the worktree goes nowhere, whatever the clone's settings say;
  - obid's refusals of publishing commands (`policy::publishes`: `git push`, `gh pr`, `gh api` and the rest) hold for every call Claude Code asks obid about; a command the owner's own permissions let through, with credentials of the owner's own setup, is the owner's setup at work, as LANE-12's MCP tools are;
  - only obid's Publish puts the job's branch on the code host.

  **The owner's own MCP tools are the owner's choice** (LANE-12, issue #2044, [why](../decisions/2026-11-09-lane-12.md); "Oby forbids nothing"). An own job or conversation keeps the MCP servers the owner configured (Claude Code's settings, `.mcp.json`, plugins, Codex's `config.toml`) as configured, a code host's included, such as a GitHub MCP server that can push and merge: obid doesn't strip or disable them. A push or a merge such a tool makes is the owner's setup at work, not obid publishing, and the code host's own rules (branch protection, required reviews) are its limits. In the foreign lane none of them load, as today: Oby's box, no login, `--setting-sources ""`, `--strict-mcp-config`.
- **Own Claude Code runs on its own folder and refreshes itself.** `CLAUDE_CONFIG_DIR` is the account's `configDir` for an account with one; the default account runs with none and the owner's own `HOME`, as the terminal does, so Claude Code reads `~/.claude` and `~/.claude.json` (its MCP servers), and the login is the account's own Keychain item. obid writes no login copy for it and doesn't refresh it: Claude Code does, as in the terminal. Its commands run as the owner's terminal runs them, under whatever sandbox the owner's own settings set ([why](../decisions/2026-11-16-own-lane-trusts-the-cli.md)); obid's `--settings` deny its file tools obid's secret places and pin its git folders. `claudeOwnSandbox` stays in `config.json` as a key obid reads and ignores: every own Claude Code job is in this lane, and a list there changes nothing.
- **Own runs get the owner's environment.** obid reads the owner's login shell's environment (the password database's shell, `-l`), as the terminal starts with it, and gives it to own runs, less obid's own variables (`OBY_*`, `OBID_*`), git's (`GIT_*`) and what pushes (LANES-2's `process::agent_withheld`: `SSH_AUTH_SOCK`, `GH_*`, …; every `ANTHROPIC_*` and `CLAUDE*` of the owner's reaches a Claude Code run, LANES-22, but the account's folder, `CLAUDE_CONFIG_DIR` and `CLAUDE_SECURESTORAGE_CONFIG_DIR`, which obid sets as the dispatcher, and a launching Claude Code session's own variables, `CLAUDECODE` and `CLAUDE_CODE_SESSION_ID` among them). So a gateway reaches the agent as the owner set it (`ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, `AWS_*`, `OPENAI_BASE_URL`), and a provider's model id (Bedrock's `us.anthropic.…`, Vertex's) is passed to the CLI as written, never mapped to another name (`settings::valid_model` takes it). A job with no model picked (its own or its account's) passes no `--model` when that environment names one (`ANTHROPIC_MODEL`), so the owner's own default holds. obid reads the environment again when the owner's shell files change; a shell that doesn't answer in 10 seconds leaves own runs with obid's allowlist and says so on the job. The foreign lane keeps obid's allowlist (`process::sandbox_env`).
- **Own runs get the owner's settings, skills and MCP servers, as the terminal does** ([why](../decisions/2026-11-16-own-lane-trusts-the-cli.md)). Claude Code gets no `--setting-sources` and no `--strict-mcp-config`, so it loads every source the terminal loads: the owner's user settings, skills, plugins, hooks and MCP servers, and the repository's own `.claude/`, `.mcp.json` and `CLAUDE.md`, every server as configured (a code host's too, LANES-2), with obid's `obi-mcp.json` beside them. obid's `--settings` set no sandbox, no hook switch and no permission rule but deny rules: they pin obid's own variables (`PINNED_ENV`: the empty `GH_CONFIG_DIR`, git's no-publish settings and the job's git folders) and deny the file tools obid's secret places (its vault, keys, token, logins and accounts). obid refuses no run for what the owner's settings, `.claude.json` or managed settings hold (LANES-23). Codex reads its own `config.toml`, skills and MCP servers from its `CODEX_HOME`, none disabled. Own conversations load them the same way, with no `--restricted`, which would drop them. The foreign lane loads none of them, as today. **Tetrix is always wired**, as today: every job but another Oby's gets it, in either lane.
- **The own run's network, and its check.** Own runs skip obid's egress proxy: no `HTTP(S)_PROXY` of obid's. Claude Code's commands reach the network as the owner's own settings let them, as in the terminal ([why](../decisions/2026-11-16-own-lane-trusts-the-cli.md)): through the owner's sandbox when they turn it on, directly when they don't; the sites Claude Code asks about come to obid as any permission does and follow the job's mode. Codex has none (below). What the run reaches is still known: WebFetch, WebSearch, a site Claude Code's sandbox asks about past the package registries, and a call to an MCP server that isn't obid's mark the job `reached`, as the proxy does today, with the same consequences for its check (MERGING-31). **The check stays boxed** in Oby's box in both lanes, with no network (loopback only for a job no other Oby asked for, `check_keeps_loopback`) and declared secrets as today (`check_refuses_secrets`); the repository's setup step runs boxed with the network through the egress door, as today.
- **Own Codex runs on its own `CODEX_HOME` under obid's permission profile, in Bypass only, on macOS** (LANES-18, the owner's CODEX-1, "Yes, Bypass only"). A Codex job of the owner's is in the own lane only in Bypass, and only on macOS, whose sandbox is the one measured: the M2 probes (codex 0.162.1) showed an approved command can ask to run outside Codex's sandbox, that obid can't tell that ask from a plain one, and that Codex refuses it only with `approval_policy = "never"` (or the granular `sandbox_approval = false`); in Ask, Accept edits, Plan and Sandbox the owner's approvals are the point, so those jobs stay in Oby's box, as does a job on a ChatGPT login (its run reaches OpenAI only through obid's relay). **A Codex job that builds stays in Oby's box too** (LANES-19, the owner's CODEX-BUILDS, "Build in Oby's box"): a `build`, `fix` or `test` job, whatever its mode. obid's profile hides obid's home and the person's home (`none`), and Codex's profile gives a folder `read`, `write` or `none`, with no way to show the folders above the worktree by name only, so a command can't resolve its worktree's path: rustup's `could not canonicalize path`, and cargo's `crates/*` matching nothing (codex-cli 0.163.0, measured). Oby's box shows those folders by name only and lists none of them, so the job builds there. `CODEX_HOME` is the account's folder (`~/.codex`, or its `configDir`), its login the account's own `auth.json`, refreshed by Codex; obid copies nothing and checks no copy. Codex itself, and the owner's MCP servers it starts, run outside its sandbox, so their `HOME` is the person's own, never a folder a command writes; so is their `CFFIXED_USER_HOME`, and their `TMPDIR` stays the job's temporary folder, as an own Claude Code run's; its commands' `HOME` and `CFFIXED_USER_HOME` are the job's temporary folder (`shell_environment_policy.set`). The CLI obid starts is an absolute path, whichever tool and lane: a relative `bin` in obid's configuration is taken from obid's own folder and relative `PATH` folders are left out, so a run that starts in a worktree never runs a program the repository put at that relative place. obid's `-c` settings, which outrank the owner's `config.toml`, set `approval_policy = "never"` and a permission profile, `default_permissions = "oby_own"`, with `network.enabled = false`, whose filesystem reads everything but obid's home, the person's home and every account's folder (`none`, the run's own account's too, so no command reads its `auth.json`), writes only the worktree, the worktree's own git folder (`<clone>/.git/worktrees/<name>`, which commit and stash need) and the job's temporary folder, and keeps the worktree's `.git`, the git folder's `commondir`, `gitdir`, `config.worktree` and `oby-common` read-only, so a command can't steer the git Codex or obid run outside the sandbox. (The legacy `sandbox_mode` and `sandbox_workspace_write` keys aren't set: Codex ignores them once a profile is named.) **The repository's own Codex settings never load** (LANE-6a): the worktree is an untrusted project in those settings (`projects`, as named and where it leads), which outranks any trust the owner's `config.toml` gives the worktree or its clone, so Codex loads none of its `.codex/config.toml`, MCP servers, hooks or exec-policy rules, and doesn't write its trust into the account's `config.toml` (without it, codex-cli 0.162.1's app-server trusts a project it may write by itself, and started a repository's MCP server outside the sandbox); its `AGENTS.md` and its skills are still read, as words, as in the box. **No `notify` program** (`notify = []`): Codex runs it outside the sandbox when a turn ends, whatever `features.hooks` says. **obid starts no run on settings that aren't its own.** Codex merges `-c` settings with its other layers table by table, and a managed layer outranks them, so before every thread obid asks Codex which settings hold (`config/read` for the worktree) and starts none unless the approval policy, the profile's name, no hooks, no `notify` and the worktree's trust are obid's, the profile's network is off, the commands' `HOME` is obid's own setting (`shell_environment_policy.set.HOME`) with no `include_only`, which Codex applies after `set` and would drop it, and every key of the profile comes from obid's own `-c` (an entry the account's `config.toml` adds under `[permissions.oby_own]`, an `auth.json` to read, would widen it: the job then says which key, and to take it out or pick another mode). A thread, new or resumed, names the profile (`config.default_permissions`: a resumed thread otherwise comes back in the profile it was last saved with, full access included) and must come back with `never` and `oby_own`, or no turn starts. **An exec-policy rule of the owner's** (`rules/` in the account's folder: "always allow" from the owner's terminal) doesn't take a command out of the sandbox: codex-cli 0.162.1 keeps a command sandboxed whenever the profile denies a read, which obid's always does; a file edit outside what the profile writes is refused under `never`. **Leaving Bypass ends the run**: an own run asks obid nothing, so nothing else would hold it to Ask or Plan; at obid's next one-second tick its turn is ended, and the round goes on in Oby's box under the new mode, in a new session told why (a Codex thread is kept in its lane's own `CODEX_HOME`, so neither lane resumes the other's). Its branches and stash stay in the job's own git folder through `oby-common` (LANE-10a, as an own Claude Code job's), and its commits' objects in its own object folder: nothing of its reaches the clone's refs or objects. **Its network is off**, and the profile hides the account's `auth.json` from its commands besides; the secret scan before publishing is any job's (gitleaks' rules and the secrets obid holds): obid never reads the account's `auth.json`, so it doesn't look for that login's tokens by value. Codex asks obid nothing about commands and file changes (`never`); its own questions still reach the owner, and an MCP tool Codex asks about goes to obid by the job's mode, the owner's servers' included (LANE-12). None of the owner's hooks runs (`features.hooks = false`, LANES-17's rule). Its check gets no declared secrets, as an own Claude Code job's (LANES-6), from its first own launch on: the job remembers that a run of its had no proxy (`ran_unproxied`), whatever its mode, tool or account becomes, and its follow-up carries it (LANE-3a). That is in the job's file before the run starts (a run whose mark can't be saved doesn't start), and a snapshot of the job taken earlier and saved later never replaces a later one (`Store::save` keeps the newest revision), so a restart doesn't lose it. Known gaps: LANES-16's sweep of what a command leaves running doesn't cover an own Codex run (it reads Claude Code's `CLAUDE_ENV_FILE`); a managed requirement Codex's server pushes during a run isn't seen after the thread starts (MANAGED-1); Linux isn't measured, so the own Codex lane is macOS's only.
- **Stash and branches work, and stay in the job; hooks and config stay closed** (LANE-10a, "Keep them in the job"). In the own lane:
  - `git stash`, `git stash pop`, `git branch`, `git switch -c`, `git checkout -b` and `git checkout` between its own branches work, and so do commits on those branches; all of it stays in the job's worktree's own git folder. The clone's refs (`refs/heads`, `refs/stash`, `packed-refs`) stay obid's alone and no agent writes them: a job never sees or pops another job's or the owner's stash, never sees another job's branch, and no branch of an agent's reaches the clone, where obid bases follow-ups and Try again (`refs/heads/<branch>`) and where a commit held only in one job's objects would break every other job's `--branches` walk, the secret check's copy and `gc`;
  - git keeps a worktree's branches and stash in the folder its `commondir` names, whatever `GIT_COMMON_DIR` says, so before an own Claude Code run obid points `commondir` at `oby-common` in the worktree's git folder: links to the clone's git folder but for its refs, which are the job's, beside it (`oby-refs`: its branches and stash, with links to the clone's remotes and tags, which it can't write; `oby-logs`; `oby-packed-refs`, a copy of the clone's packed refs but its branches and stash). Its commands can't write `oby-common`. After the run obid points `commondir` back at the clone's folder, so its own git calls on the job (keeping its commits, its branch `oby/…`, rebasing onto the base, publishing) see the clone's refs as before. A run cut short (obid killed, its task panicked, setting it back failed) is set back by obid's first git call on the job outside an own run, and if that fails obid reads none of the job's git: obid never reads a ref an agent wrote. A remotes or tags folder its commands left in `oby-refs` goes before the next own run; a HEAD left on one of the job's branches is detached at that commit for them, and the next own run is on that branch again while it's still at HEAD;
  - the clone's hooks (`hooks/`, `core.hooksPath`), its `config` and `config.worktree` (the worktree's too), and the pointers (`.git`, `commondir`, `gitdir`) stay read-only, so nothing an agent writes runs later in obid's or the owner's git. obid's own git calls keep `git::SAFE`.

  The foreign lane keeps today's: a detached HEAD, the clone read-only, objects in the job's own folder.
- **A resume command.** An own job with a session shows the command that continues it in the owner's terminal: `cd '<worktree>' && claude --resume <session>` (with `CLAUDE_CONFIG_DIR='<folder>'` first for an account that isn't the default) or `cd '<worktree>' && codex resume <session>` (with `CODEX_HOME`). obid gives it to the app on this Mac only: the gateway leaves it out, as it does `session`. A foreign job has none: its session lives in Oby's copy of the login, which the terminal can't open.
- **Foreign work is unchanged.** A job another Oby asked for or marked `untrusted` runs exactly as every job runs today: Oby's box, a private login copy with no refresh token, obid's egress proxy, obid's allowlisted environment, `--setting-sources ""` and `--strict-mcp-config`, Codex's `danger-full-access` inside the box; a boxed conversation runs no commands (CONVO-2).
- **Cursor stays boxed**, in both lanes, with its login copy as today, until a sandbox of Cursor's own is proven to hold what Claude Code's and Codex's do (commands kept off obid's home, other accounts' folders, the git pointers and the code hosts). Proving it is a change to this contract.
- **Own Claude Code conversations get their own Bash.** A conversation the owner started runs its Claude Code turns on the account's own folder and login, with Claude Code's own Bash, under the owner's own settings, as their terminal runs it ([why](../decisions/2026-11-16-own-lane-trusts-the-cli.md)), its file tools denied obid's secret places, the stored threads and the room's `repos/` and own settings, and with the owner's settings, skills and MCP servers (CONVO-4). **A conversation that has read something untrusted stays in the own lane** (CONVO-1): it keeps its own Bash; its untrusted mark (`read_untrusted`) stays, and with the owner's Confirm guards what goes out (the jobs it starts are marked `untrusted` and run boxed, Bypass waits for the owner's Confirm), and each call of the owner's own MCP tools counts as an untrusted read. Only a conversation with another Oby (ASK-16) runs foreign, boxed. **The brain's planner stays boxed** with its login copy (CONVO-5), and **Cursor conversations stay boxed** (CONVO-2).
- **A boxed conversation runs no commands** (the owner's CONVO-2a and 2b; OBY-25 deleted obid's `oby_shell`). Every boxed conversation (Claude Code off macOS or another Oby's, Codex outside Bypass or on a ChatGPT login, every Cursor one) reads the room with its own read tools or `oby_read`, `oby_search` and `oby_list`, and runs no command, of Oby's or of its CLI's: its orientation says it runs none and that work goes to a job (`oby_dispatch`); Claude Code's Bash and every other code-running tool are left out of `--tools` and refused by name; Codex's `shell_tool` stays off; Cursor's commands are refused. The owner's own macOS conversations keep their CLI's own shell (LANES-12, LANES-13). **Implemented** (`brain::harness::tests::convo_2_a_boxed_conversation_gets_no_shell`, which fails if a boxed conversation gets a shell tool again).

### Failures and recovery

- Claude Code's sandbox, when the owner's settings turn it on, fails as it fails in their terminal; obid sets no sandbox of its own for an own Claude Code run and never moves it to the box by itself.
- A Codex too old for `workspace-write`'s settings obid passes: the run fails and names the version it needs.
- An own account whose own login is signed out or expired: the run fails with the CLI's own words and how to sign in again ("run claude", "run codex login"); obid copies nothing and refreshes nothing.
- The login shell's environment unreadable: LANES-4's fallback (obid's allowlist), said on the job.
- obid restarts during a run: the run's lane is the one kept on the job; it's never decided again for that run.

### Invariants

- Nothing obid gives an agent publishes, in either lane (LANES-2); obid publishes. The owner's own MCP tools in the own lane are the owner's.
- A boxed job never gets an account's own folder (#655); only the own lane runs on it, as the owner's terminal does.
- Secrets in Oby's vault never reach an agent, in either lane. The owner's login shell's environment is the owner's, not the vault's. obid gives no agent a vault secret, and an own run's file tools are denied obid's secret places; an own Claude Code run's commands run as the owner's user, as in their terminal, unless the owner's own settings sandbox them ([why](../decisions/2026-11-16-own-lane-trusts-the-cli.md)).
- The secret scan, the merge rules (`merge::SECURITY_PATHS`, two reviews for an untrusted job) and the check's secret rules hold in both lanes.
- obid's API stays add-only: the lane and the resume command are new keys.
