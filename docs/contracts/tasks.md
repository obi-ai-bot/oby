# Task actions and the task page

The business behavior contract for a task's menu and its page in the Electron app, on obid's data ([#1575](https://github.com/obi-ai-bot/oby/issues/1575)), from [the template](../business-contract-template.md). Scenarios are numbered `TASKS-n`; the tests that prove them are named after them (`apps/electron/src/renderer/src/test/taskActions.test.ts`, `jobPage.test.ts`).

## Feature and status

- **Outcome:** The owner renames, archives and deletes a task, and reads its page (Result, What went out, Timeline, Usage, Details, Full session), and what they see is what obid has: an action holds after the next update, and the page shows the job's own times, activity, usage and session instead of the mock's.
- **Status:** **Implemented** in the Electron app (this change). obid's routes and job keys already existed (`docs/runner-api.md`), but for one added for Delete's ask-first (`POST /v1/jobs/{id}/delete`).
- **Scope:** Sangam's TaskMenu (Rename, Stop, Archive, Delete), the task page (`TaskCard.tsx` with `alone`, `TaskView.tsx`, `SessionView.tsx`) and the result line's pull request link. **Out of scope:** the page's Mode menu (#1570 wires it to `POST /v1/jobs/{id}/mode`; this change only shows the job's mode), a tool call's detail in the session (`GET /v1/jobs/{id}/transcript/{n}`: the lines don't open yet on obid), check rows under Check and Publish (obid's job has no per-check rows), Unarchive (Sangam's Archive has no control for it).

## Behavior

### Actors and ownership

- **obid** owns every decision: whether a job may be renamed (any time), archived (ended and needing nothing) or deleted (ended, not being published, its pull request not open, no follow-up carrying its branch), and the words of a refusal. It owns the job's stage times, estimate, activity, usage, window share, outgoing actions and transcript.
- **The app** sends the owner's action and shows obid's answer. It never decides whether an action is allowed, and it shows obid's refusal in obid's own words (the live problem line, `live.ts` `say`).

### The menu

| Action | Sends | On success | On refusal |
|---|---|---|---|
| Rename (menu, side panel, title bar) | `PATCH /v1/jobs/{id}` `{"title"}`, trimmed; nothing when it's the name it has | The new title shows at once, and obid's job replaces it | The old title comes back; obid's words show (`422`: not one line of 1 to 60 characters) |
| Stop | `POST /v1/jobs/{id}/stop` (as before) | obid's job | obid's words |
| Archive task (done tasks) | `POST /v1/jobs/{id}/archive` `{"archived": true}` | The job's `archived` is set: off Home, under Archive | Stays where it was; obid's words (`409`: `Dismiss it first, or publish it.`) |
| Delete task | `POST /v1/jobs/{id}/delete` | Nothing unpublished: gone from Home and Archive at once, its unsent words too. Commits that aren't published: obid's Confirm on the task's card (and Home's stack), naming them (`Delete Vault tests (its worktree and local branch go; 2 commits that aren't published are lost)`); only the owner's Confirm there deletes it | Stays; obid's words (`409`: running, publishing, pull request open, a follow-up on its branch). Proposed (not built): obid asks first instead, naming what's in the way, and the owner's Confirm deletes it anyway (a running task stopped first; an open pull request stays on GitHub) |

A delete of a job obid no longer has (`404`) counts as gone. Asking first only when something would be lost is the owner's decision of 2026-10-30 ("Yes, ask first"); otherwise Delete stays one click, as in Sangam's design. The Confirm is obid's own `delete_job` item, the one `oby_delete_job` raises, shown on Sangam's existing Confirm card: no new dialog. Its Confirm is signed by this Mac's device key (main), and obid refuses it once the job changed (another round, a commit). The job's `job` event (`deleted: true` for a delete) keeps every other open app in step.

### The page

What obid has goes into Sangam's `Page` (`mock.ts`) and stages, in `jobPage.ts`; a part with no data isn't drawn, as his page already does:

- **Stages:** each one's time: `seconds` when it's over ("22s", "3m 19s"), counted from `started` less `waited` while it's current ("9m 38s so far"), the middle of its `estimate` while it's to come ("≈ 30s"). Under Work, the activity when there's any, and the agent's latest words (`context`) while it's current.
- **Timeline:** from `estimate` and the stage times. Running: "10m in · done in about 2–10m", the track's done, from and to, paused while the task needs the owner, and `basis` under it; past the range, "25m in · jobs like this: 12–20m". Done: "Took 25m · estimated 10–18m" (the range first given). Failed or stopped: "Ran 25m · jobs like this: 12–20m". With no estimate, the section stays "Stages".
- **Activity:** `activity.counts` as Sangam counts them ("31 read · 6 edits · 2 test runs"), kinds with none left out; `activity.groups` with their time, the running one's last file and diff, and its tools.
- **Usage:** only when a plan covers it (`usage.priced` `plan`), the tool gave a cost and the account's 5-hour and weekly windows are known, since Sangam's line says "covered by your plan": every token count summed ("3.0M"), the cost, each window's use and the job's share from `windowShare` ("11%", "<1%" under one point or when no report rose).
- **What went out:** each `outgoing` action in words, with its clock time: "Pushed oby/fix-75 to deskree-inc/oby", "Opened pull request oby#375, ready for review", "Merged oby#375 into dev". A check run (its id is its own URL) is named by the job's pull request; a comment by the pull request its URL is on. Any other action shows as obid names it, with its id (`issueLabels https://github.com/…/issues/12`).
- **Mode:** the job's `mode` as Sangam names it (Ask, Accept edits, Plan, Bypass; Sandbox for an older job).
- **Pull request link:** the short name ("oby#375"), opening `published` on GitHub in the browser (only `https://github.com/…`).
- **Full session:** `GET /v1/jobs/{id}/transcript` when it opens, page after page (`?after=` obid's `next`, at most 1,000 entries each) until `next` is null; then `?after=` the highest `n` it has at each of the job's events, updated by `n`. Each entry as Sangam's session line: a round's start, the agent's words, its thinking, the owner's words, its to-do list, and each tool call (verb and target from obid's summary, its time, a failed command's exit code, an edit's lines added and removed).

### Failures and recovery

- obid unreachable or refusing: the action's task stays as it was (a rename goes back), and the reason shows in the problem line for a few seconds.
- A session fetch that fails shows its reason; the next job event tries again. Two events while one fetch is out make one more fetch, never two at once.
- The app restarting: everything comes from obid again (`GET /v1/jobs`); nothing of this is kept by the app.

### Invariants

- obid's API only grows: one route added, `POST /v1/jobs/{id}/delete` (docs/runner-api.md); `DELETE /v1/jobs/{id}` is unchanged, and the Swift apps are untouched.
- The mock (`npm run web`, `?everything`, `?dev=`) keeps working in place and calls nothing.
- What came from GitHub stays data: only an `https://github.com/` link opens.

## Acceptance scenarios

- **TASKS-1** Rename sends `PATCH /v1/jobs/{id}` with the trimmed title, shows it at once and keeps obid's; the same name again sends nothing; refused, the old title comes back and obid's words show.
- **TASKS-2** Archive sends `POST /v1/jobs/{id}/archive`; the archived job is off Home and in Archive; a `409` leaves it on Home with obid's words.
- **TASKS-3** Delete sends `POST /v1/jobs/{id}/delete`; a `409` leaves the task with obid's words; deleted, or `404`, it's gone.
- **TASKS-4** The result line's pull request shows its short name and opens its GitHub page.
- **TASKS-5** The stages' times and the timeline come from obid's stage times and estimate, running, paused, done and failed.
- **TASKS-6** Activity counts and groups show under Work, with the agent's latest words.
- **TASKS-7** Usage shows only when a plan covers it, with the job's share of each window.
- **TASKS-8** What went out lists every outgoing action in words; a check run by the job's pull request; any other action as obid names it, with its id.
- **TASKS-9** Full session shows obid's transcript in order, as Sangam's lines: every page until `next` is null, then only what came since (`?after=` the highest `n`), merged by `n`, with events during a fetch making one more fetch.
- **TASKS-10** On the mock, the menu works in place and calls nothing.

- **TASKS-11** Delete on a task with commits that aren't published, or with work that isn't committed (obid's `wip:` commit holding what a stopped agent left, or changes in its worktree; [#1644](https://github.com/obi-ai-bot/oby/issues/1644)), deletes nothing yet: obid's Confirm, naming the commits lost or saying `work that isn't committed is lost`, comes onto the task's card, and only the owner's Confirm there deletes it; once deleted, the task leaves the side panel at once, with no reload ([#1707](https://github.com/obi-ai-bot/oby/issues/1707)) (`tasks_11_delete_asks_first_when_commits_arent_published` in obid's `conversation_harness`, `tasks_11_a_stopped_task_with_only_a_wip_commit_asks_before_its_deleted` in `jobs_api`, the TASKS-11 tests in `taskActions.test.ts`, step 8 of `npm run test:core`).
- **TASKS-12** A task that ended with nothing done reads that way, never as plain Done ([#1665](https://github.com/obi-ai-bot/oby/issues/1665)). obid decides it once, from its own facts: a `build`, `fix` or `test` job that ended `done` with no commits, nothing published and nothing pushed has `nothingDone: true` (`Job::nothing_done`; a review or research job, one that committed, pushed or published, or one still running doesn't). Its conversation's turn says `<title> ended with nothing done. Nothing committed, so nothing was published.`, then the agent's first line; its card in the conversation reads `Nothing done · <agent> · <account>`, its result line (Home's card, its page) `No changes`, and its notification is titled `Nothing done`. Its `status` stays `done` (the Swift apps decode it as closed). Tests: `tasks_12_a_job_that_committed_nothing_ended_with_nothing_done` (obid's `job.rs`), `job_report`'s TASKS-12 case (`conversation.rs`), `tasks_12_nothing_committed_is_done_with_nothing_done_and_needs_nothing` (`jobs_api`), TASKS-12 in `nothingDone.test.tsx`.
- **TASKS-13** Home keeps only what still needs the owner ([#1666](https://github.com/obi-ai-bot/oby/issues/1666)'s drive). obid settles, with no answer, every open item about one of its own jobs (a question, permission, plan, the agent's question, a merge card, a limit, its crash or review failure) once the job is gone, or ended let go or with its pull request merged or closed (an Oby review's is the one it reviewed); and Oby's own escalation (only Done) on an ended job with an open merge card, crash or review failure or limit, where obid offers that decision now (MERGING-8's); and a permission of no job (a conversation's shell command an older obid left: nothing runs it since OBY-25); beside anything else, a Confirm say, it stays. It checks when it starts and on every job and inbox change, and the apps hear each settled item. A failed or interrupted task whose pull request (an Oby review's: the one it reviewed) was merged or closed is let go, so Home doesn't keep it either, and its history says Oby let it go; not one with commits that never went out, one an account limit holds (the owner's decision), or one Oby is publishing. An Oby review still at work, or parked on the owner's OK, of a pull request merged or closed since is stopped and let go the same way, and its items settle (the drive of 2026-10-31: six such cards stayed on Home). A Confirm whose action can no longer happen settles with a plain note saying why: a merge of a pull request of Oby's own that it read merged, or closed or at another head since the card, an action on a task that's gone; one that still can, or one Oby can't tell about (a pull request it doesn't follow), stays. Otherwise a queued or running job's items stay (an agent's question while its task waits, parked or not, among them: it truly waits on the owner), as does everything not about one of its jobs: an offer, GitHub's, another Obi's, a teammate approval to remove on GitHub. Tests: `tasks_13_items_about_an_ended_job_settle_and_what_needs_the_owner_stays` (obid's `sphere/link.rs`), `tasks_13_a_let_go_tasks_crash_card_settles` (`jobs_api`), `tasks_13_an_oby_reviews_card_settles_once_its_pull_request_closes` (`merge_api`), `tasks_13_a_task_ended_with_its_pull_request_is_let_go_unless_it_needs_the_owner` (obid's `job.rs`), `tasks_13_a_parked_review_of_a_closed_pull_request_stops_and_its_card_settles` (`merge_api`), `tasks_13_a_confirm_whose_action_can_no_longer_happen_settles_and_one_that_can_stays` (obid's `sphere/link.rs`).
- **TASKS-14** Cards and replies use Sangam's words ([#1666](https://github.com/obi-ai-bot/oby/issues/1666)): a task by its title, never an id; never "job" or "room". Oby's escalation is titled in obid's own words, `<task title> needs your decision` (never the model's recommendation, written after reading agents' text: a lone Done under a question would look like an approval); its text is what Oby found and recommends, in words for the owner, and the Electron app shows that text under the title on obid's own Question card. Every brain prompt that writes to the owner (the conversation's, the recap's, the check-in's) takes one rule for it (`owners_words!`, `brain/mod.rs`), and obid's own answers to its tools and its cards' texts (limit, crash, stalled task, Not merged reasons, Settings) say "task". obid makes no escalation since the event orchestrator retired (TASKS-17); open ones keep these words. Tests: `tasks_14_every_prompt_to_the_owner_takes_its_words` (obid's `brain/harness.rs`), TASKS-14 in `asks.test.ts` and `taskActions.test.ts`. On a task that stopped (`failed` or `interrupted`, not let go, with no follow-up carrying it on and no account limit holding it), the Electron app's card answers that question with Give it another round, Tell it something and Stop here instead of Done, no button looking recommended, as what Oby recommends is in its text. A round or words the task took settle an escalation with Done; Stop here sends none, as obid settles it itself. A stalled task's question (`supervisor-`) takes no answer, so none is sent and it shows only while the task is stopped. Any other item of the task (a Confirm past a safety limit) shows over the question.
- **TASKS-17** *Retired* with the event orchestrator (rules-delete-orchestrator, [recovery.md](recovery.md), "End-of-job rules"): obid makes no escalation any more, and a failed task shows only its own card. An escalation already open (`orchestrator-`) still shows on the AskStack as this scenario said, its box and Done still settling it, until it closes; its tests stay: `tasks_17_escalation_card_shows_whole_text_and_tell_it_what_to_do` (`tasks17.test.tsx`), `tasks_17_tell_it_what_to_do_messages_the_job_then_settles_done` (`taskActions.test.ts`).
- **TASKS-15** What a job's agent is told apart from its task, only in obid's own words, stays with it through a summary of its session: on every run, a resumed one too, in Claude Code's `--append-system-prompt` and Codex's `developerInstructions`; Cursor, with no system prompt, hears it with each prompt. No prompt states a limit obid holds the job to; Codex and Cursor are told long work is fine. `jobs::tests::tasks_15_no_prompt_states_a_time_limit`, `jobs::tests::tasks_15_no_prompt_states_a_round_limit`, `jobs::tests::tasks_15_the_standing_rules_are_only_obids_words`, `long_jobs::tasks_15_every_run_gets_the_standing_rules`, `adapters::tasks_15_codex_and_cursor_hear_the_standing_rules`.
- **TASKS-16:** A finished task's turn in its conversation carries the agent's whole report (at most 6,000 characters, its own "Summary" heading dropped), after obid's line of how it ended; when nothing was published, it says so and that a reply acts on it. The conversation's row shows the latest words, or that its tasks finished, never "Started" for a task that ended.
- **TASKS-18** A stopped task says who stopped it and why in its `stoppedBy` (add-only, obid's words, not the words a person sees: the apps show their own, as Sangam's screens say): "Stopped through Oby's API" (`POST /v1/jobs/{id}/stop`, `POST /v1/stop-all`), "Stopped by a conversation" (`oby_stop_job`, "stop everything"), "Stopped: its pull request was merged or closed", "Stopped: its job pushed a newer head to review", "Stopped: the exchange with the Oby that asked for it ended", or the words a stop already wrote as its `reason` (work on a ChatGPT plan turned off, the account it waited on removed). A stop leaves `reason` as it was. A stop the owner asked for (the API's, a conversation's) while the task waited on them for what they were shown (its agent's question or permission, a yes to a login; a question of a turn still under way isn't shown yet) ends "while its question waited", and a failure record (`failed`) keeps it; obid's own stops never say so, and no other stop is a failure. A wait for a reset or for room isn't a question. Try again clears it. Tests: `jobs_api::tasks_18_a_stopped_job_says_who_stopped_it`, `jobs::tests::tasks_18_only_the_owners_stop_says_a_question_waited`, `failures_api::tasks_18_a_job_stopped_while_its_question_waited_is_recorded`.
- **TASKS-19** The end of an agent's turn isn't the end of its goal. A `build`, `fix` or `test` task with no check, one round too, and any task with no check and more rounds (never a review, whose last line is its verdict) is told to end its summary with a last line `GOAL MET` or `GOAL NOT MET: <what's left>`. `GOAL MET` ends it as before. `GOAL NOT MET: …` on its last round, with commits of its own, ends it `interrupted` with that line as its `reason` and no `nextStep`: its commits are kept on its branch and nothing goes out by itself, though the owner's Publish still sends them (PUBLISHING-9); with none, it ends as one that committed nothing. A last round that ends with neither line is told once, in the same session and spending no round, to carry on and say it; its reply leaves the task's summary to the work's, and with neither line again it ends as before. Earlier rounds go on as before: any line but `GOAL MET` is another round, and each round is judged by its own line, never an earlier round's (a reply to obid's commit or rebase prompt keeps its round's). A restart that picks such a task up to publish reads its last line from the replies it kept. The rules name no tool (`with your own file-editing tool`): Codex and Cursor have no Edit or Write. Tests: `long_jobs::tasks_19_goal_not_met_with_commits_ends_interrupted_and_unpublished`, `long_jobs::tasks_19_a_one_round_job_with_no_check_is_asked_for_its_goal_line`, `long_jobs::tasks_19_a_silent_round_after_goal_not_met_is_asked_again`, `jobs::tests::tasks_15_the_standing_rules_are_only_obids_words`.
- **TASKS-22** A worker ends only the round it is running ([#1649](https://github.com/obi-ai-bot/oby/issues/1649), Stop then Try again). A worker keeps the round it last launched, and `Jobs::end_done` writes `done` only while the job is active and still in that round. So a job stopped while its worker wraps up after its agent's last turn (keeping its commits, reading teammates' pull requests, before it ends), then tried again (`round` N+1, `queued`), stays `queued` or `running` in round N+1 when the old worker's end comes: round N+1 then runs once the old worker has left, and only its own run ends it. An end in the same round, and a stop with no Try again, are as before. Test: `jobs_api::tasks_22_an_old_worker_cannot_end_a_new_round`.

**On a real Mac (Test it when it's done):** rename a task from its page's menu, then quit and reopen: the name stays. Archive a done task: it's under Archive after a reopen. Delete a task whose pull request is open: obid's words show and it stays. Delete a task whose commits weren't published: its card asks Confirm, naming the commits; Cancel keeps it, Confirm deletes it. Open a done task's page: its pull request opens in the browser; Timeline, Usage and What went out show the job's own numbers. Open Full session on a running task: lines come in as the agent works.
