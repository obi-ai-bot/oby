# Chrome-style profiles

The business behavior contract for local profiles on this Mac (Chrome-style), from [the template](../business-contract-template.md). Scenarios are numbered `PROFILES-n`; the tests that prove them are named after them (`profiles_1_…` in `core/crates/obid/src/profiles.rs` and `core/crates/obid/tests/profiles_api.rs`, `profiles_26_…` to `profiles_31_…` in `core/crates/obid/tests/profiles_api.rs`, `profiles_33_…` to `profiles_40_…` in `core/crates/obid/tests/profiles_scope_api.rs`, `profiles_32_…` in `core/crates/obid/src/profiles.rs`, `profiles_12_…` in `core/crates/obid/src/lib.rs`, `profiles_19_…` to `profiles_25_…` and `profiles_41_…` in `apps/electron/src/renderer/src/test/profileMenu.test.tsx`, `profiles_42_…` in `apps/electron/src/renderer/src/test/navigate.test.ts`, `profiles_43_…` to `profiles_45_…` in `core/crates/obid/tests/profiles_manage_api.rs`, `profiles_46_…` in `core/crates/obid/src/conversation.rs`, `profiles_47_…` in `core/crates/obid/src/brain/harness.rs`, `profiles_48_…` and `profiles_49_…` in `apps/electron/src/renderer/src/test/profileMenu.test.tsx`, `profiles_50_…` in `apps/electron/src/renderer/src/test/profileLogins.test.tsx`).

## Feature and status

- **Outcome:** The owner can have more than one local working context on this Mac (a profile: its own name and colour), the way Chrome keeps people on one browser. A profile is a local id and name on this Mac, never an identity, never a sign-in, never something that leaves the Mac.
- **Status:**
  - **PROF-1 is implemented**: `home/profiles.json`, `GET /v1/profiles` returning `[{id, name, color, default, waiting}]`, and the upgrade that gives an install with no file one first profile holding everything it already has.
  - **PROF-2 is implemented**: an internal refactor. `Config.mac_home` names the Mac-wide stores; it adds no screen, setting, API field or profile selection.
  - **PROF-3a is implemented**: creating a profile (`POST /v1/profiles`) and renaming or recolouring one (`PATCH /v1/profiles/{id}`), and the storage-root rule that gives each profile its folder, with its Kani proof (PROFILES-17).
  - **The Electron app's panel title and menu are implemented (A00-76, screen 07)**: the chat-first side panel's title is the open profile's name, and its menu lists the profiles, chooses one, creates one, and edits the open one (its name, its colour, and deleting it); the app keeps which one is open across restarts. Choosing a profile changes the title and the check, and the window reads everything again as that profile's (B00-40, below): its own conversations, tasks, accounts and the rest. On the mock, each profile shows its own too.
  - **A request names its profile (A00-79, first slice) is implemented**: the `Oby-Profile` header, the one resolver that turns it into a storage root, with its Kani proofs (PROFILES-28, 29, 32), and projects kept per profile, reconciled across every profile at start. obid lists `profile-projects-v1`.
  - **Each profile keeps its own conversations, jobs, helpers, accounts and vault (B00-40) is implemented**: a request's `Oby-Profile` decides what it sees, changes and uses, on every `/v1` route and on the event stream; the Electron app names its open profile on every call and on its stream.
  - **Deleting a profile is implemented**: `DELETE /v1/profiles/{id}` takes a profile that isn't the default off the list, and everything it kept becomes the default profile's; nothing is deleted with it.
  - **The Mac's own logins in a profile are implemented**: a profile is offered the tools' own logins no profile holds, and told which profile holds the others (`otherProfileLogins`).
  - **A Claude Code ahead in each profile is implemented**: the next new conversation of each profile with a Claude Code account finds its Claude Code waiting, up to three profiles at once.
  - **Not built yet:** changing which one is the default; moving one account from a profile to another; settings, permissions, routines, connections, the Obysphere and the inbox per profile (one per Mac still); a `waiting` flag that is ever `true`; alerts from a profile that isn't open (A00-84).
- **Plain statement:** a profile is a separate place for the owner's work. A conversation, the jobs it starts, a helper, an agent account and a vault secret made in one profile are that profile's alone: another profile doesn't list, search, read, change, delete, use or hear about them. Everything an install kept before profiles is the default profile's. Settings, permissions, routines, connections and the Obysphere are still one per Mac.
- **Scope for PROF-1:** the registry file, the list route, the upgrade. **Scope for PROF-2:** Mac-wide vs profile storage roots. **Scope for PROF-3a:** the create and rename routes and the storage-root rule. **Scope for A00-76:** the Electron app's panel title, its menu and the New profile form. **Scope for A00-79's first slice:** the `Oby-Profile` header, the resolver, and projects per profile. **Scope for B00-40:** conversations, jobs, helpers, accounts and vault secrets per profile, the event stream per profile, and the Electron app naming its profile. **Scope for deleting, logins and the Claude Code ahead:** `DELETE /v1/profiles/{id}`, `otherProfileLogins`, the next conversation's id and its Claude Code per profile, and the app's Edit profile form and Settings › Agents line. **Out of scope:** profile switching in obid, moving one thing from a profile to another (a deleted profile's things all become the default's), linking a profile to a person or an Obysphere member.

## Behavior

### Actors and ownership

- **obid** owns the registry (`home/profiles.json`, 0600), writes the first profile on upgrade, answers `GET /v1/profiles`, creates and changes profiles, and owns all storage decisions (Mac-wide vs profile roots).
- **Clients** show the list and create profiles: the Electron app's side panel title is the open profile, its menu lists them from `GET /v1/profiles` and makes one with `POST /v1/profiles`. Which one is open is the app's own choice, kept in the window's local storage (`oby.profile`): the kept one while obid lists it, else the default, else the first. The app names the open profile with `Oby-Profile` on every call and on its event stream (B00-40); main keeps it in the app's `settings.json`, so it names it from launch, and when the owner opens another profile the window reads everything again as that profile's. PROF-2 adds no client surface.

### Triggers and prerequisites

- obid starts, or `GET /v1/profiles` is asked: with no `profiles.json` (or one whose `profiles` list is empty), obid writes one first profile and leaves every other file and folder in its home as they were.
- A profile's `id` is a lower-case UUID obid makes. On a new install, the first profile's `name` is `Default` (a label, never who the person is); an install whose registry already exists keeps its names, so one upgraded before PROF-3a keeps `Personal`. Its first `color` is `#3a5a8c` (Sangam's first avatar colour). It is `default: true`. `waiting` is always `false` until later work has something in a profile that waits on the owner.

### States and transitions

- **No registry:** upgrade writes the first profile; existing jobs, conversations, accounts, usage, permissions, logins and every other home path stay where they are, with the same names and contents. Nothing signs out.
- **Registry present:** obid answers its profiles as kept; it does not rewrite them on start.
- **Unreadable registry:** obid logs why, answers one first profile for the request, and does not write over the file: creating and renaming are refused until obid starts again with a file that reads.

### Creating and renaming (PROF-3a)

- `POST /v1/profiles` takes `{"name", "color"}`, both required, and no other key. The name is trimmed and must be 1 to 40 characters; the colour must be `#` and six hex digits, kept as sent. obid makes a lower-case UUID id, makes the profile's folder (0700, and `home/profiles` if missing), adds `{id, name, color, default: false}` to `profiles.json` and answers it as `GET` shows it.
- `PATCH /v1/profiles/{id}` takes `name`, `color` or both, checked the same way, and changes only those. `id` and `default` can't be changed: a body with them, with no key, or with any other key is refused. The default profile can be renamed or recoloured; it stays the one default.
- A refused request writes nothing. A failed write leaves the registry as it was.

### Storage root

A profile's own things go under its storage root: the default profile's is obid's `home` itself, whatever its id, so an existing install has nothing moved; any other profile's is `home/profiles/<id>`, only when its id is a lower-case UUID (hex digits with `-` at 8, 13, 18 and 23). Any other id (empty, the wrong length, holding `/`, `\`, `.`, a NUL or an upper-case letter) has no root. Creating a profile uses the rule to make the folder, and the resolver (below) to find the root a request reaches.

### A request names its profile (A00-79, first slice)

- **The header.** A request names a profile with one `Oby-Profile` header (any case) whose value is the profile's id. With none it is for the default profile, exactly as before. A value that is no profile's id exactly, empty or not plain text is refused with `400` "There's no such profile on this Mac.", and two `Oby-Profile` headers with `400` "Send one Oby-Profile."; nothing is read from or written to any store, and a refused request never falls back to the default profile. It is `400`, not `404`, so an app never mistakes it for a route an older obid lacks.
- **The resolver.** One function, `profiles::root_of`, turns the header into the folder a request's stores are in, reading the registry under its own lock and letting it go before any store is opened: no header is obid's `home`; the id of the profile at a place in the registry is that place; anything else is unknown. The pure rule `root_for` then picks the root: none named, or the default profile named, is `home`; another profile is its storage root (a profile with none is refused as unknown); an unknown profile is refused, never the default. Kani proves the rule for every place in the registry (PROFILES-28, 29, 32).
- **Projects per profile.** Each profile's projects are kept in `projects.json` (0600) under its root: the default profile's stays `home/projects.json`, in place, format and bytes; another's is `home/profiles/<id>/projects.json`. Every profile's projects are behind one lock, taken before the conversations'. A profile's file is read the first time it is needed; no file is no projects, and nothing is written, nor any folder made, until a project is made, changed or deleted there. A profile's file that doesn't read is answered as `500` naming the file by that profile's project routes only. The project routes (`GET`/`POST /v1/projects`, `PATCH`/`DELETE /v1/projects/{id}`) answer for the profile the request names: another profile's project isn't listed, and is `404` on `PATCH` and `DELETE`, as an id no profile has.
- **A conversation's project.** `PATCH /v1/conversations/{id}` and `POST /v1/plans` with a non-null `project` resolve the profile (after the gateway and relay refusal) and join only a project of that profile: another profile's is `422` "There's no project with that id.", nothing changed and no conversation made. Without a `project`, or with `"project": null`, they read no header in this slice.
- **The reconcile.** At start, obid reads every registry profile's projects (`home`, and each other profile's storage root, skipping one that has none). A conversation in a project of any of them gets that project's folders as they are now; one in a project of none leaves it, keeping its folders. When any profile's `projects.json` doesn't read, no conversation changes. Reading a profile at start makes no file and no folder.

### Each profile keeps its own (B00-40)

- **One check per request.** Every `/v1` request goes through one check (`profile_scope::scoped`) that finds its profile as the resolver does: none named is the default profile; an unknown one, an empty one or two are refused `400` on every route, the event stream included, and nothing is read or written. A request for one job, conversation, account or helper by id (`/v1/jobs/{id}…`, `/v1/conversations/{id}`, `/v1/accounts/{id}…`, `/v1/helpers/{id}`) that is another profile's is answered `404`, as one this Mac doesn't have, before its route runs.
- **Where it's kept.** A conversation, a job and a helper keep their profile in their own file (`profile`, the profile's id; a helper's has always been there). An account's profile is kept in `home/account-profiles.json` and a vault secret's in `home/vault-profiles.json` (each `{"<id or name>": "<profile id>"}`, 0600), so `config.json`, `accounts.json` and the vault file keep the shape an older obid reads. Something kept with no profile, or one not in those files, is the default profile's: nothing an install had moves, and the default profile's files keep their shape (it writes no `profile`). A side file that doesn't read is left as it is; everything in it reads as the default's, and adding an account or a secret to another profile is refused until obid starts with one that reads.
- **Conversations.** `GET /v1/conversations` (with or without `q`) and `GET /v1/conversation` list, search and page only the profile's; with no `id`, the latest is the profile's latest. `POST /v1/plans` with `new` makes the conversation in the request's profile; with `conversation` naming another profile's it is `404` and nothing is stopped or added; with neither it joins the profile's latest. A job's task conversation, and a helper's, are made in the job's or the helper's profile. The conversation's Oby, in its tools, lists and searches only its profile's conversations and is told only its profile's jobs and accounts.
- **Jobs.** A job is made in the profile the request names (`POST /v1/jobs`), else in its conversation's, else in the job it follows up's (a review is its author's); it's set once and never changes. `GET /v1/jobs` lists only the profile's. A job runs only on its profile's accounts: picking one (Auto, a named one, a move at a limit) skips every other profile's, so naming another profile's account is refused as one obid doesn't have.
- **Accounts.** `POST /v1/accounts` adds the account to the request's profile, the tool's own login brought back too. `GET /v1/status`'s `accounts` and the `accounts` event list only the profile's. A conversation talks only through its profile's accounts; the owner's choice of one in another profile is passed over. Removing an account forgets its profile.
- **Helpers.** `POST /v1/helpers` makes the helper in the request's profile; a `profile` that isn't the request's is `422`. `GET /v1/helpers` lists only the profile's.
- **Vault.** `GET /v1/obid/vault` lists only the profile's names. `PUT` keeps a secret in the request's profile; a name another profile keeps is `409` and nothing is written over. `DELETE` of another profile's is `404`. Every secret, of any profile, is still taken out of every answer, log line and push, and a connection (one per Mac) may still name any secret.
- **The event stream.** `GET /v1/events` with `Oby-Profile` sends a job's, a conversation's and their turns', steps' and transcripts' events only when they're the profile's, and `accounts` with only the profile's accounts. What belongs to no profile (the inbox, GitHub, the Obysphere, routines) goes to every follower.

### Deleting a profile

- `DELETE /v1/profiles/{id}` of a profile that isn't the default answers `204`. The profile goes from `profiles.json`, and its id is kept there under `merged`: every conversation, job, helper, account and vault secret it kept is the default profile's from then on, as one kept with no profile is. Its projects are added to the default profile's `projects.json`, after the default's own, and its folder `home/profiles/<id>` goes. Nothing is deleted, stopped or signed out: a task running in it runs on, and its accounts keep their logins.
- A request naming the deleted profile is refused `400` as an unknown one; the app, its open profile gone, opens the default.
- The default profile is not deleted (`409`: everything kept before profiles is its, and which one is the default can't be changed yet); an id no profile has is `404`; both write nothing. While `profiles.json` didn't read at start, `409`. When the default's `projects.json` doesn't read, or can't be written, `500` and nothing changes; when `profiles.json` can't be written, the default's projects are put back as they were and `500`.
- The app asks first. Edit profile… in the panel title's menu opens the profile's form: its name and colour (Save sends only what changed, `PATCH`), and, for a profile that isn't the default, Delete profile…, which asks "Delete <name>?" and says that its conversations, tasks, agents, projects and accounts move to <the default's name>, with nothing deleted. Delete sends `DELETE`; a refusal shows obid's words in the form.

### The Mac's own logins in a profile

- `GET /v1/status`'s `availableLogins` are the tools' own logins on this Mac that no profile holds as an account (B00-40: an account is in exactly one profile), whichever profile asks; `POST /v1/accounts` `{"agent", "default": true}` makes one an account of the request's profile.
- `otherProfileLogins` (add-only) lists the tools' own logins on this Mac that another profile holds: `[{"agent", "id", "profile", "profileName"}]`, by the holding profile's id and name; a profile's own aren't in it.
- The app says so in Settings › Agents, under the list: "Claude Code’s login on this Mac is in <profile>. Add another account to sign in with a different login here." Add an account then signs one in with the tool's own sign-in page, a login of its own.

### A Claude Code ahead in each profile

- obid names the next new conversation's id ahead for each profile (`next-id` in `home/conversations` for the default, as before; `next-id-<profile id>` for another), and a conversation made in a profile takes that profile's.
- After each of the owner's turns, obid starts the agent for the next new conversation of the turn's profile first, then of each other profile, in the registry's order, whose first turn would talk through Claude Code, or through Codex on a `codex login` (its thread started too, CONVERSATION-AGENT-51), on one of its own accounts, one at a time, until three wait: no more than three profiles have one ahead at once, and a profile with no such account gets none. It is ended as before (30 minutes, its account changed or removed).
- `GET /v1/status`'s `talkNext` is the account the next new conversation of the request's profile would talk through.

### Failures and recovery

| What happens | What obid does | What the owner sees |
|---|---|---|
| `profiles.json` can't be written on upgrade | Logged; `GET` may still answer the in-memory first profile | Nothing |
| `profiles.json` doesn't parse | Logged; answered as one first profile; file left as it is | Nothing |
| A bad name or colour, a body that isn't a profile, an unknown key, or a change with no key | `400` with the reason; nothing written | obid's reason in the New profile form |
| `PATCH` of an unknown id | `404`; nothing written | Nothing (the app doesn't rename) |
| A request whose `Oby-Profile` names no profile on this Mac, is empty or not text, or is sent twice | `400` with the reason; nothing read or written, never the default profile | The app names only profiles obid lists; one obid refuses on its stream is dropped, and the app follows the default profile |
| A request naming a profile that has no storage root (an id in `profiles.json` that isn't a lower-case UUID) | `400` as an unknown profile; nothing read or written | Nothing yet |
| A profile's `projects.json` doesn't read | Logged and left as it is; that profile's project routes answer `500` naming the file; the start's reconcile changes no conversation | Nothing yet |
| Create or rename while `profiles.json` didn't read at start | `409`: the file couldn't be read and is left as it is; nothing written | obid's reason in the New profile form |
| The folder or `profiles.json` can't be written | `500` with the reason; the registry is left as it was | obid's reason in the New profile form |
| `DELETE` of the default profile, or while `profiles.json` didn't read | `409`; nothing written | obid's reason in the Edit profile form (the app offers no Delete for the default) |
| `DELETE` of an id no profile has | `404`; nothing written | obid's reason in the Edit profile form |
| `DELETE` when the default's `projects.json` doesn't read or can't be written, or `profiles.json` can't be written | `500`; the default's projects and the registry as they were | obid's reason in the Edit profile form |

### Invariants and boundaries

- A profile is a local id and name on this Mac, never an identity, never sent to another Oby, an agent, GitHub or the Obysphere.
- Upgrade never moves, renames, deletes or signs out a job, conversation, account, login, setting or any other home path.
- API add-only: `GET /v1/profiles`, `POST /v1/profiles`, `PATCH /v1/profiles/{id}`, `DELETE /v1/profiles/{id}` and `otherProfileLogins` are new; no existing key or closed enum the Swift or Kotlin apps decode gains a new value.
- The registry and the storage roots are read by the resolver (`profiles::root_of`), for the project routes and a conversation's `project`, and by the start's reconcile; only `projects.json` is read or written inside `home/profiles/<id>`. Each request's profile is found by the one check (`profile_scope::scoped`), and a thing of one profile is never listed, read, changed, used or sent to a follower of another (B00-40). Settings, permissions, routines and connections stay one per Mac.
- A request that names a profile this Mac doesn't have reaches no store: it is refused, never answered from the default profile.
- The design, every store under the profile's root, is checked by [oby_home.qnt](../models/oby_home.qnt): as the specs stood before A00-79 (`oby_home_specs`) `isolated` is violated, and with each store per profile (`oby_home_fixed`) `isolated`, `switchMovesNothing` and `projectsInTheirProfile` hold. obid implements it with projects under each profile's root and the other stores tagged with their profile (B00-40).

## Implemented: Mac-wide storage (PROF-2)

`Config.mac_home` identifies the root for the API token, publishing devices and pairing
file, gateway devices, phone relay key, push registrations and startup cleanup measurement.
Configuration loading sets it to `home`: every file stays where it was, with the same
permissions, failure handling and recovery. It is not a JSON configuration option.
Sandbox detection and the in-memory egress proxy retain their existing startup behavior.
Per-profile stores (including `home/profiles.json`) and `Jobs::open` are unchanged; splitting them belongs to PROF-3.

## Interfaces and dependencies

- Persistence: `home/profiles.json` (0600), `{"profiles":[{"id","name","color","default"}]}` under the profile root (`home`), with `"merged": [ids]` once a profile is deleted (left out until then, so the file keeps its shape). Mac-wide stores use `Config.mac_home` (today equal to `home`).
- `GET /v1/profiles` (obid only): `[{id, name, color, default, waiting}]`. Older runners answer `404`. Documented in [runner-api.md](../runner-api.md), "obid only: profiles".
- `POST /v1/profiles` (`{name, color}` → `201` and the profile) and `PATCH /v1/profiles/{id}` (`{name?, color?}` → `200` and the profile), obid only, on the same token as the list; phones can't reach them through the gateway. Documented in [api/profiles.md](../api/profiles.md).
- A profile's folder: `home/profiles/<id>` (0700), holding only `projects.json` (0600) once a project is made in it.
- `home/account-profiles.json` and `home/vault-profiles.json` (0600): which profile an account, or a vault secret, belongs to; none there is the default's (B00-40).
- `profile` (add-only) on a conversation's summary, a job and their events: the profile's id, only for a profile that isn't the default.
- `Oby-Profile` (obid only): the header that names a request's profile, read on the project routes and on a non-null `project` of `PATCH /v1/conversations/{id}` and `POST /v1/plans`. obid lists `profile-projects-v1` in `GET /v1/status`'s `capabilities` ([capabilities.md](capabilities.md)); an app sends the header only to an obid that lists it. The gateway doesn't forward it, so a phone reaches the default profile. Documented in [api/profiles.md](../api/profiles.md).
- The model: [docs/models/oby_home.qnt](../models/oby_home.qnt).

## Acceptance scenarios

- **PROFILES-1** (`profiles_1_upgrade_keeps_everything_in_the_first_profile`): an install with no `profiles.json` (and with accounts, jobs, usage and permissions already there) → after start, `GET /v1/profiles` is one profile `{id, name: "Default", color: "#3a5a8c", default: true, waiting: false}`, `profiles.json` holds that profile, and every other home file is byte-identical; the account is still signed in. A home that already has a registry keeps it and answers it with `waiting: false`.
- **PROFILES-12** (`profiles_12_mac_stores_use_the_mac_home`): With distinct internal `mac_home` and `home` roots, startup prepares the Mac root, uses its API token, devices/pairing, gateway, relay and push stores, and measures its worktrees. Profile stores remain under `home`. Normal configuration still makes both roots equal.
- **PROFILES-13** (`profiles_13_a_new_profile_is_added_with_its_own_folder`): on an install with accounts, usage and permissions, `POST /v1/profiles {"name":"  Acme  ","color":"#7a4a8c"}` answers `201` with exactly `id` (a lower-case UUID), `name: "Acme"`, `color`, `default: false` and `waiting: false`; `GET` then lists both, the first still the default; `profiles.json` (0600) holds both; `home/profiles/<id>` is an empty 0700 folder; every other file is byte-identical and the account is still listed.
- **PROFILES-14** (`profiles_14_a_bad_name_or_colour_writes_nothing`): an empty, blank or 41-character name, a colour `red` or `#12345`, a missing colour, an extra key or a body that isn't JSON each answer `400` with an `error`; `profiles.json` is byte-identical, `home/profiles` doesn't exist, and `GET` lists one profile.
- **PROFILES-15** (`profiles_15_a_profile_changes_only_its_name_and_colour`): renaming the default profile keeps its id, colour and `default: true`; recolouring a created one changes only its colour; `{"default":true}`, `{"id":"x"}` and `{}` answer `400` and an unknown id `404`, each leaving `profiles.json` byte-identical; exactly one profile stays the default.
- **PROFILES-16** (`profiles_16_an_unreadable_registry_is_never_written_over`): with `profiles.json` holding `not json`, `GET` answers one first profile, and creating and renaming answer `409`; the file still reads `not json` and `home/profiles` doesn't exist.
- **PROFILES-17** (`profiles_17_a_storage_root_is_inside_home_under_its_id`, and the Kani harness `profiles_17_only_a_lower_case_uuid_is_a_profile_id` in `core/crates/obid/src/profiles.rs`): the default profile's root is `home`; another's is `home/profiles/<id>`, inside `home`, for a lower-case UUID id; an empty, `.`, `..`, `../x`, `a/b`, upper-case, dotted, slashed, 35- or 37-character id has none. Kani proves that of every 36 bytes, exactly the lower-case UUIDs are accepted, so an accepted id never holds a path separator, a dot, a NUL or an upper-case letter.
- **PROFILES-18** (`profiles_18_an_install_with_one_profile_behaves_as_before`): an install with accounts, usage, permissions and one default profile named `Personal` starts as before: `GET` answers that profile with `waiting: false`, every file is byte-identical, `home/profiles` doesn't exist, and the account is listed.
- **PROFILES-19** (`profiles_19_one_profile`): obid lists one default profile `Default` `#3a5a8c` → the panel's title is its name with a chevron, and its menu holds one checked row (its mark in `#3a5a8c`), then Edit profile… and New profile….
- **PROFILES-20** (`profiles_20_three_profiles_and_a_choice`): obid lists Default (the default), Deskree and Acme → the menu shows the three in obid's order, only Default checked.
