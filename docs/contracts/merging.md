# Merging: no silent waits, a repository without GitHub checks, and the stages' real words

The business behavior contract for what happens to a task's pull request after Oby publishes it: Oby's review, the merge by a workflow the owner taught it, and the cards that ask the owner when it can't go on by itself. Sangam's design ([#1564](https://github.com/obi-ai-bot/oby/pull/1564): `apps/electron/src/renderer/src/TaskCard.tsx`, the task's stages; the inbox's cards; `src/main/notify.ts`, the alerts), from [the template](../business-contract-template.md). Issues [#1636](https://github.com/obi-ai-bot/oby/issues/1636) and [#1646](https://github.com/obi-ai-bot/oby/issues/1646) (MERGING-13 to 16), from the core audit of 2026-10-30; [#1659](https://github.com/obi-ai-bot/oby/issues/1659) and [#1662](https://github.com/obi-ai-bot/oby/issues/1662) (MERGING-18 and 19), from `npm run drive` of 2026-10-31. Scenarios are numbered `MERGING-n`; the tests that prove them are named after them (`merging_1_…`).

## Feature and status

- **Outcome:** Oby carries a task the whole way, and asks the owner only when something goes wrong (AGENTS.md). Every way a merge can stop ends in something the owner can act on: a card that says why and what to do, its words on the task's Merged stage. A repository without GitHub checks (Oby's own, where Actions is off) merges on the job's own check.
- **Status:** **Implemented** (#1636). Before it, a conflict, a branch behind its base, checks that never finished and a signed-out `gh` were silent waits; a `mac` workflow never merged and its card offered only Dismiss; reviews that ran out raised no inbox item; the task card replaced the Review stage's words with "Waiting for review". MERGING-8's item after a review whose round couldn't start, and MERGING-17's Merge on it: **Implemented** (#1658); before it, the orchestrator asked the owner a question that offered only Done, and nothing in the app merged the pull request.
- **Status of MERGING-40:** **Implemented** (OBY-83). Before it, every change request on a pull request obid carried, whoever wrote it, got the card (`Not merged yet: a review asks for changes.`).
- **Status of MERGING-41:** **Implemented** (OBY-86; turned off at once on the owner's let-go, by any route, or `Leave it open`, and read every 30 seconds for the 10 minutes after arming, OBY-83). Before it, a learned workflow's pull request whose required checks were still running got `Not merged: GitHub's rules for <base> still block it` as a card, and one with only optional checks running waited for obid's next read.
- **Scope:** obid's merge follower (`core/crates/obid/src/merge.rs`, `Jobs::carry` in `jobs.rs`, `jobs/by_github.rs`), Oby's review rounds, the pull request's description, and the Electron task card and alerts. **Out of scope:** the Swift Mac app (frozen).

| The design | What obid promises |
|---|---|

## Behavior

### Actors and ownership

- **obid** reads the pull request every 3 minutes (`OBID_FOLLOW_SECONDS`), decides whether it may merge, merges with the owner's own `gh`, and raises the cards.
- **The job's own check** runs in the job's box. When it passes, obid keeps the commit it passed on, clean, and decides there whether it can stand for the Mac's checks (`Job::checked`, kept in the job's file, never in the API).
- **The owner** answers cards (Merge, Leave it open, Dismiss, One more round) in their own app, or asks Oby to rebase in a message to the task.
- **The Electron app** shows obid's words: stages, cards and alerts.

### Scenarios

- **MERGING-1:** A repository whose workflow waits on the Mac's checks (`checks: mac`) and has no GitHub checks merges by itself once the job's own check passed in its box on exactly the head being merged, with nothing left uncommitted, where it can stand for the Mac's (MERGING-2), as long as every other rule holds (MERGING-7). For 5 minutes after obid pushed the head, "no checks" on GitHub waits: GitHub may not show the checks it will run yet.
- **MERGING-2:** obid decides when the check passes, from what it knows itself, never from what the check printed: the check stands for the Mac's only when the job is the owner's own (its check gets their secrets: started from their own words in Oby's apps, nothing untrusted read, nobody else's code), its change leaves the check's own files alone (what its command runs: a program it names by its path, the script it hands an interpreter, and `Makefile` or `package.json` for `make` or a Node package manager), and it touches nothing only the Mac tests (Swift, Swift packages and Xcode projects anywhere, and what scripts/oby-check.sh sends to the Apple apps and `swift test`). The changed files are what obid's git reads against `origin/<base>`; when they can't be read, it doesn't stand. Otherwise, or when the check passed on another commit, or the job has none, the owner is asked with a card titled `Ready to merge: <task>` that offers **Merge** and **Leave it open**, saying why: `Its check passed, and left the Mac's own tests for this Mac, so it's yours to merge.`, `Its check passed, but this change edits the check itself (<file>), so it's yours to merge.`, `Its check passed, but <why it isn't the owner's own>, so it's yours to merge.`, `Its check passed, but Oby couldn't read what the change touches, so it's yours to merge.`, `Declared secrets withheld: <why>. Its check ran without them, so it's yours to merge.` (its base's `secretspec.toml` names secrets and its last check got none of them, whatever the reason: a reach to `chatgpt.com`, MERGING-30, a marked clone, a base GitHub doesn't say is reviewed, a head obid couldn't read; `Job::check_withheld`, cleared by a check that gets them), `Its check didn't pass on exactly this commit, so it's yours to merge.`, or `No check ran on its head (this repository has none), so it's yours to merge.` The owner's Merge merges it (`mergedBy` `owner`); it lifts every hold its card names (here the missing check). Another base than the learned workflow's has a card of its own (MERGING-7, #1658). Every other hold of Oby's own, a pull request that isn't the job's own included, is on the same card and lifted by the owner's signed Merge (MERGING-20, 21); what GitHub's own rules refuse is the code host's, and Oby says so.
- **MERGING-3:** A pull request that conflicts with its base (`CONFLICTING`, `DIRTY`, or a conflict GitHub finds only when asked to merge) gets one rebase round by itself first, on obid's own branch (MERGING-38): its job is queued at its check, rebased onto the base as it is now, and a conflict gets its agent's one round to rebase it (`The base branch dev moved while you worked, …`); then it's checked and pushed again over the head obid pushed. Nothing else is sent. When that round doesn't settle it (GitHub still says it conflicts, at a head that had its round), or on a branch obid didn't make, the owner is asked: `Not merged: it conflicts with dev. Ask Oby to rebase it onto dev, or settle it on GitHub.`, with Dismiss. A round whose agent couldn't rebase it ends the job as any moved base does (`dev moved while this ran, …`, Try again), its branch as it was.
- **MERGING-4:** A branch behind a base whose rules take only up-to-date branches (`BEHIND`), or under a workflow that rebases first (`rebaseFirst`) not on its base's latest commit, gets the same one rebase round by itself (MERGING-38), and once the new head is pushed it merges as any other does. When the round didn't settle it, or on a branch obid didn't make, the owner is asked: `Not merged: it's behind dev, and GitHub merges only up-to-date pull requests into dev. Ask Oby to rebase it onto dev, or update it on GitHub.`, or with `rebaseFirst` `Not merged: <repo> rebases onto dev first, and it isn't on its latest commit. Ask Oby to rebase it onto dev.`
- **MERGING-5:** GitHub's checks still running an hour after obid pushed the head ask the owner: `Not merged: its checks on GitHub are still running an hour after Oby pushed it. Look at them on GitHub.` A `github` workflow with no checks on the head an hour after the push: `Not merged: GitHub still has no checks on its head an hour after Oby pushed it, and <repo> merges once they pass. Look at it on GitHub.` Within the hour it waits quietly. Checks that finish later merge it by themselves, and the card is settled.
- **MERGING-6:** obid's `gh` signed out, or its login expired, can't read the pull request at all. When a read fails, obid asks gh whether it's signed in, and when gh says for sure it isn't (no account for github.com, or its active one refused with HTTP 401): `Not merged: obid's gh isn't signed in to GitHub. Sign in to GitHub again, and Oby carries on.` A gh that only can't reach GitHub raises no card. Once it's signed in again, the merge goes on by itself. A pull request obid couldn't read (`pullRequestError`) shows under the stage that waits on it, Merged, else Review, while that stage is current.
- **MERGING-7:** Nothing here relaxes a rule of Oby's own: Oby merges by itself only under a workflow the owner agreed to remember; never into `main`, `master` or `trunk` by itself; only Oby's approval (or the workflow's reviewer's) of exactly the head obid pushed, two by different tools where MERGING-14 or 15 asks; only with a clean secret scan of it. Into `main`, `master` or `trunk` the owner's own Merge merges (the owner's decision of 2026-10-31, AGENTS.md "Oby forbids nothing"): once every other rule holds, they get `Ready to merge: <task>`, with **Merge** and **Leave it open**, saying `Its base is main, which Oby merges into only on your word, so it's yours to merge.`. The owner's Merge lifts only what its card says (MERGING-2's missing check, MERGING-14's second review, the base, MERGING-17's review). A pull request into another base than the learned workflow's is the owner's Merge too, by the workflow its card proposes, which isn't remembered over the learned one: `It goes into <base>, and <repo> merges into <learned base>, so it's yours to merge.` What GitHub's own rules refuse (branch protection, required reviews) is the code host's, and the owner reads it as GitHub's, with how to change it: `Not merged: GitHub's rules for <base> still block it: a check or a review they require hasn't passed. The pull request's page on GitHub says which. If it shouldn't be required, change <base>'s branch protection there.`, `Not merged yet: GitHub requires another person's approval here. Ask someone with write access to approve it on GitHub, or change <base>'s branch protection there.`, `Not merged: GitHub didn't merge it (…).`
- **MERGING-8:** When Oby's reviews run out (`review::REVIEWS`, 3) still asking for changes, or an earlier review's round can't start (a follow-up carries its branch, another job holds it, it passed its safety limit), or a round leaves the head as it was, the owner gets one inbox item (`failed`, `<job>-review-<review job>`): `Oby's review still asks for changes. Take it from here.`, with **One more round** and **Merge** (MERGING-17). One more round hands that review to the job's agent once more, past the limit; Oby reviews what it pushes, and if that review still asks for changes, a new item replaces the old. While a follow-up still works on the job's branch, the item waits for it: what it pushes is the head to merge. Why obid couldn't hand the review to the agent, when it couldn't (`reviewError`), follows the item's words. An item still open from an obid before takes Merge too. Never a question of Oby's that offers only Done (#1658). In the app, a failure's card leads with these words, since it shows the task's name already (#1827).
- **MERGING-9:** *Retired* with the event orchestrator (rules-delete-orchestrator, [recovery.md](recovery.md), "End-of-job rules"): no event turn exists to answer that item or be woken for a review left to the owner, so it holds by construction. It said: no event turn of Oby's answers that item (or the item of a review that couldn't run), and none is woken for a review left to the owner.
- **MERGING-10:** A done task's stages show obid's own words: the Review stage's detail as obid says it (never only "Waiting for review"), and the Merged stage's why it isn't merged (`mergeError`, the open card's text).
- **MERGING-11:** The pull request's description says how it merges: under a workflow the owner taught Oby, `Oby merges it by itself, the way its owner taught it: <the workflow's sentence>`; otherwise `Oby merges it only when its owner says so.`
- **MERGING-12:** The alert for a merge that waits on the owner is titled as its card is (`Ready to merge`, `Needs a teammate`, `Not merged`), not always "Not merged", and is said once per card (a new reason on the same head alerts again).

- **MERGING-13:** The reviewer is told when the author is untrusted: its quoted `.obi/inputs/asked.md` says, in obid's words, that the agent that made the change is untrusted because its task read text Oby didn't write, and why (the job's `foreign` reason, or that its conversation read something Oby didn't write). The words of that text are never included.
- **MERGING-14:** An untrusted task's pull request (its conversation read something Oby didn't write; it's someone else's code; words no app of the owner's signed reached it; or a memory known to come from someone else's words, one found in a review comment say, reached its agent: `Job::untrusted_why`. A memory kept before obid marked where memories came from, whose source is unknown, and one the owner's own words made, the workflow Oby asked to remember among them, don't count. Issues and comments by the owner's organization's members stay the owner's own words, and being given Tetrix's tools or reaching its own tool's API hosts or Codex's `chatgpt.com` doesn't count: MERGING-30, nor does reaching any other site past the package registries but a host that serves anyone's source code, which only withholds its check's secrets: MERGING-31) merges by itself only after two approving reviews of the exact head, each by a different tool (Claude Code and Codex, say). Oby asks for the second review once the first approves, on a tool none of the head's approvals came from. With no such tool signed in with room, it waits by itself, with no card (MERGING-34), and a teammate's Oby is still asked where GitHub requires another person's approval. When a check that can't stand for the Mac's (MERGING-2) asks the owner meanwhile, its card names the second review too, and any answer of theirs lifts that. A second review that never started (obid restarted in between) starts on obid's next pass. A job approved once before obid asked for two still needs the second. Approvals are on the job (`approvals`), and why a head needs two is on its review (`review.twoReviews`).
- **MERGING-15:** The same rule holds when the reviewed commit, against its base, touches a security-sensitive path, whoever wrote it: the files the repository's `check` command runs; what steers agents (`AGENTS.md`, `AGENTS.override.md`, `CLAUDE.md`, `.cursorrules`, `.mcp.json`, and the folders `.cursor/` (its rules, `cli.json`, `hooks.json` and `mcp.json`), `.claude/`, `.codex/`, `.agents/`); the secret scan's settings (`.gitleaks.toml`, `.gitleaksignore`, `secretspec.toml`); who must review (`CODEOWNERS`, wherever it is); and CI files (`.github/workflows/`, `.github/actions/`, `.gitlab-ci.yml`, `.circleci/`, `.buildkite/`, `azure-pipelines.yml`, `bitbucket-pipelines.yml`, `Jenkinsfile`, `.travis.yml`). Each matches at any depth and in any letter case (macOS reads `sub/claude.md` as `CLAUDE.md`). The list is one constant (`merge::SECURITY_PATHS`). When the changed files can't be read, it counts as touching one.
- **MERGING-16:** A second review that asks for changes counts like any other review: a change round runs while reviews are left (`review::REVIEWS`, 3), and past them the owner gets MERGING-8's item.
- **MERGING-18:** The reviewer holds the change to what the owner wants now: its quoted `.obi/inputs/asked.md` has what the author was first asked, then the owner's own words to the task after that, oldest first, saying the later ones are what the owner wants where they differ ([#1659](https://github.com/obi-ai-bot/oby/issues/1659)). The owner's own words are their signed messages and Confirms, their conversation turns' words (never the text Oby adds after them, fenced, which can quote GitHub or Tetrix), their signed answers to the agent's questions with each question, and, for a follow-up that carries an earlier task's branch on (TASKCONV-3), the words that started it and those sent to the earlier task; never obid's Try again, or words or answers no app of the owner's signed (the words sent through obid's API come after them, apart: MERGING-33). Words already listed aren't listed again, so the first ask, repeated by a restart, never comes last. They are quoted data, as the first words are. Rules from another context aren't the reviewer's: it is told of Tetrix only as a reader (no session to save), and that what Oby told the author about Tetrix isn't the repository's rules: a `Tetrix-Session` line is asked of the change only where the base's rules or the owner's words ask for one. When the work is from an issue, the issue is quoted too (`.obi/inputs/issue.md`), so the review doesn't go asking the owner for it and a stranger's comment it reads marks the task: two reviews (MERGING-14), the reviewer told why (MERGING-13) (`merging_18_the_review_has_the_issue_its_work_is_from`, `merging_18_a_strangers_comment_the_review_reads_marks_the_task`; #1799).
- **MERGING-19:** The review reads exactly the head obid pushed, even when the owner's clone was made again since the author pushed (a marked clone moved aside, `home/marked/<when>`): when its clone doesn't have that commit, obid fetches it from origin by its id (40 hex characters) before the review starts. A review never makes a marked clone again itself: it only reads, and finds its commit either way, and the fetch is held to the rule of any fetch into the owner's clone (commits that aren't all obid's record of the owner's jobs mark it someone else's). A review never ends with `Couldn't find <head>` because of where its clone is ([#1662](https://github.com/obi-ai-bot/oby/issues/1662)).

- **MERGING-17:** **Merge** on MERGING-8's item is the owner's own Merge of the pull request as it is, the head that item's review read (#1658), never one that came after (`Not merged: Its head moved since…`): GitHub is read again, and it merges with the owner's own GitHub login (`mergedBy` `owner`) by the workflow Oby learned, or, where it hasn't learned one, the one a card would propose, which the owner's yes doesn't remember. Every other rule still holds (its checks, a conflict, a branch behind, a clean secret scan; into main, master or trunk too, on this Merge: MERGING-7); one that can't go says why (`Not merged: <why>`) and leaves the item open, unless a newer review settled it meanwhile. Any other answer is refused naming the item's own (`The answer is One more round or Merge.`). A learned workflow never merges it by itself, and no merge card stands beside the item. The owner's own click merges, and so do their own words in a conversation (docs/contracts/task-conversations.md, TASKCONV-9): the brain's `oby_answer` answers Merge on their signed word in a turn that read nothing untrusted, and otherwise makes a Confirm of Merge, which their click carries out.

- **MERGING-20:** Every hold of Oby's own is Oby's to keep by itself and the owner's to lift (the owner's decision of 2026-10-31, AGENTS.md "Oby forbids nothing"): the pull request's base not the workflow's, a branch obid didn't make for the job (`oby/`, or a new one the owner named: PUBLISHING-13), a job not done, dismissed or with commits Oby hasn't published, a head Oby didn't push, a head holding another job's push its carrier doesn't follow up (MERGING-23), a review that hasn't approved its head or asks for changes, a pull request someone else opened, GitHub's checks red, pending or missing, GitHub's rules Oby couldn't read, and a merge or rebase with more commits than GitHub lists or one saying it closes an issue. By itself, Oby merges nothing while one holds: silently while each may still go by itself (a review or a check under way, a job still at work), else with one card naming every one of them (MERGING-21). The owner's Merge (`merge_by_owner`) lifts what the card they answered named, and only on an answer their app signed (`X-Oby-Words`); a hold the card didn't name, or one that came since, stops it: `Not merged: your Merge didn't cover this. <why>`, and the card stays open. An answer no app of theirs signed lifts only the holds of before 2026-10-31 (MERGING-2's check, MERGING-14's second review, the base, MERGING-17's review). Merge, and remember keeps the workflow as theirs only on a signed answer. It checks every other rule: it merges only while the pull request is open, at the head their card showed (sent as `sha`), not another Obi's, with a clean secret scan, mergeable, and as GitHub's own rules allow (`BLOCKED`, `BEHIND`, a draft, a required review stay GitHub's to refuse; `UNSTABLE`, non-required checks failing, merges on their word). Its branch is deleted only when it's the job's own.
- **MERGING-21:** Every card about a hold the owner can lift offers **Merge** and **Leave it open**, titled `Ready to merge: <task>`: a change request (once obid's round for it is spent, or where it can't have one: MERGING-40), red checks (likewise: MERGING-39), a reviewer account signed out (where Oby knows how it would merge), and each of MERGING-20's holds, in its own words. Only what Oby can't lift (a conflict, a branch behind, GitHub's rules, a signed-out `gh`, another person GitHub requires) keeps **Dismiss** alone, says what to change, and names every hold of Oby's still waiting behind it. A card's text always says why it stopped: the app shows it, its first sentence leading, where no model headline came, never the title alone (#1680). It says each thing once (the drive of 2026-10-31): a Merge card leads with what it asks, in Sangam's words (`Merge tetrix-e2e #153 into main?`), a Dismiss card with the stop's reason and what to change, then each hold on a line of its own, without the `Not merged yet: ` or `so it's yours to merge` the first line already says; the owner's signed answer to it lifts each hold it lists.
- **MERGING-22:** A workflow into `main`, `master` or `trunk` is saved on the owner's own signed Remember, and on "Merge, and remember" . Oby still doesn't merge there by itself (MERGING-7): each pull request there gets its card with Merge. A Remember no app of the owner's signed can't save one, nor anything else that would widen what Oby does by itself (pushing to or merging into a default branch, skipping checks); what binds the owner too until they decide (the secret scan, outside text as data, logins and secrets, the microphone, telemetry) refuses every Remember.
- **MERGING-23:** A follow-up that adds to its task's pull request (`addedTo`, #1663) pushes as Oby: its push is Oby's own. Follow-ups on a branch make one line: words to a task, or to any follow-up of it, start a follow-up of the newest job on that branch that follows the task up, never a second one beside it, and words go to the one at work, at any depth. The marks a follow-up carries (untrusted, unsigned, a memory from someone else's words, not vetted) are then every earlier job's, and one marked later reaches the follow-ups made before. Of the owner's own jobs that published to one pull request on its branch, the one that pushed there last carries it: its head is the commit that job pushed, its review, its record (`mergedBy`) and its merge, by itself or on the owner's Merge, whichever job's card or words named the pull request. Another Obi's push never counts as Oby's. A carrier that doesn't follow up, at any depth, every other job that pushed there (siblings made before follow-ups made one line) still has the one card, but doesn't merge by itself, and Oby's reviewer account approves nothing for it: `Not merged: its head holds what <task> pushed, and this task doesn't follow that one up, so its review alone doesn't count for that work.` It's one of MERGING-20's holds, in the merge rule itself: only the owner's signed Merge on a card naming it, or their own word (MERGING-27), lifts it; an answer no app of theirs signed, or MERGING-17's review item, merges nothing (MERGING-14, 20). The new follow-up's account, agent, mode and quoted report are the newest follow-up's.
- **MERGING-24:** One pull request gets one merge card: the job that carries it (MERGING-23). The jobs before it on that pull request have none, and nothing about merging waits on them (`mergeNeedsYou` false, no `mergeError`); a card one of them had is settled, and so is MERGING-8's item for a review of an older head. While the carrier works again, nobody's card shows. When it was let go or ended unfinished, the latest job before it that Oby still carries has the card instead, with Dismiss: `Not merged: its head is what <task> pushed, and you let that task go.` (or `and that task didn't finish.`) `Tell Oby to carry on in it, or settle it on GitHub.`
- **MERGING-25:** A head no job of Oby's pushed, a follow-up's included, is still not Oby's: nothing merges by itself, and the carrying job's one card says `Not merged: its head is a commit Oby didn't push.` (the owner's Merge lifts it, MERGING-20).
- **MERGING-26:** While Oby's own review of a pull request is at work (`reviewing`, the review queued or running), it has no merge card and nothing merges by itself: `Ready to merge` and `Nobody has approved its head` would be said of a head Oby is still reading. The review's own permission card still shows. Any card comes when the review ends, and one stopped at its account's limit counts as ended, though it stays named while the owner decides. The owner's own words still merge it (MERGING-27). A card names what a task read in the same words every time, `its task read something Oby didn't write`: the chain of what read what stays the job's own record (`foreign`).
- **MERGING-27:** The owner's own word merges over every hold of Oby's, whether or not a card named it: their signed words on a turn (`oby_merge`, or `oby_answer` with Merge on a merge card), or their click on the Confirm those words made. A review still at work, one asking for changes, red or missing checks, a workflow's rebasing first and the rest of MERGING-20's holds all go, and Oby says what was still open (`Still open: Oby's review hasn't approved its head.`), on the Confirm before the click and in its answer after the words, rather than refusing (AGENTS.md, "Oby forbids nothing"). What's listed is what obid knows before it asks GitHub: a rebase merge's own checks, and a branch behind its base under a workflow that rebases first, go unlisted. GitHub's own rules, a conflict and a branch GitHub won't merge stay the limit, in GitHub's words. A signed answer to a card still lifts only what that card named (MERGING-20): a card answered late, from an alert, can't lift a hold that came after it.
- **MERGING-28:** A card keeps which device signed the answer that settled it (`answeredBy` on the item, null for an answer no app signed, an answer that didn't settle it, or an item settled by itself), and obid's log says so too, so a merge can be traced afterwards (#1825).
- **MERGING-29:** A merge or a publish that stops part way, its future dropped (a request that went, obid moving on) or a panic, frees its task at once: the next merge isn't told `Not merged yet: Oby is merging it already.`, the next publish isn't refused as one under way, and the task shows no publish step nothing runs any more. Its scratch folder goes too, and a `gh` it was waiting on is killed with it.
- **MERGING-30:** Being given Tetrix's tools, before any call, leaves a job the owner's own: no mark, so it doesn't count toward MERGING-14's two reviews, nor take its check's values away. So does a job's reach to its own tool's API hosts on port 443 (`egress::tools_api`: Claude Code's `api.anthropic.com`, `statsig.anthropic.com` and `console.anthropic.com`; Codex's `api.openai.com` and `auth.openai.com`; Cursor's `api2.cursor.sh`, `api3.cursor.sh` and `api4.cursor.sh`), by the CLI or by anything in its box: the proxy can't tell the CLI from a `curl` in the box, lets either through and marks nothing. Codex's `chatgpt.com`, a ChatGPT login's API that serves shared conversations too, marks nothing either, but that job's own check gets no declared secrets from then on, and where its base declares secrets, the card that leaves its merge to the owner says `Declared secrets withheld: this job reached chatgpt.com.` (MERGING-2).
