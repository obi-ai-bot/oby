# Merging: no silent waits, a repository without GitHub checks, and the stages' real words

The business behavior contract for what happens to a task's pull request after Oby publishes it: Oby's review, the merge by a workflow the owner taught it, and the cards that ask the owner when it can't go on by itself. Sangam's design ([#1564](https://github.com/obi-ai-bot/oby/pull/1564): `apps/electron/src/renderer/src/TaskCard.tsx`, the task's stages; the inbox's cards; `src/main/notify.ts`, the alerts), from [the template](../business-contract-template.md). Issues [#1636](https://github.com/obi-ai-bot/oby/issues/1636) and [#1646](https://github.com/obi-ai-bot/oby/issues/1646) (MERGING-13 to 16), from the core audit of 2026-10-30. Scenarios are numbered `MERGING-n`; the tests that prove them are named after them (`merging_1_…`).

## Feature and status

- **Outcome:** Oby carries a task the whole way, and asks the owner only when something goes wrong (AGENTS.md). Every way a merge can stop ends in something the owner can act on: a card that says why and what to do, its words on the task's Merged stage. A repository without GitHub checks (Oby's own, where Actions is off) merges on the job's own check.
- **Status:** **Implemented** (#1636). Before it, a conflict, a branch behind its base, checks that never finished and a signed-out `gh` were silent waits; a `mac` workflow never merged and its card offered only Dismiss; reviews that ran out raised no inbox item; the task card replaced the Review stage's words with "Waiting for review". MERGING-8's item after a review whose round couldn't start, and MERGING-17's Merge on it: **Implemented** (#1658); before it, the orchestrator asked the owner a question that offered only Done, and nothing in the app merged the pull request.
- **Scope:** obid's merge follower (`core/crates/obid/src/merge.rs`, `Jobs::carry` in `jobs.rs`), Oby's review rounds, the pull request's description, and the Electron task card and alerts. **Out of scope:** a rebase round Oby starts by itself for a conflict or a branch behind its base (obid's rule: a pull request that can't merge cleanly gets no rebase round by itself; docs/runner-api.md, "What the runner doesn't do by itself"); the Swift Mac app (frozen).

## What Sangam's design assumes (each one kept)

| The design | What obid promises |
|---|---|
| A task's stages, each with a line under it. | `pipeline.stages[].detail`: obid's own words, shown as they are ("Oby is reviewing", "Pull request open · waiting for your review on GitHub", why it isn't merged). |
| Cards in the inbox, answered in one click. | `merge` items with their options; `failed` items with theirs. |
| An alert when something needs you, titled as what needs you. | `mergeNeedsYou` and `mergeError` on the job; the card's title. |

## Behavior

### Actors and ownership

- **obid** reads the pull request every 3 minutes (`OBID_FOLLOW_SECONDS`), decides whether it may merge, merges with the owner's own `gh`, and raises the cards.
- **The job's own check** runs in the job's box. When it passes, obid keeps the commit it passed on, clean, and decides there whether it can stand for the Mac's checks (`Job::checked`, kept in the job's file, never in the API).
- **The owner** answers cards (Merge, Leave it open, Dismiss, One more round) in their own app, or asks Oby to rebase in a message to the task.
- **The Electron app** shows obid's words: stages, cards and alerts.

### Scenarios

- **MERGING-1:** A repository whose workflow waits on the Mac's checks (`checks: mac`) and has no GitHub checks merges by itself once the job's own check passed in its box on exactly the head being merged, with nothing left uncommitted, where it can stand for the Mac's (MERGING-2), as long as every other rule holds (MERGING-7). For 5 minutes after obid pushed the head, "no checks" on GitHub waits: GitHub may not show the checks it will run yet.
- **MERGING-2:** obid decides when the check passes, from what it knows itself, never from what the check printed: the check stands for the Mac's only when the job is the owner's own (its check gets their secrets: started from their own words in Oby's apps, nothing untrusted read, nobody else's code), its change leaves the check's own files alone (what its command runs: a program it names by its path, the script it hands an interpreter, and `Makefile` or `package.json` for `make` or a Node package manager), and it touches nothing only the Mac tests (Swift, Swift packages and Xcode projects anywhere, and what scripts/oby-check.sh sends to the Apple apps and `swift test`). The changed files are what obid's git reads against `origin/<base>`; when they can't be read, it doesn't stand. Otherwise, or when the check passed on another commit, or the job has none, the owner is asked with a card titled `Ready to merge: <task>` that offers **Merge** and **Leave it open**, saying why: `Its check passed, and left the Mac's own tests for this Mac, so it's yours to merge.`, `Its check passed, but this change edits the check itself (<file>), so it's yours to merge.`, `Its check passed, but <why it isn't the owner's own>, so it's yours to merge.`, `Its check passed, but Oby couldn't read what the change touches, so it's yours to merge.`, `Its check didn't pass on exactly this commit, so it's yours to merge.`, or `No check ran on its head (this repository has none), so it's yours to merge.` The owner's Merge merges it (`mergedBy` `owner`); it lifts every hold its card names (here the missing check). Another base than the learned workflow's has a card of its own (MERGING-7, #1658). A hold no card names (a pull request that isn't the job's own) stops it today, and is proposed to be the owner's to lift too (docs/runner-api.md, "When Oby merges by itself"); what GitHub's own rules refuse is the code host's, and Oby says so.
- **MERGING-3:** A pull request that conflicts with its base (`CONFLICTING`, `DIRTY`, or a conflict GitHub finds only when asked to merge) asks the owner: `Not merged: it conflicts with dev. Ask Oby to rebase it onto dev, or settle it on GitHub.`, with Dismiss. Nothing is sent.
- **MERGING-4:** A branch behind a base whose rules take only up-to-date branches (`BEHIND`) asks the owner: `Not merged: it's behind dev, and GitHub merges only up-to-date pull requests into dev. Ask Oby to rebase it onto dev, or update it on GitHub.` A workflow that rebases first (`rebaseFirst`) and a branch not on its base's latest commit: `Not merged: <repo> rebases onto dev first, and it isn't on its latest commit. Ask Oby to rebase it onto dev.` Oby starts no rebase round by itself.
- **MERGING-5:** GitHub's checks still running an hour after obid pushed the head ask the owner: `Not merged: its checks on GitHub are still running an hour after Oby pushed it. Look at them on GitHub.` A `github` workflow with no checks on the head an hour after the push: `Not merged: GitHub still has no checks on its head an hour after Oby pushed it, and <repo> merges once they pass. Look at it on GitHub.` Within the hour it waits quietly. Checks that finish later merge it by themselves, and the card is settled.
- **MERGING-6:** obid's `gh` signed out, or its login expired, can't read the pull request at all. When a read fails, obid asks gh whether it's signed in, and when gh says for sure it isn't (no account for github.com, or its active one refused with HTTP 401): `Not merged: obid's gh isn't signed in to GitHub. Sign in to GitHub again, and Oby carries on.` A gh that only can't reach GitHub raises no card. Once it's signed in again, the merge goes on by itself. A pull request obid couldn't read (`pullRequestError`) shows under the stage that waits on it, Merged, else Review, while that stage is current.
- **MERGING-7:** Nothing here relaxes a rule of Oby's own: Oby merges by itself only under a workflow the owner agreed to remember; never into `main`, `master` or `trunk` by itself; only Oby's approval (or the workflow's reviewer's) of exactly the head obid pushed, two by different tools where MERGING-14 or 15 asks; only with a clean secret scan of it. Into `main`, `master` or `trunk` the owner's own Merge merges (the owner's decision of 2026-10-31, AGENTS.md "Oby forbids nothing"): once every other rule holds, they get `Ready to merge: <task>`, with **Merge** and **Leave it open**, saying `Its base is main, which Oby merges into only on your word, so it's yours to merge.`, and no workflow into one is remembered, since Oby would never follow it by itself. The owner's Merge lifts only what its card says (MERGING-2's missing check, MERGING-14's second review, the base, MERGING-17's review). A pull request into another base than the learned workflow's is the owner's Merge too, by the workflow its card proposes, which isn't remembered over the learned one: `It goes into <base>, and <repo> merges into <learned base>, so it's yours to merge.` What GitHub's own rules refuse (branch protection, required reviews) is the code host's, and the owner reads it as GitHub's, with how to change it: `Not merged: GitHub's rules for <base> still block it. Approve it on GitHub as they ask, or change <base>'s branch protection there.`, `Not merged yet: GitHub requires another person's approval here. Ask someone with write access to approve it on GitHub, or change <base>'s branch protection there.`, `Not merged: GitHub didn't merge it (…).`
- **MERGING-8:** When Oby's reviews run out (`review::REVIEWS`, 3) still asking for changes, or an earlier review's round can't start (a follow-up carries its branch, another job holds it, it passed its safety limit), or a round leaves the head as it was, the owner gets one inbox item (`failed`, `<job>-review-<review job>`): `Oby's review still asks for changes. Take it from here.`, with **One more round** and **Merge** (MERGING-17). One more round hands that review to the job's agent once more, past the limit; Oby reviews what it pushes, and if that review still asks for changes, a new item replaces the old. While a follow-up still works on the job's branch, the item waits for it: what it pushes is the head to merge. Why obid couldn't hand the review to the agent, when it couldn't (`reviewError`), follows the item's words. An item still open from an obid before takes Merge too. Never a question of Oby's that offers only Done (#1658).
- **MERGING-9:** No event turn of Oby's answers that item (or the item of a review that couldn't run), and none is woken for a review left to the owner: an answer from Oby would loop it, and a question of its own would be a second card with no way forward.
- **MERGING-10:** A done task's stages show obid's own words: the Review stage's detail as obid says it (never only "Waiting for review"), and the Merged stage's why it isn't merged (`mergeError`, the open card's text).
- **MERGING-11:** The pull request's description says how it merges: under a workflow the owner taught Oby, `Oby merges it by itself, the way its owner taught it: <the workflow's sentence>`; otherwise `Oby merges it only when its owner says so.`
- **MERGING-12:** The alert for a merge that waits on the owner is titled as its card is (`Ready to merge`, `Needs a teammate`, `Not merged`), not always "Not merged", and is said once per card (a new reason on the same head alerts again).

- **MERGING-13:** The reviewer is told when the author is untrusted: its quoted `.obi/inputs/asked.md` says, in obid's words, that the agent that made the change is untrusted because its task read text Oby didn't write, and why (the job's `foreign` reason, or that its conversation read something Oby didn't write). The words of that text are never included.
- **MERGING-14:** An untrusted task's pull request (its conversation read something Oby didn't write; it's someone else's code; words no app of the owner's signed reached it; or a memory known to come from someone else's words, one found in a review comment say, reached its agent: `Job::untrusted_why`. A memory kept before obid marked where memories came from, whose source is unknown, and one the owner's own words made, the workflow Oby asked to remember among them, don't count. Issues and comments by the owner's organization's members stay the owner's own words) merges by itself only after two approving reviews of the exact head, each by a different tool (Claude Code and Codex, say). Oby asks for the second review once the first approves, on a tool none of the head's approvals came from. With no such tool signed in with room, `noReviewer` says `Oby's second review waits for a tool other than <tool> signed in with room.`, and a teammate's Oby is still asked where GitHub requires another person's approval; once every other rule holds the owner gets `Ready to merge: <task>`, with **Merge** and **Leave it open**, saying why: `Oby's review approved it, but it needs a second approving review by another tool (<why>), and no other tool is signed in with room. It's yours to merge.` When a check that can't stand for the Mac's (MERGING-2) is missing too, the one card says both reasons. Their Merge lifts only what the card says. A second review that never started (obid restarted in between) starts on obid's next pass. A job approved once before obid asked for two still needs the second. Approvals are on the job (`approvals`), and why a head needs two is on its review (`review.twoReviews`).
- **MERGING-15:** The same rule holds when the reviewed commit, against its base, touches a security-sensitive path, whoever wrote it: the files the repository's `check` command runs; what steers agents (`AGENTS.md`, `AGENTS.override.md`, `CLAUDE.md`, `.cursorrules`, `.mcp.json`, and the folders `.cursor/rules/`, `.claude/`, `.codex/`, `.agents/`); the secret scan's settings (`.gitleaks.toml`, `.gitleaksignore`, `secretspec.toml`); who must review (`CODEOWNERS`, wherever it is); and CI files (`.github/workflows/`, `.github/actions/`, `.gitlab-ci.yml`, `.circleci/`, `.buildkite/`, `azure-pipelines.yml`, `bitbucket-pipelines.yml`, `Jenkinsfile`, `.travis.yml`). Each matches at any depth and in any letter case (macOS reads `sub/claude.md` as `CLAUDE.md`). The list is one constant (`merge::SECURITY_PATHS`). When the changed files can't be read, it counts as touching one.
- **MERGING-16:** A second review that asks for changes counts like any other review: a change round runs while reviews are left (`review::REVIEWS`, 3), and past them the owner gets MERGING-8's item.

- **MERGING-17:** **Merge** on MERGING-8's item is the owner's own Merge of the pull request as it is, the head that item's review read (#1658), never one that came after (`Not merged: Its head moved since…`): GitHub is read again, and it merges with the owner's own GitHub login (`mergedBy` `owner`) by the workflow Oby learned, or, where it hasn't learned one, the one a card would propose, which the owner's yes doesn't remember. Every other rule still holds (its checks, a conflict, a branch behind, a clean secret scan; into main, master or trunk too, on this Merge: MERGING-7); one that can't go says why (`Not merged: <why>`) and leaves the item open, unless a newer review settled it meanwhile. Any other answer is refused naming the item's own (`The answer is One more round or Merge.`). A learned workflow never merges it by itself, and no merge card stands beside the item. Only the owner's own click merges: the brain's `oby_answer` can't, and told to merge in words, Oby says the card is in the inbox, or what keeps it from merging.

The words of MERGING-14's card and stage, and MERGING-17's Merge, are obid's own until Sangam's screens have them (his review card offers `One more round` and `Open it as it is`, before a pull request is open).

### Failure and recovery

- A card answered (Leave it open, Dismiss) isn't asked again for that head and reason; a new head, or a new reason, brings a new card, and the old one is settled.
- A read of GitHub that fails waits and reads again, as before: only the states above end in a card.

## Invariants

- obid's API is add-only: no key is renamed or removed. `Job::checked` is kept in the job's file, never in the API.
- Oby pushes nothing while merging, so it force-pushes nothing.
- Text from GitHub stays data: card words are obid's own.

## Test it when it's done (on a real Mac)

1. In this repository (workflow `checks: mac`, Actions off), let a task's check run `scripts/oby-check.sh` on an obid-only change and publish: once Oby's review approves, it merges into `dev` by itself and says "Merged into dev, as you like".
2. A change that touches `Engine/` (the box leaves `swift test` for the Mac): the inbox shows `Ready to merge: <task>` with Merge, saying it left the Mac's own tests; Merge merges it. The same for a change to `scripts/oby-check.sh`.
3. Make a task's pull request conflict with `dev` (merge a conflicting change first): within 3 minutes the task's Merged stage and a card say it conflicts and what to do.
4. `gh auth logout` on the Mac obid runs as: the card says obid's gh isn't signed in; `gh auth login` again, and the merge goes on.
5. With Claude Code and Codex both signed in, a task that changes an `AGENTS.md`: Oby's review runs twice, once on each tool, and it merges only after both approve. Sign Codex out and do it again: after Claude Code's approval, the task's Review stage says the second review waits for another tool, and the inbox shows `Ready to merge: <task>` with Merge.
