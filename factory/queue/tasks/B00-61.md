Step 1 of the Agents plan (docs/decisions/2026-11-16-agents-follow-openbot.md). OpenBot (commit 6b2ccd1f2) is the reference for behaviour only; none of its code is copied (PolyForm Noncommercial).

## What
Today every agent's conversation runs on Oby's own-lane sandbox: its commands write only its room, and anything it would send or merge after reading mail, a web page or another Oby waits for the owner's Confirm. An agent meant to triage an inbox every morning can't act on its own. OpenBot gives each agent one level the person chooses, and a new agent starts at Full access, which never asks.

## Why
- **The owner, 2026-11-16:** "Follow exactly what OpenBot does!", answering whether an agent that reads mail needs a click for every send.
- **Lane: dispatcher**, by that decision: which box a run gets, and whether it asks, is the dispatcher's.

## How
1. **The level.** A helper gains `level`: `workspace`, `ask` or `full` (add-only; `full` when absent, as in OpenBot). It's kept in `home/helpers.json` and answered by `GET /v1/helpers`.
2. **Who changes it.** Only the owner's signed words widen it: `PATCH /v1/helpers/{id}` with a wider level is refused unless the app's main process signed it (docs/contracts/signed-words.md). A narrower level is accepted from anyone, an agent's own tool included (`oby_narrow_level`, its own agent only).
3. **What each level runs.**
   - `workspace`: today's own-lane conversation, unchanged: commands write only the room (LANES-12, CONVERSATION).
   - `ask`: the whole Mac, and before each command, file write outside the room, or `oby_*` tool that sends, writes or starts work, a permission card the owner answers (the conversation's existing permission and Confirm cards).
   - `full`: the whole Mac, no card. The kernel sandbox still denies obid's home and every account's login folder but the run's own (the vault, `api-token`, other logins), and the git pointers obid pins. That is a non-negotiable, never a setting.
   The mechanism per tool (Claude Code's sandbox settings, Codex's `-c` profile, Cursor's box) is the builder's; each must be a kernel sandbox, never an instruction to the model.
4. **Untrusted reads.** At `full`, reading mail, a page or another Oby's answer still marks the conversation untrusted (CONVO-1) but brings no Confirm for the agent's own actions. Jobs it starts in a project stay untrusted and follow the merge rules (two reviews or the owner's click).
5. **The app.** The agent's sheet shows the level with Sangam's words, and the agent's title bar shows it when it isn't Full.
6. **Contract.** docs/contracts/helpers.md (the level, AGENTLEVEL-1 to 7) and docs/contracts/lanes.md (an agent's lane follows its level).

### Formal verification
A Kani harness over the pure decider `may_set_level(current, wanted, signed_by_owner) -> bool`: true exactly when `wanted` is not wider than `current`, or the change is signed by the owner. A Kani harness over `denied_for_full(path)`: obid's home and every other account's login folder are always denied, whatever the level.

Acceptance (each a test named after it):
1. AGENTLEVEL-1: a new agent is `full`; an agent from before this task reads `full`.
2. AGENTLEVEL-2: an unsigned `PATCH` from `workspace` to `full` is refused and changes nothing; a signed one is kept.
3. AGENTLEVEL-3: `oby_narrow_level` from `full` to `ask` is kept; to a wider level, refused.
4. AGENTLEVEL-4: a `full` agent's command writes a file in the person's home outside its room with no card.
5. AGENTLEVEL-5: a `full` agent's command can't read `vault/secrets.json` or `api-token`, and the turn says why.
6. AGENTLEVEL-6: an `ask` agent's command outside its room waits for the owner's permission card, and runs on Allow.
7. AGENTLEVEL-7: a `full` agent that read an outside page sends with its tool without a Confirm; a job it starts in a project is marked untrusted.
