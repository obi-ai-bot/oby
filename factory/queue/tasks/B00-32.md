## What
After B00-31 the factory's pipeline is data, but only this repository's feeder runs it. An owner without that feeder gets the build and Oby's review, nothing else. This task has obid run a project's workflow itself: the steps before the build (an intake, a spec), the build, and the steps after it (lenses, an approver, the owner's click), each as a job of its own, as `oby-feed` does over obid's API today.

## Why
- **The owner, 2026-11-16:** "easy for people to create their own workflows like T3 Code and OpenBot." Today only someone who runs this repository's feeder has one.
- **OpenBot runs a workflow a person defines** and keeps the steps a run started with (`src/backend/workflows/workflow-schema.ts:1-40`); routine flows hand one agent's answer to the next (`packages/contracts/src/ipc-routine-flows.ts:7-11`).
- **Lane: dispatcher.** "Which agent, account and worktree; start, stop and resume; what state the work is in; asking the owner" (AGENTS.md, "Dispatcher, not harness"). obid only starts steps, orders them and reads their header lines. Each step's work is an agent's, and obid makes no model call: rules decide what happens to a job.

## How
1. **A project's workflow** (B00-31's format) is kept beside B00-06's `factory.json` in the project's folder in obid's home (`profiles/<profile>/projects/<project>/workflow.json`, 0600, written whole by rename). It's set two ways: `PUT /v1/projects/{id}/workflow` with `{workflow, revision}`, signed words only (`409` stale, `422 {problems: [{path, message}]}`), or by Confirming a repository's offer, a `confirm` inbox item as B00-30's hooks are offered when the project's repository's `oby.json` on its base has a `workflows` entry. `GET /v1/projects/{id}/workflow` answers it with its source. No workflow is today's behaviour.
2. **Running it.** When a task starts in a project with a workflow, obid saves the workflow on the job and runs its steps in order around the job's build:
   - `agent`: a job of kind `research`, its prompt the step's `prompt` file read from the base and quoted, the task and the earlier steps' answers as quoted inputs (`.obi/inputs`, as today). Its answer is kept on the job.
   - `build`: the job itself, today's lifecycle, with the earlier answers quoted as its inputs.
   - `check`: its `run` command in the job's box under the check's rules (PUBLISHING-6 to 8). A step whose `runsOn` names another machine waits for the owner, saying which machine it needs: obid doesn't reach other machines yet.
   - `review`: one of Oby's reviews of the head, with the step's `prompt` as its lens. `VERDICT: CHANGES` sends the build a follow-up quoting it, up to B00-28's `reviews.rounds`; past that, the owner is asked.
   - `approve`: a research job with the step's `prompt`; APPROVE lets the merge rules decide as today, ESCALATE asks the owner.
   - `owner`: waits for the owner's signed Merge, as MERGING-21's card.
3. **`when`** is read from the header lines of the earlier answers (`RISK: high`, `SURFACES: ui, security`). A line that's missing counts as a match, so a step runs when obid can't tell, never the reverse.
4. **Who runs each step** comes from `factory.json`'s `steps.<id>` (B00-06): tool, account, model and effort; with none, as today.
5. **The job shows it.** Each step is a stage in the job's `stages`, an open string id (`apps/electron/src/shared/obid-wire.ts:22`), and `pipeline` counts them (`obid-wire.ts:97`). Each step's job links to its task.
6. **What doesn't change:** the merge rules (B00-27, B00-28), the two approvals a sensitive change needs (a lens review's APPROVE counts as Oby's review of that head), the secret scan, signed approvals, lanes and boxes.
7. **Docs.** `docs/contracts/workflows.md` (new): WORKFLOW-1 to 7. `docs/api/` for the project's workflow routes. The Claude Code factory and `oby-feed` keep working; the feeder can hand its pipeline to obid in a later task.

### Formal verification
A Kani harness over the pure step chooser: for every workflow and every set of answers, the next step is the first one in order not yet done whose `when` matches or can't be read, and none runs before an earlier one is done.

Acceptance (each scenario a test named after it; time faked through the existing hooks, never a sleep):
1. WORKFLOW-1 (`workflow_1_no_workflow_is_today`): a task in a project with no workflow runs exactly as on `origin/dev`.
2. WORKFLOW-2 (`workflow_2_steps_run_in_order`): a workflow of intake, build and one review starts a research job whose prompt quotes the intake file, then the build with intake's answer as a quoted input, then the review with its lens, in that order, each a stage of the job.
3. WORKFLOW-3 (`workflow_3_when_reads_the_answers`): a step with `when: {"RISK": ["high"]}` runs after an answer saying `RISK: high`, doesn't after `RISK: low`, and runs after an answer with no `RISK` line.
4. WORKFLOW-4 (`workflow_4_changes_send_a_round`): a review step's `VERDICT: CHANGES` sends the build a follow-up quoting it, and after `reviews.rounds` the owner is asked (`reviewNeedsYou`).
5. WORKFLOW-5 (`workflow_5_the_owner_step_waits`): an `owner` step holds the merge until the owner's signed Merge.
6. WORKFLOW-6 (`workflow_6_a_task_keeps_its_workflow`): a task started under one workflow keeps it when the owner changes the project's.
7. WORKFLOW-7 (`workflow_7_only_the_owner_sets_it`): an unsigned `PUT` changes nothing, and a repository's offered workflow runs nothing before the owner's Confirm.
