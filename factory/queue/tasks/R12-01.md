# feat(cli): an `oby` command over the loopback API with fixed exit codes

<!-- Roadmap R12-01 · Sprint 8 · R12 Developer workflows · effort M · risk low -->

### Sangam's screen

engine only

### Outcome

A script, CI step or git hook runs `oby run obi-ai-bot/oby "fix the lint" --wait` and gets one exit code it can trust. No more hand-written curl with the token on the command line.

### Status and scope

Proposed (roadmap R12-01, milestone R12 Developer workflows).

**Why:** Only oby-mcp (Swift, mcp/server, docs/mcp.md) reads obid's token today, and only as an MCP server. Scripts guess job states and token handling with curl. docs/install.md tells Linux users to curl with the token.

**In:**
- A new Swift executable `oby` in Package.swift, beside `oby-mcp`.
- Move the token and URL rules out of mcp/server/RunnerAPI.swift into one library target that `oby-mcp` and `oby` both import (a rule is written once).
- Subcommands: `oby status`, `oby jobs [--json]`, `oby job <id>`, `oby run <repo> <task|-> [--kind --agent --account --mode --check --title] [--id <key>] [--wait] [--timeout 30m] [--json]`, `oby wait <id> [--timeout]`, `oby stop <id>`, `oby routine run <id>`.
- Exit codes: 0 done, 1 failed or stopped, 2 usage, 3 waits for the owner (permission, question, limit or Confirm), 4 timed out (the job goes on), 5 obid not reachable or no usable token.
- `--wait` uses GET /v1/jobs/{id}/wait and reads the token again once on a 401.

**Out:**
- `oby inbox` and `oby answer` (R12-02).
- `--payload` on `oby routine run` (R12-04).
- Pairing a phone from the shell (R12-14 decides it).
- Any call to a non-loopback runner with the token: the token goes only to 127.0.0.1, localhost or [::1], as oby-mcp does.

### Actors and ownership: what obid owns

- Nothing new: every rule stays in the existing routes. Jobs started by the CLI carry no device signature, so they get no declared secrets (docs/mcp.md, 'No declared secrets').

### Actors and ownership: what the apps show and send

- Nothing changes for the apps. The CLI prints key=value lines, or JSON with `--json`.

### Steps

- Move RunnerAPI.swift's token, URL and send rules into a library target; make oby-mcp import it with no change in behaviour (MCPTests stay green).
- Add the `oby` executable target and its argument parser; exit 2 on any usage error before a network call.
- Map job status and `ask` to exit codes in one function, and test each CLI scenario against a stub runner.
- Implement `--wait` on GET /v1/jobs/{id}/wait with the 401 re-read, and `--timeout`.
- Send `--id` as the retry key from R02 on POST /v1/jobs.
- Write docs/contracts/cli.md and a 'Command line' section in docs/install.md that replaces the curl examples.

### Acceptance scenarios

- CLI-1 (proposed): Given obid runs and `api-token` is a 0600 file of the user's, when `oby run <repo> <task> --wait` starts a job that ends done, then it prints the job id and exits 0.
- CLI-2 (proposed): Given a job that ends failed or stopped, when `oby wait <id>` returns, then it exits 1.
- CLI-3 (proposed): Given unknown flags or a missing task, when `oby run` runs, then it prints usage and exits 2 without a call to obid.
- CLI-4 (proposed): Given a job that opens a permission, question or limit card, when `oby wait` sees it, then it exits 3 and names the inbox item.
- CLI-5 (proposed): Given `--timeout 1m` and a job still running after it, when the minute ends, then it exits 4 and the job keeps running.
- CLI-6 (proposed): Given obid is not listening or `api-token` is missing, readable by others or a link, when any command runs, then it exits 5 and never prints the token.
- CLI-7 (proposed): Given `--id k1` sent twice, when both calls reach obid, then one job exists and both print its id.
- CLI-8 (proposed): Given a token that obid rotated while `--wait` ran, when obid answers 401, then the CLI reads the token once again and goes on.
