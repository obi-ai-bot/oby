# feat(obid,ios): the iPhone attaches files over the sealed relay with a hash check

<!-- Roadmap R07-17 · Sprint 6 · R07 One wire contract · effort M · risk medium -->

### Sangam's screen

needs Sangam's design first

### Outcome

The owner attaches photos and files from the iPhone; a cut or reordered relay frame is refused, never kept as a wrong file.

### Status and scope

Proposed (roadmap R07-17, milestone R07 One wire contract).

**Why:** #1169 is open; POST /v1/attachments is not in the gateway allowlist (gateway.rs has no attachments entry), so attaching works only on the Mac.

**In:**
- Allow POST /v1/attachments for paired phones with a smaller cap that fits the relay
- The client sends the SHA-256; obid answers 422 on mismatch
- The iPhone composer shows attach only when obid's capabilities list the route

**Out:**
- Android (follows the same route later)
- Thumbnails in the thread (#1168)

### Actors and ownership: what obid owns

- The cap, the hash check, the allowlist entry.

### Actors and ownership: what the apps show and send

- Sangam's attach action in the composer.

### Interfaces and dependencies

- Add-only gateway allowlist entry for POST /v1/attachments.
- Add-only `sha256` request field.
- Add-only capability name in R06's list.

### Steps

- Confirm where obid handles POST /v1/attachments.
- Add the allowlist entry and cap.
- Add the hash check.
- Gate the iPhone composer on the capability.
- ATTACH-18 and 19 tests; real-iPhone upload.

### Acceptance scenarios

- ATTACH-18 (proposed): Given a paired phone sends a file whose SHA-256 does not match the bytes obid kept, when obid stores it, then it answers 422 and keeps nothing.
- ATTACH-19 (proposed): Given an obid that does not list the phone attachment capability, when the iPhone composer opens, then it shows no attach action.
