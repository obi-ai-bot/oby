## What
Oby's factory feeder runs one pipeline, written as code: the steps a task goes through are `ACTIVE` and `STEPS` in `factory/bin/oby-feed:122-123` and the functions after them (`intake_brief` 442, `spec_brief` 453, `start` 553, `ask_approver` 779, `lens_routing` 891, `lens_brief` 928). Which lens reviews which change is `routing` and `surface_reviewers` in `factory/config.json`, read by `factory/bin/route:25-38`. This task writes that pipeline as data, a list of steps in this repository's `oby.json` under `workflows.factory`, and makes `oby-feed` follow the list. Nothing obid does changes.

## Why
- **The owner, 2026-11-16:** the pipeline is ours, and people should be able to write their own "like T3 Code and OpenBot".
- **OpenBot keeps a workflow as steps a person defines** (trigger, prompt, agent, condition, approval, output), and a run keeps the steps it started with (`src/backend/workflows/workflow-schema.ts:1-40`).
- **Smallest step first.** Proving the format on the real factory, with no change to obid, is the cheapest way to get it right before obid runs it for everyone (B00-32).
- **Lane: dispatcher.** Which step runs next, and from which rule. Every step's work stays an agent's job, as today.

## How
1. **The format** (plan §4): `workflows.<name>` is a list of steps. Each has an `id` and a `kind`: `agent` (with `prompt`, a file path at the base), `build` (exactly one), `check` (with `run` and an optional `runsOn` role), `review` (with `prompt`; ends `VERDICT: APPROVE` or `VERDICT: CHANGES`), `approve` (with `prompt`; ends APPROVE or ESCALATE) or `owner` (waits for the owner). `when` is an object of header line names to the values that run the step (`{"SURFACES": ["ui"]}`), read from the earlier steps' answers.
2. **This repository's workflow**, in `oby.json` under `workflows.factory`, is today's pipeline exactly: intake, spec (when `DECISION` is `ACCEPT`), build, the gate and the proofs check, the lenses (code always; ux and ui for `ui`; security for `security`; proofs for `proofs` or `model`), the approver. Each prompt is the `.claude/agents/*.md` file it uses today.
3. **`oby-feed` reads it** from `oby.json` on `origin/<base>` at each pass. Its states and step names come from the list instead of `ACTIVE` and `STEPS`; `lens_routing` takes the review steps and their `when` instead of `factory/config.json`'s `routing` and `surface_reviewers`; a step's brief quotes its `prompt` file from the base, as the briefs do today.
4. **A task keeps the workflow it started with.** `oby-feed` saves the list in the task's state when it starts it, so a change to `oby.json` affects only tasks that start after it lands.
5. **A workflow that can't be read starts nothing.** If `workflows.factory` is missing or invalid, `oby-feed` starts no new task, says why in `--status`, and carries on with the tasks under way. It never falls back to steps in code.
6. **Machines stay where they are.** A `runsOn` role (`linux-gate`, `mac`) is looked up in `factory/config.json` (`remote_gate`, `mac_worker`), the owner's own file; `oby.json` names no host.
7. **Who runs each step** stays as it is today, and moves to B00-06's `factory.json` when that lands, keyed by these step ids (the plan's §7, item 4). `routing` and `surface_reviewers` stay readable for the Claude Code factory's `/factory run` until it reads the same list.
8. **Docs.** `docs/contracts/factory.md`: FEEDFLOW-1 to 5. `factory/README.md`: where the pipeline is written.

`factory/config.json` and `oby.json` are protected paths, so this change waits for the owner.
