# feat(obid,android): seal Android pushes as the iPhone's are (skip if Android is frozen)

<!-- Roadmap R07-16 · Sprint 5 · R07 One wire contract · effort S · risk low -->

### Sangam's screen

engine only

### Outcome

If Android stays in scope, Google carries only a sealed blob; the alert text is opened on the phone.

### Status and scope

Proposed (roadmap R07-16, milestone R07 One wire contract).

**Why:** push.rs sends FCM data messages with readable alert text (registration shape at push.rs:662: token, platform fcm, topic), while the iPhone path seals with HPKE `oby push v1` to a registered `sealKey` (runner-api.md:1309).

**In:**
- Android registers a sealKey with POST /v1/notifications
- obid seals FCM data with the same construction
- The app opens it in its messaging service
- Known-answer vector test

**Out:**
- Everything, if R03 freezes Android: close as skipped

### Actors and ownership: what obid owns

- Sealing; dropping plain FCM for a phone that registered a key.

### Actors and ownership: what the apps show and send

- The same alert as today.

### Interfaces and dependencies

- Add-only `sealKey` in the FCM registration body of POST /v1/notifications.

### Files

- core/crates/obid/src/push.rs
- apps/android/app/src/main/java/com/deskree/oby/
- docs/runner-api.md
- docs/contracts/alerts.md

### Steps

- Check R03's decision; stop if Android is frozen.
- Accept sealKey for fcm registrations.
- Seal the data; reuse the APNs sealing function.
- Open it on Android; add vectors both ways.
- ALERTS-9 test.

### Acceptance scenarios

- ALERTS-9 (proposed): Given an Android phone that registered a sealKey, when obid pushes an alert to it, then the FCM data holds only `sealed` and the phone opens it to the same alert the iPhone gets.
