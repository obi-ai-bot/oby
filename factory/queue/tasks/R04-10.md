# feat(obid): store the task chain's branch once and let follow-ups read it

<!-- Roadmap R04-10 · Sprint 3 · R04 One owner for job state · effort M · risk medium -->

### Sangam's screen

engine only

### Outcome

A task and all its follow-ups keep one branch and one pull request, whatever happened in between: a failed follow-up with no commits, an unpublished one with commits, a clone made again. Publish is offered only where it goes through.

### Status and scope

Proposed (roadmap R04-10, milestone R04 One owner for job state).

**Why:** #1859 (a follow-up with no commits loses the chain; a second PR new-blok #433 beside #430), #1861 (an unpublished follow-up with commits leaves its branch), #1846 (clone_root not updated for a job without a worktree after remake_marked_clone, jobs.rs:9141), #1779 (can_publish true while publish_action_of refuses). follow_up (jobs.rs:14582) derives the branch from one job's commits and published state instead of reading the chain.

**In:**
- Add `chain: Option<String>` (the root job id) to Job, add-only, in to_json as `chain`.
- A chain record on the root job's file (`chainRecord`: branch, madeBranch, pullRequest, cloneRoot, tip), written only by job/chain.rs, not in the API.
- follow_up reads branch and start point from the chain record: a follow-up carries the chain's branch whenever the chain has one and its PR is not merged or closed.
- remake_marked_clone updates the chain record's cloneRoot, so every job of the chain finds it.
- can_publish takes the carrier from chain.rs (the chain's tip), so the job's `canPublish` and push.rs's 'Ready to publish' agree with publish_action_of.
- At load, a job file with no chain gets one built once from follow_up_of links (a pure fn with fixtures of each old shape).

**Out:**
- Removing follow_up_of (the Swift apps read followUpOf).
- A separate home/chains/ store (two-file writes are the risk R04-15 studies).

### Actors and ownership: what obid owns

- The chain record, its branch, PR, clone root and tip; which job may publish.

### Actors and ownership: what the apps show and send

- Nothing new to draw: canPublish and the alert become right. The new `chain` key is read by nobody yet.

### Interfaces and dependencies

- Add `chain` (string, root job id) to the job object in GET /v1/jobs and the job event.

### Acceptance scenarios

- PUBLISHING-33 (proposed): Given a task with an open pull request whose follow-up failed in Prepare with no commits, when the owner gives it another round, then the new follow-up starts on the task's branch with its commits and publishing updates the same pull request.
- PUBLISHING-34 (proposed): Given a follow-up that carried the branch, made commits and was stopped before publishing, when the owner sends it words, then the next follow-up stays on that branch.
- PUBLISHING-35 (proposed): Given a task whose worktree was cleaned up and whose clone was made again, when the owner sends it words, then the follow-up finds the branch in the chain's clone.
- PUBLISHING-36 (proposed): Given a done job whose follow-up carries its branch, when the apps read it, then canPublish is false and no 'Ready to publish' alert is sent, while Publish anyway (PUBLISHING-9) still works.
- PUBLISHING-37 (proposed): Given job files written before this change (one chain of three, a lone job, a follow-up whose parent was deleted), when obid starts, then each gets a chain id and the same branch it ran on.
