# refactor(electron): words to Oby as a pending overlay keyed by the turn id

<!-- Roadmap R06-10 · Sprint 5 · R06 Events that clients only apply · effort M · risk medium -->

### Sangam's screen

uses an existing screen: apps/electron/src/renderer/src/ChatView.tsx and Composer.tsx (no visual change)

### Outcome

The owner's words show at once as they do now, and become obid's turn when obid's `turn` event with the same id comes; a send with no answer is sent again only with the same id. No conversation is matched by its text any more.

### Status and scope

Proposed (roadmap R06-10, milestone R06 Events that clients only apply).

**Why:** live.ts keeps `starting`, `expected`, `unanswered`, `alias` and `working` (live.ts:40-54) and matches a new conversation by the words' text (live.ts:556). `sent()` retries 3 times on status 0 (live.ts:938) with no written rule for how long obid remembers an id (it keeps it while the turn is in the conversation: Conversations::begin, conversation.rs:606).

**In:**
- A pending overlay in the renderer: an entry per send, keyed by the turn `id` POST /v1/plans already takes, holding what the screen shows now (words, files' previews, the new conversation's own id).
- An entry leaves when the `turn` event with that id is in the state; the new conversation's id comes from that turn's `conversation`.
- A send with no answer stays pending and is sent again only with the same id (POST /v1/plans answers `repeated`); a reconnect reads, it never sends new words.
- REST answers clear or fail an entry; they never write obid's state.
- Delete `starting`, `expected`, `unanswered`, `alias` by text, and their special cases in `apply`.
- docs/runner-api.md: how long obid answers `repeated` for an id (while the turn is kept: 500 turns, 200 conversations).

**Out:**
- A visible 'not confirmed' state: it needs Sangam's design; until then a pending send looks as it does today.
- obid-side delivery state (R05).

### Actors and ownership: what obid owns

- The turn id and `repeated` (Conversations::begin).

### Actors and ownership: what the apps show and send

- LIVE-15 (proposed): Given the owner sends words that start a conversation, when obid's `turn` event with that id arrives, then the pending entry goes and the conversation opened for it is obid's, whatever its text.
- LIVE-16 (proposed): Given two devices start conversations with the same words at once, when both turns arrive, then this window shows its own and not the other's.
- LIVE-17 (proposed): Given a send whose answer is lost (status 0), when the app sends again, then it sends the same id and obid adds one turn.
- LIVE-18 (proposed): Given the stream reconnects while a send is pending, when the snapshot arrives, then no words are sent again and the entry stays until its turn or its failure.
