## What
- **Finding from V01-44's own review** (its `round-1/review-pstack.md`, interrogate): suppose the base's `.gitattributes` marks a path `working-tree-encoding=UTF-16LE`, and a builder writes an ordinary UTF-8 file there, with an even byte count, holding a token. `test-run`'s `git add -A` reads the UTF-8 bytes as UTF-16LE. The blob it stores is CJK-looking text with no token in it. Both the payload and the scan copy hold that blob, so gitleaks finds nothing and the run goes to the VM.
- There, `git apply --index --binary` writes the file back in its working-tree encoding, and the token is in plain text in the slot's worktree. `write-tree` still matches, so the run starts.
- Reproduced against the real `test-run` and `oby-remote-gate` on `factory/tests/test_test_run_remote.py`'s harness. The base's scan was just as blind.
- It needs the attribute on the base, not only on the branch. When the same change adds it, the VM keeps the garbled text, but any later checkout of that tree restores the token.

## Why
AGENTS.md, "Non-negotiable": everything that leaves is scanned for secrets first. V01-44 assumed that a blob that is sent and a blob that is scanned are the same bytes, as they are for `filter=`. That holds here too, but the receiver undoes the conversion by itself.

## How
- Decide whether the scan also reads each changed file as its working tree holds it, or whether test-run refuses to send a change that touches a path with a `working-tree-encoding` attribute. The second is simpler.
- A test beside REMOTE-66.

### Files
- factory/bin/test-run (`to_send`), factory/tests/test_test_run_remote.py, docs/contracts/remote-gate.md

## Acceptance
1. With `working-tree-encoding=UTF-16LE` on the base and a UTF-8 token file under it, the run stays here and nothing is sent. The test fails on the code before the fix.
2. REMOTE-26 and REMOTE-66 pass unchanged.
