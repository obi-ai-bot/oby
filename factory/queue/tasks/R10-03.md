# feat(obid): a teammate's review request alerts with Accept and Decline

<!-- Roadmap R10-03 · Sprint 7 · R10 Finish the Obysphere client · effort S · risk medium -->

### Sangam's screen

uses an existing screen: the Mac banner drawn by apps/electron/src/main/notify.ts

### Outcome

The Mac banner for a teammate's review request has buttons, as AGENTS.md says every request that waits on the owner must, so the owner can answer without opening the window.

### Status and scope

Proposed (roadmap R10-03, milestone R10 Finish the Obysphere client).

**Why:** push.rs `answers` (line 196) gives buttons only to `permission` and `start`; a review_request alert has none (personCard.test.tsx peer_30 serves 'Review request from alex' with no answers). The receiving side stalls, and teammate approval waits up to its 2-hour expiry (map: 'Incoming review requests cannot be answered in the Electron app').

**In:**
- `answers` gives `Accept` and `Decline` for an `obiRequest` of type review_request, only when the banner shows its text whole (the existing `fits` rule) and the item has no `custom` condition.
- notify.ts sends the button's words to POST /v1/inbox/{id}/answer, as for other answers.

**Out:**
- The remembered options (they need the card, R10-04).
- Questions (their Answer takes the owner's own words, PEER-30).
- host_approval: approval on GitHub still needs its own signed Confirm.

### Actors and ownership: what obid owns

- Which answers a review request's alert carries (push.rs `answers`), decided once.

### Actors and ownership: what the apps show and send

- The Mac banner draws the served answers (notify.ts already draws `answers`). Phones are unchanged.

### Interfaces and dependencies

- No new key: `answers` on GET /v1/alerts gets values for one more item kind.

### Files

- core/crates/obid/src/push.rs
- apps/electron/src/main/notify.ts
- apps/electron/src/renderer/src/test/personCard.test.tsx
- docs/contracts/alerts.md

### Steps

- Extend `answers(kind, …)` in push.rs for review_request with the custom-condition check.
- Confirm notify.ts maps `Accept`/`Decline` to the inbox answer route; add the mapping if it does not.
- Change peer_30_the_mac_alert_says_who_and_their_words_as_plain_text so the review request is served with the two answers.
- Add ALERTS-9 to 11 to alerts.md and their tests.

### Acceptance scenarios

- ALERTS-9 (proposed): Given a teammate's review request whose typed text fits the banner, when obid serves GET /v1/alerts, then its answers are `Accept` and `Decline`, and a click answers the item once.
- ALERTS-10 (proposed): Given a review request with a `custom` condition, or text the banner cuts, when obid serves the alert, then it has no buttons and a click opens Home.
- ALERTS-11 (proposed): Given a review request answered on another device, when the banner's Accept is clicked, then obid answers `409` and nothing more is sent.

Contract: docs/contracts/alerts.md (existing, last ALERTS-8)

### Tests

- alerts_9_a_review_request_alert_has_accept_and_decline (new, unit test in core/crates/obid/src/push.rs)
- alerts_10_a_custom_condition_alert_has_no_buttons (new, push.rs)
- alerts_11_a_settled_review_request_click_sends_nothing (new, apps/electron/src/renderer/src/test/alerts.test.ts)

### Done when

- `scripts/oby-check.sh` passes.
- Real Mac: a rig request shows a banner with Accept; the click starts the review job.
