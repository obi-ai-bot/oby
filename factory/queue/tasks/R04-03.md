### Sangam's screen

engine only

### Outcome

obid has one place, job/lifecycle.rs, where a command meets a job and the next status and every side field are decided together. The two most-copied decisions move there first, with no behaviour change.

### Status and scope

Proposed (roadmap R04-03, milestone R04 One owner for job state).

**Why:** next_round (jobs.rs:14231) is called from 11 places in jobs.rs and 5 jobs/ modules and clears 17 fields by hand; the interrupted-or-failed rule (jobs.rs:7197-7222) is separate from Job::needs_you (job.rs:1661). Writes go through Jobs::update (jobs.rs:2734) but also through direct lock-and-save paths (message_as at jobs.rs:4400 saves on its own; Jobs::open saves on its own).

**In:**
- new: core/crates/obid/src/job/lifecycle.rs, a child module of job.rs (declared `mod lifecycle;` in job.rs) so it may later write private fields of Job.
- `pub enum Command` (closed): to begin with `NextRound` and `RunEnded(EndKind)`; `pub fn transition(job: &Job, cmd: &Command) -> Result<Change, Refused>`; `Change::apply(&mut Job)` writes the status and clears the declared field list.
- `Jobs::apply(&self, id, Command) -> Option<Result<Job, Refused>>` in jobs.rs (or jobs/lifecycle.rs) built on update_after, so stamp(), estimate, save, failures::observe and the job event stay as they are.
- Replace next_round's body and the work end closure's status decision with calls to transition; keep every caller's other edits.

**Out:**
- Stop, Try again, Running, Done and the restart path (R04-06, R04-07).
- Making status private (R04-08).
- Any change in the API, the wire statuses or the job file.

### Proofs (a trial)

The owner asked on 2026-11-14 to try machine-checked proofs on two real tasks, to see what they cost and what they catch that tests do not. This task and R04-04 are the two. A proof here is a Kani harness (https://model-checking.github.io/kani/): a test whose inputs are every value of their type, not a sample.

**Properties, fixed before the build:**

- `transition_answers_every_command_in_every_status`: for every status and every `Command`, `transition` returns `Ok` or `Err`. It never panics and never overflows.
- `jobstate_7_holds_in_every_status`: JOBSTATE-7 for every case, not one. Start from a job with every field of lifecycle's cleared list filled; for every status and every `Command`, when `transition` returns a `Change` that leaves the job queued for another round, every one of those fields is empty after `Change::apply`.

Prove they can fail: for the first, put a `panic!` on one arm of `transition`; for the second, drop one field from the cleared list.

**One line in core/Cargo.toml**, under `[workspace.lints.rust]`, so that `#![cfg(kani)]` does not fail clippy's `-D warnings` with "unexpected `cfg` condition name: `kani`": `unexpected_cfgs = { level = "warn", check-cfg = ['cfg(kani)'] }`.

**How the harnesses are written** (measured on `dev` on 2026-11-14 with Kani 0.68.0):

- They live at the end of job/lifecycle.rs in `#[cfg(test)] mod proofs {` whose first line is `#![cfg(kani)]`: a test module, so it adds nothing to obid_lines_limit, and ordinary `cargo test` skips it.
- `kani::any()` stands for every value of a type. Vary only enums and integers with it (the status, the command, the end kind, counters, the run token); every other field of the job comes from one fixed job the harness builds.
- Never compare text in a harness (`as_str()`, a reason, a name): the solver loops in `memcmp` and does not end. Compare enum values.
- No `kani::assume` but the ones this task lists, and no `#[kani::stub]`, `#[kani::should_panic]` or lowered `#[kani::unwind]`. A property that does not hold is a finding: say so in build.md and leave the property as written. Never weaken it, and never change lifecycle's code only to make it pass.
- Prove each harness can fail: break the rule it guards once (the task says how), see `VERIFICATION:- FAILED`, restore the code. A harness that stays green on the broken code is not done.

**How they run:**

- `cd <worktree>/core && CARGO_TARGET_DIR=<worktree>/core/target nice -n 15 cargo kani -p obid --tests --harness <name>`, one harness a run. A first build took 4 to 8 minutes and 3 GB; each run after an edit took 1 to 4 minutes.
- Run it directly, on this Mac, not through factory/bin/test-run: test-run would send it to the gate VM, which has no Kani. This is the trial's one exception to the builder's rule for Cargo commands.
- If `cargo kani --version` fails where the builder runs, do not install it: write "not proved: cargo kani is not installed" in build.md and finish the task on its tests. The proofs gate nothing: scripts/oby-check.sh does not run them.

**What build.md records, per harness:** the command, its last line (`VERIFICATION:- SUCCESSFUL` or `FAILED`), the verification time, how many runs it took to get there, the broken-rule run's result, and anything a proof showed that the tests had passed. This record is what the trial is for.
