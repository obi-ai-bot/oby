Design: docs/connections-screens.md (the answer to R11-01) and the owner's answer q054 in docs/decisions/2026-11-13-roadmap-answers.md: "A 'Custom MCP server' row in Settings > Connectors that opens the existing custom step (name, address, sign in with OAuth / API key / none), with a Remove button on each".

What. The first run's Knowledge step promises "Or add any MCP server in Settings after setup." (`FirstRun.tsx`). On obid, Settings › Connectors shows GitHub and Tetrix only (`Connectors.tsx`, `function Live`); the custom MCP server step exists only inside an Obysphere's Knowledge (`AddSourceModal.tsx`, used by `KnowledgeView.tsx`). R11-06 builds obid's registry (`GET/POST/DELETE /v1/connections`) and says "Out: any Settings screen"; no task builds the screen q054 decided.

Why. The app makes a promise on its first screen that Settings doesn't keep, and without the screen the registry R11-06 to R11-11 build can't be used by the owner.

How. As q054 says: a "Custom MCP server" row in Settings › Connectors (live) opens the existing custom step of `AddSourceModal` (name, address, and sign-in: API key or none here; OAuth's button once R11-09 is in), posts it to `/v1/connections` through main, and lists the owner's servers with a Remove button each. An API key goes to obid in the request body and is kept as obid's registry says (never in the window's settings or local storage). The words are Sangam's (the existing step's).

Acceptance (CONNECTORS scenarios, each a test named after it, against the mock obid):

2. Saving name, address and an API key posts one `POST /v1/connections` and lists the server; the key appears in no window storage.
3. Remove sends `DELETE /v1/connections/{id}` and the row goes.
4. An obid without the registry (`404`) shows the row disabled with obid's own reason, and nothing breaks.
