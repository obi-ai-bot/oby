# feat(obid): sign in to a registry server with OAuth

<!-- Roadmap R11-09 · Sprint 10 · R11 Connections: MCP, sign-in and the vault · effort M · risk medium -->

### Sangam's screen

engine only now; the screen needs Sangam's design first (R11-01). His AddSourceModal.tsx already has an OAuth / API key / None choice for an Obysphere's Knowledge, which may be the model he picks.

### Outcome

A registry row with auth oauth signs in through the server's own page once, in obid; agents use it through the broker without the token, as Tetrix works.

### Status and scope

Proposed (roadmap R11-09, milestone R11 Connections: MCP, sign-in and the vault).

**Why:** Most hosted MCP servers offer only OAuth (#1133); today only Tetrix can be signed in to.

**In:**
- POST /v1/connections/{name}/sign-in and DELETE (cancel), loopback only, signed words, answering the page to open, as /v1/tetrix/sign-in does.
- Tokens in the vault per address (oby.mcp.<name>.access / .refresh) through oauth.rs; the row's signIn state (idle, waiting, signedIn, error with words).
- A 401 upstream renews once and retries; never falls back to another secret.
- DELETE /v1/connections/{name} signs out first (OAUTH-2).

**Out:**
- Several accounts per server (#1133 asks; later).
- The screen (R11-01).

### Actors and ownership: what obid owns

- The sign-in, the tokens, their refresh and sign-out.

### Actors and ownership: what the apps show and send

- The sign-in page opens in the browser from the Mac app; the row's state on the screen R11-01 settles. Until then, nothing on screen.

### Interfaces and dependencies

- POST/DELETE /v1/connections/{name}/sign-in (new).
- signIn object on a connection (new key).

### Steps

- Add the sign-in routes on the R11-04 Client with the row's URL as the resource.
- Store tokens under oby.mcp.<name>.*; refuse `oby.` names in R11-06's secret field (already: Connection::problem).
- Make Connections::authorized take the access token for oauth rows, renewing through oauth.rs.
- Add CONNECT-12 to 15 with a fake OAuth MCP server (tetrix_api.rs pattern).

### Acceptance scenarios

- CONNECT-12 (proposed): Given an oauth row, when the owner starts its sign-in and the server's page redirects back, then obid keeps the tokens in the vault, the row says signedIn, and GET shows no token.
- CONNECT-13 (proposed): Given a signed-in row whose access token the server refuses with 401, when an agent calls a tool, then obid renews once, retries once, and the call succeeds or answers why.
- CONNECT-14 (proposed): Given a sign-out or a refused refresh, when a running job calls the row's tool, then nothing is sent and the answer says to sign in again in Settings.
- CONNECT-15 (proposed): Given a sign-in started from the gateway, when obid reads it, then it is refused.
