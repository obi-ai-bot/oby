The second of the simple factory's three tasks (B00-50, B00-51, B00-52). Sangam owns what the user sees: the canvas is a proposal, and his words lead.

## What
A project has no factory until its owner first sends it a task with `/factory`. That first task makes the factory, with nothing to set up, and runs in it. After that, `/factory` sends each task into the same factory. While the switch is off (B00-50), every factory route refuses and says where to turn it on, and `/factory` isn't offered.

B00-05 already plans the route this uses, `POST /v1/projects/{id}/factory/run` with `words`. This task adds three things on top of it: the switch, the factory being made on first use, and a mark on each job saying it came from the factory.

## Why
- **The owner, 2026-11-16:** "use "/" to send stuff to the factory and then it will create a factory for that project … Simplify it as much as possible!" No setup questions: a project's factory starts with the default steps, and Settings › Factory (B00-09) is there for anyone who wants to change them.
- **The default steps are the job's own lifecycle.** Prepare and Work (Build), Check (Test), Review, then Merge (`job.rs:162`, `Phase`). Nothing new runs. B00-32 later lets a project add steps around the build.
- **Lane: dispatcher.** Which project's factory a task goes to, and whether that factory exists. Nothing here reads, edits or runs anything for an agent, and obid makes no model call.

## How
1. **Off refuses.** While `factory` is false, every `/v1/projects/{id}/factory/*` route answers `409` with `code` `factory-off` and the words `The factory is off. Turn it on in Settings › Factory.`, and starts and writes nothing. `GET /v1/commands` (B00-02) leaves out the factory's entries.
2. **Only in a project.** `GET /v1/commands` offers `/factory` only for a conversation in a project. A conversation in no project gets nothing to pick, and the run route is always a project's.
3. **Made on first use.** The first run in a project gives that project `factory: {"since": <ms>}` in `projects.json`, in the same save that records the run, and answers `"created": true`. Later runs answer `"created": false` and leave `since` as it was. `GET /v1/projects` answers each project's `factory` (null until it's made). These are new keys: nothing is renamed or removed (add-only API).
4. **The job.** The words become one job of the project, started through `routes::dispatch` with the owner's signed body, as `POST /v1/jobs` starts one. So it's the owner's own work by MERGING-44 (b), and it merges by itself once its check and review pass (MERGING-45), unless the project asks before anything merges (B00-12). The job's project is set as it starts (PROJECTS-13). The job answers `"via": "factory"` everywhere a job is answered (`GET /v1/jobs`, `GET /v1/jobs/{id}`, its `job` event), so the app can list the project's factory work apart from its conversation work. Every other job answers `"via": null`.
5. **Off, then on.** Turning the switch off leaves running factory jobs to finish and keeps each project's `factory`. Turning it on again asks nothing and finds each factory where it was.
6. **Repeats.** A repeated `clientRequestId` answers the first run. A double click starts one job and makes one factory (R02).
7. **Docs.** `docs/contracts/factory-switch.md` gains FACTORYON-6 to 11. `docs/contracts/projects.md` describes the project's `factory` key. `docs/api/factory.md` (B00-05's) describes `created`, `factory-off` and `via`. `docs/api/projects.md` describes `factory`.
