# feat(obid): stable codes on obid's sentences and an explicit inbox kind

<!-- Roadmap R07-10 · Sprint 5 · R07 One wire contract · effort S · risk low -->

### Sangam's screen

engine only

### Outcome

Clients decide by a code, never by obid's English or an id prefix, so a reworded sentence no longer changes app behaviour.

### Status and scope

Proposed (roadmap R07-10, milestone R07 One wire contract).

**Why:** apps/electron/src/renderer/src/live.ts:247-248 decides by `i.id.startsWith('supervisor-')` and `startsWith('orchestrator-')`. obid sends refusals, failure reasons and card titles as English only.

**In:**
- An add-only `code` next to each user-facing sentence obid sends on refusals, failure `reason` and card titles (for example publish.branch-moved)
- An add-only `origin` key on inbox items; live.ts uses it
- A rule in runner-api.md: a client never parses obid text or ids; a code is never renamed

**Out:**
- Translating obid's text
- The rule table that replaces the orchestrator and supervisor (#1939)

### Actors and ownership: what obid owns

- The list of codes and origins.

### Actors and ownership: what the apps show and send

- Same words as today; clients may later map codes to Sangam's words.

### Interfaces and dependencies

- Add-only `code` on refusals and reasons.
- Add-only `origin` on inbox items.

### Steps

- Inventory the sentences clients branch on (grep the clients for obid strings).
- Add codes there first, not everywhere.
- Add `origin`; switch live.ts.
- Add both to the schema.
- Prove WIRE-12 red.

### Acceptance scenarios

- WIRE-12 (proposed): Given a stalled job's inbox item, when the Electron app reads it, then it decides 'takes no answer' from `origin`, and the same item with a different id still behaves the same.
- WIRE-13 (proposed): Given obid refuses a request with a sentence, when the client reads the answer, then a `code` from the documented list is present.
