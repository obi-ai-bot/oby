# feat(obid): the broker hands registry servers to every owner run, resolved per request

<!-- Roadmap R11-07 · Sprint 9 · R11 Connections: MCP, sign-in and the vault · effort M · risk medium -->

### Sangam's screen

engine only

### Outcome

Every owner's Claude Code, Codex and Cursor run, in either lane, gets the registry's servers through the one `oby` broker server with the job's token, so a job that lands on Cursor or moves tools keeps them. Removal or sign-out closes a server at the next call.

### Status and scope

Proposed (roadmap R11-07, milestone R11 Connections: MCP, sign-in and the vault).

**Why:** Today the broker gives only oby_ask_owner to Codex and Cursor and nothing to Claude (jobs.rs:10507-10510). #1073: Cursor jobs miss the owner's apps. Own-lane runs get only what the CLI's own config has (LANE-12), and boxed runs, Cursor and a run after a tool move get none.

**In:**
- tools/list on /v1/agent/mcp/{job} lists each usable row's tools as `<connection>_<tool>` (filtered by the row's tools allowlist), read from the registry on every request, no cached route table.
- tools/call forwards with the vault secret through Connections::authorized and upstream_rpc, after the secret scan of the arguments (as tetrix.rs scanned:305); a finding or a scan that can't run sends nothing.
- Results scrubbed (mcp.rs) and fenced; marks_on_result set for every registry tool (an answer marks the job where read).
- Each call recorded in connectionUses and vault/uses.jsonl.
- Claude gets the `oby` server in its --mcp-config when the registry has a usable row; Codex via codex::argv; Cursor via ACP session/new mcpServers.
- Foreign-lane runs (another Oby's, untrusted, Oby's review) get no registry server.

**Out:**
- OAuth rows (R11-09).
- Restarting warm sessions (R11-10).
- Agent-MCP plug-ins (#1074) and the Swift-era allowlist work in #1073.

### Actors and ownership: what obid owns

- Which runs get which servers, forwarding, the scan, scrubbing, marks and the use log.

### Actors and ownership: what the apps show and send

### Acceptance scenarios

- CONNECT-6 (proposed): Given a registry row and an owner's job, when its agent sends tools/list to its broker, then the row's tools are listed as <connection>_<tool>, limited to the row's tools allowlist when it has one.
- CONNECT-7 (proposed): Given the same row, when a Claude Code, a Codex and a Cursor job of the owner's each call one of its tools, then each call reaches the server with the vault secret and each job's connectionUses records it.
- CONNECT-8 (proposed): Given a running job that listed a row's tools, when the row is deleted, then its next call answers an error naming the removed connection and nothing is sent upstream.
- CONNECT-9 (proposed): Given any job given registry servers, when its files, transcript, environment, arguments and MCP config are read, then the row's secret is in none of them.
- CONNECT-10 (proposed): Given arguments that hold a vault secret or a built-in scan finding, when the agent calls a registry tool, then obid sends nothing upstream and answers why.
- CONNECT-11 (proposed): Given another Oby's job, an untrusted job or Oby's review, when its broker lists tools, then no registry tool is listed.
