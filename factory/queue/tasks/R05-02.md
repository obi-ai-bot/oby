# feat(obid): a durable delivery status on each owner's turn in a conversation

<!-- Roadmap R05-02 · Sprint 2 · R05 Durable words · effort M · risk medium -->

### Sangam's screen

engine only

### Outcome

Each message the owner sends in a conversation carries `delivery: {status, by?, why?, error?}` in the conversation file and in the `turn` and `conversation` events, so obid and the apps know whether it waits, runs, was answered, cancelled, failed or was cut.

### Status and scope

Proposed (roadmap R05-02, milestone R05 Durable words).

**Why:** Words that wait behind a turn live only in `Turns.waiting` (brain/turn.rs:88, memory). After `POST /v1/plans/cancel` they 'stay in the conversation unanswered' (docs/runner-api.md:2311) and nothing records that. The user turn has no status field (conversation.rs:33 `struct Turn`). Map problem 'In-flight turn state does not survive a restart' (high).

**In:**
- New module `delivery.rs` with a `Delivery` type and guarded transitions: `start` (queued -> starting), `confirm` (starting -> running, with `by`: the turn id that carries the words), `restore` (starting -> queued, with `why`), `finish` (running -> answered | failed | interrupted), `cancel` (queued | running -> cancelled). Any other move is refused and logged; a terminal status never changes.
- `Conversations::begin` writes the user turn with `queued` in the same file write as the turn.
- brain/mod.rs `plan`: `start` + `confirm` when `wait_turn` gives the words to a turn (every turn in `Next.turns` gets `by` = the latest turn); `finish` when the answer is kept (`respond`): `answered`, `failed` with a redacted `error` for `End::BrainFailed`; `cancel` from `POST /v1/plans/cancel` for running and waiting words.
- Keep what a replay needs: the attachment paths (today only names are on the turn; paths are in `Thread.uploads`), the attached jobs, and `signed` on the delivery.
- docs/runner-api.md: the `delivery` key on a turn, its open string values, and the cancel sentence.

**Out:**
- Recovery at start (R05-03).
- Replacing `Turns.waiting` and the locks (R05-04).
- Job words (R05-06).
- Any app change.

### Actors and ownership: what obid owns

- The delivery status, its transitions, and when each is written.
- What a queued delivery keeps to be replayed: words, attachment paths, jobs, signed.

### Actors and ownership: what the apps show and send

- Nothing changes for clients yet; the key is there for R05-08.

### Interfaces and dependencies

- Add-only: `delivery` object on a user turn in GET /v1/conversation and in `turn` and `conversation` events: `{status, by?, why?, error?}`; `status` is an open string.

### Acceptance scenarios

- DELIVERY-1 (proposed): Given no turn under way in a conversation, when the owner's words arrive by POST /v1/plans, then their turn is on disk with `delivery.status: queued` before the agent starts, then `running` with `by` its own id, then `answered` once Oby's answer is kept.
- DELIVERY-2 (proposed): Given a turn under way, when the owner sends two more messages, then both stay `queued` until the next turn takes them, then both are `running` with `by` the latest message's turn id, and `answered` together.
- DELIVERY-3 (proposed): Given a turn under way and words waiting, when POST /v1/plans/cancel names the conversation, then the running and the waiting words read `cancelled`, and their requests answer `none` as today.
- DELIVERY-4 (proposed): Given no agent session can answer (End::BrainFailed), when the turn ends, then its words read `failed` with an `error` that has every known secret taken out.
- DELIVERY-5 (proposed): Given a conversation file written before this change, when obid reads it, then its turns have no `delivery` key, are shown as before, and nothing changes them.
- DELIVERY-6 (proposed): Given a delivery that is `answered`, `cancelled`, `failed` or `interrupted`, when any transition is asked, then it is refused and the status stays; only `queued` may start or be cancelled before it runs.
