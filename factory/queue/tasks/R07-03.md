# spike: how obid's wire schema is made and how client types are generated

<!-- Roadmap R07-03 · Sprint 3 · R07 One wire contract · effort S · risk low -->

### Sangam's screen

engine only

### Outcome

A written answer (in the issue and as a short section of docs/contracts/wire.md) that chooses how the schema is produced, which generators make the TypeScript, Swift and Kotlin types, and how it joins R01's API snapshot.

### Status and scope

Proposed (roadmap R07-03, milestone R07 One wire contract).

**Why:** Four changes ask to derive the schema from Rust types (schemars, ts-rs, specta), but obid builds most answers with json! (2,081 json!( calls against 170 Serialize derives in core/crates/obid/src). Issue #921 found that Job::to_json (job.rs), the conversation summary and inbox Item::to_json are hand-built, so a derived schema would describe stored files, not the wire. jsonschema 0.58.6 is already a dependency (review.rs). R01 plans docs/api/obid-api.json as an API snapshot; two artifacts would drift.

**In:**
- Compare: (a) schemars on new wire DTO structs that to_json uses, (b) a hand-written JSON Schema held by tests, (c) a schema inferred from recorded answers
- Cost in obid production lines for each (obid_lines_limit in scripts/oby-check.sh)
- Pick a generator per language with a permissive licence (Apache-2.0 or MIT) that emits open enums
- Decide one location (docs/contracts/wire/) and how R01's snapshot uses the same file
- Decide the fixture corpus layout (one JSON per answer and event)

**Out:**
- Writing the schema
- Changing any client
