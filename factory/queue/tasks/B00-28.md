## What
After B00-27 the paths are data, but the rest of the merge rules are still constants the owner can't change without editing obid: the approvals a sensitive change needs (two, by different tools: `core/crates/obid/src/merge.rs:1393`, `merge.rs:1242`, the second-review rule at `core/crates/obid/src/jobs.rs:11528`), the review rounds before the owner is asked (`core/crates/obid/src/review.rs:77`, read at `jobs.rs:11936`), and the branches Oby doesn't merge into by itself (`merge.rs:66`, read at `merge.rs:483`, `893`, `1248`, and `core/crates/obid/src/memory.rs:132,188`). Each becomes a value of B00-27's `Rules`, with a third layer on top: the owner's word, kept on the repository's entry in obid's configuration and changed only from the owner's own app.

## Why
- **AGENTS.md, "Defaults: Oby forbids nothing":** these are defaults "each overridden by the owner's word". Today that word has nowhere to go.
- **Some repositories differ.** A repository whose protected branch is `release` can't say so; an owner who wants one approval for untrusted work, or a third reviewer, can't either.
- **T3 Code does it this way:** each setting has three layers (global, the person's project settings, `t3.json`) and the screen says where each value came from (`packages/shared/src/projectSettings.ts:21`, `apps/web/src/components/settings/SettingInheritance.tsx:106-115`).
- **Lane: dispatcher.** Which rules hold a job before it merges, and asking the owner. No model call.

## How
1. **The values.** `Rules` (core/crates/obid/src/rules.rs) gains `reviews.rounds` (default 3), `reviews.sensitive.approvals` (default 2, any of 0 to 5), `reviews.sensitive.differentTools` (default true) and `protectedBranches` (default `main`, `master`, `trunk`). The constants become the built-in defaults in `rules.rs` only; every reader above takes the job's `Rules`.
2. **The repository's file may raise, never lower.** B00-27's `oby.json` may also set `reviews.rounds`, `reviews.sensitive.approvals` (the larger of it and the built-in counts) and add `protectedBranches`.
3. **The owner's layer.** A `rules` object on the repository's entry in `config.json` (`core/crates/obid/src/config.rs:199`, beside `check` and `setup`): any key above, and for each list `add` and `remove`. It can add, remove or change anything, the built-in defaults included. It wins over the file and the built-ins.
4. **`GET /v1/repos/rules?repo=<owner/name>`** → `{repo, base, rules, sources, revision}`: the rules as they apply on the repository's default branch now, and for each value, or each list entry, its source: `obid`, `repository` or `owner`. `404` for a repository obid doesn't know.
5. **`PUT /v1/repos/rules`** with `{repo, rules, revision}` replaces the owner's layer whole. Signed words only: docs/contracts/signed-words.md gains the shape, signed by its Save button's label as the vault's routes are. `409` on a stale revision, `422 {problems: [{path, message}]}` for an unknown key or a bad value, never a silent fix; unsigned, it changes nothing. Not on the gateway: a paired phone doesn't change a rule. Kept like `POST /v1/repos/check` keeps a check: on the repository's entry, written whole.
6. **The factory reads it too.** `oby-feed`'s `security_paths()` asks this route for its repository instead of reading `merge.rs`'s text, so B00-27's regular expression goes.
7. **Docs.** `docs/api/github.md` (repositories) and `docs/api/routes.txt` gain the routes. `docs/contracts/repo-rules.md`: REPORULES-6 to 12. `docs/contracts/merging.md`: MERGING-7 and 13 to 16 say "the repository's protected branches (`main`, `master` and `trunk` unless its owner changed them)" and "the approvals its rules ask for (two, by different tools, unless its owner changed them)".

A repository with neither a file nor the owner's layer behaves exactly as on `origin/dev`. An older obid reading a `config.json` with `rules` refuses it (`deny_unknown_fields`), as for any key added there; R02-11's home format covers a downgrade once it lands.
