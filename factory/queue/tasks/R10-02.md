# feat(obid): an operation id makes an owner's Obi-to-Obi send safe to repeat

<!-- Roadmap R10-02 · Sprint 7 · R10 Finish the Obysphere client · effort S · risk low -->

### Sangam's screen

engine only

### Outcome

A retry over the phone relay or an MCP retry never sends a teammate's Oby the same question or review request twice.

### Status and scope

Proposed (roadmap R10-02, milestone R10 Finish the Obysphere client).

**Why:** POST /v1/obid/sphere/requests, POST /v1/obid/sphere/peers/{owner}/ask and oby-mcp's sphere_review_request (mcp/server/Server.swift:321) take no id: each call builds a new exchange. A lost answer over the relay (three relay fixes in a week: #1949, #1992, #2001) makes the client retry, and the teammate gets a duplicate, which also counts against its 5-open-per-owner limit (`busy`).

**In:**
- Accept an optional `operationId` in the body of the two routes and R02's `Idempotency-Key` header; the first exchange is the answer to a repeat, and nothing is sent again.
- Keep the receipt (operation id to correlationId) for the exchange's lifetime, through R02's receipt store.
- oby-mcp passes the MCP tool call id as `operationId`.

**Out:**
- Other mutating routes (R02).
- Any protocol change: the envelope's own id stays as it is.

### Actors and ownership: what obid owns

- The receipt and the decision that a repeat is the same send.

### Actors and ownership: what the apps show and send

- Nothing changes; clients that retry send the same id. oby-mcp sends its tool call id.

### Interfaces and dependencies

- Add optional `operationId` to POST /v1/obid/sphere/requests and POST /v1/obid/sphere/peers/{owner}/ask; accept `Idempotency-Key` as R02 defines it.

### Steps

- Read R02's receipt store and Idempotency-Key rules; reuse them, do not write a second store.
- In the requests route and the peer ask route, look up the receipt before the secret scan, the signature-use check and the send.
- Write the receipt in the same save as the new exchange; remove it when the exchange file goes.
- Pass the tool call id from Server.swift's sphere_review_request.
- Add OBIREQ-7 to 10 to the contract and the tests; document the field in runner-api.md.

### Acceptance scenarios

- OBIREQ-7 (proposed): Given a request sent with operationId X, when the same body comes again with X, then obid answers the first exchange and the fake Sphere sees one envelope.
- OBIREQ-8 (proposed): Given operationId X used for one body, when a different body comes with X, then obid answers `409` and sends nothing.
- OBIREQ-9 (proposed): Given a signed peer ask with operationId X that went, when the same signed body is retried, then the first exchange is answered and the used signature is not refused as reused.
- OBIREQ-10 (proposed): Given a client that sends no operationId, when it posts twice, then two exchanges go, as today.
