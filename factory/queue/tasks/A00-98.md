Contract: docs/contracts/merging.md (MERGING-38 to 41).

What. When obid hands a pull request to GitHub's auto-merge (MERGING-41, `Jobs::by_github` in `jobs/by_github.rs`), it records `job.auto_merge` for that head. From then on, every pass that finds the same head answers "handed to GitHub" (`crate::merge::handed()`) without asking GitHub whether auto-merge is still on: the follower's fields (`github::FIELDS`: `state,reviewDecision,mergedAt,baseRefName,headRefOid,statusCheckRollup,mergeable,mergeStateStatus,author`) carry neither `autoMergeRequest` nor the merge-queue entry. When the queue drops the entry (its Check fails on the combined code, or dev moved and the head conflicts), GitHub turns auto-merge off and leaves the pull request open at the same head. obid keeps saying GitHub will merge it, with no round and nothing for the owner, indefinitely.

Why. The owner's own work merges by itself through dev's merge queue. A queue drop is the commonest way a ready change fails to land (another change merged first), and today it is silent: the task looks like it is about to merge, for days. The factory's own feeder sees drops (A00-80) and rebuilds them (A00-96), but jobs obid armed itself, the owner's daily work, get neither. T3 Code's PR watch wakes the agent on a PR change, with fixed caps (`PullRequestWatchReactor.ts`: a 2-minute sweep, 8 failed reads, 10 wakes).

How.
- **Read the state.** Add `autoMergeRequest` (and, where `gh` gives it, the queue entry's state) to what the follower reads. Decode it as add-only fields of `PullRequest`.
- **Spot a drop.** A head obid armed whose pull request is open with no auto-merge request and no queue entry was dropped. Clear `job.auto_merge` for it and note the drop on the job (head, and GitHub's reason only if it is one of GitHub's enum values, else none).
- **Fix it once by itself.** The job gets one round on its own branch, the same kind and gates as MERGING-38's rebase round (only on a branch obid made, `--force-with-lease`). The round rebases onto the base, runs the check and pushes a new head, which follows the normal path: reviews, then arm again. It is one round per head and at most 2 per job, counted with `checks_rounds`. The agent hears fixed words naming the base; GitHub's check output is never put in its prompt (AGENTS.md, "From outside"); it reads the checks itself with `gh`.
- **Then say why.** Past that, nothing more happens by itself. For the owner's own work, the job's conversation gets a line in obid's words ("Not merged: GitHub's merge queue dropped it twice. …"), as A00-51 does for GitHub's refusals, with no card. Other work keeps today's `needs_you` hold.

### Formal verification
A Kani harness over the pure function that reads the queue state from the decoded fields (armed head, current head, state, auto-merge request, queue entry). It answers `InQueue`, `Merged`, `Dropped` or `NotArmed`; it is `Dropped` only for the head obid armed, open, with neither a request nor an entry; and it never answers `Dropped` for a new head. The loop logic (one round per head, then stop with a reason) is the `loops_fixed` design of `docs/models/oby_feed_loops.qnt` (A00-96), applied to obid's own armed heads. Each test below fails on today's code.

Acceptance (MERGING scenarios, each a test named after it, against the fake `gh` the merge tests use):
1. An armed head whose pull request comes back open with `autoMergeRequest: null` is seen as dropped at the next pass, and `job.auto_merge` is cleared.
2. The drop starts one rebase round on the job's own branch. Its new head is reviewed and armed again.
3. A second drop on the job, or a drop on a branch obid didn't make, starts no round. Own work gets the conversation line and no card; other work gets today's hold.
4. A head still in the queue, or merged, is never taken for dropped.
5. The agent's message for the round holds no text read from GitHub.
