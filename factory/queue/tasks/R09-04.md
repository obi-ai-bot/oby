# feat(obid): a bounded per-job trace of dispatcher steps, with outcome codes and no content

<!-- Roadmap R09-04 · Sprint 6 · R09 Ship and debug safely · effort M · risk low -->

### Sangam's screen

engine only

### Outcome

Every job keeps a small file of what the dispatcher did and how long each step took. A failure record carries it as evidence, the apps and agents can read it, and nobody needs obid.log to see where a job stopped.

### Status and scope

Proposed (roadmap R09-04, milestone R09 Ship and debug safely).

**Why:** failures.rs `to_json` always sends `"log": []`; the evidence is only the summary, the step string and the check tail. Crash detection reads reason text (`job::obids_doing`, a string prefix). #903 (E1.10) lost the Swift engine's failure study; #1650 says per-job logs already grow without bound.

**In:**
- home/jobs/<id>/trace.ndjson: one line per step with a fixed name (admit, prepare, setup, round, check, publish, rebase, stall, retry, account_move, park, restart_recovery, crash), start, duration, outcome code; never prompts, words, paths or output.
- A cap (for example 2,000 lines, oldest dropped) and removal with the job's other files.
- Failure records fill `evidence.log` from the trace's last 50 lines.
- GET /v1/jobs/{id}/trace (add-only) and a read tool on Oby's MCP (mcp/server).

**Out:**
- The post-mortem (R09-05).
- Replacing `obids_doing` everywhere: only the crash record reads the outcome code here.

### Actors and ownership: what obid owns

- The step names and outcome codes (a closed list in Rust, open as strings on the wire), the file, its cap and its removal.

### Actors and ownership: what the apps show and send

- Nothing changes for clients; the trace is readable through the API and the MCP tool.

### Interfaces and dependencies

### Steps

- Write trace.rs: an append with a cap, a closed enum of step names and outcome codes, no free text field.
- Call it at the existing step boundaries in jobs.rs (admission, prepare, each round, check, publish, rebase, stall, retry, account move, park, restart recovery, crash); one call per boundary, no new state.
- Fill `evidence.log` in failures.rs from the trace.
- Add the route and the MCP read tool.
- Remove the trace with the job (delete and cleanup).
- Write FAILURES-1 to 4.

### Acceptance scenarios

- FAILURES-1 (proposed): Given a job that runs a round and its check, when it ends, then its trace has admit, prepare, round 1 and check lines in order, each with a duration and an outcome code, and no line holds text from the agent or the owner.
- FAILURES-2 (proposed): Given a job whose trace reached its cap, when another step ends, then the oldest line is dropped and the file stays under the cap.
- FAILURES-3 (proposed): Given a job that failed, when its failure record is read, then `evidence.log` holds the trace's last lines.
- FAILURES-4 (proposed): Given a job that is deleted, when cleanup runs, then its trace is gone with it.
