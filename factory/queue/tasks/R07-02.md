# feat(obid): old clients keep the six released job statuses

<!-- Roadmap R07-02 · Sprint 4 · R07 One wire contract · effort S · risk medium -->

### Sangam's screen

engine only

### Outcome

obid can add a job state without breaking the iPhone builds already in people's hands: an old client gets the nearest released status, and the new state is in a new key.

### Status and scope

Proposed (roadmap R07-02, milestone R07 One wire contract).

**Why:** Shipped iPhone builds decode Job.Status as closed (apps/shared/Runner.swift:5). AGENTS.md:39 therefore forbids any new value, which blocks R04's state work. OpenBot's reasoning-efforts-v1 fallback gives an old client the nearest released value.

**In:**
- One function in obid that maps any internal status to one of queued, running, done, failed, stopped, interrupted
- `status` keeps the released values unless the request declares the capability `job-status-open-v1`
- A new add-only key `phase` carries the full state for every client
- The same rule for every event `job` payload

**Out:**
- Adding any new state (R04)
- The capability header itself (R06)

### Actors and ownership: what obid owns

- The mapping from each internal state to a released status, in one place, and the decision per request.

### Actors and ownership: what the apps show and send

- Nothing changes for clients today. New builds declare job-status-open-v1 after R07-01.

### Interfaces and dependencies

- Add-only key `phase` on Job and on the `job` event.
- Reads the R06 client capability header (for example `Oby-Capabilities`).

### Steps

- Find where Job::to_json writes `status` (job.rs) and where the `job` event is built.
- Add the mapping function and a test table for every state.
- Pass the request's declared capabilities to the serialisation; default is released values.
- Add `phase`; document both in runner-api.md.
- Prove WIRE-3 red with a test-only internal state.

### Acceptance scenarios

- WIRE-3 (proposed): Given a job in a state that is not one of the six released statuses, when a client that does not declare job-status-open-v1 reads it, then `status` is the nearest released value and `phase` names the real state.
- WIRE-4 (proposed): Given the same job, when a client that declares job-status-open-v1 reads it, then `status` is the real state.
