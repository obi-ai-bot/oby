# fix(obid): a run token so a stale worker cannot end a run Stop, Try again or a move took over

<!-- Roadmap R04-04 · Sprint 4 · R04 One owner for job state · effort M · risk medium -->

### Sangam's screen

engine only

### Outcome

Stop then Try again never loses the retry: the old worker's end is dropped and logged, and the new round runs. A move or a follow-up started in the same window never starts from a stale commit count.

### Status and scope

Proposed (roadmap R04-04, milestone R04 One owner for job state).

**Why:** #1649: stop marks the job Stopped at once while its worker still finishes; Try again's next_round sets it back to Queued; the old worker's end_done (jobs.rs:12211) checks only `status.is_active()` and marks it Done, so the retry is lost. schedule (jobs.rs:3698) already waits for the old worker to leave `workers` before starting the queued job, so only the end write needs a fence.

**In:**
- Add `run: u64` to Job (stored with serde default 0, not in to_json).
- Raise it inside lifecycle transitions for Start (schedule), Stop, NextRound (Try again, Another round, limit resume), move (jobs/moves.rs) and failover.apply.
- `work` reads the token when it is spawned and passes it to end_done, the work end closure (RunEnded) and every worker-side status write; transition refuses RunEnded/Finished when the token differs, and the caller logs `job {id}: run {n} ended after run {m} began; dropped`.
- Stop keeps its immediate stopped status (TASKS-18 unchanged).

**Out:**
- The owner's words taken too early (R04-05).
- Moving Stop and Try again fully into lifecycle (R04-06): this task adds only the token raise there.
- Any API key.

### Actors and ownership: what obid owns

- The run token, its raise on each takeover, and dropping a stale end.

### Actors and ownership: what the apps show and send

- Nothing changes for clients: the job no longer flips to done after a retry.

### Proofs (a trial)

The second task of the owner's trial of 2026-11-14 (R04-03's "Proofs (a trial)" says what it is). The run token is the kind of rule a proof suits: tests show that one stale end is dropped, a proof shows that no stale end gets through.

**Properties, fixed before the build:**

- `a_stale_end_is_refused`: for every status, every end kind and every pair of tokens, when the end carries a token that is not the job's `run`, `transition` returns `Err`.
- `every_takeover_raises_the_token`: for every status and every command that takes a run over (Start, Stop, NextRound, the move and the failover), when `transition` returns a `Change`, the job's `run` after `Change::apply` is greater than before. The harness may assume `job.run < u64::MAX`, and says so in its comment; it is the only `kani::assume` this task allows.
- `no_end_of_the_run_before_a_takeover_lands`: TASKS-20 and TASKS-21 as one rule. For every status, every such command and every end kind: apply the takeover, then offer an end that carries the token from before it. `transition` returns `Err`.

Prove they can fail: for the first and the third, take the token comparison out of `transition`; for the second, stop one of those commands from raising the token.

The line in core/Cargo.toml is R04-03's; if it is not on dev yet, add it here.

**How the harnesses are written** (measured on `dev` on 2026-11-14 with Kani 0.68.0):

- They live at the end of job/lifecycle.rs in `#[cfg(test)] mod proofs {` whose first line is `#![cfg(kani)]`: a test module, so it adds nothing to obid_lines_limit, and ordinary `cargo test` skips it.
- `kani::any()` stands for every value of a type. Vary only enums and integers with it (the status, the command, the end kind, counters, the run token); every other field of the job comes from one fixed job the harness builds.
- Never compare text in a harness (`as_str()`, a reason, a name): the solver loops in `memcmp` and does not end. Compare enum values.
- No `kani::assume` but the ones this task lists, and no `#[kani::stub]`, `#[kani::should_panic]` or lowered `#[kani::unwind]`. A property that does not hold is a finding: say so in build.md and leave the property as written. Never weaken it, and never change lifecycle's code only to make it pass.
- Prove each harness can fail: break the rule it guards once (the task says how), see `VERIFICATION:- FAILED`, restore the code. A harness that stays green on the broken code is not done.

**How they run:**

- `cd <worktree>/core && CARGO_TARGET_DIR=<worktree>/core/target ../factory/bin/test-run -- cargo kani -p obid --tests --harness <name>`, one harness per run. test-run sends it to a builder slot on the gate VM, where `factory/remote/setup.sh` installed Kani 0.68.0 for `oby-builder` (A00-35), and it runs there at nice 15 in the slot's own build folder. A first build took 4 to 8 minutes and 3 GB on a Mac, and each run after an edit took 1 to 4 minutes.
- Never run `cargo kani` outside test-run, and never install Kani. A proof counts only when test-run's output has `running in builder slot <N>` and a `VERIFICATION:-` line. If test-run says `on this Mac:` or `fell back to this Mac:`, or the VM can't run it (for example `no such command: kani`), don't run it again elsewhere: write "not proved: <test-run's or the VM's line>" in build.md and finish the task on its tests. The proofs gate nothing: scripts/oby-check.sh does not run them.

**What build.md records, per harness:** the command, its last line (`VERIFICATION:- SUCCESSFUL` or `FAILED`), the verification time, how many runs it took to get there, the broken-rule run's result, and anything a proof showed that the tests had passed. This record is what the trial is for.
