# feat(obid): memory stops asking twice and goes out on the event stream

<!-- Roadmap R12-10 · Sprint 9 · R12 Developer workflows · effort M · risk low -->

### Sangam's screen

engine only

### Outcome

A suggestion the owner declined is not asked again, and every memory change reaches the Mac and a paired phone as an event, ready for Sangam's screen.

### Status and scope

Proposed (roadmap R12-10, milestone R12 Developer workflows).

**Why:** `dismiss` (memory.rs 1974) keeps no record, so `find` can ask the same thing again. No `memory` event exists in events.rs, and gateway.rs allows no /v1/memory route, so suggestions pile up where no app sees them.

**In:**
- On dismiss, append the suggestion's NFKD-normalized text (memory.rs's normalizer) and scope to `home/memory/declined.jsonl`, newest 200.
- `find` and staged proposals drop a candidate whose normalized text equals a declined one or a saved memory.
- DELETE /v1/memory/declined clears the list.
- A `memory` event when a memory or suggestion is added, removed, used or declined.
- Add GET /v1/memory, DELETE /v1/memory/{id} and the suggestion remember and dismiss routes to the gateway allowlist.

**Out:**
- Any screen: no UI until Sangam designs one.

### Actors and ownership: what obid owns

- The declined list, the match rule and the event.

### Actors and ownership: what the apps show and send

- Nothing changes until Sangam's screen exists.

### Interfaces and dependencies

- DELETE /v1/memory/declined (new).
- SSE: `memory` event (new).
- Gateway: memory routes allowed (add-only).

### Steps

- Expose memory.rs's normalizer as one function used by `widens` and the declined match.
- Write and cap declined.jsonl (0600) on dismiss.
- Filter `find` and `suggest` against declined and saved memories.
- Add the DELETE route and the event, sent only after each save.
- Extend the gateway allowlist and its test.

### Acceptance scenarios

- MEMORY-1 (proposed): Given a dismissed suggestion, when `find` returns the same text with other accents or case, then no new suggestion is made.
- MEMORY-2 (proposed): Given 201 declines, when the next is written, then the oldest is dropped and the file holds 200.
- MEMORY-3 (proposed): Given a declined list, when DELETE /v1/memory/declined arrives, then it is empty and the text can be suggested again.
- MEMORY-4 (proposed): Given an SSE client, when a memory is saved, removed or used or a suggestion is dismissed, then one `memory` event arrives after the save.
- MEMORY-5 (proposed): Given a paired phone, when it calls GET /v1/memory through the gateway, then it is allowed, and PUT on the same path is not.
