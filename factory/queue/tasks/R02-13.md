# feat(obid): keep unknown keys on save, and load settings.json field by field

<!-- Roadmap R02-13 · Sprint 2 · R02 Commands that are safe to repeat · effort S · risk medium -->

### Sangam's screen

engine only

### Outcome

An older obid never deletes a newer field when it saves. One bad value in settings.json resets that value only, and the old file is kept.

### Status and scope

Proposed (roadmap R02-13, milestone R02 Commands that are safe to repeat).

**Why:** Job (job.rs:344), Settings (settings.rs:112), Thread (conversation.rs:85) and inbox Item (sphere/inbox.rs:386) drop unknown keys on save. conversation.rs:172 `Task` refuses them. settings::load (settings.rs:341) gives all defaults when the file does not parse, and settings::save writes over it. permissions.rs already copies a bad file aside before a save (#1652).

**In:**
- `#[serde(flatten)] extra: serde_json::Map` on Job, Settings, Thread, Task and Item.
- settings::load parses to a JSON object and decodes each field alone; a bad one gets its default and a warning.
- settings::save copies a file that did not read to settings.json.unreadable-<time> first, as permissions::save does.

**Out:**
- config.json.
- Removing deny_unknown_fields from request bodies (conversation.rs:2004 `Change` is a request, keep it).

- Copy aside before save as permissions::save does; share one helper.
- Write HOME-10 to 12.

### Acceptance scenarios

- HOME-10 (proposed): Given a job file with a key obid does not know, when obid changes and saves the job, then the key and its value are still in the file.
- HOME-11 (proposed): Given settings.json with a bad maxRunning and a good defaultAccount, when obid loads it, then maxRunning is the default and defaultAccount is kept.
- HOME-12 (proposed): Given settings.json that does not parse, when the owner saves a setting, then the old file is copied to settings.json.unreadable-<time> first.
