# feat(obid): a `secret` ask for missing secrets, answered on its own route

<!-- Roadmap R11-14 · Sprint 9 · R11 Connections: MCP, sign-in and the vault · effort M · risk medium -->

### Sangam's screen

needs Sangam's design first for the card (his design has no secret card, #899); the engine can merge first with the plain inbox row

### Outcome

When a check's secretspec.toml names secrets the vault lacks, or the conversation needs a key, Oby raises one `secret` inbox item naming them. The owner types the value into it; the value goes straight to the vault and never into a conversation, a turn, an answer's words or a transcript.

### Status and scope

Proposed (roadmap R11-14, milestone R11 Connections: MCP, sign-in and the vault).

**Why:** secretspec.rs fill (:1087) only notes missing check.<NAME> values in the check's notes; nobody is asked. The conversation has no tool to ask for a key, so it asks in words and the owner pastes it (#899), where it reaches the model provider and the conversation file.

**In:**
- Inbox kind `secret` with {name, why, replaces}; the name comes from obid, never from the answer.
- PUT /v1/inbox/{id}/secret {"value"} (loopback, signed words; not on the gateway at first): Vault::add, settles the item as saved, 204.
- POST /v1/inbox/{id}/answer on a secret item takes only 'Not now', never words.
- A brain tool `oby_request_secret` {name, why} in the R11-03 table (owner_only answer), refusing oby. names and a why the scan flags.
- One item per job for the missing check.<NAME> names when a check runs without them.

**Out:**
- Catching a key pasted into the owner's words (#899 part 3).
- Answering from the iPhone (later, once the route is on the gateway by the owner's word).

### Actors and ownership: what obid owns

- When to ask, the item, the name, the write to the vault.

### Actors and ownership: what the apps show and send

- The Mac shows the item where Sangam's design puts it (R11-01). Until then, the Mac shows it as a plain inbox row with Not now; the iPhone shows its title only (InboxItem.kind is a String in apps/shared/Runner.swift:422, so no closed enum breaks).

### Interfaces and dependencies

- Inbox kind `secret` (new value; Swift decodes kind as String).
- PUT /v1/inbox/{id}/secret (new, loopback only).

### Steps

- Add the `secret` kind to the inbox with its payload; refuse words on its answer.
- Add PUT /v1/inbox/{id}/secret using R11-12's write path.
- In secretspec.rs fill, return the missing names; raise one item per job from where jobs.rs calls it.
- Add oby_request_secret as a table entry (R11-03).
- Add VAULT-8 to 11a; update runner-api.md 'Inbox item' and 'obid only: secrets a check declares'.

### Acceptance scenarios

- VAULT-8 (proposed): Given a repository whose base secretspec.toml declares STRIPE_KEY and a vault without check.STRIPE_KEY, when a job's check runs, then one secret item names check.STRIPE_KEY and the check runs as today without it.
- VAULT-9 (proposed): Given an open secret item, when the owner's signed PUT /v1/inbox/{id}/secret carries a valid value, then the vault has the item's name, the item says saved, and the value is in no answer, event, inbox listing, conversation or log.
- VAULT-10 (proposed): Given an open secret item, when an answer with words reaches POST /v1/inbox/{id}/answer, then it is refused with 422 and nothing is kept.
- VAULT-11 (proposed): Given the conversation needs a key, when its agent calls oby_request_secret, then a secret item opens and the tool answers that the owner was asked in a secure card, never the value.
