What. The Mac's Obysphere membership (`home/sphere/membership.json`, `crate::sphere`) is not one of the stores A00-79 moves under a profile, and what another Oby sends (a teammate's review request, a question, a peer thread) names no profile. After A00-79 all of it is the default profile's: a review a teammate's Oby asks for runs on the default profile's accounts, in its clones, and its inbox item and thread show in the default profile.

Why. A company's Obysphere is that company's: its teammates' review requests should run on that company's profile, with its account and its repositories, and show up there. Today an Acme teammate's request would run on the Deskree profile's Claude Code account and land among Deskree's conversations.

How. A membership records the profile it belongs to: the profile current when it joined, the default one for a membership made before profiles (so an install with one profile changes nothing). Everything that arrives on it (review requests, questions, peer threads, inbox items) is handled in that profile: its jobs on that profile's accounts and vault, its items in that profile's `waiting`. What is Mac-wide stays Mac-wide (PROF-2: the gateway, devices, the relay key). The membership's profile is shown and changed in Settings › Obysphere only once Sangam has a screen for it (a question for the owner); until then it is set at join and never moves.

Acceptance (OBYSPHERE scenarios, each a test named after it):
1. A membership joined while profile B was current records B; a teammate's review request on it starts its review job in B, on B's account.

### The owner's answer (2026-11-15)
"Every profile sees it": an Obysphere membership is one for the whole Mac, shared by all profiles, and the requests it brings run in the default profile (with its accounts and vault). This replaces the assumption above that a membership belongs to the profile it was joined from; change the model's invariant to match before building.
