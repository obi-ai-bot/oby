Contract: docs/contracts/teammate-review.md, TEAMREVIEW-3 and TEAMREVIEW-4 (proposed there, with their words).

What. The receiving side of a teammate review. Two cases leave the asking Oby waiting for nothing today:
- A request for a repository that isn't in obid's `repos` (though the owner's GitHub login can push to it), or one the review can't start for (no repository the owner can push to, no signed-in account that can review, no job sandbox), is `accept`ed and then ends with a `failed` result, or isn't reviewed at all.
- A receiver with no `check` for the repository reviews anyway, and the asking Oby stops at "its checks didn't pass on it, or it has none" instead of asking the next teammate.

Why. Both make a teammate's pull request wait on an Oby that can't help it: the asking owner's merge stalls, and the teammate's own owner sees an accepted request that goes nowhere.

How. As TEAMREVIEW-3 and 4 say. A repository the owner's login can push to is reviewed and kept in `repos` (`config.repos.keep`), as the owner's own jobs do. A request the review can't start for is answered with `decline`, its note in obid's own words, never `accept` then `failed`; an inbox Accept for one closes the item with that reason. A receiver with no check answers a `result` with outcome `failed`, no findings, and obid's summary "This Oby has no check for <repo>, so it can't vouch that the tests pass." (never `changes_requested`), and the sender takes that as spent and asks the next teammate. Move both scenarios to Implemented.
