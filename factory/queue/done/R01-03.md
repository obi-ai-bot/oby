# chore(process): dev merges through GitHub's merge queue, gated by Check; main requires Check

<!-- Roadmap R01-03 · Sprint 1 · R01 Safety net · effort S · risk medium · rewritten 2026-11-13 by docs/ci-architecture.md -->

### Sangam's screen

engine only

### Outcome

No pull request lands in dev, by Oby, the factory or a person, until its batch passed Check in GitHub's merge queue. Up to 5 pull requests are tested together on top of dev and squash-merged in order, so the code that lands is the code that was tested. A pull request into main needs Check green. Oby needs no new code: obid's MERGING-41 already hands a merge GitHub routes through a queue to `gh pr merge --auto`, which queues it.

### Status and scope

Proposed (roadmap R01-03, rewritten by docs/ci-architecture.md, "The merge queue on dev").

**Why:** dev and main have no branch protection (`gh api …/branches/dev/protection`: 404), so the factory's `gh pr merge` lands before any CI starts, and a merge that ran only the tests its change reached broke others on dev (#2152, fixed by #2155). A queue tests the combined code once per batch instead of each pull request's full suite 2–3 times. dev is this repository's default branch, and merge queues are open to public organization repositories (GitHub docs, "Merging a pull request with a merge queue").

**In:**
- A repository ruleset on `dev` (owner step; "Require merge queue" is repository-level only):
  - require a pull request with 0 approvals
  - required status check `Check`
  - require merge queue: squash, build concurrency 1, minimum group 2 with a 15-minute wait, maximum group 5, every entry must pass, status-check timeout 60 minutes
- A ruleset on `main`: required status check `Check`, no queue
- AGENTS.md "How we work" and docs/ci.md: a merge into dev goes through the queue and needs Check (AGENTS.md is the owner's; the pull request proposes the lines, the owner merges)
- docs/contracts/merging.md: one cross reference from MERGING-41 to CI-7
- One real Oby job on this repository and one factory job, each proven merged through the queue

**Out:**
- Code changes in obid (none needed)
- The factory's own change to queue instead of merging (R01-12)
- A self-hosted Mac runner

### Steps

- After R01-02's ci.yml has run green on dev (a nightly run) at least once, the owner adds the two rulesets with the settings above. Record them with `gh api repos/obi-ai-bot/oby/rulesets` in the pull request.
- Dispatch one small Oby job on obi-ai-bot/oby. Record that GitHub refused obid's REST merge (`PUT …/merge` doesn't merge into a queue), that obid armed `gh pr merge --auto --match-head-commit` (MERGING-41), that the pull request entered the queue, and that it merged after the group's Check. Link the job and the pull request.
- Merge one factory pull request by hand with `gh pr merge <n> --auto`, and record that it queued.
- Write the AGENTS.md and docs lines and CI-7, CI-8.

### Acceptance scenarios

- CI-7 (proposed): Given dev requires the merge queue and Oby has learned to merge into dev, when Oby's job's pull request passes Oby's own rules, then obid arms GitHub's auto-merge pinned to that head (MERGING-41), the pull request enters the queue, and it lands only after its group's Check is green.
- CI-8 (proposed): Given a group's Check fails, when the queue removes the pull request, then it doesn't merge, and obid treats the failure as a red check on that head (MERGING-39: one round, then the owner's card).
- CI-21 (proposed): Given a group of several pull requests passes Check, when the queue merges it, then each lands in dev as its own squash commit, in queue order, and dev's head is the commit the group tested.
