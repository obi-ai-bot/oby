## What
The owner, 2026-11-22: "We do not share the browser with other people, only we can do like T3Code where we can have multiple devices to run stuff and on the browser you have the option to open on your current computer a server or something that is running as a localhost on the other computer just like T3Code does."

So: only the owner's own paired computers (docs/contracts/remote.md, COMPUTERS-n). An agent on devbox runs `npm run dev` on devbox's `localhost:3000`. A page the window draws on this Mac opens `http://localhost:3000` and gets devbox's server, with its `localhost` origin kept. Nothing is reachable by another person's Oby, a phone, the Obysphere or an agent.

This task builds obid's two ends. W01-31 puts the window's tabs on them.

**What Oby has on `dev`** (verify each before relying on it):
- **Computers** (`core/crates/obid/src/remote/`). Pairing is over SSH or with a code. Routes: a direct address is HTTPS with its certificate pinned (`pinned.rs`, `pinned::tls(pin)` gives a rustls `ClientConfig`). An SSH route is an `ssh -N -L` tunnel to the other obid's gateway on its own 127.0.0.1 (`tunnels.rs`). `reach::way` picks the best route that answers, and the supervisor moves between routes. The device token is in the vault as `oby.computer.<id>` (`computers.rs`).
- **The window's requests to another computer.** `forward.rs` (COMPUTERS-22) carries them as reqwest calls. Only obid's own token on loopback may name `Oby-Computer`; gateway or relay requests and agents' broker tokens get `400 not_the_window`. Only routes on the gateway's `COMPUTER_ROUTES` go (`gateway.rs`, about line 155), each with its screen. There are no WebSocket upgrades.
- **The gateway** forwards an allowed route to obid's router with `api.oneshot` (`gateway.rs` `forward`, about line 1026), as a fresh request. A hyper upgrade does not survive that.
- **The egress proxy** (`egress.rs`): obid's HTTP proxy on loopback, with a door per job and a token per door (`Proxy-Authorization`). It handles `CONNECT` and plain absolute-form `http://`. `Kind::Browser` is a box page's door, which main sets on a box partition's session and answers with the door's login (`apps/electron/src/main/browserGuest.ts`, `setProxy`, about line 130; `login`, about line 238).
- **The host's own ports.** `lib.rs` (about line 543) hands `browser.set_host_ports` obid's API port, its gateway's port and the `direct` listeners' ports. The box refuses those as `outside_box`.
- **A task's servers** (docs/contracts/task-servers.md). obid lists the ports a job's agent listens on, and `GET /v1/jobs/{id}` is already forwarded to a computer.

**T3 Code** (pingdotgg/t3code@1d028248, shallow clone):
- `apps/server/src/preview/PreviewTunnel.ts`. `GET /api/preview/tunnel?port=N`, a WebSocket upgrade, authenticated (`authenticateMediaRequest(AuthTerminalOperateScope)`). It dials `127.0.0.1`, then `::1`, within 5 s, before the upgrade "so a dead port fails the handshake instead of an open socket". The server's own port is refused ("Tunnelling to this server would hand the page an unauthenticated loopback client"). Each refusal is `403` with `x-t3-tunnel-port-refused` ("Not 502: Cloudflare … swaps an origin 502"). The tunnel pumps raw bytes both ways, waits on the socket's drain past 1 MiB, and closes when its session is invalidated or the tunnel is switched off.
- `apps/desktop/src/preview/LoopbackTunnel.ts`. Desktop main runs one SOCKS5 listener per environment, on 127.0.0.1 port 0. The partition's proxy is `socks5://127.0.0.1:<port>` with `proxyBypassRules: "*,<-loopback>,169.254.0.0/16,fe80::/10"`, so only loopback goes to it. `0.0.0.0` and `[::]` are redirected to `localhost`, and a WebSocket to them is cancelled. A connection to a non-loopback host is refused `NOT_ALLOWED`. Each connection asks the renderer for a fresh ticketed tunnel URL and rides its own WebSocket. It "never falls back to a direct local connection". Forwards are capped at 64 connections.
- `docs/internals/remote.md` ("Desktop previews tunnel loopback"). "Chromium can't authenticate to a SOCKS proxy, so any local process can connect to the listener and ride this user's tunnel"; T3 checks the client's uid only on Linux.

## Why
Board 14 promises that a page of devbox's agent shows devbox's `localhost`. Since the browser moved to the window's own `<webview>` (docs/plans/browser-t3.md), that page is drawn on this Mac, and on `dev` its `localhost` is this Mac's. Nothing in obid can carry a TCP connection to another computer's loopback. `forward.rs` carries whole HTTP calls only.

## How
Port T3's tunnel: one WebSocket per TCP connection, raw bytes both ways, to the other computer's loopback only. Two choices differ from T3. Each is marked `ponytail:` with its reason:

- **The listener on this Mac is an egress door, not a SOCKS5 listener in main.** Chromium can't authenticate a SOCKS proxy. On macOS, any local process could ride T3's listener, Oby's box included: its Seatbelt profile allows `localhost:*` (`sandbox.rs`, about line 906). obid's egress door already is an authenticated HTTP proxy, and main already answers its login (box partitions). The device token is in obid's vault, and main never holds it. So the Mac's hop is in obid.
- **There is no ticket.** T3's renderer mints a media ticket because the renderer holds the credentials. Here obid holds the computer's device token and sends it itself, over the pinned or SSH route. No credential leaves obid.

### 1. The other computer: `GET /v1/preview/tunnel?port=<1-65535>` (COMPUTERS-26)
- It is served by the gateway itself, beside its pairing endpoints, not through `forward`/`oneshot`, so the upgrade survives. It is listed in `COMPUTER_ROUTES` with its screen ("a page's localhost in the window, board 14"), so `allows_computer` names it and `gateway.rs`'s list test covers it.
- Only a computer's own device token reaches it, through the gateway listener or a `direct` address. Any other caller gets `404`, as an unlisted route does: a phone's token, no token, the Obysphere relay (`Relayed`), obid's loopback API, or a request naming `Oby-Computer`.
- A bad port or no `Upgrade: websocket` is `400`.
- obid's own ports are refused: the list `lib.rs` already gives `set_host_ports`, kept once at start, never recomputed. The refusal is `403` `{"reason": "own_port"}`.
- It dials `127.0.0.1:<port>`, then `[::1]:<port>`, within 5 s, before the upgrade. Nothing listening is `403` `{"reason": "nothing_listens"}`. Use a 403, not a 502, as T3 does, so a proxy can't swap it.
- Then it upgrades and pumps binary frames to and from the socket until either side closes. It holds no more than 1 MiB unsent. It closes when that pairing ends (`DELETE /v1/pairing`, or revoking it there, COMPUTERS-16).
- Never another host: the dial is only to the two loopback addresses, from a port number.

### 2. This Mac: a computer's door (COMPUTERS-27)
- `egress.rs` gets `Kind::Computer(<id>)` and `Egress::open_computer(id)`, made as `open_browser` is. The door's `CONNECT host:port` and plain `http://host:port/…` go only to a loopback name: `localhost`, `*.localhost`, `127.0.0.0/8`, `::1`, or IPv4-mapped loopback. Anything else is refused, `403`, and nothing is dialed.
- Each connection is carried to the computer's `GET /v1/preview/tunnel?port=<port>`, over `reach::way`'s best route:
  - a direct route: `wss://` with `pinned::tls(pin)` as tokio-tungstenite's rustls connector;
  - an SSH route: `ws://127.0.0.1:<tunnel port>`.
  The device token comes from the vault, in `Authorization`. obid already depends on `tokio-tungstenite`; no new dependency.
- It never dials this Mac's own loopback. A computer no route reaches, a refusal there, or a cut connection is a closed connection, never a local one (T3's "never falls back"). A plain `http://` request is forwarded as `plain` forwards one, one request per connection, the door's `Proxy-Authorization` taken out.
- At most 64 connections per door at once. The 65th is closed at once (T3's `MAX_FORWARD_CONNECTIONS`).
- The door ends with its computer: `DELETE /v1/computers/{id}` closes it and every connection it carries.

### 3. The route main asks for it (COMPUTERS-28; add-only)
- `POST /v1/computers/{id}/door` answers `{"proxy": "http://oby:<64 hex>@127.0.0.1:<port>"}`, the shape `BOX_PROXY` already takes in `browserRelay.ts`, for a computer this Mac keeps. Asked again, it gives the same door.
- An unknown computer is `404 no_such_computer`.
- Like every `/v1/computers` route, it is this Mac's only (COMPUTERS-22). Only obid's own token on loopback may ask: an agent's broker token, a paired device or the relay gets `403`. It is never through the gateway.
- The door's token is a secret in the vault's sense: out of every log line, event and other answer, as a box door's is.

### Whose state (AGENTS.md, "Dispatcher, not harness")
The dispatcher's: which computer a page's loopback goes to, and over which route. The door lives in obid's memory only. Nothing is written to disk, and nothing is added to `home/computers.json`.

### The rules this keeps
- **Own computers only:** a computer's token, as paired by the owner (COMPUTERS-7, 13). Never the Obysphere (COMPUTERS-8).
- **Secret scan:** the bytes go between the owner's own two paired computers over the pinned or SSH route, as COMPUTERS-22's answers do. Nothing goes to a third party, so no scan is added. If the security review reads "everything that leaves" as covering this, stop and ask the owner.
- **Add-only:** one route on each side, one door kind, two `reason` values on a new route. Nothing is renamed or removed.
- **Not an agent's:** no agent gets a door, and no broker token reaches either route.
