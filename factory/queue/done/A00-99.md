What. Two things in `factory/bin/job` stop the factory when nobody is watching.
- **A long-running reader holds every job's lock.** `load()` takes an exclusive `fcntl.flock` on the job's `.lock` and keeps it in `_locks` "until this process exits". `all_jobs()` loads every job. That is right for a one-shot command, but `factory/bin/oby-feed` imports the module and calls `job.all_jobs()` on every pass (`ready_tasks`) while it loops for hours, so after its first pass it holds every job's lock. Any `job advance` hangs, and so does any other command that loads jobs, because `require_slot` calls `all_jobs()` too. This was seen live on 2026-11-15: five `job advance` calls hung for 11 to 29 minutes, until the feeder was stopped.
- **Merging dev brings a closed task back.** A build closes its task by moving `factory/queue/tasks/<KEY>.md` to `factory/queue/done/<KEY>.md` (or by copying it into `done/` when the task isn't on dev yet). When dev adds or changes `tasks/<KEY>.md` afterwards (the orchestrator queues the task file, or edits its DEPENDS), merging dev into the branch puts `tasks/<KEY>.md` back next to `done/<KEY>.md`. `check_task_closed` then refuses `advance gate` ("the branch doesn't close its task"). This happened three times on 2026-11-15, to A00-67, A00-70 and A00-91.

Why. The factory has to run with nobody watching. A lock nobody releases freezes every other step behind it, and a refusal the factory could settle itself sends a job back to a person for a file move.

How.
- **Reading takes no lock.** `load()` reads `job.json` without a lock (writes are already atomic: `save` writes a temp file and renames it). The lock is taken only by what changes a job: a new `load_for_update(job_id)`, used by `advance`, `merge`, `answer`, `feedback`, `reject`, `agents` and `sync`. It is held only while the command reads, decides and saves, and released when it ends (a context manager), never kept for the process's life. `all_jobs()` and `job queue` read without locks, and `require_slot` reads without locks too. The other job's state it counts may be a moment old, which is acceptable for a slot count.
- **Re-close the task the factory itself undid.** Before `check_task_closed` refuses, `advance gate` looks at the job's branch. If `done/<KEY>.md` is there and `tasks/<KEY>.md` came back from the base (it is in `origin/<base>`), it removes `tasks/<KEY>.md` on the branch, makes `done/<KEY>.md` the base's text of the task (the one the orchestrator last committed), commits that as "chore(factory): close <KEY> again after merging <base>", pushes it as the job's other pushes are made, and goes on. It refuses as today when the branch has no `done/<KEY>.md` at all, or when `tasks/<KEY>.md` on the branch differs from the base's (the builder changed it: a person decides).

### Formal verification
Two red proofs, kept as the tests below. Both were run on 2026-11-15 against `factory/bin/job` as on origin/dev, in scratch copies:
- A process that imports the module and calls `all_jobs()` once, then keeps running (as oby-feed does), still holds the job's `.lock`: a second process's non-blocking `flock` on it fails with `BlockingIOError`.
- In a git repository where a branch adds `factory/queue/done/A00-99.md` and dev then adds `factory/queue/tasks/A00-99.md`, merging dev into the branch leaves both files in `HEAD`, so `check_task_closed` refuses.

No Quint model: no protocol decides here, only whether a lock is held and a file is in place.

Acceptance (tests named after each scenario):
1. JOBLOCK-1: with a process that imported the module and called `all_jobs()` still running, a second process's `job advance <job> <stage>` completes within a few seconds.
2. JOBLOCK-2: two `advance` calls on the same job, at once, are still serialized: neither loses the other's save.
3. JOBLOCK-3: a command that loaded a job for update releases its lock when it ends, including when it refuses.
4. TASKCLOSE-1: a branch with `done/<KEY>.md` whose merge from dev brought `tasks/<KEY>.md` back advances to `gate` after one "close again" commit, and `check_task_closed` passes on it.
5. TASKCLOSE-2: a branch with no `done/<KEY>.md`, or one whose `tasks/<KEY>.md` differs from the base's, is refused as today.
