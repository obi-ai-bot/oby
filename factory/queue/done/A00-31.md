TITLE: perf(factory): builders run their Rust builds and tests on the gate VM, in slots, not one at a time on the Mac

The factory has to roughly triple its pace (the owner, 2026-11-14: about 135 roadmap tasks left and two days). The bottleneck is this Mac, not the models: its load average sits at 31 to 37 on 10 cores. Every builder's heavy run (cargo build, test, clippy, nextest) goes through `factory/bin/test-run`, which lets only one heavy run at a time take `~/Library/Caches/oby-factory/test-run.lock`, at nice 15 and half the cores, while the gate's macOS part also runs here. Each job also builds obid from scratch in its own worktree's `core/target` (3 to 10 GB each; the disk is down to about 39 GB free). Builders report waiting on that lock for long stretches. Meanwhile the gate VM (`remote_gate`, `oby-gate`, 32 cores) is busy only while a gate runs.

Do this:
- `factory/bin/test-run` sends a heavy run that doesn't need macOS (no sandbox-exec, Keychain, Swift or Xcode suite: use the same rule the gate uses to decide what runs on the Mac) to the gate VM, the way `factory/bin/gate` sends a gate's Linux groups: the worktree's current tree (committed and uncommitted, but never untracked secrets or anything gitignored), run in a slot, the output streamed back, the exit code returned. The builder's command line stays the same.
- Builders share the VM's slots with gates; a gate never waits for a builder's run (gates first, or slots set aside for gates).
- The number of VM slots comes from `remote_gate` in `factory/config.json` (default 4, today's), so a bigger VM can get more slots by setting it.
- Each slot keeps its own Cargo build folder between runs so a rebuild is incremental, without A00-23's stale-build bug: a crate built from another worktree must never stand in for this one's (prove it with a test that fails the old way).
- When the VM can't be reached, is stopped and can't start in 3 minutes, or every slot is busy past a timeout, the run falls back to this Mac exactly as today.
- macOS-only runs keep today's lock. Nothing secret goes to the VM, the SSH arguments stay quoted and checked as `gate`'s are, and the run's user on the VM has no sudo.
- Also prune a job's `core/target` once the job is merged or rejected (`factory/bin/job` already knows when), so finished jobs stop holding gigabytes.

Prove it: a builder's `cargo test -p obid --test <one>` run through test-run lands on the VM, two builders' runs go at once in two slots, a macOS-only suite still runs here under the lock, and the fallback works with the VM stopped. Report how long a cold and a warm obid test build takes in a slot.
