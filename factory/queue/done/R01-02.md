# chore(ci): one ci.yml: lanes, a nextest archive in 4 shards, and one Check for pull requests, the merge queue and the nightly run

<!-- Roadmap R01-02 · Sprint 1 · R01 Safety net · effort M · risk medium · rewritten 2026-11-13 by docs/ci-architecture.md -->

### Sangam's screen

engine only

### Outcome

One workflow, `.github/workflows/ci.yml`, replaces linux.yml. It runs in three modes, and one job named Check says pass or fail for each run:
- **pull request (ready):** plan, gitleaks, fmt and clippy only, about 5 billed minutes.
- **merge queue (`merge_group`):** everything the batch's combined diff reaches, the whole Rust suite built once and run in 4 nextest shards.
- **nightly on dev, and `workflow_dispatch`:** everything, the only runs that save caches.

Each shard keeps a JUnit report, and Check's summary names any test that passed only on a retry.

### Status and scope

Proposed (roadmap R01-02, rewritten by docs/ci-architecture.md, "Trigger matrix" and "Each run's cost").

**Why:** linux.yml runs the whole suite in one 60-minute job on every ready pull request, has no single status to require, and doesn't listen to `merge_group`, which a merge queue's required check needs ("If a merge queue requires a GitHub Actions check, trigger the workflow with the merge_group event", GitHub's troubleshooting required checks). A workflow skipped by a path filter leaves its check Pending and blocks merging, so lanes must be jobs skipped by `if:` (a skipped job reports success), never workflow-level `paths:`.

**In:**
- A `plan` job: lanes from the paths changed. For a pull request that is the PR's diff; in the queue, `merge_group.base_sha..head_sha`; nightly, everything. It also runs gitleaks over that range (today's scan logic). The lane table is docs/ci-architecture.md's, copied into docs/ci.md.
- `lint`: `cargo fmt --check` and `cargo clippy --workspace --all-targets --locked -D warnings`
- `rust-build`: `cargo nextest archive --workspace --locked`, uploaded with retention 1 day
- `rust-test` × 4: `cargo nextest run --archive-file … --workspace-remap . --partition slice:k/4 --profile ci --no-fail-fast`, with bubblewrap and gitleaks set up as today, each uploading `target/nextest/ci/junit.xml` (retention 14 days)
- `e2e`, `control-plane` (as today), `electron` (new: Node 22, `npm ci`, typecheck, test, build in apps/electron), `tools` (new: `cargo test` for tools/oby-check-blok), each only when its lane is reached
- `Check`: `needs` every job, `if: always()`, fails when any needed job failed or was cancelled or `plan` failed; writes the lane set and the flaky tests to the step summary
- Modes by event, as in the design's trigger matrix: pull request into dev = plan + lint + Check; label `full-ci` or a pull request into main = everything its lanes reach; `merge_group`, `schedule`, `workflow_dispatch` = everything their lanes reach (nightly: all)
- `concurrency`: cancel older runs of the same pull request only; never `merge_group` or nightly
- `core/.config/nextest.toml`: a `ci` profile with `retries = 1`, JUnit, `slow-timeout`; R01-13 adds the quarantine overrides
- rust-cache with one `shared-key` per job kind and `save-if` only on schedule and dispatch (R01-01's rule)
- delete linux.yml in the same pull request

**Out:**
- Apple suites (they stay on the Mac)
- The ruleset and merge queue settings (R01-03, the owner's step)
- The quarantine list's entries (R01-13)
- macOS or larger runners (billed even on a public repository) and self-hosted runners

### Steps

- Spike first, on a throwaway branch: install a pinned cargo-nextest (`taiki-e/install-action` by SHA); run `cargo nextest run --workspace` once in one job and compare with `cargo test`. nextest runs each test in its own process, so watch `tests/swift_client.rs`'s per-process build, and check that `CARGO_BIN_EXE_obid` and the fixtures under `tests/` resolve from an archive with `--workspace-remap`. If nextest can't run obid's tests as they are, shard by test binary (`cargo test --test <name>` lists) and say so in the pull request.
- Write `plan` with a pinned paths-filter action (it supports `merge_group`) or a short `git diff --name-only` script; output one boolean per lane.
- Write the jobs above; put the shared setup (toolchain, bubblewrap, gitleaks) in a local composite action under `.github/actions/` only if it removes real repetition.
- Write `Check`.
- Prove each scenario on throwaway branches with `workflow_dispatch` or a `full-ci` pull request, and link the runs, red ones included.
- Record in docs/ci.md the measured billed minutes of one pull-request run and one full run (the design's numbers are estimates).

### Acceptance scenarios

- CI-3 (proposed): Given a ready pull request that changes only `docs/**` or `factory/**`, when the workflow runs, then only `plan` and `Check` run and Check passes.
- CI-4 (proposed): Given a run in the merge queue whose group changes `core/Cargo.toml`, when the workflow runs, then every lane runs.
- CI-5 (proposed): Given one Rust shard fails, when the workflow ends, then Check fails and its summary names the shard and the test.
- CI-6 (proposed): Given `plan` fails, when the workflow ends, then Check fails rather than passing over skipped lanes.
- CI-17 (proposed): Given a ready pull request into dev that changes `core/`, when the workflow runs, then it runs plan, gitleaks, fmt and clippy and no test job.
- CI-18 (proposed): Given a `merge_group` run that changes `core/`, when the workflow runs, then the Rust suite is compiled once (`rust-build`) and its tests run across 4 shards, each uploading a JUnit report.
- CI-19 (proposed): Given a test that fails once and passes on its retry in a `merge_group` or nightly run, when the workflow ends, then Check passes and its summary lists the test as flaky.
- CI-20 (proposed): Given any run but `schedule` or `workflow_dispatch`, when it ends, then it has saved no cache.
