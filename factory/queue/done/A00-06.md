R02-01 (#2147, merged into dev as 44412fcb) made a job's in-memory state follow its saved file, and kept the restricting marks in memory when a save fails, through `carry_marks` in core/crates/obid/src/jobs/keep.rs. Its round-6 security review (factory/jobs/002-r02-01-send-a-job-event/round-6/review-security.md) found that `carry_marks` misses two restricting marks:

- `withheld`, set when a job reaches chatgpt.com (the update near core/crates/obid/src/jobs.rs:5145, whose result is ignored). Losing it on a failed save gives the job's own check the owner's declared secrets, which MERGING-30 forbids.
- `check_withheld`, set when a check ran without the declared secrets (core/crates/obid/src/jobs/secrets.rs). Losing it lets that check count for the Mac's checks, so the pull request can merge without the owner's Merge (MERGING-2).

Before R02-01 both marks stayed in memory on a failed save, so this is a regression on dev.

Fix: `carry_marks` keeps `withheld` and `check_withheld` (fail closed, like the other restricting marks), and the existing failed-save test covers every restricting mark, so a mark added later without being carried turns it red. Prove the test fails without the fix. Don't raise `obid_lines_limit` or `jobs_rs_limit`: cut lines if needed, and report BLOCKED with the count if it can't fit.
