## What
On the Azure gate VM `oby-gate`, Ubuntu's default umask (0002, user-private groups) left `~/.cargo`, `~/.cargo/bin` and `~/.cargo/bin/oby-check-blok` group-writable (775). `scripts/oby-check.sh` (around line 90) rightly refuses a check tool others may write, so A00-09's VM gate on 2026-11-13 failed with "oby-check: failed: oby-check-blok (others may write /home/oby/.cargo/bin/oby-check-blok)", and the check-tool tests that run that path failed with it. The orchestrator fixed the live VM by hand (`chmod go-w` on those three paths); `factory/remote/setup.sh` would recreate the problem on a fresh VM.

## Why
A gate that fails for the VM's own setup costs a round and reads as the change's fault; and a group-writable tool on the gate machine is a real (if small) integrity gap.

## How
- `factory/remote/setup.sh` removes group and other write from every folder and binary on the check's path that it installs or owns: `~/.cargo`, `~/.cargo/bin` and what is in it, rustup's toolchain folders, `/usr/local/bin/oby-remote-gate`, and `/srv/oby` and its slots, and runs the check's own commands with umask 022.
- It verifies the result the way `scripts/oby-check.sh` does (the same rule, reused, not copied: call the script's check if it can be called, else say why not) and stops with a clear message if anything is still writable by others.
- Test with the existing stand-in host in `factory/tests/test_remote_gate.py`: a host whose `~/.cargo/bin` is 775 ends 755 after setup; the test fails without the change.
- Re-run on the real VM (start it only for this, deallocate after) and record the modes before and after.
