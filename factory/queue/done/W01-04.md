## What
A job whose pull request the owner just merged can show "needs you" again, with the card and the error from before the merge, and nothing ever clears it.

The race: `Jobs::carry` reads the pull request while it is still open. The owner's signed Merge lands during carry's GitHub calls. Then `offer_merge_card` writes the old `mergeNeedsYou` and `mergeError` back onto the merged job.

## Why
It was seen for real: it ejected a pull request from the merge queue on 2026-11-21, and in an A/B run `dev` showed the exact failure 2 times in 48. A done task that says it still needs the owner is a lie on Home, and the owner can't answer a card for a pull request that is already merged.

## How
The fix is one commit, `fb93f1b1`, on `origin/claude/merging-17-stale-card`: 92 lines in `core/crates/obid/src/jobs/merge_by_owner.rs` and the MERGING-20 lines of `docs/contracts/merging.md`. It rebases onto `dev` with no conflict. Before a card is offered, the job is read again: a job the owner's Merge already settled gets no card.

Take that commit onto fresh `origin/dev`. Its deterministic test, `jobs::merge_by_owner::tests::merging_20_a_read_from_before_the_owners_merge_brings_no_card_back`, is red on `dev` and green with the fix: run both and keep the output.

One gap to close: the commit message says the job's inbox item is settled too, but the test passes no link, so that half is unproven. Either add an assertion with a link that the stale merge item is settled, or take the claim out of the commit message and the contract line. Don't leave a sentence no test holds.
