## What

obid keeps agents from pushing by passing git, through its run environment (`core/crates/obid/src/process.rs` around line 103), first an empty `remote.origin.pushurl=` to clear the list of push URLs and then its own invalid `obid-agents-cannot-push:///`. Git only treats an empty value as "clear the list" from version 2.46 on. On older git the empty value is just one more entry, so the clone's own push URL stays first in the list.

Measured on 2026-11-14 with the same repository and settings, running `git remote get-url --push --all origin`:

| git | push URLs it lists |
|---|---|
| 2.54.0 (this Mac) | only `obid-agents-cannot-push:///` |
| 2.43.0 (Ubuntu 24.04's default, the gate VM) | `https://example.com/repo.git`, an empty line, then `obid-agents-cannot-push:///` |

`process::tests::lanes_2_neither_lane_can_publish` fails on git 2.43 for this reason: it failed on the gate VM for R01-09 and R02-11, branches that don't touch this code.

## Why

On Linux with the distribution's git, which is common, an agent's `git push` goes to the clone's real push URL as well as obid's invalid one. The other locks (no code-host login in the agent's environment, the clone's own invalid push URL) still stand, but this layer silently does nothing there, and the test that guards it fails on any machine with older git.

## How

1. Make the block hold on any git obid supports. Don't rely on the empty-value reset: for example, have obid's own clone setup make sure the clone's config holds no push URL but the invalid one, or pass the override in a way older git also honours. Measure the fix on git 2.43 (the gate VM, `oby-gate`, has it) and on the Mac's git.
2. If obid has a minimum git version, write it down in docs/runner-api.md and the contract that covers lanes.
3. Acceptance: `lanes_2_neither_lane_can_publish` passes on git 2.43 and on 2.54. A test shows an agent-side push on git 2.43 never reaches the clone's real push URL, and fails on today's code.
