## What
`factory/checks.sh` holds the check lock in a small Python program that runs `scripts/oby-check.sh` as a child in its own session and, when the child ends or is stopped, sends `killpg` to that session to stop anything it left running (#2178). On macOS, `os.killpg` sometimes raises `PermissionError` ("Operation not permitted") when the process group has only just finished. The Python program then dies with exit 1 instead of passing the check's own exit code through. A00-07's builder measured the same code shape in its new `factory/bin/test-run`: 4 crashes in 40 runs (factory/jobs/022-a00-07-builders-own-test-runs/build.md). A second race: a stop signal that arrives just as the child starts can leave the child running.

## Why
A gate that passed but reads as failed costs a whole round, about an hour of builder, gate and reviews. A leftover check holding the shared build folder slows or breaks the next gate.

## How
- In `factory/checks.sh`'s lock holder, treat `ProcessLookupError` and `PermissionError` from `killpg` as "already gone", the way A00-07 does in `factory/bin/test-run`; reuse that code if A00-07 has merged rather than writing it twice.
- Install the stop-signal handlers before the child starts, and stop the child if a signal arrived while it was starting.
- The check's exit code always comes through: 0 stays 0, a failure keeps its code.
- Tests (stand-in checks, as #2178's proof did): a check that exits 0 right as its leftovers are stopped exits 0 in 100 runs out of 100; a stop sent at start leaves nothing running; each test fails without the change it covers.

`factory/checks.sh` is a protected path: this task changes it on purpose, so the approver sends it to the owner.
