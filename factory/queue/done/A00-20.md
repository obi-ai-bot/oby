## What
`factory/bin/test-run` (A00-07) makes every builder test run on the Mac take turns on one lock, whatever it runs. On 2026-11-14 R01-15's builder held it for 30+ minutes with a required load proof (its merge tests 20 times, four copies at once), and five builders waited behind it, including A00-16's Python unit tests (seconds) and R02-05, the last sprint-1 blocker.

## Why
A long run of one job stalls every other job's build; small runs that barely use the CPU gain nothing from waiting.

## How
- `test-run` lets a command that builds no Rust (no `cargo`, `rustc`, `nextest`, `xcodebuild`, `swift build`/`swift test`; for example `python3 -m unittest`, `npm test`, `npx vitest`) run at once without the lock, still at background priority, still with its leftovers stopped and its exit code passed through.
- Long runs keep taking turns as today. A `--long` hint (or an estimate from the command) is not needed in this task.
- When a run waits more than 5 minutes for the lock, `test-run` prints who holds it and since when, every 5 minutes, so a builder can say why it's waiting.
- Tests in `factory/tests/test_test_run.py`: a Python command doesn't wait behind a held lock; a `cargo test` does; the wait message names the holder. Each fails without its change.
