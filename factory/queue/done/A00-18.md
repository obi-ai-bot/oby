## What
The factory runs on the MacBook Air (Apple M4, 10 cores, 24 GB). Since A00-10 (#2193) each gate's Linux groups run on the Azure VM `oby-gate`, but a change that touches macOS-only code still runs its rust group on the Air, one at a time under the check lock (15 to 27 minutes each; 2 h 22 min on 2026-11-13 night), the nightly full Mac check (R01-14) holds the same lock for about an hour, and builders' own test runs take turns on the Air through `factory/bin/test-run` (A00-07). The owner's MacBook Pro is now reachable as the SSH host `oby-mac-pro` (the Pro's Tailscale address, the Pro's user and its own key, login shell fish, so run commands through `bash -s` or `bash -c`): Apple M1 Pro, 10 cores, 16 GB, 340 GB free, macOS 27.2, Xcode 27.2, rustc 1.99.1 (same as the Air), Node 26, gitleaks, gh and Homebrew already installed.

## Why
The Mac half of gates and builders' test runs are now the factory's slowest steps. A second Mac halves that wait without a second orchestrator: one queue, one set of job files on the Air, the Pro holds no factory state.

## How
- `factory/remote/setup-mac.sh oby-mac-pro` (run from the Air, safe to repeat, like `setup.sh` for the VM): checks Xcode, rustup's toolchain and Node against what the Air uses, installs `oby-check-blok` from origin/dev's commit (never from a commit being checked), creates `~/oby-worker/` with a bare clone and two slots, and verifies nothing on the check's path is writable by others (A00-12's rule). It writes no secret, token or login to the Pro and changes no system setting.
- A Mac slot runner on the Pro (`oby-remote-gate` reused or a Mac twin): checks out the exact commit in its own slot with its own build folder and runs the groups it is given; it refuses a commit origin doesn't have, and frees its slot when the SSH connection drops.
- `factory/bin/gate`: the macOS part of a gate (swift, rust for macOS-only code, the factory group, a change to the check's own files) runs on whichever Mac is free: the Pro if it answers within 60 seconds and has a free slot, else the Air under the check lock as today. `checks.md` says where each part ran.
- `factory/bin/test-run`: a builder's run goes to the Pro when the Air's builder lock is taken and the Pro has a free slot, else waits as today. Runs on the Pro use the worktree's pushed commit; a run of uncommitted changes stays on the Air.
- `factory/bin/nightly` may run on the Pro when it's free, so the nightly check doesn't hold the Air's lock.
- Off by default: a `mac_worker` key in `factory/config.json` (protected: the owner adds it) or `FACTORY_MAC_WORKER` for one run; put the exact config edit in build.md and the PR.
- If the Pro is asleep, off the network or busy, everything runs on the Air exactly as today.
- Tests with a fake `ssh`: a free Pro takes the macOS part; a busy or unreachable Pro falls back to the Air; two gates use the two Macs at once; test-run goes to the Pro only for a pushed commit. Each test fails without its change.
- One real run on the Pro: a macOS-only rust gate of a real obid commit, with times on both Macs in the PR body.
