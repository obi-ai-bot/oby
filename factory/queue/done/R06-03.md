# feat(obid): a `revision` on conversations, turns and inbox items

<!-- Roadmap R06-03 · Sprint 3 · R06 Events that clients only apply · effort M · risk medium -->

### Sangam's screen

engine only

### Outcome

Each conversation, turn and inbox item says how new it is, as a job already does, so a client can keep the newer of an event and an answer that crossed it for every object kind, with one rule.

### Status and scope

Proposed (roadmap R06-03, milestone R06 Events that clients only apply).

**Why:** Only jobs have `revision` (job.rs:668-671, `revised` at job.rs:1317). live.ts guards jobs with `newer` (live.ts:118) and a `gone` set, but replaces turns, conversations and inbox items by id as they come (live.ts:547-606), so the class of #1707 and #1709 stays open for them.

**In:**
- `revision: u64` (serde default 0) on conversation.rs `Thread` (sent as the Conversation's `revision`), on each `Turn`, and on sphere/inbox.rs `Item`.
- Bumped by one under the same lock as each change, and saved in the same write, so a restart never takes it back.
- In every event and REST answer that carries the object (`conversation`, `turn`, `turnAsks`, `inbox`, GET /v1/conversations, GET /v1/conversation, GET /v1/inbox).
- A deleted conversation's event (`deleted: true`) carries the revision after the last one.
- `capabilities` gains `revisions-v1`.

**Out:**
- Client use: R06-07.
- Changing how a conversation file is written (R05 'Append turns instead of rewriting the conversation file').

### Actors and ownership: what obid owns

- The revision of each conversation, turn and inbox item, saved with the object.

### Actors and ownership: what the apps show and send

- Nothing changes for clients in this task. Old clients ignore the new `revision` key (Swift Decodable ignores unknown keys; Electron's types are hand-written).

### Interfaces and dependencies

- Conversation, Turn and InboxItem JSON: add `revision: number` (add-only), in events and REST answers.
- GET /v1/status: add `revisions-v1` to `capabilities`.

### Steps

- Find each place that changes a Thread, a Turn or an Item and then sends its event (conversation.rs sends at :910, :949, :1202-1204, :1361, :1392, :1543; sphere/link.rs at :1601, :1648); add a `revised()` helper as job.rs has and call it under the same lock.
- Add `#[serde(default)] revision` to the stored structs so old files read as 0.
- Put `revision` in `Thread::summary`, the turn's JSON and the inbox item's `shown`.
- Add `revisions-v1` to CAPABILITIES; document the key in docs/runner-api.md for the three objects.
- Write EVENTS-7 to 10; prove EVENTS-10 fails when the revision is not saved.
- Run `scripts/oby-check.sh` and swift_client.rs.

### Acceptance scenarios

- EVENTS-7 (proposed): Given a conversation, when its title, pin or folders change, then its `conversation` event and its GET /v1/conversations entry carry a revision one more than before.
- EVENTS-8 (proposed): Given a turn, when its `jobs` or `asks` change, then its `turn` or `turnAsks` event carries a revision one more than before, and GET /v1/conversation lists the same revision.
- EVENTS-9 (proposed): Given an inbox item answered on the iPhone, when obid saves the answer, then the `inbox` event and GET /v1/inbox carry a revision one more than before.
- EVENTS-10 (proposed): Given an object at revision 7, when obid restarts and the object changes, then the next revision is 8.
