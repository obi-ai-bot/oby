# chore(factory): pull requests stay drafts until approved, and an approved one is queued, not synced, gated again and merged

<!-- Roadmap R01-12 · Sprint 1 · R01 Safety net · effort S · risk medium · new 2026-11-13 from docs/ci-architecture.md -->

### Sangam's screen

engine only

### Outcome

A factory pull request runs no GitHub job while it is being built, gated and reviewed. When the approver says APPROVE, the factory marks it ready and hands it to GitHub, `gh pr merge --auto` pinned to the head. On a dev with a merge queue (R01-03) that queues it; without one, it merges as today. The job waits in a new stage, `queued`, without holding a slot. A pull request the queue removes is queued once more by itself, then gets a builder round with the failed log. No full Mac check runs again after approval: the queue tests the combined code on Linux, and the nightly Mac run (R01-14) tests dev as merged. Each pull request's Mac time falls from about 25–36 minutes to about 11–14 (docs/ci-architecture.md).

### Status and scope

Proposed (new, docs/ci-architecture.md, "What changes in the factory"). Item 3 below changes AGENTS.md's remembered workflow ("the checks on the user's Mac pass on the same commit"). The owner decided it on 2026-11-13: "Yes, drop the Mac merge gate". So this task also rewrites that line of AGENTS.md: the Mac check passes on the pull request's own head, the merge queue's full Linux suite passes on the combined code, and the nightly full Mac run (R01-14) checks dev as merged.

**Why:** 27 gates on 2026-11-13 took 286 Mac minutes for 8 merged pull requests, one at a time, so the Mac gate, not the agents, sets the factory's pace. A needs-human escalation marks a pull request ready, so every later push runs the full Linux suite. `job merge` merges seconds after `gh pr ready`, so the run that starts tests a pull request that has already merged.

**In:**
1. `factory/bin/job` `advance`: going to `needs-human` posts the decision but no longer marks the pull request ready.
2. `factory/bin/job merge`:
   - when the approved head is the gated head: `gh pr ready` if it is a draft, then `gh pr merge <n> --auto --match-head-commit <head>` (no `--squash`: the queue's method rules; without a queue, the repository's squash)
   - then read the state: MERGED → `merged`; queued or auto-merge armed → `queued`; anything else → `needs-human` as now
3. No sync with dev and no `gate --merge` before queuing: the head is the one the gate passed (the owner's decision of 2026-11-13, above). AGENTS.md's remembered workflow for this repository says so in the same pull request.
4. New stage `queued` in WAITING, and `job queue` reads each queued job at most once every 2 minutes (`gh pr view --json state,mergeStateStatus,autoMergeRequest` and the timeline's last `removed_from_merge_queue`):
   - merged → `merged`
   - removed the first time → queue again, once
   - removed again, or for failing checks → a builder round: the failed run's log written fenced as data into `round-N/queue-failure.md` (the last 300 lines of up to 3 failed jobs, as obid's MERGING-39); the pull request back to draft (`gh pr ready --undo`)
   - removed for a conflict → a builder round that merges `origin/dev`
   - rounds run out → `needs-human`, as now
5. `.claude/agents/builder.md`: while it works, the builder runs only the test binaries and suites its change touched (`cargo test --test <x>`, `cargo test -p obid <module>::`, `npm run typecheck`), not the whole check; the gate runs it next. `.claude/skills/factory/SKILL.md` describes `queued` and the re-queue.

**Out:**
- The queue's settings (R01-03, the owner's)
- The nightly Mac run (R01-14)
- Any change to factory/checks.sh or factory/bin/gate (the gate's reuse rule from #2160 already passes an unchanged head)

### Steps

- Add `queued` to WAITING and the transitions merging → queued → merged | build | needs-human, with `advance`'s checks.
- Change `cmd_merge` and the `needs-human` branch of `advance` as above.

- Update builder.md, SKILL.md, README.md and the dashboard.

### Acceptance scenarios

- CI-22 (proposed): Given a factory job in build, gate or review, when its builder pushes, then its pull request is a draft and no GitHub job runs on it, a needs-human escalation included.
- CI-23 (proposed): Given an approved job whose head is the gated head, when `job merge` runs, then it marks the pull request ready, runs `gh pr merge --auto --match-head-commit <head>`, runs no Mac check, and the job is `merged` (no queue) or `queued` (a queue).
- CI-24 (proposed): Given a queued job the queue removes for the first time, when `job queue` reads it, then it is queued again with no builder round; removed a second time, it gets one builder round with the failed log in `queue-failure.md` and its pull request is a draft again.
- CI-25 (proposed): Given four queued jobs, when `job queue` runs every minute for an hour, then it makes at most 30 GitHub reads per job.
