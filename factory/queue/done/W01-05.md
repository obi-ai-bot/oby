## What
The owner opens an artifact and asks Oby to change it. When Oby's own conversation makes the change, version 2 appears. When a task makes it, a second artifact appears instead, and the open one never changes. The loop the Prototype board draws breaks at its second step.

Read from the code on `dev` (verify each before relying on it; `reports/w01/readers/artifacts.md` has the trace):

- A job publishes with `artifact: None` unless `job.artifacts` already names one (`core/crates/obid/src/jobs/publishing.rs`). A dispatched job and a follow-up both start with `job.artifacts` empty: `NewJob` has no field for it, and `follow_up()` in `jobs.rs` builds `..NewJob::default()`.
- Neither the job's worktree nor the conversation's room gets the open version's files. The brain is told only the artifact's id, version, kind and title (`brain/open_artifact.rs`, `brain/harness.rs`), so an agent asked to "make the button blue" has nothing to edit.
- Every existing proof goes around the gap: ARTIFACTS-7's unit test calls the store with `artifact: Some(id)` directly, and the stand-in brain publishes through its own `oby_artifact`.

## Why
"Ask for a change, see the next version" is the heart of Oby Artifacts, as LibreChat has it. Without it the owner gets a new card for every change and the version menu stays at v1. Nothing else in the Artifacts lane makes the loop true.

## How
Write the red test first: `artifacts_19_a_task_started_about_the_open_artifact_makes_its_next_version`, in `core/crates/obid/tests/plans_artifact.rs`, which already drives a conversation and a job on stand-in agents. With an artifact open in the conversation, the owner's words start a task; the task's agent edits the file it was given and the job publishes; the same artifact now has version 2, and no second artifact exists. Run it on `dev` and keep the failing output. If it passes on `dev`, stop and say so in `build.md`: the task closes with the test alone.

Then both halves:

1. **The job.** A job dispatched while an artifact is open starts with that artifact in `job.artifacts` (its id, version and entry), and the open version's files copied into its worktree where a job's inputs go (`jobs/owner_run.rs`, `jobs/files_at_work.rs`), under `.obi/artifacts/<entry>/`. A follow-up carries the earlier job's `job.artifacts` and gets the latest version's files the same way.
2. **The brain.** The conversation's room gets the same files, and the line the brain is told names the path, so Oby's own turn edits the real files too.

Rules that bind this change:

- Imported agent-steering files stay out of every room and worktree: never copy `CLAUDE.md`, `AGENTS.md`, `AGENTS.override.md` or anything under `.claude/` from an artifact's files.
- `NewJob` is read from `POST /v1/jobs`. A new field naming an artifact must not let any caller seed another conversation's artifact into a job: either obid sets it only from the conversation's own open artifact (`#[serde(skip)]` on the wire), or it is checked against the job's conversation and profile and refused otherwise. Say which in the spec, and test the refusal.
- The API is add-only: one new field at most, with a serde default, no renamed or removed key. The artifact's `kind` is a closed enum in the Swift apps: add no value to it.
- An artifact's files are text from outside: they reach the agent as files in its room, never inside a prompt.
- `jobs.rs` may only shrink in net lines unless the owner raises its limit: put new logic in the `jobs/` modules, and keep `jobs.rs` to the one field and its wiring.
