# feat(factory): run the gate's Linux checks on an Azure VM, four at once

### Outcome

A factory gate runs Oby's Linux-capable check groups (rust, electron, scan) on the Azure VM `oby-gate`, with up to four gates in parallel, each in its own slot with its own checkout and Cargo build folder. The Mac runs only the macOS-only suites, and only when the job touches their paths. The VM starts when a gate needs it and deallocates itself after 30 idle minutes. If the VM can't be reached, the gate runs on the Mac exactly as today.

### Status and scope

Proposed. The design is `docs/factory-remote-gate.md`, which the owner asked for on 2026-11-13. It needs the owner's steps 1 to 4 in that document first: Azure CLI signed in, the VM created, a budget alert, and an SSH host `oby-gate`. If those aren't done, intake answers NEEDS-INFO and names the missing step.

**In:**
- `factory/remote/setup.sh`: provisions the VM (cloud-init or SSH), idempotent. It installs the same Rust toolchain as `.github/workflows/linux.yml` (`RUSTUP_TOOLCHAIN`), Node 22, gitleaks at the workflow's version, bubblewrap and slirp4netns with unprivileged user namespaces allowed, `oby-check-blok` built from `origin/dev`, the bare clone at `/srv/oby/repo.git`, four slots at `/srv/oby/slot-{1..4}`, and the idle-deallocate timer (a systemd timer that calls `az vm deallocate` with the VM's managed identity, or `shutdown` if deallocation is done from the Mac).
- `factory/remote/oby-remote-gate`: runs on the VM. Arguments are commit, base and changed-path list. It takes a free slot's lock (waiting for one if all four are busy), fetches the commit, checks it out in the slot's worktree, touches tracked files under `core/` and `tools/` (as `factory/checks.sh` does), runs `scripts/oby-check.sh <base>` with `OBY_CHECK_ONLY` set to each planned Linux group, streams the output and exits 0, 1 or 2.
- `factory/bin/gate`: when `config.json` has `"remote_gate": {"host": "oby-gate", "vm": "<name>", "resource_group": "oby-factory"}` and the plan has a rust or electron group, it:
  - starts the VM if it is deallocated;
  - runs the remote gate over SSH, using the job's pushed commit, which the gate already requires to be on origin;
  - runs the Mac-side groups only when the diff touches the macOS-only paths listed in the design;
  - writes `HOST: oby-gate` or `HOST: mac`, with the reason, into `checks.md`;
  - falls back to the Mac when SSH or start fails within 3 minutes.

  Without `remote_gate`, nothing changes.
- `factory/config.json` gains `remote_gate` set to `null`. The owner fills it in when the VM exists. It's a protected path, so the builder never fills it in.
- Docs: `factory/README.md` and `.claude/skills/factory/SKILL.md` say where gates run and how to turn the VM off (`remote_gate: null`).

**Out:**
- Creating or paying for Azure resources. That is the owner's step, and Claude does it only on the owner's word.
- GitHub self-hosted runners. The repository is public, and the CI design (#2163) rules them out.
- Moving builders' test runs to the VM. That's a later task, after this one measures gate times.

### Acceptance scenarios

- REMOTE-1: Given `remote_gate` is set and the VM is deallocated, when a Rust gate runs, then the gate starts the VM, runs rust and scan there, and `checks.md` says `HOST: oby-gate`.
- REMOTE-2: Given four gates are running on the VM, when a fifth starts, then it waits for a free slot, and no two gates ever share a slot's build folder.
- REMOTE-3: Given the VM can't be reached, when a gate runs, then it runs on the Mac within 3 minutes and `checks.md` says why.
- REMOTE-4: Given a job that touches `core/crates/obid/src/sandbox.rs`, when its gate runs, then the macOS-only rust tests also run on the Mac and both verdicts must pass.
- REMOTE-5: Given no gate for 30 minutes, then the VM is deallocated, which `az vm get-instance-view` shows as `PowerState/deallocated`.
- REMOTE-6: Given `remote_gate` is `null`, then the gate behaves exactly as before. The existing factory tests and a docs-only gate show this.

### Tests

- A shell test of `oby-remote-gate`'s slot locking: run two at once against a fake check script and show that they used different slots.
- Gate fallback: point `remote_gate.host` at an unreachable host, and show the gate passes on the Mac with the reason written in `checks.md`.
- End to end, on the real VM: one real job's gate with REMOTE-1 timings recorded, compared with the same commit on the Mac.

### Done when

- REMOTE-1 to 6 are shown, each with its output in the PR body.
- Gate time for one real Rust job is measured on the VM and on the Mac, and both numbers are in the PR.
- The VM was found deallocated after an idle period, and the PR body has the cost-analysis numbers for that day.

### Notes

The VM is the owner's resource. Never create, resize or delete Azure resources and never change the budget; turning the VM on with `az vm start` and letting it deallocate is the only Azure action the factory takes. Security path: this changes `factory/checks.sh`'s callers and the factory's agents' environment, so it merges on the owner's word.
