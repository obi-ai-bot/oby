The scheduled CLI canary (workflow "CLI canary", run 43660292711, 2026-11-15T00:51:53Z, its first run) fails only on cursor-agent/signed_out. The test `the_real_cursor_agent_signed_out_says_so` (core/crates/obid/tests/adapters.rs:1335) expects the job's summary to start "Cursor · Fresh is signed out", but the job failed before Cursor ran:

"Cursor stopped without finishing (exit status 1). bwrap: Can't create file at /home/runner/work/_temp/cursor-home/.local/bin/cursor-agent: No such file or directory / obid: the sandbox never started"

The canary installs cursor-agent with HOME="$RUNNER_TEMP/cursor-home" (`curl -fsS https://cursor.com/install | bash`), so the binary is at $RUNNER_TEMP/cursor-home/.local/bin/cursor-agent (cursor-agent 2026.11.13-eacade1), and bubblewrap's bind of it into the boxed run fails because its parent folders don't exist inside the box.

What to build:
1. Find whether this is obid's sandbox (core/crates/obid/src/sandbox.rs: how it binds a CLI's binary and the folders it lives in on Linux) or the canary's setup (the workflow's install step), and fix it where it belongs: a CLI installed under any folder the owner chose must start in Oby's box on Linux, or the canary's install must match a real user's.
2. The canary's cursor-agent/signed_out case passes on its next run (it can be run by hand with workflow_dispatch), and the reason the job gives is Cursor's own "signed out", not the sandbox's.
3. A test that fails without the fix (a fake CLI under a deep, non-standard folder, boxed on Linux).
