## What

`core/crates/obid/tests/peer_flow.rs`, test `peer_3_a_thread_is_only_that_member`, fails on GitHub's Linux runners: at `peer_flow.rs:488` it reads "wellington" where it expects "ernesto". In R01-02's full runs it failed first and passed on retry twice (runs before 43457997275), then failed on both tries of run 43457997275 (shard rust-test 1/4) and again when that shard was re-run. It's an existing test; R01-02's ci.yml didn't touch it.

## Why

A test that fails without a code change turns the merge queue's `Check` red for a whole batch (docs/ci-architecture.md), and costs every job in it a round.

## How

- Reproduce on Linux (a container like CI's: `rust` image, `cargo nextest run --test peer_flow peer_3`, several times, under CPU load) and on the Mac.
- Find what the test waits for: most likely it reads a thread or member list before obid has applied the second member's event, or two members' threads share state under load. Wait for the state the test means (`support::within`, as R01-06 did for the other flaky tests), or fix the race in obid if the code has one: say which in the PR.
- No new fixed sleep (the check's shrink-only sleep limit, R01-06, counts them).

## Done when

- The test passes 30 of 30 runs on Linux under load and 30 of 30 on the Mac, and the PR shows both counts.
- If obid's code changed, the PR names the race and a test that failed before the fix.
