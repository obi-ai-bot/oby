# feat(electron): the app's main process reads and writes the Obysphere's policy with the admin's own token

<!-- Roadmap R10-06 · Sprint 7 · R10 Finish the Obysphere client · effort S · risk medium -->

### Sangam's screen

engine only (main process and preload; the screen is R10-07)

### Outcome

An admin's Oby can read the Sphere's rules and write them with one call from the app, signed by the owner key that stays in main. The screen in R10-07 then only shows and sends.

### Status and scope

Proposed (roadmap R10-06, milestone R10 Finish the Obysphere client).

**Why:** No app can write the policy, so a fresh Sphere refuses every question (ask-an-oby.md 'No screen for it'). The owner key is only in Electron main (obysphere.md 'Actors'), so the call belongs there, as Leave's DELETE does (shared/sphere.ts `leave`).

**In:**
- `readPolicy()` and `writePolicy(rules, expectedVersion)` in shared/sphere.ts with the scope R10-05 found, carried out by main/sphere.ts.
- Preload `window.app.spherePolicy()` and `sphereSetPolicy(...)`; the page cannot sign anything else.
- `starterRule()`: `{id: members-ask, from_owner: *, to_owner: *, actions: [question], repos: [*]}` (ask-an-oby.md).
- A version conflict reads the policy again and answers why.

**Out:**
- The screen (R10-07).
- obid: it never holds the owner key or an admin token.

### Actors and ownership: what obid owns

- Nothing new.

### Actors and ownership: what the apps show and send

- Main gets the token and calls the Sphere; the page gets the rules and the refusals in words.

### Interfaces and dependencies

- New preload calls only; no obid route.

### Steps

- Read R10-05's answer; stop if it says the server cannot do this.
- Add the token exchange with the admin scope and the two calls in shared/sphere.ts.
- Wire main and preload with a decoder for the page's payload.
- Add POLICY-1 to 4 to the contract; POLICY-1 and 3 run in test-sphere.mjs against a real obi-sphere.

### Acceptance scenarios

- POLICY-1 (proposed): Given an admin owner on a local obi-sphere with policy `[]`, when main writes the starter rule, then GET policy lists it and the next member question is not `policy_denied`.
- POLICY-2 (proposed): Given a member who is not an admin, when the page asks to write, then nothing is sent with a token it cannot get and the answer says only admins can change the rules.
- POLICY-3 (proposed): Given the policy changed since it was read, when main writes with the old version, then nothing is replaced and the page gets the new policy with 'changed meanwhile'.
- POLICY-4 (proposed): Given any policy write, when it runs, then the owner key never leaves main and the token is used once and not kept.
