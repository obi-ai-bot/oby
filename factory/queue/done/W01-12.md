## What
The browser panel's address row draws the board's buttons, and none of them does anything. In `apps/electron/src/renderer/src/browser/Panel.tsx` on `dev` (`Nav`, lines 88 to 93; verify them):

- **Back** (`aria-label="Back"`) has no `onClick`. It is disabled only by the `back` prop or on board 17's `off` set.
- **Forward** (`aria-label="Forward"`) is always `disabled`.
- **Reload** (`aria-label="Reload"`) has no `onClick`.
- **Stop loading** (`aria-label="Stop loading"`, drawn instead of Reload while `BrowserPane.tsx` sees obid's `tab.state === 'loading'`) has no `onClick`.
- **New tab** and **Page options** have no `onClick`.

Nothing knows whether a tab has a page behind it or ahead of it. Board 10's ways out (Try again, Go back, Reload) show only on the demo data. On obid, `PageState` hides them (`ways = mode !== 'obid'`, Panel.tsx:141), because the contract's Open list says they need routes obid doesn't have for the owner.

T3 Code does this in the window and in its main process, and obid has no part in it. This task ports T3 Code's way (pingdotgg/t3code@304cf149, MIT). Verify each line before relying on it:

- The page asks main, by tab: pingdotgg/t3code@304cf149:apps/web/src/browser/HostedBrowserWebview.tsx:337-339 (`previewBridge.goBack(tabId)` / `goForward(tabId)`). The bridge invokes one channel per act: pingdotgg/t3code@304cf149:apps/desktop/src/preload.ts:393-396 (`goBack`, `goForward`, `refresh`, `stopLoading`, each `{ tabId }`). Main handles each: pingdotgg/t3code@304cf149:apps/desktop/src/ipc/methods/preview.ts:157-175.
- Main acts on the guest's own `webContents`, never through the debugger: pingdotgg/t3code@304cf149:apps/desktop/src/preview/Manager.ts:2213-2232. `goBack` runs `navigationHistory.goBack()` only if `canGoBack()`, and `goForward` likewise with `canGoForward()`. `refresh` is `wc.reload()`. `stopLoading` is `wc.stop()`. pingdotgg/t3code@304cf149:apps/desktop/src/preview/GuestInput.ts:182-191 says why: Electron's debugger sends `Page.reload` on a webview to its embedder window, so reload and stop go to `webContents.reload()` and `webContents.stop()`.
- Before leaving a page, main checks that the page isn't stuck in a script (`leavePage`, Manager.ts:2213-2221; `leaveBusyPage`, Manager.ts:2077-2093). It sends `Runtime.evaluate` `{expression: "0"}` on the guest's debugger and waits up to `BUSY_PAGE_PROBE_MS = 1_000` (Manager.ts:139). If nothing answers, it sends `Runtime.terminateExecution` without awaiting it, then acts. Back, Forward and Reload leave the page. Stop doesn't (`withWebContents`, Manager.ts:2232).
- Main publishes the tab's state from the guest's own events. `computeNavStatus` (Manager.ts:1185-1192) gives loading from `wc.isLoadingMainFrame()`. `syncState` (Manager.ts:1214-1257) reads `wc.navigationHistory.canGoBack()` and `canGoForward()` and emits them as the tab's state. Its listeners (Manager.ts:1662-1670) are `did-navigate`, `did-navigate-in-page`, `did-start-loading`, `did-stop-loading` and `did-fail-load`.

## Why
The owner can see an agent's page but can't move it: no Back after following a link, no Reload after the app under test restarts, no Stop on a page that hangs. In the W01 plan this is the first half of the handoff's B8, the nav row. Only after it does board 2's row do what it draws.

It goes in main, as T3 Code has it, and not through the `<webview>` element's own methods. Main holds each tab's `webContents` (`keyed` in `browserGuest.ts`) and its debugger, which the busy-page probe needs. A page stuck in a script still answers main.

No signed words. The four acts are the owner's clicks on a page in their own window, and they reach no obid route: no `window.app.obid.call` and no `…/take`-style body, so there is nothing for main's signer to sign (docs/contracts/signed-words.md covers words sent to obid). obid hears what happened as it hears any navigation, through its own CDP events (`Page.frameNavigated`, `Page.loadEventFired`, `Page.navigatedWithinDocument`), which main already forwards. obid needs no change. obid's own `Page.stopLoading` stays refused by the relay (BROWSERAPP-27). The owner's Stop is main's `wc.stop()`, not a relayed command.

## How
In main (`browserGuest.ts`, with `browser.ts` wiring the channel):

- `hosting(...)` gains `nav(k, op)`, with `op` one of `back`, `forward`, `reload` or `stop`. It finds the webview `keyed` to that tab in this window and does what Manager.ts:2223-2232 does: `navigationHistory.goBack()` if `canGoBack()`, `goForward()` if `canGoForward()`, `reload()`, `stop()`. Back, Forward and Reload probe first, as `leaveBusyPage` does: `Runtime.evaluate` `{expression: "0"}` on that webview's debugger with a 1 s limit, then `Runtime.terminateExecution` (not awaited) if nothing answered. With no debugger attached (DevTools open), they act at once, as T3 does with no control session. A tab with no webview of this window's gets an answer that says so, and nothing moves. These debugger calls are main's own, not obid's: they don't go through `relayCommand` or its allowlist.
- In `did-attach-webview`, add T3's listeners (`did-navigate`, `did-navigate-in-page`, `did-start-loading`, `did-stop-loading`, `did-fail-load`). Once a webview is keyed to a tab, each listener reports `{threadId, tabId, canGoBack, canGoForward, loading}`, with `loading` from `wc.isLoadingMainFrame()`. Report it once right after `register` too, so a tab's first state isn't missed.
- `browser.ts`: one `handle` channel, `browser-nav` (`string` the tab's job, `string` the tab, `oneOf('back', 'forward', 'reload', 'stop')`), through `ipc(trusted)` like `browser-shown`. Main sends the state to the page on `browser-nav-state`, the way `browser-pointer` goes. Add the channel to `docs/contracts/ipc.md`'s table and to `ipc.test.ts`'s list of every channel.

In the preload: `browser.nav(threadId, tabId, op)` and `browser.navState(fn)` (which returns a function that stops listening), beside `shown` and `pointer`. Add the same to `window.app.browser`'s type in `renderer/src/Oby.tsx`.

In the page:

- `view.ts`: `Tab` gains `canGoBack?` and `canGoForward?`, which are main's and set only on obid, plus `pageLoading?`. `BrowserApi` gains `nav(tab, op)`.
- `live.ts`: `Calls` gains `navState`. Main's last state per tab (job and tab) is merged into each `Tab` in `view()`. On obid both start `false` until main says otherwise.
- `store.tsx`: on obid, `nav` calls `window.app.browser.nav(job, tab, op)` for the tab's job. On the demo data it does nothing, and so does `OFF`'s.
- `Panel.tsx` `Nav`, with the labels exactly as the boards write them:
  - **Back** calls `nav(back)` and is disabled when `tab.canGoBack === false`, so on a tab's first page.
  - **Forward** calls `nav(forward)` and is enabled only when `tab.canGoForward === true`.
  - **Reload** calls `nav(reload)`.
  - **Stop loading** calls `nav(stop)`.

  With `undefined` (the demo data), each draws as now, so boards 2 and 10 are unchanged.
- `BrowserPane.tsx`: on obid, the row shows board 10's loading set (Back, then Stop loading in Reload's place) while main says `pageLoading`, as T3 reads `isLoadingMainFrame`. On the demo data it shows that set when the board's `state` is `loading`, as now. The strip under the row (`Control`, "Waiting for the page") still follows obid's `state`.

Board 10's ways out that are these same calls show on obid now:

- **Try again** (failed, timed out) is `nav(reload)`.
- The crashed page's **Reload** is `nav(reload)`.
- The certificate page's **Go back** is `nav(back)`, disabled like Back when there's nothing behind.

Ways out that are other calls stay hidden on obid, as now. **Go on anyway** is a certificate decision (T3's `BrowserSession.ts`, a later task). A dialog's **Leave** and **Stay** answer the page's own dialog (B10). Update BROWSERAPP-14 and the contract's Open item to say exactly this.

**New tab** and **Page options** stay without an `onClick`. The owner's own tabs come later, and the page's menu has no board of its own yet. Write that in the contract.

Port the technique, don't copy T3's code verbatim (verbatim code needs T3's MIT notice in NOTICE, which is not this task). Credit T3 in comments with its paths, as `browserGuest.ts` already does.
