# feat(obid): a `capabilities` list in GET /v1/status

<!-- Roadmap R06-01 · Sprint 3 · R06 Events that clients only apply · effort S · risk low -->

### Sangam's screen

engine only

### Outcome

Every client can ask obid which optional features it serves, by stable name, instead of guessing from its version or from a 404. A new optional feature ships with its name in the same pull request.

### Status and scope

Proposed (roadmap R06-01, milestone R06 Events that clients only apply).

**Why:** Clients find out what an obid serves by failing: live.ts:668 catches an older obid's limit-decisions answer, folders hang on an ad hoc boolean (`status.folders`, api.rs:653), and #1653 lists routes clients call that obid does not serve. Four proposed changes ask for the same list.

**In:**
- `capabilities: [string]` on `Status` (core/crates/obid/src/api.rs struct Status), a static sorted list of short names with a version suffix (`folders-v1` first; R06-02 and R06-03 add theirs).
- Keep `folders` and every other boolean: released apps decode them.
- A 'Capabilities' table in docs/runner-api.md under GET /v1/status: name, what it means, since which obid.
- A test that every listed name has a row in that table and that no row names a missing capability.

**Out:**
- Request headers `Oby-Client` / `Oby-Capabilities`: the gateway forwards only content type and the words signature (gateway.rs:793-799), and obid choosing per client is the version guessing this removes.
- Deleting the dead routes of #1653 and the Bonjour path: R01 'Check that every client route exists in obid' and R03 own them.
- Gating in the iPhone app: its own task once an iPhone action needs it.

### Actors and ownership: what obid owns

- The list of optional features it serves and their names; a name never changes meaning (a new behaviour gets `-v2`).

### Actors and ownership: what the apps show and send

- Nothing changes for clients in this task; R06-05 gates the Electron app on it.

### Interfaces and dependencies

- GET /v1/status: add `capabilities: [string]` (add-only). Old clients ignore the key (Swift's Decodable RunnerStatus and TypeScript's Status ignore unknown keys).

### Files

- core/crates/obid/src/api.rs
- docs/runner-api.md
- new: docs/contracts/capabilities.md
- core/crates/obid/tests/runner_api.rs

### Steps

- Add `pub const CAPABILITIES: &[&str]` next to `struct Status` in api.rs and a `capabilities: Vec<&'static str>` field filled from it (with `folders-v1`).
- Write docs/contracts/capabilities.md: the rule (a name means one behaviour forever; an obid without it answers as an older obid does; a client hides the action whose name is missing).
- Add the Capabilities table to docs/runner-api.md under GET /v1/status.
- Write caps_1 and caps_2 in tests/runner_api.rs; caps_2 parses the table out of docs/runner-api.md.
- Run `scripts/oby-check.sh`; prove caps_2 fails by adding an undocumented name, then remove it.

### Acceptance scenarios

- CAPS-1 (proposed): Given any obid, when a client reads GET /v1/status, then `capabilities` is a list of strings, sorted, with no duplicate, and `folders-v1` is in it exactly when `folders` is true.
- CAPS-2 (proposed): Given the capability table in docs/runner-api.md, when the test reads it and the list obid serves, then each served name has a row and each row's name is served.
- CAPS-3 (proposed): Given an older client that decodes Status without `capabilities`, when it reads GET /v1/status, then it decodes as before (the key is added, nothing renamed or removed).

Contract: new: docs/contracts/capabilities.md (new prefix CAPS)
