## What

Every factory worktree builds obid into one shared Cargo folder, `~/Library/Caches/oby-factory/core-target` (the gate's Mac part through `factory/checks.sh`, and builders' and approvers' runs through `CARGO_TARGET_DIR`). On 2026-11-14 R02-10's approver ran `cargo nextest` there for its worktree and got a stale `jobs_api` test binary that didn't contain the branch's new test. Only a rerun in the worktree's own `core/target` ran the right code.

A likely cause: Cargo decides a build is fresh by comparing the timestamps of the source files its last build read. In a shared folder those are another worktree's files, so a branch whose files are older than that build can reuse it. This is a guess. Prove it before fixing it.

## Why

A gate or a reviewer's run that tests another branch's build can pass code that was never tested: a green check over the wrong code. It also wastes rounds when a test "fails" against code the branch doesn't contain.

## How

1. Reproduce it first: build worktree A in the shared folder, then run worktree B, which has a test A lacks, and show the stale binary. Write down what Cargo printed (`CARGO_LOG=cargo::core::compiler::fingerprint=info` names the reason). If it doesn't reproduce, report that with the evidence and stop.
2. Fix it the smallest way that keeps the cache's speed. For example, give each worktree its own folder under the shared cache, or have the gate's lock holder record which worktree built last and force a fresh build of the workspace's own crates when that changes. Dependencies must stay shared.
3. Acceptance:
   - A factory test runs two fake worktrees through the same shared folder and fails on today's code.
   - The gate's Mac part and `factory/bin/test-run` never run a binary built from another worktree.
   - The gate's time on an unchanged branch doesn't grow by more than the workspace crates' own rebuild.
