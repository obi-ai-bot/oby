## What
Two gaps in the remote gate (A00-10, #2193) showed up on 2026-11-13 night:
1. The VM's network rule (`oby-gateNSG`, rule `ssh-from-owner`, resource group `oby-factory`) allows SSH only from one public IP. The owner's home IP changed; every gate then waited 180 s for SSH and fell back to the Mac (R02-05's gate took 2 h 22 min there) until the orchestrator updated the rule by hand.
2. `factory/bin/gate --idle` (run by `job queue`) deallocates the VM only when no job is in `gate` or `merging`. A job gating on the Mac (a fallback, or macOS-only code) kept the VM running idle for about 6 hours (about $9).

## Why
The VM is only worth its cost if gates actually use it and it stops when they don't.

## How
- When a gate can't reach the VM by SSH, before falling back: read this Mac's public IP (one HTTPS request to a plain IP-echo service; say which one and why), and if it differs from the rule's source, update the rule with `az network nsg rule update` using the Azure login already on this Mac, wait for SSH once more (up to 60 s), then fall back if it still fails. Record the change in checks.md. The rule only ever allows a single /32 address; never open it wider.
- The idle rule counts only gates that are using the VM: the gate records its remote slot use (start and end) in `factory/jobs/remote-gate/state.json`, and `--idle` deallocates when no recorded use is open and the last one ended 30 or more minutes ago, whatever stage other jobs are in.
- Tests with the fake `az`, `ssh` and IP lookup: a changed IP updates the rule and the gate then uses the VM; an unchanged IP falls back as today; a Mac-only gate doesn't keep the VM up; an open VM use does. Each test fails without its change.
- Writes no secret; the Azure login stays the Mac's own.
