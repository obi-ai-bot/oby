## What
Fill in (board 8, W01-21) has main type the owner's password into the tab's own page. After that, until the page leaves that document, the window must not run a script of the agent's there: a script could read the field and hand the value on. W4's fill commit (`1262567f`, not on `dev`) did that by refusing every `Runtime.evaluate` and `Runtime.callFunctionOn` on a filled page (`NO_SCRIPT` in its `browserRelay.ts`). obid's own reads use exactly those calls, so every agent step after a fill would fail. The reader report `reports/w01/readers/browser-window.md` ("Corrections") names them: `page_info` and `eval_value` (`window/page.rs`), and `on_node`'s fixed functions.

On `dev` (verify each before relying on it):
- obid's CDP leaves through one place, `Relay::cdp` (`core/crates/obid/src/browser/relay.rs`, about line 205), which sends `RelayCommand::Cdp { thread_id, tab_id, message }` (`browser/contract/relay_command.rs`).
- Only one command carries the agent's own code: `oby_browser_evaluate`, which reaches `window/page.rs`'s `["eval", expression]` arm and `eval_value`. Every other `Runtime.evaluate` obid sends is its own fixed text: `page_info`, `["get", "url"]`, `wait_for`'s probes (the selector or text quoted with `json!`), the viewport read. Every `Runtime.callFunctionOn` (`on_node`) runs one of obid's fixed functions (clear a value, choose options).
- Main's `relayCommand` (`apps/electron/src/main/browserRelay.ts`, `relayCommand`) and obid-spec's stand-in window (`tools/obid-spec/src/browser_window.rs`, `command`) both read only the keys they know, so a new key changes nothing for either.

So obid says which command is the agent's code, with one add-only key, and the window (W01-21) refuses only that one on a filled page.

## Why
Without it, Fill in either leaves the agent free to read the password it just typed, or breaks every agent step after a sign-in. The brief's D2 decided the second half: "no agent script until navigation" (`reports/w01/orchestrator-brief.md`, section 3). Only obid knows which script is the agent's. T3 Code needs no such mark, since it has no password the agent mustn't see (pingdotgg/t3code@304cf149:apps/desktop/src/preview/DesktopBrowserHost.ts:25-26 treats every `Runtime.evaluate` alike). This is Oby's guard on top of T3's relay, the way `METHODS` already is.

## How
1. **The wire** (`browser/contract/relay_command.rs`): `RelayCommand::Cdp` gains `agent_code: bool`, `#[serde(default, skip_serializing_if = …)]`, so it is sent as `"agentCode": true` only on the agent's own script and is absent otherwise. `type` and every existing key stay as they are: add-only. No Swift app decodes `/v1/browser/relay` (`git grep` over `apps/shared`, `apps/ios`, `apps/watch` finds none: verify).
2. **The relay** (`relay.rs`): `cdp` keeps its signature and sends `agent_code: false`; a sibling (`cdp_agent`, or one `bool` argument) sends `true`. Update the test patterns that list `Cdp`'s fields.
3. **The page** (`window/page.rs`): only the `["eval", expression]` arm sends its `Runtime.evaluate` as the agent's code. `eval_value`'s other callers, `on_node` and everything else stay obid's own. Keep the change to that arm and one helper.
4. **The doc guard** (`browser/contract/doc_guard.rs`): its `RelayCommand::Cdp` sample carries `agent_code: true`, so the guard holds `agentCode` documented.
5. **Docs.**
   - `docs/api/browser.md`, the relay's commands: `cdp` may carry `"agentCode": true`: this frame is the agent's own script (`oby_browser_evaluate`), and a window may refuse it, as it refuses any command, with a CDP error. Absent, the frame is obid's own.
   - `docs/contracts/browser.md`: add **BROWSER-33** (implemented), naming its tests.
   - Classify BROWSER-33 in `tools/obid-spec/scope.json`'s `browser.md` block, and nothing else there.
