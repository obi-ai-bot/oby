# feat(obid): number events and replay what a client missed (`?after=`, Last-Event-ID, `resync`)

<!-- Roadmap R06-02 · Sprint 3 · R06 Events that clients only apply · effort M · risk medium -->

### Sangam's screen

engine only

### Outcome

A client that drops its connection gets the events it missed instead of fetching everything again, and one that was away too long is told so with one `resync` event. Phones over the relay get the same through a query parameter.

### Status and scope

Proposed (roadmap R06-02, milestone R06 Events that clients only apply).

**Why:** events.rs sends events with no id and keeps no history: a client more than 1,024 events behind has its stream ended (events.rs:52-56, WIRE-4), and every client refetches status, jobs, inbox, conversations and limits after every reconnect (live.ts:737 sync, notify.ts:351 sync). Issue #1000 asks for ids and replay; #917's 'told to reload' half is done by WIRE-4.

**In:**
- An epoch (random, made at obid start, not saved) and a u64 `seq` for every event on the main queue except `delta`.
- A ring of the last 2,000 numbered events (also capped at 8 MB of data), filled and broadcast under one lock so a follower that reads the ring and subscribes sees no gap and no duplicate.
- The SSE `id: <epoch>-<seq>` line on numbered events; the data stays as it is (`accounts` data is a JSON array, so no key can be added to it).
- GET /v1/events reads `Last-Event-ID` and `?after=<epoch>-<seq>` (the query wins); inside the ring it replays the rest and goes live; from another epoch or older than the ring it sends one `resync` event (`{"epoch": "…"}`) and goes live.
- `capabilities` gains `events-replay-v1` (R06-01).
- docs/runner-api.md GET /v1/events: the id, `after`, `resync`, and that clients must not infer a gap from the numbers (the gateway drops Mac-only frames for phones).

**Out:**
- `transcript` events: they keep their own queue and `transcriptStale` (WIRE-4).
- `delta` events: not numbered and not in the ring, so a burst of tokens never pushes a job's end out; catching up a half-written answer (#1000's mid-turn part) stays open.
- Forwarding Last-Event-ID through the gateway: phones use `?after=`, which the gateway already forwards (gateway.rs:779-783).
- Any client change: R06-09 (Mac) and R06-14 (iPhone).

### Actors and ownership: what obid owns

- The numbering, the ring, its size, the epoch, and when a client must refetch (`resync`).

### Actors and ownership: what the apps show and send

- Nothing changes for clients until they send `after` (R06-09, R06-14). Old Electron (sseReader in shared/obid-wire.ts:337) and Swift (EventParser in apps/shared/Runner.swift:1978) parsers read only `event:` and `data:` lines, so they ignore `id:`; they never send `after`, so they never get `resync`.

### Interfaces and dependencies

- GET /v1/events: add the SSE `id:` field on numbered events (add-only).
- GET /v1/events: add the query `after` and the header Last-Event-ID (add-only).
- GET /v1/events: add the event `resync` (`{"epoch": string}`), sent only to a client that asked to resume.
- GET /v1/status: add `events-replay-v1` to `capabilities`.

### Steps

- In events.rs give `Event` an `id: Option<u64>` and keep `epoch: String`, `next: u64` and a `VecDeque<Event>` ring in one Mutex; `send` numbers, pushes and broadcasts under that lock (not `transcript`, not `delta`).
- Add `Events::follow_from(after: Option<(String, u64)>)`: under the lock, subscribe, then copy the ring after `seq`; return replay chained with live, dropping live events whose seq is not above the last replayed; return a leading `resync` when the epoch differs or seq is older than the ring's first.
- Keep WIRE-4: a follower behind on the main queue still has its stream ended; it can now resume with `after`.
- In routes.rs `events`, parse `after` from the query, else the Last-Event-ID header; put `SseEvent::id` on numbered events.
- Add `events-replay-v1` to CAPABILITIES; write docs/contracts/events.md and the runner-api.md text.
- Write the EVENTS tests; prove EVENTS-2 fails with the replay removed.
- Run `scripts/oby-check.sh` and core/crates/obid/tests/swift_client.rs.

### Acceptance scenarios

- EVENTS-1 (proposed): Given obid sends a `job` event, when a client follows GET /v1/events, then the frame has an `id: <epoch>-<seq>` line, the seq is one more than the last numbered event's, and the data is unchanged.
- EVENTS-2 (proposed): Given a client saw id E-10 and obid then sent E-11 to E-15, when it reconnects with `?after=E-10`, then it gets E-11 to E-15 in order, then live events, and none twice.
- EVENTS-3 (proposed): Given a client's last id is from an earlier epoch or older than the ring, when it reconnects with that id, then the first event is one `resync` with the current epoch, and live events follow.
- EVENTS-4 (proposed): Given a client reconnects with `Last-Event-ID: E-10` and no query, when obid answers, then it replays as for `?after=E-10`.
- EVENTS-5 (proposed): Given an old client that sends no id, when it follows GET /v1/events, then it gets no `resync` and no replay, only live events as today, with `id:` lines it ignores.
- EVENTS-6 (proposed): Given a phone follows through the gateway with `?after=`, when Mac-only events (`tetrix`, `hooks`, `watch`, `roomPost`) were among those missed, then the phone's replay leaves them out and is otherwise complete.
