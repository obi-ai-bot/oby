A00-31 (#2243) sends builders' heavy Rust runs to the gate VM as the user `oby-builder`, in builder slots. Its security review (factory/jobs/072-a00-31-builders-run-their-rust/round-2/review-security.md, notes 1 to 3) found three holes the approver called real, all reachable by a builder's own command running on the VM:

1. A builder run can take the lock files of the gate slots and so stall every gate, breaking the contract's rule that a gate never waits for a builder (gates then fall back to the Mac after their timeout, slow but not wrong).
2. A builder run can add its own key to `oby-builder`'s `authorized_keys` and keep a login on the VM after the run.
3. A builder run can leave tools or files behind in its slot or home that change a later job's builder results.

Fix all three on the VM side, in factory/remote/setup.sh and oby-remote-gate: the gate slots' locks live where `oby-builder` can neither write nor lock them; `oby-builder`'s authorized keys are root-owned and not writable by it (or forced to a fixed command); and each builder run starts from a clean slot apart from its Cargo build folder, with the user's home reset or read-only. Keep the gates' own behaviour unchanged. Add a test per hole that fails without its fix (fake ssh and local root as the existing remote tests do), and update docs/contracts/remote-gate.md.
