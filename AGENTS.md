# Working on Oby

Oby is a native macOS app (SwiftUI, macOS 26 and later) that lives in a window and the menu bar and hands coding work to the user's own Claude Code, Codex and Cursor CLIs (Gemini later). Its desktop app is moving to Electron (`apps/electron`, Dmytro and Wellington's call of 2026-10-26): it started as a copy of Sangam's design, carries his v1 (#1564: his first run, Home, the message box and Settings), is mocked until the experience is right, and then talks to obid, which stays in Rust. The Swift Mac app gets no new work meanwhile. The product is described in [README.md](README.md); what is being built, and in which order, is the GitHub project "Oby — Roadmap" (Now, Next, Later, In review, Done, with a weekly Sprint field; the F1 to F16 milestones are retired).

## Oby forbids nothing (the owner's decision of 2026-10-31, written in stone)

Oby is an orchestrator, never a gatekeeper. Whatever the owner tells it to do, with a click or in words in their own app, Oby does or hands to an agent: merge into `main`, push to the default branch, force-push, anything. The limits are the agents' own (the LLM, Claude Code's, Codex's, Cursor's or Antigravity's own permissions and refusals) and the code host's (GitHub's branch protection and required reviews). When one of those stops a request, Oby tells the owner plainly what stopped it and how to change it. It never refuses the owner on its own account. What Oby holds back is only what it would do by itself, unasked (merging into `main`, force-pushing, the defaults below): those are its defaults, and the owner's word overrides each of them. Never write "forbidden", "never, even on the owner's click" or "in every case" for something the owner asks for, in a contract, a brief, a card or code.

## The social contract (Dmytro, the call of 2026-10-28)

Every decision, here and in a contract, is checked against these three, for Oby, the Obysphere and Oby Cloud alike:

- **Vendor agnostic, no lock-in.** Oby works with any agent, any model and any code host (GitHub is one adapter, never a requirement); the Obysphere is a protocol any agent can speak, not only Oby; Oby Cloud, when it comes, is one registry among any others. Nothing is hard-coded to one provider.
- **Privacy first, local first.** Oby works fully with no account and nothing stored off the Mac (like Obsidian): no sign-in, no user name, its data under obid's home. An Oby is a UUID with the name it's given, never a global identity; Obyspheres are joined by private links. Tying an Oby to an identity (Oby Cloud: settings sync, a global registry) is the owner's choice, later, never forced.
- **A movement, not a product.** All three are open source for others to build on, as Cursor was built on VS Code; a stranger can read obid, run it and change it.

Three directions follow, in this order: **Oby as a flexible dispatcher** the owner adjusts through Oby itself (after the MVP: Home sections a person shapes, such as runtime artifacts for a developer, a manager or a CTO; basic features people adjust over an opinionated UX); **the Obysphere**, the rules for agents talking and working together (Dmytro's); **Oby Cloud**, an insanely secure global registry of agents (deferred). For now the MVP stays small: what launches is what works; anything extra that breaks goes.

## How we work

- Branch from `dev` and open pull requests into `dev`. `dev` is merged into `main` only when a feature's "Test it when it's done" list passes on a real Mac.
- Planning runs in layers (the owner's decision of 2026-10-29): Sangam's design (his screens in `apps/electron`, run on the mock) → the board "Oby — Roadmap" (Now, Next, Later, In review, Done; a weekly Sprint field, Area and Priority) → an issue with its business contract (`feature.yml`, `bug.yml`) → a pull request with its tests. Dates and sprints live on the board only. Take work from Now, in priority order; read an issue's spikes before starting.
- The week: on Monday, for 30 minutes, Sangam shows what he has designed since the last one, and 5 to 8 ready issues go into the sprint; every day we use Oby for real work, and anything that breaks is a bug issue the same day; on Friday, a demo on a real Mac, then 15 minutes on what to change.
- **Ready** means a contract with numbered scenarios (`FOLDERS-3`), the Sangam screen it serves, what obid owns and what the app shows, and the files it will touch. The words a person sees come from his screen, never from the contract. **Done** means every scenario is a test named after it; `scripts/oby-check.sh`, gitleaks and the Brain tool's tests (once it exists) pass on the same commit; `docs/runner-api.md` matches the code; and the issue's real-Mac steps ran.
- Borrowed from Dieta Flexível: a rule is written once and imported, never copied; every rule gets a test that fails without it; each workstream lists the files it owns.
- Plans are written in [obi-ai-bot/oby-plan](https://github.com/obi-ai-bot/oby-plan) (internal; since 2026-10-26), not in this repository, and stay dateless: the Obysphere roadmap and its epics, the research behind them, the working system (`process/working-system.md`), and ideas not yet scheduled. Features are still issues here and on the board. When a plan's epic has a piece that lands in Oby, follow its order and its "done when".
- The desktop client is the Electron app, `apps/electron` (the owner's decision of 2026-10-26): Sangam's v1 (#1564), on obid's API. The Swift Mac app (`apps/mac/app`) is frozen after 0.4.5: it takes bug fixes only, no new features, until users have moved to the Electron app. obid (`core/`) stays the engine. The iPhone and Apple Watch apps stay in Swift on obid's API, so that API stays add-only: new keys and values, never a renamed or removed one, and no new value in an enum the Swift apps decode as closed.
- Work from this repository is Oby only (the owner's decision of 2026-10-26): Dmytro owns the Obysphere (obi-ai-bot/obi-sphere: its server, spec and deploys). Don't open pull requests there or deploy it unless the owner asks.
- Update the issue at every step, in the same turn: `status:in-progress` and the branch name when work starts; `status:in-review` and the pull request link when it's open; `status:blocked` and what it waits on; status labels off when it's merged. Move it on the board too (Now, In review, Done).
- Commits follow Conventional Commits. Agents commit unsigned in their worktree (they have no signing key); commits are signed when Oby pushes them. Report the checks you actually ran and what they printed.

## Business behavior contracts and code design

- Every new feature has a business behavior contract before implementation, using [docs/business-contract-template.md](docs/business-contract-template.md). While it's proposed it lives in the feature issue (`feature.yml`), linked to Sangam's screen; once built it moves to `docs/contracts/<area>.md`, with numbered scenarios (`<AREA>-<n>`) that its tests are named after, and the implemented runner API and its behavior go in `docs/runner-api.md` in the same change. Plans, epics and unscheduled ideas stay in `obi-ai-bot/oby-plan`. Link the contract from the issue and implementation; update it when the owner's decisions change. Mark proposed behavior separately from what is implemented. A bug fix updates the affected contract when it changes or clarifies a promised behavior.
- The contract names the user outcome, triggers, states, decisions, observable results, failure and recovery behavior, invariants, and acceptance scenarios. It identifies what obid owns and what clients display or send. Apply existing security, API compatibility and Sangam design rules; a contract does not override them.
- **Clean Architecture:** keep business decisions in obid's domain and application logic, independent of UI, transport, persistence and provider-specific details. Those outer adapters translate inputs and outputs through explicit boundaries; dependencies point toward the business rules. Use the existing architecture where it serves the feature, and introduce boundaries when they reduce coupling rather than adding layers for their own sake.
- **Clean Code:** use clear names, focused responsibilities, explicit state and errors, and small cohesive changes. Avoid duplicated policy and hidden side effects; preserve existing behavior outside the contract. Test observable business outcomes and meaningful failures at the appropriate boundary, and keep the contract and API documentation in step with the code.

## Rules Oby never breaks

- Oby carries a task the whole way by itself (the owner's decision of 2026-10-24): it publishes the PR, reviews it itself (its own review of the exact commit counts for the owner's own pull requests) or, where a repository's rules need another person's approval (Tetrix's), gets it approved by a teammate's Oby over the Obysphere, and merges it with the owner's own GitHub account the way the repository's workflow says (below), as Claude Code does (the owner's decision of 2026-10-24). Obys talk to Obys; Oby asks its owner only when something goes wrong: checks that still fail after its rounds, a review asking for changes it can't settle, a conflict it can't resolve, a permission it may not grant, or a repository whose workflow it hasn't learned yet.
- How work merges is learned, not fixed (the owner's decision of 2026-10-18): Oby learns each person's and each repository's workflow (where a PR merges, rebasing first, who reviews) from what they say or do, saves it as memory only after asking "Can I remember that?" and hearing yes, and follows it, saying so ("Merged into dev, as you like"; docs/onboarding.md, "Learned workflow: memory"). Until it has learned a repository's, it takes the safe default: it opens the PR, asks before any merge, and doesn't push to, merge into or force-push the default branch or `main` on its own, nor force-push a branch it didn't create, unless the owner tells it to ("Oby forbids nothing", above). This repository's remembered workflow: squash-merge a PR into `dev` after the review approves and the checks on the user's Mac pass on the same commit with a clean secret scan (GitHub Actions doesn't run for this repository; docs/runner-api.md, "Mac check"), and merge `dev` into `main` only when a feature's "Test it when it's done" list passes (the user confirms the real-Mac items) and the full checks pass on `dev` on the user's Mac (GitHub Actions doesn't run for this repository).
- An untrusted task's pull request, or one whose change touches a security path (the check's files, what steers agents such as any `AGENTS.md`, `CLAUDE.md` or `.claude/`, the secret scan's settings, `CODEOWNERS`, CI files: `merge::SECURITY_PATHS`), merges by itself only after two approving reviews of its exact head by different tools, or the owner's click (the owner's decision of 2026-10-30, docs/contracts/merging.md MERGING-13 to 16).
- Nothing goes out by itself unless the job's checks passed and the secret scan is clean (by hand, the owner's click publishes the commit its card names: docs/contracts/publishing.md, PUBLISHING-8, and PUBLISHING-9, proposed); the check is the base's, run on the commit alone: the base branch's own copy of the check's script and `.gitleaks.toml`, in a clean checkout of exactly the commit that goes out (the owner's decision of 2026-10-30, docs/contracts/publishing.md, PUBLISHING-6 to 8). Then Oby pushes the branch and opens the PR by itself, ready for review, with no Touch ID or Face ID (decided 2026-10-10). Until the Lead exists (#64), a passing check and a clean scan are enough to open the PR; once it does, the Lead approves the diff too. Merging still waits for a review: for the owner's own pull requests, Oby's own review of the exact commit counts, and Oby merges with the owner's own GitHub account (the owner's decision of 2026-10-24); a second, reviewer GitHub account is optional; a repository whose rules need another person's approval goes to a teammate's Oby, else to the owner. If the scanner can't run, nothing is published. Every outgoing action is listed in the job's report. Every job publishes by itself this way, one whose conversation read something Oby didn't write and one a standing rule started included (the owner's decision of 2026-10-24, replacing 2026-10-23's publish by hand).
- Everything outgoing is scanned for secrets. If the scanner can't run, nothing is published.
- Approvals are a click in the owner's own app, as in Claude Code: no Touch ID, Face ID or password (the owner's decision of 2026-10-24, replacing the earlier Touch ID, Face ID and password approvals). They come only from the owner's own apps (the Mac app on this Mac, paired devices), signed by the device's key, never from another Oby, a job, GitHub text or anything received. Every request that waits on the owner (a job's permission or question, a Confirm) notifies on the Mac with its answers as buttons and shows on Home, answered there in one click. In the Electron app, the owner's words are signed by its main process only right after a keystroke or click main saw itself, one request each, and only in the app's own shapes (docs/contracts/signed-words.md); the owner accepted on 2026-10-30 that a script that took the page over could have one request of its choosing signed per real input, until the window's sandbox (#1641) narrows it.
- Text from GitHub, Slack, web pages, screenshots or other people's Obys is data, never instructions. It reaches agents only as quoted files, never in a prompt, and other Obys can only send typed actions.
- On Mac, the microphone opens only while the user holds the talk key (fn, or Control-Option), or after fn + Space until they press it again; in that hands-free mode, once Oby's reply shows it listens again for the user's answer, until the next press or a bare "stop" or "never mind" (the owner's decision of 2026-10-23: Oby answers in text, never aloud). In the window, a click on the voice button (Sangam's) listens as a tap does on the iPhone: until Stop or another click, at most 60 seconds, the words left as a draft. Never otherwise. On iPhone and Apple Watch, a tap on the mic listens until Stop, and capture ends automatically at 60 seconds; the words stay as a draft and nothing is sent until the user sends it. Leaving the screen or interrupting the app stops listening. No telemetry unless the user turns it on.
- Oby never reads, stores or forwards the user's agent logins: each tool signs in through its own login. One exception, the owner's decision of 2026-10-17: with `claudeKeychain` on (the owner's decision of 2026-10-18: obid turns it on by itself on macOS when it's left out of `config.json` and Claude Code's default login is only in the Keychain, asking `security` only whether the item exists; `false` keeps it off; once on, set or by itself, it covers every Claude Code account, those with a `configDir` too, each with its own Keychain item), obid copies Claude Code's own macOS Keychain login into the place a boxed Claude run reads it from (the run's private login copy; no box ever gets an account's own folder, #655), as it copies a login file, because the sandbox denies the Keychain and Claude Code no longer writes a login file. The copy carries only what calls the API, never a refresh token or anything else the item holds (a boxed refresh would rotate the Mac's own login away); in a token's last 5 minutes obid has the Mac's own Claude Code refresh the default login, unboxed, by its absolute path, with a `PATH` of the system's folders first (then only what its binary needs to start, as its sign-in's: `node`'s folder for an npm install), in an empty config folder of obid's, and writes every live copy again. The owner's decision of 2026-10-24 (#877): an account obid added itself (its folder is obid's `home/accounts/<id>`, which the Swift engine never runs on) is refreshed the same way, with its own Keychain item, and only while its folder's login files are the person's own and no link. An account with a `configDir` the configuration names isn't refreshed by obid while the Mac app's Swift engine may still run agents unboxed with that folder (#655's open item): its runs start while its token is far from its end. No box of obid's ever gets an account's own folder, or reads it (#655): every run gets a folder of its own with a copy of the login. A third exception, the owner's decision of 2026-10-26, opt-in per account: a Claude Code account listed in `claudeOwnSandbox` runs its jobs unboxed by obid, with its own folder and Keychain login and no copy. Only its commands are kernel-sandboxed (Claude Code's own sandbox, which obid's settings keep out of obid's home, the person's home and every account's folder but the job's own paths, and off the git pointers); its Read, Edit and Write tools run in Claude Code's own process, outside any sandbox, and rely on Claude Code's own path checks and obid's refusal of any path outside the worktree, so a link swapped between that check and the open isn't stopped (docs/runner-api.md, `claudeOwnSandbox`; proven by `own_sandbox_probes`). The owner accepted that race on 2026-10-27, for this opt-in mode only: the kernel enforces commands only, and Oby's box stays the default. obid's own git calls in a worktree are pinned to the job's git folders as obid checked them. Every Codex run gets `auth.json` with `tokens.refresh_token` set to `""` in its own `CODEX_HOME` (OpenAI rotates refresh tokens too); a copy whose access token ends within 5 minutes doesn't run ("run codex once"), nor does one OpenAI refused, until the owner signs in again ("run codex login"), and obid never writes a token back. A Cursor job's copy of its login file (kept as a file with `AGENT_CLI_CREDENTIAL_STORE=file`) holds only its `accessToken` and `apiKey`, never the refresh token. A second exception, the owner's direction of 2026-10-23 (the launch plan's "Cursor's Keychain login"): with `cursorKeychain` on (obid turns it on by itself on macOS when it's left out of `config.json`, no `~/.cursor/auth.json` is there and Cursor's own login is in the Keychain, asking `security` only whether the item exists; `false` keeps it off), obid copies Cursor's own login (the account with no `configDir`, only: accounts obid adds sign in to a file of their own) from the macOS Keychain, where cursor-agent keeps it by default, into the run's private login copy: only its `accessToken` and `apiKey`, as for the file; it never asks for the refresh token, and never refreshes the login or writes anything back. No run gets an account's other files that start programs or carry tokens (Codex's `config.toml`, Cursor's `mcp.json`): agents have no code-host login. A `configDir` is never `~/.claude`, `~/.codex` or inside them. Secrets in Oby's vault never reach an agent (no prompt, environment, file, argument or log). Oby uses a secret only for a connection the user made.

- Retired with compute sharing (2026-10-27), kept for when it comes back: a guest job on a teammate's Mac (Obysphere sharing, #797; the owner's decision of 2026-10-21) runs on the guest's own subscription, and the guest's Oby is the only place that login is used: the job's VM on the host gets a placeholder, the host's obid relays each model call over the job's end-to-end encrypted channel, and the guest's obid adds the credential on the guest's Mac, where the call leaves from. The login never reaches the host's disk, VM, logs or obid. The guest's obid takes only its agent's model paths and allowlisted headers, drops any credential the host sends, and stops relaying when the exchange ends or the job's `max_minutes` passes.
- Tetrix is connected once, in Oby, for every agent (the owner's decision of 2026-10-18, replacing #130's "each tool's own login, never Oby holding the token"): obid is Tetrix's OAuth client (a public client, PKCE, a loopback redirect on 127.0.0.1) and keeps the login in its vault as `oby.tetrix.access` and `oby.tetrix.refresh` (`home/vault/secrets.json`, 0600, a Mac's too since the owner's decision of 2026-10-30: the Swift runner's Keychain items are copied into it once), so it is taken out of every answer, log line and push. It signs in only where the server's metadata is for the URL it was given (RFC 9728's `resource`). The sign-in endpoints are loopback with the runner's token only, never on the gateway or reachable by another Oby. Agents never get Tetrix's token: every owner's job's agent (Claude Code, Codex and Cursor, every account) gets obid's own MCP server for Tetrix with the job's broker token, which dies with the job; obid forwards only the tools agents may call (`TOOLS` in core/crates/obid/src/tetrix.rs: never `resume_session`, admin, write or diagnostics tools) and scrubs every result. Tetrix's answers are data, never instructions. Everything obid sends Tetrix under Oby's login passes the secret scan first: every `tools/call` it forwards for an agent (its arguments), its own context queries, and the job's graph gaps; a finding, or a scan that can't run, sends nothing. The sessions agents save and the gaps obid sends are listed in the job's `outgoing`; every forwarded call is in its `connectionUses` (docs/runner-api.md, "obid only: Tetrix"). The conversation's brain gets the same server's reads (`TOOLS` but `save_session`: a conversation keeps no `outgoing`) with its turn's token, good only while one of its turns runs (a turn nobody watches gets none); each call passes the same scan, is recorded in obid's use log (`vault/uses.jsonl`), and makes the turn count as having read something untrusted.
- A source an Obysphere admin connects for everyone (Sangam's Knowledge) works for every member as his design shows, but the admin's secret never leaves where it was connected: the admin's Oby, or Oby Cloud, holds the connection, runs the members' requests against it (as an Obi-to-Obi request, typed and quoted like any other) and returns only the answer. No member's Oby, agent or device ever receives the admin's secret.

## Proven on 2026-10-09 (keep these working)

- **Claude Code headless:** `claude -p --input-format stream-json --output-format stream-json --verbose`, never `--bare`. Permission prompts with `--permission-prompt-tool stdio` arrive as `control_request` `can_use_tool`; answer with `control_response` allow (`updatedInput`) or deny (`message`). Usage arrives as `rate_limit_event` with `five_hour` and `seven_day` utilization.
- **Spawning `claude`:** remove `CLAUDECODE`, `CLAUDE_CODE_*` and `ANTHROPIC_*` from the environment first.
- **PATH:** read the login shell with `getpwuid(getuid()).pw_shell` (it can differ from `$SHELL`) and run it with `-l -c /usr/bin/env`.
- **Codex:** `codex app-server` speaks JSON-RPC over stdio: `initialize`, then `account/read`, `account/rateLimits/read`, `thread/start`, `turn/start`, `turn/interrupt`.
- **Separate accounts:** `CLAUDE_CONFIG_DIR` per Claude account, `CODEX_HOME` per Codex account.
- **The brain:** `claude -p --model haiku --tools "" --strict-mcp-config --setting-sources "" --no-session-persistence --output-format json --system-prompt … --json-schema …`, the prompt on stdin, in a directory of its own; the plan is `.structured_output` (it can be missing even on success). 3–4 s. Swift validates every plan (`Plan.problems`). Since #65 the prompt carries a briefing (the conversation, the jobs' titles and stages, the inbox, usage), and what agents wrote is quoted in `work.md` in that directory: then it runs with `--tools Read --allowedTools Read --max-turns 6` (a StructuredOutput call that misses the schema costs a turn; a run that ends `error_max_turns` is retried once, told to read less, #535), boxed like the Lead (`Agents.sandboxed`, bubblewrap on Linux). The cost of that read against a real `claude` isn't measured yet.
- **Codex jobs:** `thread/start` with `sandbox: "workspace-write"`, `approvalPolicy: "on-request"`, `approvalsReviewer: "user"` and `config.sandbox_workspace_write` (`writable_roots`: the clone's git directory, `network_access: false`), so commits stay sandboxed. Approvals arrive as `item/commandExecution/requestApproval` and `item/fileChange/requestApproval`; answer `{"decision": "accept" | "decline"}`.
- **Reading agents' output:** split on `\n` only. Foundation's `lines` also breaks at U+2028 inside JSON strings, and a broken `result` line hangs the job.
- **Agents can't publish:** they run with an empty `GH_CONFIG_DIR` (no GitHub login) and Oby's clone has an invalid `remote.origin.pushurl`. Only Publish pushes: by itself when a job ends done with commits, or by hand (a click in the owner's own app, signed by the device's key; the owner's decision of 2026-10-24) when that failed or didn't go out by itself, for any job the owner names (today refused where docs/contracts/publishing.md says; PUBLISHING-9, proposed).
- **On Linux, agents run in bubblewrap** (`Agents.sandboxed`, proven 2026-10-10 on tetrix-lab): they run as the runner's user, so home is empty except for `Agents.tools` (throwaway copies of the folders the CLIs live in), git's settings (read-only) and the job's own account, all of `OBY_HOME` is empty, and `/` is read-only. Real writes: the worktree, the clone's objects, refs, packed-refs and the worktree's own git folder, and the job's account home. Codex's own sandbox (bubblewrap too) can't nest under Ubuntu's AppArmor profile, so on Linux Codex runs `danger-full-access` with `approvalPolicy: "untrusted"` and Oby answers every command.
- **The character in the window:** `oby.html` served from the `oby://` scheme into SwiftUI's `WebView` on the window's Home; JavaScript calls go to the page's own world (`contentWorld: .page`). It's paused while the window is closed or out of sight. Oby has no always-on panel; it follows the pointer anywhere on screen (Sangam's design) only while its window is visible, and stops watching it the moment the window closes or goes out of sight, so with the window closed and nothing running it should sit at about 0% CPU (check it in Activity Monitor over 1 minute). While the window isn't showing the talk key's turn (closed, behind another app, or on a page other than Home and the conversation; while Oby's reply shows, anywhere but the conversation the words went to, since Home doesn't show replies), the talk key shows a small floating pill (`TalkPillPanel`): your words while it's held or hands-free is on, then Thinking, then the reply's first lines for a few seconds or until the next press; it never takes a click or the keyboard.

## Build and run

- The Electron app: `cd apps/electron && npm install && npm run dev` (the window), or `npm run web` for the renderer alone in a browser; `npm run typecheck`. `?everything` shows all of Sangam's design; `apps/electron/README.md` maps it.
- Open `apps/Oby.xcodeproj` in Xcode 27 and run the `Oby` scheme on My Mac, or `xcodebuild -project apps/Oby.xcodeproj -scheme Oby build`.
- Tests: `MacTests` (Swift Testing, hosted by the app). Run them with ⌘U or `xcodebuild -project apps/Oby.xcodeproj -scheme Oby -destination 'platform=macOS' test`. While tests run, a test-host Oby is alive, so a freshly launched Oby quits (one instance at a time): launch it again when they finish.
- What changed, checked: `scripts/oby-check.sh` runs only the suites a change reaches (obid's touched lib modules and test binaries with fmt and clippy, the touched MacTests or iOSTests suites, `swift test`), then gitleaks; `OBY_CHECK_PLAN=1` prints what it would run. It's this repository's check in obid (`"check": "scripts/oby-check.sh"` on `obi-ai-bot/oby` in its `config.json`, docs/runner-api.md, `repos`), so Oby's jobs here run it in their sandbox.
- Oby keeps its clones, job worktrees, `oby.sqlite` and `accounts.json` in `~/Library/Application Support/Oby`.
- The character's source is `character/`. A build phase runs `character/package/build.sh` and bundles the clean copy (no playground) into the app.
- The app isn't sandboxed (it runs the user's CLIs) and ships with Developer ID, not the App Store.
- `Engine/` is Oby's engine with no UI (the brain, jobs, the agent runners, accounts, models, Publish). The Mac app compiles it with `apps/mac/app/`, and the runner on Linux builds the same files. Keep AppKit, SwiftUI and other Apple-only frameworks out of it. The runner's API is `docs/runner-api.md`; change it in the same pull request as the code.
- `cloud/control-plane/` is Oby's control plane on Cloudflare (a Worker with D1, TypeScript, #285): `pnpm install`, `pnpm test` (vitest inside Miniflare), `pnpm check`. Deploying is the user's step (docs/remote-access.md); the Worker's secrets are never in git.
- One repository for every platform. The Apple apps share `apps/Oby.xcodeproj`: the Mac app's sources are in `apps/mac/app/`, and the iPhone (`apps/ios/app/`) and Apple Watch (`apps/watch/`) apps join it as targets. `apps/android/` (phones and Wear OS, one Gradle project) and `Desktop/` (Windows and Linux) come later. Every app shows the same character from `character/`.
- macOS ignores letter case in paths by default: `oby/` and `Oby/` would be the same folder. Never create a folder that differs from an existing one only by case.
